三、关键问题详细分析
问题 1：接口报文定义是最大缺口
project_ana.md 定义了业务规则和页面交互，但没有定义具体的 HTTP 接口报文。拆分要求 #2 需要：

每个接口的完整定义：HTTP Method + URL + 请求体(ReqDTO) + 响应体(RespDTO/VO)

技术方案 §4.1 只给出了 REST 风格示例（如 GET /api/customers），但没有为每个功能点逐一定义接口。

影响：这是从"需求文档"到"开发文档"的核心转化工作，文档中没有现成内容，需要根据功能规格推导设计每一个接口。

建议：这部分工作量最大，需要逐模块基于功能规格推导出完整的接口清单和报文定义。

问题 2：跨模块依赖的"拆分后自包含"问题
这是你特别关心的问题。以客户营销中心为例：

客户营销中心的功能	依赖的模块	依赖的具体内容
线索提交审批	workflow-center	WorkflowApi.startProcess() 的入参/出参契约
线索审批回调	workflow-center	流程完成事件 workflow.process.completed.v1 的 payload
认领客户	auth-permission-center	BizScopeApi 数据范围校验、CurrentUserApi 当前用户
触达成功后跳转中场支持	business-application-center	需要知道中场支持发起接口的入参
客户标签选择	自身	标签是本模块内部功能
产品列表选择（中场支持）	portal-content-center	ProductApi 查询可用产品
当前拆分要求 #4 说要写明 API/Facade 契约，但问题在于：

A 模块的文档说"调用 WorkflowApi.startProcess()"
但 startProcess 的完整入参定义在 workflow-center 的文档里
如果开发者只看 A 模块文档，他不知道调用方的 DTO 字段是什么
建议：每个模块文档中需要一个"依赖契约摘要"章节，把该模块调用其他模块的接口签名和 DTO 结构复制一份到本模块文档中（标注"来源于 xxx 模块，以 xxx 模块为准"）。否则开发者必须同时翻阅多份文档。

问题 3：认证授权链路的"公共知识"问题
技术方案 §4.2 定义了一套完整的鉴权链路：


Filter → Interceptor → @BizAuth → DataPermissionChecker → AuditService
每个模块的每个接口都需要遵循这个链路，但这个链路的定义在 auth-permission-center 模块。

如果拆分后各模块文档不包含这套鉴权规范的摘要，开发者会不知道：

@BizAuth(bizType = "LEAD", action = "WRITE") 怎么用
DataScopeContext 怎么获取
写操作的二次校验怎么做
建议：需要一份"公共开发规范"文档（不属于任何模块），包含：

统一鉴权链路使用方式
统一响应模型
统一错误码规范
统一分页参数
统一审计切面使用方式
统一事件发布规范
问题 4：Flowable 工作流的"边界模糊"问题
拆分要求说 workflow-center 是唯一调用 Flowable 的模块，但实际上：

BPMN 流程定义（XML）的设计需要业务方参与（如线索审批流程的节点设计属于客户营销的业务知识）
节点表单绑定的配置涉及业务模块的字段定义
候选人规则涉及角色和组织模型
问题：线索审批流程的 BPMN XML 应该放在客户营销中心的文档里，还是 workflow-center 的文档里？

建议：BPMN 流程定义放在 docs/workflow/ 公共目录（已在拆分要求中规划），但每个业务模块文档中需要包含：

该模块涉及的流程定义 Key 和节点 ID 清单
每个节点的候选人规则描述
每个节点的表单字段要求
business_key 格式约定
问题 5：DATA_SCOPE → SQL 过滤条件的映射缺失
拆分要求 #6 明确要求：

DATA_SCOPE 枚举值必须映射到具体 SQL 过滤条件模板
例：SELF_CREATED → WHERE created_by = #{empId}

project_ana.md 定义了 7 种 DATA_SCOPE 枚举，但没有给出 SQL 模板。技术方案 §0.4 说"先用显式校验为主"，但没有给出具体实现模式。

建议：需要在公共规范或 auth-permission-center 文档中补充每种 DATA_SCOPE 的 SQL 过滤模板，以及 WORKFLOW_PARTICIPANT 这种复杂范围的查询策略。

问题 6：领域事件契约不完整
技术方案 §4.3 定义了事件命名规范和消息结构，列出了几个示例事件，但没有给出完整的事件清单。

拆分要求 #4 需要：

领域事件清单：事件名、payload 结构、发布时机（事务后）、消费方

需要根据功能规格推导出完整的事件清单，例如：

customer.claim.created.v1 — 客户认领后通知创建触达任务
workflow.process.completed.v1 — 流程完成后通知业务模块回写状态
performance.target-adjustment.approved.v1 — 目标修正审批通过后触发历史回算
governance.permission-cache.invalidated.v1 — 权限变更后缓存失效
问题 7：幂等策略和并发控制缺乏场景级细节
拆分要求 #7 需要按场景标注事务边界和并发控制策略。project_ana.md 在各功能点散落提到了幂等要求（如导入批次号、client_uuid 等），但没有集中整理。

例如：

客户认领的"争抢模式"：文档说"允许多机构认领"，但没说同机构重复认领如何防范（乐观锁？唯一约束？）
触达日志的幂等：字段 client_uuid 存在但没有说明去重策略

五、改进建议汇总
新增"公共开发规范"文档 — 放在 docs/common-dev-guide.md，包含鉴权链路、响应模型、错误码、分页、审计切面、事件规范等所有模块共享的开发知识

每个模块文档增加"依赖契约摘要" — 把调用其他模块的接口签名和 DTO 复制到本模块文档中，标注数据来源，避免开发者跨文档翻阅

每个模块文档增加"流程交互说明" — 包含该模块涉及的流程 Key、节点 ID、候选人规则、business_key 格式

补充 DATA_SCOPE → SQL 模板映射 — 放在 auth-permission-center 文档或公共规范中

补充完整领域事件清单 — 每个模块标注发布哪些事件、消费哪些事件

补充 ObjectMeta Registry 的具体配置 — 每个模块的业务对象需要注册哪些元数据
