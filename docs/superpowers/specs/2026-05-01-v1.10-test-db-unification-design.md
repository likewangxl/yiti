## 2. Goal

- 平台测试 mysql 库**唯一为 `onepl_test_bootstrap`**，废弃 `onepl_test_v103`
- 各模块 FlywayIT（performance + report）改为指向 `onepl_test_bootstrap`，通过 `baseline-version` 高版本兼容已应用的历史 V_*.sql
- bootstrap test profile 配置零改动（`spring.sql.init` + `init.sql` 流程保留）
- 全平台 `mvn verify` 全绿（FlywayIT 个别因 baseline 失效需评估接受/废弃）

## 3. Architecture（关键决策）

| 决策点 | 选择 | 理由 |
|---|---|---|
| 唯一库名 | `onepl_test_bootstrap` | 用户明确"以 bootstrap 为准" |
| `onepl_test_v103` | 废弃 + 文档移除生产/CI 引用 | 用户"不再维护多库"|
| bootstrap test profile | 零改动 | 用户约束 + 该 profile 已稳定（V1.9 P5 全绿）|
| `PerformanceFlywayTestBase` | url → onepl_test_bootstrap，`baseline-version=1.7.99` | 库已含 V1.0-V1.7 全部历史 schema；baseline 让 Flyway 把这些视为 applied，未来 V1.8+ 增量 migrate 仍生效 |
| `ReportFlywayTestBase` | url → onepl_test_bootstrap，`baseline-version=1.0.99` | 库已含 V1.0.x 报表全部 schema；同 perf 处理 |
| FlywayIT 失败的 individual case | 逐 IT 评估：接受（baseline 不影响断言）/ 改造（断言不依赖"刚 migrate"）/ 废弃（断言强依赖空库迁移） | V1.10 P2 阶段决定 |
| Flyway `clean-disabled` | 保持当前 `clean-disabled=false`（允许 clean）但 IT 实际不 clean | 不引入新行为；如某 IT 真要 clean 跑，需重审 |
| 数据冲突处理 | perf V1_0_1__performance_resources.sql 等 INSERT INTO PT_RESOURCE 等已应用，baseline 跳过故无冲突；运行时若 IT 主动 reset → 加 INSERT IGNORE | 默认无冲突，故 V1.10 不预先改 V_*.sql |
| schema_history 表 | perf 用默认 `flyway_schema_history`，report 用现有 `flyway_schema_history_rpt` | 已隔离，不动 |

## 5. Risks

### 5.1 FlywayIT baseline 后断言失效

某些 FlywayIT 的具体断言可能假设"我刚 migrate 完，schema 是这一刻产生的"——baseline 后历史脚本不重跑，schema 来自其他来源（init.sql 已 apply 过）。

| 类型 | 例子 | 处理 |
|---|---|---|
| 验证表存在 | `V1_2_0FlywayIT` 断言 perf_alloc_adjust_apply 表存在 | onepl_test_bootstrap 已含 → 通过（接受）|
| 验证字段存在 | `V1_4_0FlywayIT` 断言 perf_target_plan.owner_emp_id 列存在 | 同上 → 通过（接受）|
| 验证特定数据存在 | `V1_2_3FlywayIT` 若有 → 断言 perf_seed_data 行 | onepl_test_bootstrap init.sql 步骤 3 已导入 → 通过（接受）|
| 验证 schema_history applied | 任何 IT 断言"flyway_schema_history 含 V1.x.x success=1" | baseline 后 V_*.sql 标 baseline 而非 applied → **断言失败** → 改造或废弃 |
| 验证 clean → migrate 全流程 | 若 IT 主动 clean 后再 assert | baseline 后历史不重跑 → 失败 → 废弃或改造 |

**Mitigation**：V1.10 P2 跑全量 verify 后，按上述 4 类逐 IT 判定。

### 5.2 onepl_test_bootstrap 库 schema 与 V_*.sql baseline 不一致

如果某开发者本地 `onepl_test_bootstrap` 没按 init.sql 完整导入（如漏导入步骤 3 perf V_*.sql），baseline=1.7.99 后 Flyway 不会补，schema 可能缺 perf_target_owner_cols 等字段，运行时 FlywayIT 错乱。

**Mitigation**：
- V1.10 P0 增加预检 SQL：`SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='onepl_test_bootstrap' AND table_name LIKE 'perf_%'` 期望 ≥13 行
- 若不足 → 提示运维补跑 init.sql 步骤 2/3
- CLAUDE.md 强调"V1.10 后开发环境必须按 init.sql 完整跑步骤 1/2/3/4"

### 5.3 多 IT 并发跑同库导致数据互污染

V1.10 后 perf FlywayIT + bootstrap @SpringBootTest IT + report FlywayIT 都在同一库跑。如某 IT 不 cleanup 自身数据，下个 IT 见到残留。

**Mitigation**：
- 现有 IT 大多已经有 cleanup 机制（V1.9 P5 修过的 cleanup SQL 系列）
- V1.10 不主动改 IT cleanup 逻辑；如 P2 发现新污染，单独打补丁
- 长期：mvn 默认串行跑 IT，不会真并发；只要每个 IT 自带 cleanup，互污染受限

### 5.4 V1.10 删除 onepl_test_v103 库后无法回滚

如果 V1.10 出问题需要 rollback，onepl_test_v103 库已 drop。

**Mitigation**：
- V1.10 P5 之前**不**实际 DROP DATABASE onepl_test_v103（仅文档/代码层面切换）
- 让 v103 库在开发者本地物理保留 1-2 周作为 fallback
- 若 V1.10 稳定 1 周后无回滚需求，再人工 DROP
