## § 2. 业务代码现状审计（重要意外发现）

### 2.1 WorkflowCallbackListener.onProcessCompleted javadoc 声称已修

`customer-marketing-center/src/main/java/com/bank/branch/platform/customer/listener/WorkflowCallbackListener.java`:

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public void onProcessCompleted(ProcessCompletedEvent event) {
    try {
        if (!businessKey.startsWith("LEAD:")) return;
        CustLead lead = leadMapper.selectById(leadId);
        if (lead == null) return;
        if ("REJECTED".equals(event.outcome())) {
            reconcileService.reconcileRejected(...);
        } else {
            reconcileService.reconcileApproved(...);
        }
    } catch (Exception e) {
        log.error("[WorkflowCallbackListener] 处理流程完成事件异常 ...", e);
    }
}
```

javadoc 明确标注：
- ✅ "**事务策略（P0 bug 修复）**：@Transactional(REQUIRES_NEW) 让 publishEvent 在新事务内"
- ✅ "**FU-2 异常兜底**：整体 try-catch"
- ✅ "**FU-14 抽 reconcile**：补偿任务共用同样语义"

### 2.2 矛盾点

`WorkflowCallbackEventChainBugIT` javadoc：
> "**当前生产代码下断言 fail**，cust_master 永不创建。修复后断言转绿。"

`WorkflowCallbackListener` javadoc：
> "事务策略（**P0 bug 修复**）：@Transactional(REQUIRES_NEW)..."

**两个 javadoc 互相矛盾** —— 要么 IT javadoc 过时（修复后未更新），要么 listener javadoc 过乐观（修复实际不工作）。

## § 4. 解决方案设计

### 4.1 P0: D-0 隔离诊断（必做，验证 H1 / H4 / H5）

**目标**：通过单 IT 隔离运行 + DEBUG 日志，**实证 H1**（H2/H3 已证伪，H4/H5 一并复核）。

**步骤**：
1. （data.sql 已自动 cleanup，无需手动 truncate）
2. 单跑 `LeadApprovedCreatesCustomerMasterIT`（最简单，仅一条事件链 — 命中 H1 主路径）
   ```bash
   mvn verify -pl bootstrap -Dit.test=LeadApprovedCreatesCustomerMasterIT 2>&1 | tee /tmp/v1.11-1-d0-iso-1.log
   ```
3. 在 listener 关键路径加 logback DEBUG（临时分支，**不 commit 主线**，验证后 revert）：
   - `WorkflowCallbackListener.onProcessCompleted` entry / exit / try-catch
   - `LeadCallbackReconcileService.reconcileApproved` entry / exit / conditionalUpdate 返回值 / publishEvent
   - `LeadApprovedListener.handle` entry / exit
   - `CustMasterAssemblerService.assembleFromLead` entry / exit / masterMapper.insert 受影响行数
4. 看日志哪一步缺失，实证落在 H1（最可能）。
5. 单跑 `WorkflowCallbackEventChainBugIT`（H5 验证）：
   ```bash
   mvn verify -pl bootstrap -Dit.test=WorkflowCallbackEventChainBugIT 2>&1 | tee /tmp/v1.11-1-d0-iso-3.log
   ```
   - 如不再报 'Duplicate entry'，H5 重跑即消失证实
6. 单跑 `CustomerMarketingCenterIT`（H4 验证）：
   ```bash
   mvn verify -pl bootstrap -Dit.test=CustomerMarketingCenterIT 2>&1 | tee /tmp/v1.11-1-d0-iso-2.log
   ```
   - 加 `ClaimCreatedListener.handle` DEBUG 日志，看 listener 触发与否

**Acceptance**：
- 5 IT 中至少 3 个 IT 单独运行，从日志可看出"链路从哪一步断了"
- 输出诊断报告：`docs/superpowers/sessions/2026-05-01-v1.11-1-d0-isolation-diagnosis.md`
- 报告中明确：H1 / H4 / H5 各自实证状态（成立 / 不成立 / 不可断）

**工时**：1-2 h

### 4.2 P1: D-1 业务修复（视 D-0 结论）

根据 D-0 结论分支（H2/H3 已证伪，仅保留 H1/H4/H5 分支）：

**分支 H1（Spring 事务监听器组合不工作 / 最可能）**：
- 候选改造方向（D-0 实证后选 1 个）：
  - **方向 A**：onProcessCompleted / handle 改用 `@EventListener`（非 transactional）+ 内部用 `TransactionTemplate.execute(...)` 显式开事务 + 手动判断 outcome
  - **方向 B**：保留 `@TransactionalEventListener(AFTER_COMMIT)`，但去掉 `@Transactional(REQUIRES_NEW)`，改为 reconcileService 自身保留 REQUIRES_NEW 控制事务边界
  - **方向 C**：onProcessCompleted 直接同步调用 CustMasterAssemblerService（绕过 LeadApprovedEvent 二级 listener），与 bizapp.LoanWorkflowListener pattern 对齐
- 同 pattern 改 LeadApprovedListener / LeadDeletedListener / ClaimCreatedListener 等下游

**分支 H4（ClaimCreatedListener 同根 / 半确认）**：
- 与 H1 同方向修
- 注意 ClaimCreatedListener 当前**无 REQUIRES_NEW**，pattern 已与 WorkflowCallbackListener 不同；统一到 H1 选定方向

**分支 H5（V1.10 P2 临时失败）**：
- 重跑即消失 → 0 改动
- 仅在 D-2 IT cleanup 中确认 5 IT 反复跑 3 次都全绿

**Acceptance**：
- D-0 报告中明确的根因被修复（H1 方向 A/B/C 选定 + 改造）
- 单跑 5 IT 各 1 次全绿
- mvn verify -pl bootstrap 5 IT 全绿，无新增回归

**工时**：2-4 h（视改造方向复杂度）

### 4.3 P2: D-2 IT cleanup 改造（独立做）

**目标**：5 IT 加 `@Sql executionPhase=BEFORE_TEST_METHOD` 显式 cleanup，避免任何残留触发 dup。

**改动**：
- 5 IT 加 `@Sql(scripts = "/customer-marketing-cleanup.sql", executionPhase = BEFORE_TEST_METHOD)`
- 新建 `bootstrap/src/test/resources/customer-marketing-cleanup.sql`：

**Acceptance**：
- 5 IT 反复跑 3 次都全绿
- 无 Duplicate entry / EmptyResult 等残留性失败

**工时**：0.5-1 h
