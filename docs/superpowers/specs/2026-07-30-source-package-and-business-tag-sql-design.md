# 前后端源码包与业务标签部署 SQL 设计

## 目标

为当前 `master` 分支生成前端、后端两个源码压缩包，并生成一个可单独执行的 MySQL 部署 SQL 文件。三个交付文件放在同一发布目录。

## 交付目录与文件

发布目录为 `release/yiti-20260730/`，包含：

- `yiti-frontend-src-20260730.zip`
- `yiti-backend-src-20260730.zip`
- `yiti-business-tag-deploy-20260730.sql`

## 源码包范围

前端包仅包含 `xanzc_frontend` 的版本库已跟踪源码。

后端包包含 Maven 根工程、全部后端模块、构建脚本及项目文档，不包含前端目录。

两个源码包均基于当前 Git `HEAD` 生成，只收录版本库已跟踪文件，因此不会带入工作区中的 `node_modules`、`dist`、`target`、`coverage`、日志、Git 元数据及其他未跟踪构建产物。

## SQL 内容

SQL 使用 MySQL 8 语法，并按可重复执行设计，包含：

1. 创建最终结构的 `PERSON_TAG` 与 `PERSON_TAG_REL` 表，直接包含员工、机构两种成员维度所需字段和索引。
2. 登记“系统设置 > 业务标签”菜单及业务标签的查询、维护、导入接口资源。
3. 业务标签管理权限延续当前权限模型：
   - 系统管理员获得菜单和全部业务标签接口权限。
   - 资财部经办人获得菜单、标签列表和成员列表只读权限。
4. KPI 规则页查询业务标签范围复用 `GET /api/admin/sys/person-tags`，对应资源 `G_PTAG_LIST`。所有拥有 `M_PERF_KPI_RULES` 菜单的角色获得该查询资源，但不因此获得业务标签菜单或写接口权限。

角色授权通过既有资源绑定关系动态复制，避免硬编码当前环境中的角色 ID；重复执行时使用不存在判断避免重复授权。

## 验证

- 对两个 ZIP 执行完整性测试。
- 检查压缩包清单，确认没有 `node_modules`、`dist`、`target`、`coverage`、日志目录及 `.git`。
- 检查前端包只含前端目录，后端包不含前端目录。
- 静态检查 SQL 中的建表、资源登记和三类角色授权语句，并附带部署后自检查询。
