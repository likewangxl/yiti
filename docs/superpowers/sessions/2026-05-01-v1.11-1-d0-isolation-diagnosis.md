### 1.3 H1 根因实证

> **Spring 6.x `@TransactionalEventListener(AFTER_COMMIT)` 内部嵌套 `@Transactional` 子链路下，INSERT 实际不持久化到数据库。**

**事务嵌套链路**:
```
Tx1 (txPublisher) commit
  → AFTER_COMMIT → Tx2 (onProcessCompleted REQUIRES_NEW) begin
    → Tx3 (reconcileApproved REQUIRES_NEW) begin
      → conditionalUpdate (Tx3) Updates: 1
      → publishEvent(LeadApprovedEvent) [registered to Tx3 sync]
    → Tx3 commit
      → AFTER_COMMIT → LeadApprovedListener.handle (no @Transactional)
        → assembler.assembleFromLead (@Transactional REQUIRED)
        → Tx4 (REQUIRED) — 但 Spring 在 Tx3 commit 阶段 thread-local sync state 异常
        → mybatis INSERT 显示 "Updates: 1" + "committing"，但 Tx4 实际不持久化
    → Tx2 commit (空)
  → Tx1 cleanup
```

**Spring 已知陷阱**：在 `AFTER_COMMIT` 回调内启动新事务，因 `TransactionSynchronizationManager` 状态特殊（外层 commit 期间 sync 仍 active 但 transaction status COMPLETED），下游 `@Transactional` 方法**实际未真正 commit 到 DB**。

**conditionalUpdate 的 lead_status=APPROVED 反而 persist 了**（同 IT 日志验证 selectById 返 APPROVED）—— 因为 conditionalUpdate 直接在 reconcileApproved 自身的 Tx3 内，Tx3 正常 commit。但 LeadApprovedListener 是嵌套在 Tx3 commit 之后启动的，二级嵌套事务才是 H1 触发点。

### 1.4 H4 半确认验证（推断）

`ClaimCreatedListener` 用 `@TransactionalEventListener(AFTER_COMMIT)` **无 REQUIRES_NEW**：
```
ClaimService.claim @Transactional
  → INSERT cust_claim
  → publishEvent(ClaimCreatedEvent) [bound to ClaimService Tx]
→ ClaimService Tx commit
  → AFTER_COMMIT → ClaimCreatedListener.handle (no @Transactional)
    → touchTaskService.createFromClaim (@Transactional REQUIRED)
    → 同 H1 嵌套事务陷阱 → INSERT 不持久化
```

**H4 实证**：CustomerMarketingCenterIT line 135 `SELECT id FROM touch_task WHERE cust_id=?` 返 0 行 — 同款症状。判定 H4 与 H1 同根（嵌套事务问题），无论 listener 自身有无 REQUIRES_NEW。

## § 2. 跨模块事件订阅 audit

`grep -rn "@EventListener|@TransactionalEventListener" *modules*/src/main/java`：

| 事件 | 监听者 | 跨模块? |
|---|---|---|
| LeadApprovedEvent | LeadApprovedListener (customer) | ❌ 仅 customer |
| LeadDeletedEvent | LeadDeletedListener (customer) | ❌ 仅 customer |
| LeadRejectedEvent | (无消费) | — |
| ClaimCreatedEvent | ClaimCreatedListener (customer) | ❌ 仅 customer |
| ClaimCancelledEvent | (无消费，预留) | — |
| ClaimTransferredEvent | (无消费，预留) | — |
| CustomerDeletedEvent | (无消费，预留) | — |
| TouchCompletedEvent | TouchTaskCompletedListener (customer) | ❌ 仅 customer，且不调 @Transactional 链路 |
| ProcessCompletedEvent | WorkflowCallbackListener (customer), LoanWorkflowListener (bizapp), SupportWorkflowListener (bizapp) | ✅ 跨 customer/bizapp，但不嵌套，单层 listener |

**结论**：H1 触发点仅 customer 模块内的**双层 listener** 链（WorkflowCallbackListener → LeadApprovedListener / LeadDeletedListener、ClaimService → ClaimCreatedListener）。bizapp/portal/perf 的 listener 都是**单层**或用 `fallbackExecution=true`，未触发同款问题。

## § 3. D-1 改造方向选定

### 评估三方向

| 方向 | 改造范围 | 优势 | 劣势 |
|---|---|---|---|
| **A** TransactionTemplate 显式 | 改 listener 内部用 `TransactionTemplate.execute(...)` | 保留事件解耦语义 | 复杂度增加 + AFTER_COMMIT 内 TT 行为不一定纯净 |
| **B** 去 REQUIRES_NEW，让 reconcile 接管 | 减少嵌套层数 | 单点修复 | 二级 listener 仍有事务陷阱（LeadApprovedListener 内 assembler @Transactional） |
| **C** 同步调用，删除二级 listener | 删除 LeadApprovedListener / ClaimCreatedListener / 对应 Event；reconcile 内同步调 assembler；ClaimService.claim 同步调 touchTaskService | 链路最简 + 与 bizapp.LoanWorkflowListener 模式统一 + 测试可重现 | 失去 Spring 事件解耦（但实际无跨模块订阅，无价值损失） |

### 选定方向 C

**理由**:
1. **D-0 实证**：嵌套 listener 是 H1 根因，方向 C 直接消除嵌套
2. **跨模块审计**：LeadApprovedEvent / ClaimCreatedEvent **无外部订阅**，删除无破坏面
3. **架构对齐**：bizapp.LoanWorkflowListener 已是同步链路（单层 listener 内同步处理），方向 C 统一 customer 与 bizapp pattern
4. **简化补偿任务**：LeadCallbackCompensationService 调 reconcileApproved 时，reconcileApproved 直接同步调 assembler，补偿路径同样有效（无外层事务，REQUIRES_NEW 自启 Tx，assembler join 该 Tx，commit 一致 persist）
5. **spec 倾向**：spec § 9 A3 用户决策推荐"倾向方向 C 因与 bizapp 模式统一"

## § 5. 改造后链路（方向 C）

```
Tx1 (txPublisher) begin
  → publishEvent(ProcessCompletedEvent)
  → Tx1 commit
    → AFTER_COMMIT → Tx2 (onProcessCompleted REQUIRES_NEW) begin
      → reconcileService.reconcileApproved
        → Tx3 (REQUIRES_NEW) begin
          → conditionalUpdate (Tx3) Updates: 1
          → assemblerService.assembleFromLead (@Transactional REQUIRED, join Tx3)
            → INSERT INTO CUST_MASTER (Tx3) Updates: 1
        → Tx3 commit  ✅ conditionalUpdate + INSERT 一起 persist
    → Tx2 commit (空)
```

**不再有嵌套 AFTER_COMMIT 链路 → 不再触发 H1 陷阱 → cust_master 真持久化**。
