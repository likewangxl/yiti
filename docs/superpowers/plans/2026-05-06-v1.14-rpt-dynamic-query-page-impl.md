# V1.14 报表 / 动态指标查询页 后端 API 增量实施 Plan

- **目标版本**：V1.14（V1.13 # 1d 之后增量）
- **来源**：用户原型 `_-_.html`（Reports v2 RptDyn 组件）+ 4 轮设计迭代
- **设计契约**：见会话内最终版（§四 接口设计）；本 plan 不再重述设计，只列工程任务/边界/测试。
- **预估工作量**：约 4.3 人天，7 个互相弱依赖的任务（A→C→D 主链 + B/E→F/G 旁路）。

### 范围
1. perf 新增 `KpiApi.listEvalEmpIds(LocalDate sinceDate, Set<String> orgCodes)`
2. report 新增 `GET /api/reports/metric-library`（全库 ACTIVE 指标整树，一次性）

- **绝对禁止重新引入 Flyway**（根 CLAUDE.md 红线）：所有 DDL 由 DBA 直接在目标库执行

## 风险

1. **`EXT_USER_ORG` 跨库 JOIN**：perf 模块的 SQL 直接 JOIN auth 库表已有先例（`SubjectFetcher` 注释中举例），不算新风险；如生产部署 perf/auth 不同库，需要 DBA 确认 schema 共库或改走 Api 二级查询。
2. **考核员工"近 90 天"窗口**：硬编码可能不符合所有业务方期望，留 `perf.eval-emp.window-days` 可配置开关，默认 90。
3. **usedCount Redis 异步刷库**：进程崩溃丢失增量；可接受（误差 < 30s）；如要求强一致可改同步 incr DB 列。
4. **shareScope=DEPT 可见性**：跨支行用户可能不希望看到隔壁部门的方案；`ownerOrgCode` 用 `mainOrgCode` 是最稳，但若用户横跨多机构需在 V1.15 优化。
