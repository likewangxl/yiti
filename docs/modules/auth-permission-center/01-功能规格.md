# AUTH 认证授权中心 -- 功能规格

> 模块定位：支撑域模块，负责用户认证、RBAC权限、BizType统一数据范围、组织范围。可被所有业务模块依赖，但不依赖任何业务模块。

### 1.2 权限要素（统一口径）

权限模型由以下三个维度组成：

1. **RBAC（资源授权）**：以定制框架 `PT_RESOURCE(RESOURCE_URL + RESOURCE_METHOD)` 为最小鉴权单元；`PT_ROLE_RESOURCE` 决定"能否访问某接口/菜单/按钮动作"。
2. **数据范围（BizType 统一口径）**：以 `BizType` 为配置粒度，为每个角色在 `PT_ROLE_BIZ_SCOPE` 中配置单一 `DATA_SCOPE`；前端页面可统一承载查询与操作，后端再按 `Action + DATA_SCOPE + 实体状态/流程守卫` 做最终裁决。
3. **归属/状态/流程**：按统一顺序校验（RBAC -> 数据范围 -> 归属 -> 状态约束 -> 流程权限）。

## 4. 身份与组织模型

### 4.1 用户标识

- **用户唯一标识**：`emp_id = PT_USER.USER_ID`（工号），全系统统一口径
- **用户名**：`PT_USER.USERNAME`，用于登录
- **中文姓名**：`PT_USER.USERCHNNAME`，用于展示

### 4.2 组织维度

- **组织表**：`EXT_ORG_INFO`，树形层级结构
- **层级定义**：`ORG_LEVEL` = 1（总行）/ 2（分行）/ 3（支行）
- **层级关联**：通过 `P_ID`（上级机构编码）构成父子关系
- **用户-机构关联**：`EXT_USER_ORG`（联合主键 USER_ID + ORG_CODE）

### 4.3 V1 强约束

- **单用户单主机构**：V1 版本中，每个用户只有一个主机构（`EXT_USER_ORG` 中仅一条记录）
- **主机构用途**：用于确定用户的数据范围边界（ORG / ORG_SUBTREE 判定基准）

### 4.4 归属字段要求

所有业务实体必须包含以下归属字段，用于数据范围判定：

| 归属字段 | 数据类型 | 说明 | 对应 DataScopeType |
|:---|:---|:---|:---|
| `created_by` | varchar(50) | 创建人工号 | SELF_CREATED |
| `owner_org_id` | varchar(20) | 归属机构编码 | ORG / ORG_SUBTREE |
| `assigned_emp_id` | varchar(50) | 分配处理人工号（任务类） | SELF_ASSIGNED |
| 自身标识字段 | varchar(50) | 如通讯录的 emp_id | SELF |

## 5. 数据范围枚举与规则

### 5.1 DataScopeType 七种语义

| 枚举值 | 语义说明 | SQL 条件模板 | 典型场景 |
|:---|:---|:---|:---|
| `SELF_CREATED` | 本人创建的数据 | `created_by = #{empId}` | 客户经理的线索、资产投放申请 |
| `SELF` | 本人对象数据 | `{selfCol} = #{empId}` | 通讯录本人信息、个人KPI |
| `SELF_ASSIGNED` | 本人被分配的数据 | `{assigneeCol} = #{empId}` | 触达任务、中场支持任务 |
| `ORG` | 本机构数据 | `owner_org_id = #{orgCode}` | 客户经理认领范围、部门秘书派单范围 |
| `ORG_SUBTREE` | 本机构及下属机构数据 | `owner_org_id IN (组织子树编码集合)` | 经营机构负责人的客户/线索/报表 |
| `ALL` | 全行数据 | `1=1`（无过滤） | 系统管理员、公司部/零售部人员 |
| `WORKFLOW_PARTICIPANT` | 流程参与者可见 | 需结合 WorkflowParticipantService 判定 | 公司部审批资产投放、授信审查/批复 |

### 5.2 配置粒度

- 配置维度：`(ROLE_ID, BIZ_TYPE) -> DATA_SCOPE`
- 存储表：`PT_ROLE_BIZ_SCOPE`
- 唯一约束：`UK(ROLE_ID, BIZ_TYPE)` -- 同一角色对同一 BizType 只能配置一种数据范围

### 5.3 ActionGuard 统一口径

不同动作类型的判定规则：

| 动作类型 | 基础判定 | 二次守卫 |
|:---|:---|:---|
| `READ/LIST` | 命中 `DATA_SCOPE` | 轻量存在性校验 |
| `EXPORT` | 命中 `DATA_SCOPE` + 查询条件 | 审计（导出人、时间、过滤条件、行数） |
| `WRITE` | 命中 `DATA_SCOPE` | 状态守卫 + 实体归属校验 |
| `DELETE` | 命中 `DATA_SCOPE` | 状态守卫 + 业务前置校验 + 审计 |
| `TRANSFER` | 命中 `DATA_SCOPE` | 当前处理人 + 候选范围 + 组织边界 + 审计 |
| `APPROVE/REJECT` | 命中 `DATA_SCOPE` | Flowable runtime task 办理权 + 节点字段权限 |
| `IMPORT/CONFIG/RECALC/JOB_TRIGGER/PERMISSION_CHANGE/EXECUTE_SQL` | 动作授权 | 专项守卫 + reason必填 + 审计 |

### 5.4 多角色并集策略

当用户拥有多个角色时，对同一 BizType 的 `DATA_SCOPE` 取并集（更大的可见边界优先）。优先级排序：

```
ALL > ORG_SUBTREE > ORG > SELF_CREATED / SELF / SELF_ASSIGNED / WORKFLOW_PARTICIPANT
```

**重要约束：**
- `READ/LIST/EXPORT`：直接按合并后的 `DATA_SCOPE` 执行
- `WRITE/DELETE/TRANSFER`：叠加实体状态、归属和业务规则守卫
- `APPROVE/REJECT`：叠加 Flowable runtime task 守卫
- `IMPORT/EXECUTE/EXECUTE_SQL/CONFIG/RECALC/JOB_TRIGGER/PERMISSION_CHANGE`：叠加高危动作守卫与审计
- 资源权限取并集，但高危动作仍需单独授权，不因范围扩大而自动放宽

## 6. 功能权限（菜单/按钮/接口动作）

### 6.1 动作清单

| 动作枚举 | 说明 | 是否高危 |
|:---|:---|:---|
| `READ` | 读取/查看详情 | 否 |
| `LIST` | 列表查询 | 否 |
| `WRITE` | 新增/编辑 | 否 |
| `DELETE` | 删除 | 视场景 |
| `APPROVE` | 审批通过 | 否 |
| `REJECT` | 审批驳回 | 否 |
| `TRANSFER` | 转交 | 是 |
| `IMPORT` | 批量导入 | 是 |
| `EXPORT` | 导出 | 是 |
| `EXECUTE` | 执行（如指标计算执行） | 是 |
| `EXECUTE_SQL` | SQL 探查执行 | 是 |
| `RECALC` | 历史重算 | 是 |
| `JOB_TRIGGER` | 手动触发调度任务 | 是 |
| `PERMISSION_CHANGE` | 权限配置变更 | 是 |
| `CONFIG` | 系统配置 | 视场景 |

### 6.2 资源建模规则

- **最小鉴权单元**：`RESOURCE_URL + RESOURCE_METHOD`
- **按钮权限**：以"按钮触发的接口资源"是否授权为准，不额外发明按钮码
- **路径参数**：`PT_RESOURCE.RESOURCE_URL` 支持 Ant 风格通配（如 `/api/customers/*`）
- **通配原则**：只对 `{id}` 段使用 `*`，不使用 `/**` 吞掉动作路径，确保高危动作可独立授权
- **BizType 归属**：一个接口资源必须归属一个 BizType

## 7. 鉴权判定规则

校验按以下严格顺序执行，任一步骤失败立即拒绝：

```
Step 1: RBAC 资源校验
  ├─ 匹配 PT_RESOURCE（URL + Method -> RESOURCE_ID）
  ├─ 未登记资源 -> 默认拒绝（Fail Close）
  └─ 校验角色是否拥有该资源（PT_ROLE_RESOURCE）
      └─ 失败 -> 返回 AUTH-40301 RBAC_DENIED

Step 2: BizType 数据范围校验
  ├─ 解析接口的 BizType 和 BizAction（优先 @BizAuth 注解）
  ├─ 读取用户的 DATA_SCOPE（合并多角色，取并集）
  └─ 构建 DataScopeContext 放入 ThreadLocal

Step 3: 资源归属校验（写操作）
  ├─ 查询目标实体的归属信息（owner_org_id / created_by / assigned_emp_id）
  └─ 校验是否命中 DATA_SCOPE

Step 4: 状态约束校验（写操作）
  ├─ 检查实体当前状态是否允许该动作
  └─ 例：线索编辑要求 status = DRAFT

Step 5: 流程权限校验（审批操作）
  ├─ 校验 Flowable runtime task 的 assignee / candidateGroups
  └─ WORKFLOW_PARTICIPANT 需结合 WorkflowParticipantService
```

## 8. 高危动作控制与审计

### 8.1 高危动作清单

| 动作类别 | 具体操作 | 审计要求 |
|:---|:---|:---|
| `PERMISSION_CHANGE` | 角色删除、角色资源绑定/全量更新、BizScope配置变更、用户角色绑定/解绑 | 必须审计（变更前后快照、操作人、原因） |
| `IMPORT` | 线索批量导入、标签批量导入、绩效数据导入、目标导入 | 必须审计（文件hash、批次号、总行数、成功/失败） |
| `EXPORT` | 各模块数据导出 | 必须审计（导出人、时间、过滤条件、行数） |
| `EXECUTE_SQL` | SQL 数据探查 | 必须审计（SQL语句、执行人、执行时间、结果行数） |
| `RECALC` | 历史追溯重算 | 必须审计（重算范围、影响记录数、操作人） |
| `JOB_TRIGGER` | 手动触发调度任务 | 必须审计（任务名称、触发人、触发时间） |
| `TRANSFER` | 客户转交、待办转交 | 必须审计（转出人、转入人、原因、影响范围） |
| `DELETE` | 客户删除、资源删除、角色删除 | 必须审计（删除对象、操作人、原因） |

### 8.2 审计字段

每条审计记录必须包含：

## 9. 权限变更生效规则

### 9.1 生效窗口

- **最大延迟**：权限变更后 <= 5 分钟 全系统生效
- **实现方式**：Redis 缓存 TTL = 5 分钟；权限变更时主动发布缓存失效事件

### 9.2 Fail Close 原则

- 当权限缓存失效（Redis 不可用或缓存过期且无法重建）时，**默认拒绝访问**
- 不允许在缓存失效时放行请求
- 系统管理员可通过特殊通道（如直接Session校验）绕过缓存

### 9.3 变更通知

- 权限变更事务提交后，发布 `governance.permission-cache.invalidated.v1` 事件
- 消费方收到事件后清除本地缓存
- 事件 payload 包含：changeType、affectedRoleIds、affectedUserIds、operator、reason

## 10. 权限配置界面

### 10.1 角色管理

- **角色列表**：分页展示，支持编码/名称模糊搜索、状态筛选
- **新增角色**：录入角色编码（大写字母+下划线，max=10）、中文名（max=100）、备注
- **编辑角色**：修改角色中文名、备注
- **删除角色**：逻辑删除（RECORD_STATUS = 1），高危动作需审计
- **角色下用户**：查看该角色下所有用户列表

### 10.2 资源管理

- **资源树**：以树形结构展示全部资源（菜单 + 按钮/接口）
- **新增资源**：录入资源URL、请求方法、菜单名称、是否菜单、上级资源ID
- **编辑/删除资源**：修改资源信息或逻辑删除

### 10.3 角色-资源绑定

- **查看绑定**：以资源树形式展示某角色已绑定的资源（勾选状态）
- **批量绑定**：选择资源ID列表，批量绑定到角色
- **全量更新**：覆盖式更新角色的全部资源绑定（先删后插），高危动作需审计

### 10.4 角色-BizType-DataScope 配置

- **矩阵视图**：以角色为行、BizType为列，展示当前配置的DataScope
- **单条配置**：为指定角色的指定BizType设置DataScope
- **删除配置**：删除某角色的某BizType数据范围配置
