# AUTH 认证授权中心 -- 并发与事务策略

---

## 1. 权限缓存策略

### 1.1 缓存架构

| 缓存层 | 存储 | 说明 |
|:---|:---|:---|
| L1 - ThreadLocal | JVM 内存 | 当前请求级别，请求结束清除（CurrentUserContext / DataScopeContext） |
| L2 - Redis | Redis 6.X | 跨请求共享，所有实例可见 |

### 1.2 缓存内容与 Key 设计

| 缓存 Key | 数据内容 | 数据来源 | TTL | 序列化方式 |
|:---|:---|:---|:---|:---|
| `auth:resource:all` | 全量启用资源列表（List\<PtResource\>） | PT_RESOURCE WHERE STATUS=0 | 5min | JSON |
| `auth:role-resource:{roleId}` | 角色绑定的资源ID集合（Set\<String\>） | PT_ROLE_RESOURCE WHERE ROLE_ID=? | 5min | JSON |
| `auth:user-roles:{empId}` | 用户的角色信息列表（List\<PtRole\>） | PT_USER_ROLE JOIN PT_ROLE | 5min | JSON |
| `auth:biz-scope:{roleId}` | 角色的 BizType->DataScope 映射（Map\<String,String\>） | PT_ROLE_BIZ_SCOPE WHERE ROLE_ID=? | 5min | JSON |
| `auth:org-subtree:{orgCode}` | 机构子树编码集合（Set\<String\>） | EXT_ORG_INFO 递归查询 | 5min | JSON |
| `auth:org-tree` | 完整组织树（List\<ExtOrgInfo\>） | EXT_ORG_INFO 全表 | 10min | JSON |
| `auth:org:{orgCode}` | 单个机构信息 | EXT_ORG_INFO WHERE ORG_CODE=? | 10min | JSON |

### 1.3 缓存读取流程

```
1. 检查 Redis 缓存是否存在
   ├─ 命中 -> 直接返回缓存数据
   └─ 未命中 ->
       2. 查询数据库
       3. 写入 Redis（SET key value EX ttl）
       4. 返回查询结果

异常处理：
   ├─ Redis 不可用（连接超时/网络异常）
   │   ├─ 非权限校验场景 -> 降级为直接查库
   │   └─ 权限校验场景 -> Fail Close（拒绝访问，AUTH-40308）
   └─ 数据库不可用 -> 直接抛出系统异常（AUTH-50001）
```

### 1.4 Fail Close 原则

**核心规则：权限缓存失效时默认拒绝访问。**

| 场景 | 处理策略 |
|:---|:---|
| Redis 正常 + 缓存命中 | 正常鉴权 |
| Redis 正常 + 缓存未命中 | 查库重建缓存后鉴权 |
| Redis 不可用 + 权限校验 | **拒绝访问**（AUTH-40308），记录告警日志 |
| Redis 不可用 + 非权限场景（如组织树展示） | 降级为直接查库 |
| 数据库不可用 | 系统异常（AUTH-50001） |

**Fail Close 的豁免：**
- `/api/auth/login` 登录接口不走权限缓存校验
- `/api/auth/logout` 登出接口
- 健康检查 `/actuator/health`

## 2. 权限变更事务边界

### 2.1 事务范围定义

每个权限变更操作的事务边界：

| 操作 | 事务范围 | 事务隔离级别 |
|:---|:---|:---|
| 角色 CRUD | 单表操作 | READ_COMMITTED |
| 角色资源全量更新 | 删除旧绑定 + 插入新绑定（同一事务） | READ_COMMITTED |
| BizScope 保存/更新 | UPSERT 操作（同一事务） | READ_COMMITTED |
| 用户角色绑定 | 批量插入（同一事务） | READ_COMMITTED |
| 角色删除 | 逻辑删除角色 + 清除关联绑定（同一事务） | READ_COMMITTED |

### 2.2 事务与缓存失效的时序

```
┌─────────────────────────────────────────┐
│  @Transactional                          │
│  1. 记录变更前快照（beforeSnapshot）      │
│  2. 执行数据库变更（INSERT/UPDATE/DELETE） │
│  3. 记录变更后快照（afterSnapshot）        │
│  4. 组装审计日志                          │
│  5. 写入审计日志表                        │
│  ── 事务提交 ──                          │
└─────────────────────────────────────────┘
     |
     v
[事务提交后] @TransactionalEventListener(phase = AFTER_COMMIT)
     |
     ├─ 6. 删除受影响的 Redis 缓存 Key
     ├─ 7. 发布 PermissionCacheInvalidatedEvent
     └─ 8. 如需要，调用 invalidateSession() 踢出受影响用户
```

**关键约束：**
- 缓存清除必须在事务提交后执行（避免事务回滚但缓存已清除的不一致）
- 使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 保证时序
- 缓存清除失败不影响主事务（记录错误日志，等待 TTL 自然过期）

### 2.3 事务注解使用规范

```java
// Service 层标准写法
@Service
public class RoleService {

    @Transactional(rollbackFor = Exception.class)
    public void updateRoleResources(String roleId, List<String> resourceIds, String reason) {
        // 1. 查询变更前快照
        List<String> beforeIds = roleResourceMapper.selectResourceIdsByRoleId(roleId);

        // 2. 先删后插
        roleResourceMapper.deleteByRoleId(roleId);
        for (String resId : resourceIds) {
            PtRoleResource rr = new PtRoleResource();
            rr.setId(UuidUtil.generate());
            rr.setRoleId(roleId);
            rr.setResourceId(resId);
            roleResourceMapper.insert(rr);
        }

        // 3. 发布事件（事务提交后执行）
        eventPublisher.publishEvent(new PermissionCacheInvalidatedEvent(
            "ROLE_RESOURCE", Set.of(roleId), null, currentEmpId, reason
        ));
    }
}
```

## 3. 并发控制

### 3.1 数据库级并发控制

| 表 | 并发控制机制 | 说明 |
|:---|:---|:---|
| PT_ROLE_BIZ_SCOPE | 唯一约束 UK(ROLE_ID, BIZ_TYPE) | 防止同一角色对同一BizType创建重复配置 |
| PT_USER_ROLE | 联合主键 (USER_ID, ROLE_ID) | 防止重复绑定同一用户和角色 |
| PT_RESOURCE | 唯一约束 UK(RESOURCE_URL, RESOURCE_METHOD, SYS_CODE) | 防止重复注册资源 |
| PT_ROLE_RESOURCE | 无唯一约束 | 通过应用层"先删后插"保证一致性 |

### 3.2 角色资源全量更新的并发安全

**策略："先删后插"在同一事务内完成**

```sql
-- 在同一事务内执行
BEGIN;
  DELETE FROM PT_ROLE_RESOURCE WHERE ROLE_ID = #{roleId};
  INSERT INTO PT_ROLE_RESOURCE (ID, ROLE_ID, RESOURCE_ID, SYS_CODE, CREATE_TIME)
  VALUES (#{id}, #{roleId}, #{resourceId}, 'PLATFORM', NOW());
  -- ... 多条 INSERT
COMMIT;
```

**并发冲突处理：**
- 两个管理员同时更新同一角色的资源：后提交的事务覆盖先提交的（Last Write Wins）
- 这在 V1 中是可接受的（角色资源配置操作频率极低，且有审计日志可追溯）
- 如未来需要乐观锁，可在 PT_ROLE 表增加 VERSION 字段

### 3.3 BizScope 配置的并发安全

**策略：UPSERT（ON DUPLICATE KEY UPDATE）**

```sql
INSERT INTO PT_ROLE_BIZ_SCOPE (ID, ROLE_ID, BIZ_TYPE, DATA_SCOPE, ...)
VALUES (#{id}, #{roleId}, #{bizType}, #{dataScope}, ...)
ON DUPLICATE KEY UPDATE
  DATA_SCOPE = VALUES(DATA_SCOPE),
  UPDATE_TIME = NOW(),
  UPDATE_USER = #{operator};
```

唯一约束 `UK(ROLE_ID, BIZ_TYPE)` 保证幂等性。

### 3.4 用户角色绑定的并发安全

**策略：INSERT IGNORE（联合主键防重复）**

```sql
INSERT IGNORE INTO PT_USER_ROLE (USER_ID, ROLE_ID, CREATE_TIME)
VALUES (#{userId}, #{roleId}, NOW());
```

联合主键 `(USER_ID, ROLE_ID)` 保证绑定关系不重复。

### 3.5 登录并发控制

| 场景 | 处理策略 |
|:---|:---|
| 同一用户多终端同时登录 | V1 允许多Session共存（不做互踢） |
| 密码错误计数并发 | 使用数据库 UPDATE ... SET PASS_WRONG_COUNT = PASS_WRONG_COUNT + 1 原子操作 |
| 密码错误锁定 | 计数达到阈值后 UPDATE ISLOCKED = 1，由行锁保证原子性 |

## 4. 幂等策略

### 4.1 配置保存幂等

| 操作 | 幂等机制 | 说明 |
|:---|:---|:---|
| BizScope 保存 | UPSERT（UK约束） | 同一 (ROLE_ID, BIZ_TYPE) 重复提交只更新 DATA_SCOPE |
| 用户角色绑定 | INSERT IGNORE（PK约束） | 重复绑定请求直接跳过 |
| 资源注册 | UK 约束校验 | 重复的 (URL, Method, SysCode) 返回 409 错误码 |

### 4.2 缓存失效事件幂等

- 每个权限变更事件携带唯一 `eventId`
- 消费方维护已处理事件的 `eventId` 集合（Redis Set，TTL=1h）
- 重复事件直接跳过

```java
// 消费方幂等处理
@EventListener
public void onPermissionCacheInvalidated(PermissionCacheInvalidatedEvent event) {
    String eventId = event.getEventId();
    Boolean added = redisTemplate.opsForSet().add("auth:processed-events", eventId);
    if (Boolean.FALSE.equals(added)) {
        // 已处理过，跳过
        return;
    }
    redisTemplate.expire("auth:processed-events", 1, TimeUnit.HOURS);

    // 清除本模块相关缓存
    clearLocalCache(event);
}
```

## 5. Session 管理策略

### 5.1 Session 存储

| 配置项 | 值 | 说明 |
|:---|:---|:---|
| 存储方式 | Spring Session + Redis | 支持多实例共享Session |
| Session 超时 | 7200秒（2小时） | application.yml 配置 |
| Session Key 前缀 | `spring:session:` | Spring Session 默认 |
| Cookie 名称 | `SESSION` | Spring Session 默认 |

### 5.2 Session 失效场景

| 场景 | 触发方式 | 后续行为 |
|:---|:---|:---|
| 用户主动登出 | POST /api/auth/logout | 立即销毁Session |
| Session 超时 | 2小时无活动 | Redis TTL 自动过期 |
| 权限变更踢出 | AuthApi.invalidateSession(empId) | 删除该用户所有Session |
| 管理员禁用账号 | PT_USER.ISENABLED = 1 | 下次请求时Filter校验失败 |

## 6. 性能指标要求

| 操作 | 目标响应时间 | 说明 |
|:---|:---|:---|
| 缓存命中的鉴权校验 | < 10ms | Filter + Interceptor 全链路 |
| 缓存未命中的鉴权校验 | < 100ms | 含数据库查询和缓存重建 |
| 登录接口 | < 500ms | 含密码BCrypt校验 |
| 角色列表查询 | < 200ms | 含 userCount 统计 |
| 组织树查询（缓存命中） | < 20ms | 从Redis直接返回 |
| 权限变更操作 | < 500ms | 含事务、缓存清除、事件发布 |
