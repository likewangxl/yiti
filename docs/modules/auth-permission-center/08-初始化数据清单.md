# AUTH 认证授权中心 -- 运行配置要求

> 文件名为既有路径的一部分，内容改为记录当前有效的角色、资源和 BizScope 配置约束。它不是种子数据快照，也不承载 DDL、测试账号、测试机构或执行步骤。
>
> 运行时以目标库中的有效记录、源码校验和经审批的配置变更为准；`03-接口设计与报文.md`、`04-对外API契约.md` 和 `05-表结构DDL.md` 分别记录接口、跨模块 API 和数据模型。

## 1. 角色配置

- `PT_ROLE` 中 `RECORD_STATUS=0` 的记录才是有效角色；`ROLE_ID` 是关联表使用的标识，`ROLE_CODE` 是跨模块和机构组配置使用的业务身份。
- `ROLE_CODE` 必须经过唯一性校验，角色名称、系统编码和状态变更必须通过 AUTH 管理服务完成并保留审计记录。完整角色列表以目标库和当前资源配置为准，不在本文复制一份易漂移清单。
- 用户权限以其全部有效角色的并集计算。`DEFAULT_ASSIGN`/`primaryRoleId` 只用于默认展示，不能改变授权范围；`SYS_ADMIN` 也只在明确实现的 RBAC 环节享有跳过能力。
- 角色停用后不得继续参与资源、BizScope 或机构组运行时授权；关联关系是否清理按对应管理服务的事务规则处理。

## 2. 资源配置

- 每个非认证白名单 REST 端点都必须在 `PT_RESOURCE` 登记 `RESOURCE_URL + RESOURCE_METHOD + SYS_CODE`，并由 Controller 声明匹配的 `@BizAuth`。认证自服务例外必须显式登记并由安全测试覆盖。
- 资源 URL 的路径参数使用受控的单段通配；权限敏感的导入、导出、执行、权限变更和删除动作使用独立资源，不能借助宽泛通配继承无关权限。
- 菜单资源与 API 资源分别维护。角色菜单替换只维护菜单绑定，不推导、删除或授予 API 绑定；API 访问权必须通过角色资源关系显式配置。
- 资源启用状态、父子层级、方法和系统编码由管理服务校验；资源删除前处理子资源和角色绑定，避免留下悬挂授权。

## 3. BizScope 配置

- 配置主键语义为 `(ROLE_ID, BIZ_TYPE) -> DATA_SCOPE`，同一角色对同一业务类型只能有一条有效配置。`BIZ_TYPE`、`DATA_SCOPE` 的合法值以 common-security 中的枚举源码为准，本文不复制枚举全集。
- 新建角色时，当前服务为支持的业务类型建立最小范围 `SELF` 配置；管理员可通过 BizScope 管理接口调整到业务需要的范围，但不得把未配置或非法值解释为 `ALL`。
- 多角色场景按数据范围并集合并；资源授权和数据范围是两个独立维度。写、删、转交、审批、导入、导出、重算、调度和 SQL 探查等动作还必须执行实体、状态、流程或高危审计守卫。
- 保存和删除 BizScope 必须在同一事务内完成校验、写入和审计；失败时不得留下半套配置。权限读取以数据库有效记录为准，兼容性的 `evict*` 调用不表示存在共享缓存。

## 4. 机构画像与命名机构组

- `PT_ORG_PROFILE` 只保存 AUTH 本地经营画像，不回写外部同步机构表；画像有效性与外部机构状态共同决定运行时是否可用。
- `PT_ORG_GROUP_MEMBER` 只保存直接机构成员，不自动展开组织子树；成员必须对应有效外部机构和有效画像。
- `PT_ROLE_ORG_GROUP` 使用有效角色绑定机构组。运行时授权取“员工全部有效角色 ∩ 屏级角色白名单 ∩ 机构组绑定角色”的同一角色交集；组停用、空组、画像缺失或查询异常均拒绝放大范围。
- 画像、机构组、成员和角色绑定的覆盖更新必须校验版本、记录前后快照并写审计；写入失败整体回滚。

## 5. 变更边界

本文不保存密码、测试用户、测试机构、一次性种子 SQL 或初始化执行顺序。数据库结构变更由 DBA 按审批流程在目标库实施；配置调整应通过 AUTH 管理接口或受控的配置变更流程完成，并按本文约束验收。
