# 红色引擎任务域依赖契约摘要

> 版本：v1.2
> 最后更新：2026-09-01
> 适用范围：任务管理、任务处理、四大维度明细项导出及逾期通知

本文只描述任务域与系统治理中心的最小接入边界。当前红色引擎已有材料上报和任务域代码按
`04-对外API契约.md` 使用治理公开 API；任务 DTO、实体和 Mapper 已按任务域模型落位。
跨模块接入必须通过公开 `api/` 接口和 DTO，不得引用治理中心的 `mapper`、`entity`、内部
`service`，也不得直接访问治理表或对象存储。当前 `RE_ITEM_CODE` 是治理中心维护的逻辑字典
分组，由公开 `DictApi` 提供读取和启用状态校验，不作为新增字典表或写入入口。

## 1. 当前代码事实

- `red-engine-center` 的 Maven 依赖已包含 `system-governance-center`；当前任务调度适配器
  `ReTaskScheduler` 已直接 import `JobApi`/`RegisterJobCmd`，使用固定 job key 注册和注销治理
  Quartz；异步导出服务通过公开 `DictApi` 校验启用的 `RE_ITEM_CODE`。任务域当前未直接 import
  `NotifyApi`。
- `ReSubmitService` 已通过 `FileApi` 调用 `getFileName`/`bindFile`；任务工作流还使用
  `getFileNames`/`getFileSizes`/`getFileName`/`bindFile`，任务附件服务使用归属校验后的
  `getFileContent`/`getFileName`，异步导出使用字节上传和 `getFileContent`。不在红色引擎自建
  上传、对象存储或治理表访问。
- 治理中心公开 Java API 是模块化单体内的本地 Spring Bean 调用，不应由红色引擎通过
  HTTP 反调本模块 REST 端点来替代。

## 2. `DictApi`：`RE_ITEM_CODE` 明细项

### 2.1 公开契约与查询入口

源码事实：

- `system-governance-center/.../api/DictApi.java` 暴露
  `getDictItems`、`getDictItem`、`getDictLabel`、`batchGetDictItems`、
  `isValidDictValue` 五个方法，跨模块 DTO 为 `DictItemDTO`（类型、编码、标签、值、排序）。
- `DictFacade` 实现 `DictApi` 并委托 `DictService`；`DictService` 通过
  `DictMapper.selectByDictType` 查询 `SYS_DICT` 的 `status='ACTIVE'` 数据。
- 公共 REST 查询由 `DictController` 提供：
  `GET /api/sys/dicts` 查询字典类型，
  `GET /api/sys/dicts/{dictType}/items` 查询启用字典项；响应使用
  `DictTypeRespDTO`/`DictItemRespDTO`。这两个 REST 入口在当前 `yit_test.PT_RESOURCE`
  中分别登记为 `G_DICT_LIST`、`G_DICT_ITEMS`，均为 `GOV` 公共查询资源。
- `DictService` 实际使用 `MemoryCacheService`（Caffeine，单实例、全局写后 1 小时过期），
  不是旧注释中提到的 Redis。任务服务无需自行复制缓存。

### 2.2 `yit_test` 当前值（2026-08-31 只读核验）

当前 `SYS_DICT` 中 `dict_type='RE_ITEM_CODE'` 共 8 条，全部为 `ACTIVE`；`dict_value`
与 `dict_code` 相同，排序号为 1—8：

| 编码 | 当前标签 |
| --- | --- |
| `1.1` | 1.1 外联共建分数 |
| `1.2` | 1.2 党建项目 |
| `1.3` | 1.3 党建创新 |
| `2.1` | 2.1 业务提升分数 |
| `2.2` | 2.2 市场开拓 |
| `4.1` | 4.1 督导与工作总结 |
| `4.2` | 4.2 年度工作总结 |
| `sup` | sup 补充加分 |

需求示例中的“联建规范度、合作契约化、业务转换实质”等名称当前并不在该库的
`RE_ITEM_CODE` 中。本阶段不新增或修改字典值；若这些明细项是正式口径，需先由产品确认
编码、标签、排序及所属维度，再由 DBA 按审批结果维护 `SYS_DICT`，不能在任务服务中硬编码
或自行补种。

### 2.3 任务域最小接入建议

1. 任务新增和四大维度导出请求中的 `itemCodes` 只保存编码/快照，不复制字典行；当前导出服务
   已通过公开 `DictApi.getDictItems("RE_ITEM_CODE")` 获取启用项，并在写入或创建异步导出任务前
   校验请求编码均存在且启用，拒绝空编码和重复编码。不在红色引擎内复制字典表或直接读取
   `SYS_DICT`。
2. 展示明细项时优先使用同一次查询得到的 `DictItemDTO.dictLabel`；未知编码应
   fail-close，不用前端传入的标签覆盖字典标签。`RE_TASK_EXPORT_TASK.DETAIL_ITEM_CODES_JSON`
   仅保存经过校验的选择快照。
3. 不允许新增任务 Mapper 直接查询 `SYS_DICT`，也不允许前端把公共 REST 结果当成服务端校验；
   前端接口只用于展示选项，最终权限、启用状态和任务类型校验由任务 Service 完成。现有
   任务实现不得退回到直接查询 `SYS_DICT`，也不能据此新增字典物理表。

## 3. `JobApi`：周期实例生成

治理中心是平台唯一 Quartz 集成点。当前 `JobApi` 的公开方法为：

- `getJobConf(String jobKey)`：查询配置；
- `registerJob(RegisterJobCmd)` / `unregisterJob(String)`：声明式注册/注销；
- `triggerJobByKey(...)`：按已由上层白名单校验的固定 `jobKey` 触发；
- `isJobRunning(String)`：查询是否已有运行记录。

任务域当前由 `ReTaskScheduler` 使用固定键 `RED_ENGINE_TASK_WINDOW` 注册窗口补偿任务，由
`ReTaskScheduleJob` 扫描已发布任务并按周期键幂等生成 `RE_TASK_INSTANCE` 等任务域记录。
任务模块不得创建自己的 Quartz Scheduler、`@Scheduled` 线程、触发器或直接写
`SYS_JOB_CONF`/`QRTZ_*`；运行日志由治理中心的 `JobExecutionLogger` 统一处理。

若未来提供组织管理员手动补偿入口，只能由服务层将业务动作映射到固定 job key 后调用
`triggerJobByKey`，不能透传前端任意字符串；执行前可用 `isJobRunning` 做提示或防重复，
真正幂等仍由任务实例 `TASK_ID + PERIOD_KEY` 唯一约束保证。隔离联调 profile 关闭 Quartz，
不能以该 profile 证明生产调度已经接通。

## 4. `NotifyApi`：逾期未上报提醒

当前公开方法为 `sendNotification(NotificationCmd)`、`batchSendNotifications(List<...>)`、
`countUnread` 和 `queryNotifications`。`NotificationCmd` 至少携带接收人工号、标题，
还可携带内容、通知类型、业务类型/ID和跳转链接；治理中心当前实现同步写入
`USER_NOTIFICATION`，调用方可以在事务提交后自行异步调用。

逾期任务候选确认和扣分事务完成后，任务服务如取得产品确认的通知渠道及收件人规则，建议
通过 `NotifyApi.batchSendNotifications` 通知组织管理员、报送员和对应支部书记，并在命令中
使用任务实例/assignment 作为业务关联和跳转目标。收件人去重、数据范围和通知触发时机由
任务服务负责；不得直接插入 `USER_NOTIFICATION`。

本需求暂未确定站内信以外的外发渠道，且当前治理代码没有外部消息适配器。故
`platform.notification.outbound.enabled=false` 只表示隔离环境不外发的配置边界，不能视为
短信、邮件或企业协同渠道已经交付；渠道、失败重试和幂等策略需另行决策。

## 5. `FileApi`：任务提交附件

### 5.1 已有模式

`FileApi` 提供上传（Multipart/字节）、读取或流式下载、预签名 URL、业务绑定、业务文件列表、
删除及文件名/大小批量查询。文件对象由治理中心 `ObsStorageClient` 管理；接口 Javadoc 中
残留的 MinIO 名称不是当前实现依据。

既有 `ReSubmitService` 的模式是前端先通过治理中心上传端点取得 `fileObjectId`，红色引擎
再调用 `FileApi.getFileName` 和 `FileApi.bindFile` 写业务侧关联。任务附件当前沿用该模式，
并在权限校验后读取对象：

1. 上传仍走治理中心的文件契约；任务 Service 校验任务要求上传、允许类型/大小和当前用户
   数据范围后，再在同一业务事务中写 `RE_TASK_SUBMISSION_FILE` 快照并调用
   `FileApi.bindFile("RE_TASK_SUBMISSION", String.valueOf(submissionId), fileObjectId,
   "ATTACHMENT")`。
2. `ReTaskWorkflowServiceImpl` 使用 `getFileNames`/`getFileSizes` 补齐提交版本元数据并
   `bindFile` 建立业务关联；`ReTaskFileServiceImpl` 使用自有
   `RE_TASK_SUBMISSION_FILE` 快照，再调用 `getFileContent`/`getFileName` 下载。组织审核员
   查看附件前必须完成任务归属校验；不得读取 `FILE_OBJECT`、OBS 或治理 Mapper。若未来
   改用 `listBizFiles`/`getDownloadUrl`，同样必须受当前用户、任务归属和有效期保护。
3. `FileApi.deleteFile` 当前无引用计数保护且会删除物理对象及全部关联；任务服务不应把它
   当作普通撤销附件接口，除非先完成对象所有权和其他业务引用核验。

### 5.2 当前契约缺口

当前 `ReTaskSubmissionReqDTO` 只接收 `fileObjectIds`，治理 `FileApi` 没有按文件 ID 直接
返回完整元数据的方法；`FileObjectDTO` 的文件类型只能在上传返回或业务文件列表中取得。
因此，若后端必须强制执行每个任务的扩展名/MIME 白名单，需要在实现阶段明确采用上传响应的
可信元数据，或经架构审批扩展一个只读文件元数据 API；禁止为绕过缺口而直接查
`FILE_OBJECT`。现有共享上传资源 `G_FILE_UPLOAD` 的角色授权也需随任务角色矩阵另行核对，
本次文档不代替 RBAC 变更。

## 6. 依赖矩阵与禁止事项

| 能力 | 当前红色引擎使用事实 | 任务域建议 | 禁止 |
| --- | --- | --- | --- |
| `DictApi` | `ReTaskExportServiceImpl` 使用公开 API 校验启用明细项 | 校验启用的 `RE_ITEM_CODE`，保存编码快照 | 直查 `SYS_DICT`、硬编码明细项、把逻辑字典当物理表 |
| `JobApi` | `ReTaskScheduler` 已使用 `registerJob`/`unregisterJob` 及固定 key | 通过固定 key 接入治理 Quartz | 自建 Scheduler/`@Scheduled`、直写 `SYS_JOB_CONF` |
| `NotifyApi` | 当前任务 service 尚未接入 | 事务完成后批量发逾期提醒 | 直写 `USER_NOTIFICATION`、假设已有外部渠道 |
| `FileApi` | `ReSubmitService`、任务工作流、附件服务和异步导出已使用公开方法 | 绑定任务提交附件、权限校验后读取/上传 | 直查 `FILE_OBJECT`、直连 OBS、无核验删除 |

所有跨模块依赖必须停留在被依赖模块 `api/` 包公开的 `*Api`/`*QueryApi` 及其 DTO；新增
API import、DTO、`@BizAuth` 或资源登记时，另行同步接口契约和 `PT_RESOURCE`，本摘要不替代实现变更。

## 7. 当前 RBAC、菜单与资源边界

本节与 `03-接口设计与报文.md` 第 12 节及
`docs/superpowers/sql/2026-08-31-redengine-task-rbac-align.sql` 对齐，描述当前资源授权
目标，不把菜单隐藏当作服务端权限。资源匹配仍由 `PT_RESOURCE` 的方法、路径和
`MENU_RANK_NO` 决定；任务/组织/附件/导出读写还必须经过服务层实体与数据范围校验。

| 角色 | 菜单资源 | 任务域/API 能力 | 明确不授予 |
|---|---|---|---|
| `R_RE_REPORT` | `M_RE_ENGINE`、`M_RE_REPORT`、`M_RE_RECORDS`、`M_RE_WARNING` | 首页汇总/排名/红黄牌；我的任务、任务详情、提交和附件 | 支部/组织审核、任务管理、组织管理、映射、导出 |
| `R_RE_SECR` | `M_RE_ENGINE`、`M_RE_BRANCH_WORK`、`M_RE_WARNING` | 首页汇总/排名/红黄牌；支部工作流标准路径及别名、任务详情、附件读取 | 四维材料、上报信息、任务管理、组织审核、组织管理、映射、导出 |
| `R_RE_ORGREV` | `M_RE_ENGINE`、`M_RE_COCKPIT`、`M_RE_WARNING`、`M_RE_REVIEW_WORK`、`M_RE_TASK_MGMT`、`M_RE_ORG_MANAGE`、`M_RE_USER_MAP` | 任务查询/发布/支部进度、组织工作流、附件读取、异步导出、组织 CRUD 与用户映射；保留四维材料审核 API | 四维材料上报/上报信息菜单、支部审核工作台、逾期扣分 |
| `SYS_ADMIN` | `M_RE_ENGINE` 及当前全部新菜单 | 全部任务、支部/组织工作流、附件、导出、组织/映射、首页逾期查询与扣分 | 年度归档与旧同步导出入口（资源已停用） |

`R_RE_BRREV` 角色已停用。原用户通过幂等 `INSERT ... SELECT` 继承 `R_RE_SECR`，
`RE_USER_PARTY_MAP.PARTY_ROLE` 的 `BRANCH_REVIEWER` 同步为 `SECRETARY`；历史角色关系不删除。
为防止书记继续获得旧报送/驾驶舱/组织/旧审核入口，这些旧关系改挂到已停用角色。

新资源按当前 Controller 分组为首页 `P_RE_HOME_*`、任务管理 `P_RE_TASK_*`、任务工作流
`P_RE_WF_*`、附件 `P_RE_TASK_F_*` 和导出 `P_RE_TASK_EXP_*`。标准支部/组织审核队列的
具体资源使用 `MENU_RANK_NO=-20`，详情/动作使用 `-10`，宽泛任务详情使用 `10`，以避免
AntPath 通配符提前匹配。`P_RE_CKPT_ANNUAL`、`P_RE_EXPORT` 与旧
`P_RE_CKPT_EXEC` 仅停用，不删除关系；逾期扣分新资源 `P_RE_HOME_OVER`、`P_RE_HOME_EXEC`
仅授予 `SYS_ADMIN`。

本次 RBAC DML 没有新增跨模块 Java API，也没有扩大 Dict/File/Job/Notify 的依赖面；文件、
调度、通知和字典的边界仍分别以本摘要第 2—5 节为准。执行和只读验收仅针对已授权的
`yit_test`，不能据此推断生产库已变更。

## 8. 待决事项

- 产品确认“联建规范度、合作契约化、业务转换实质”等明细项的正式编码、标签和维度；
- 任务附件白名单由哪一层提供可信 MIME/扩展名元数据，以及任务角色的上传资源授权；
- 逾期通知的渠道、失败重试、去重键和收件人解析规则；
- 周期生成 Job 的正式 job key、手动补偿是否开放及其独立资源/审计动作。

以上事项未决前，不应通过数据库 DML、硬编码或直接跨模块表访问“补齐”契约。
