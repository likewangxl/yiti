# 红色引擎任务域并发与事务策略

> 版本：v1.1
> 最后更新：2026-09-03
> 适用模块：`red-engine-center`

## 1. 总则

任务域沿用红色引擎自管状态机，不接 Flowable。写操作必须在 Service 层重新读取目标实体、校验当前用户和数据范围；Controller/RBAC 只负责入口授权，不能替代实体级校验。事务边界以“状态、历史、待办、版本和附件关系一致”为目标，失败时整体回滚。

本次正式实现继续沿用现有红色引擎后台组件和 MyBatis-Plus 约定。前端原型仅提供业务流程/字段参考，不作为生产技术栈、视觉或持久化实现来源。

## 2. 任务定义与发布

1. 新增任务、允许文件类型和目标范围在同一写事务内保存；任务标题/说明非空，文件要求为“是”时至少保存一个启用类型；指定支部/员工时必须校验目标属于当前允许的数据范围。
2. 组织管理员和组织审核员的新增/发布权限由 `PT_RESOURCE`/角色矩阵控制；Service 仍须检查操作者角色和任务状态。
3. 发布使用 `RE_TASK.STATUS=DRAFT` 加 `VERSION_NO` 乐观条件更新为 `PUBLISHED`，同时写 `PUBLISHED_AT/PUBLISHED_BY` 与一条状态历史；重复发布或版本不匹配返回业务冲突，不覆盖他人变更。
4. 任务定义发布后不修改已生成实例的历史窗口。规则调整应生成新定义或明确的新版本策略，不能回写已提交 assignment 的标题、周期和截止时间。

## 3. 周期实例与待办幂等

### 3.1 窗口计算

- 开始锚点（周初、月初、季度初）从锚点日向后计算 `持续天数 - 1` 天；
- 结束锚点（周末、月末、季度末）从锚点日向前倒推 `持续天数 - 1` 天；
- 自然日含首尾，周最大 7 天，月/季度按实际自然长度校验；持续天数不得超过对应自然周期；
- 发布后从下一个完整周期生效，已开始的结束锚点窗口不回填；
- 每个实际窗口形成一个 `RE_TASK_INSTANCE`，`TASK_ID + PERIOD_KEY` 唯一键是生成幂等边界。

### 3.2 并发生成

1. 生成器先查询已发布任务和当前窗口，再尝试插入实例；并发命中唯一键时按“已存在”处理，不重复生成。
2. 任务实例、支部 assignment 和员工待办应在一个事务内生成。`TASK_INSTANCE_ID + BRANCH_ID` 保证支部 assignment 幂等，`ASSIGNMENT_ID + EMPLOYEE_ID + ROLE_CODE` 保证待办幂等。
3. 查询首页待办必须同时限制员工、窗口状态/时间和 `TODO.STATUS=PENDING`；提交成功只关闭对应待办，不以全局任务标题批量删除。
4. 支部书记“任务处理”待处理页按支部归属、assignment 当前状态和当前任务提交状态在数据库分页前筛选；四大维度任务即使 `RE_TASK_SUBMISSION.CONTENT` 为空，只要旧入口已创建任务 envelope 并处于 `BRANCH_PENDING`，也必须进入待处理队列，不能仅按正文非空或旧 `RE_SUBMIT` 队列排除。
5. 定时生成依赖平台调度时使用治理中心 Quartz；不得在红色引擎自行注册平行调度。隔离联调 profile 关闭 Quartz 和所有 `@Scheduled` 线程，避免写入 QRTZ/PT_LOCK。
6. 用户党组织映射变更与尚未结束的开放实例报送员待办同步在一个事务内完成。未来窗口也要提前同步，但待办沿用 `WINDOW_START_AT` 作为 `AVAILABLE_AT`，到点前不展示。补齐仍依赖 assignment/todo 唯一键幂等；旧支部未处理待办只做 `CANCELLED` 可追溯更新，不删除提交或历史。同步必须同时验证平台 `R_RE_REPORT` 角色和任务目标语义，不得把 `RE_USER_PARTY_MAP.PARTY_ROLE` 当成授权来源。

## 4. 填报、审核与重提

一次普通或临时任务提交事务至少包含：写入新 `RE_TASK_SUBMISSION` 版本、更新 assignment 当前版本/状态、写
`RE_TASK_STATUS_HISTORY`、关闭报送员待办；附件关联必须在同一业务事务中完成，平台文件上传本身仍由治理中心负责。

四维旧材料上报携带完整 `taskId`、`taskInstanceId`、`taskAssignmentId` 时，沿用同一事务边界：首个材料先创建
任务提交 envelope（`RE_TASK_SUBMISSION` 版本）并将 assignment 推进为 `BRANCH_PENDING`，再写入旧材料桥接；当前
版本仍为 `BRANCH_PENDING` 时，后续维度材料复用同一版本，仅追加桥接并为本次新材料累计一次进度，不再次创建
版本或重复推进状态。当前版本只有在支部或组织驳回后，下一次材料上报才允许创建递增的新版本；其他已通过或审核中
状态不得被旧入口绕过。

状态转换只允许：

```text
BRANCH_PENDING → BRANCH_APPROVED → ORG_PENDING → APPROVED
BRANCH_PENDING → REJECTED_BY_BRANCH → 新版本 BRANCH_PENDING
ORG_PENDING    → REJECTED_BY_ORG    → 新版本 BRANCH_PENDING
```

- 支部审核员/支部书记不能审核本人提交；组织审核员不能越过 `ORG_PENDING` 直接改判其他状态。
- 驳回必须携带非空意见；接口 DTO、Service 和数据库检查约束三层收口。
- 重提复用同一 `RE_TASK_BRANCH_ASSIGNMENT`，使用 `VERSION_NO = CURRENT_VERSION + 1`；先以乐观条件更新 assignment，再写唯一版本。唯一键冲突表示并发重提，回读最新版本并返回冲突，不覆盖已有内容。
- 审核人、审核时间和意见只能由服务端从当前会话回填；客户端传入值不得作为权限或审计事实。
- 状态更新、历史追加和待办变更必须同事务提交；事务失败时不允许留下“首页已移除但提交未落库”的半状态。

## 5. 四大维度进度与旧上报桥接

四大维度任务继续使用原材料上报入口。创建/更新旧 `RE_SUBMIT` 后，在同一事务追加
`RE_TASK_RE_SUBMIT_REL`，并记录其所属任务提交版本；以任务实例、支部 assignment 和旧上报 ID 去重。
旧上报记录或任务上下文无法关联时应整体失败，不能产生孤儿桥接行。

带完整任务上下文的版本规则如下：

1. 首个材料创建 `RE_TASK_SUBMISSION` 任务 envelope，更新 assignment 当前版本/状态为
   `BRANCH_PENDING`，完成一次 `RE_TASK_DIMENSION_PROGRESS` 进度记录，再把该材料桥接到该任务提交版本；
2. 当前版本为 `BRANCH_PENDING` 时，后续维度材料复用同一 `RE_TASK_SUBMISSION` 版本，只新增对应
   `RE_TASK_RE_SUBMIT_REL` 桥接，并为本次新材料累计一次进度；不重复创建版本或重复推进状态。桥接关系
   已存在时按幂等成功处理，不得再次累计进度；
3. 当前版本被支部或组织驳回后，下一次材料上报才以 `CURRENT_VERSION + 1` 创建新版本并回到
   `BRANCH_PENDING`；驳回前的版本和桥接关系保留为历史。其他已通过或审核中的版本不允许由旧入口绕过状态机。

`RE_TASK_DIMENSION_PROGRESS` 按 assignment 和维度唯一：

1. 首次有效上传采用条件更新或行锁，将 `STATUS` 从 `PENDING` 置为 `COMPLETED`，写首次/完成时间和触发提交版本；
2. 后续新增桥接只累加 `UPLOAD_COUNT`、更新最近提交引用，不回退完成状态，且同一材料桥接重复执行不重复计数；
3. 查询季度完成度以进度表为准，不以“最后一次提交是否存在”推断，避免驳回/重提使已完成维度回退；
4. 导出四维明细项前通过治理中心公开 `DictApi.getDictItems("RE_ITEM_CODE")` 读取启用编码，
   校验选项后再按桥接/旧上报数据取数；任务域不直接访问 `SYS_DICT`。

## 6. 逾期扣分

逾期候选查询以任务实例窗口结束时间和 assignment/提交状态为准；已提交或已完成数据不进入可执行列表。组织管理员执行扣分时，在同一事务内重新校验候选仍逾期、锁定 assignment、写入 `RE_TASK_DEDUCTION`、状态历史和审计记录。

assignment 唯一扣分约束防止重复执行；扣分原因、分值和操作人由 Service 二次校验，失败或并发冲突不产生部分扣分。通知外发不是本表事务的一部分，交由后续明确的通知契约处理；本次隔离 profile 默认不外发。

## 7. 异步导出

导出请求先按统一数据范围和任务明细项校验，再创建 `RE_TASK_EXPORT_TASK`。`PENDING → RUNNING → SUCCESS/FAILED/CANCELLED/EXPIRED` 由导出 worker 以状态条件更新抢占；重复轮询只读，不重复生成文件。

- 超过 5000 行不得同步物化响应，必须走异步任务；单个 Excel 每 Sheet 上限固定 5000 行；
- 结果统一为 ZIP，含一个 Excel（多 Sheet）和按党支部划分的附件目录；无附件时不创建空目录；
- 四维任务必须携带已校验的明细项编码，临时任务明细项为空数组；
- 导出结果先写治理中心文件对象，再以乐观条件回写 `FILE_OBJECT_ID/FILE_SIZE/FINISHED_AT`；回写失败不得把任务标为成功；
- 下载必须校验当前用户、任务归属、过期时间和 `SUCCESS` 状态。高危导出使用独立资源和审计动作。

## 8. 锁、索引与隔离

- 优先使用唯一约束和 `VERSION_NO` 乐观并发控制；需要跨步骤保护时使用平台 `LockManager/PT_LOCK`，不新引入 Redis 锁。
- 查询索引覆盖任务状态/时间窗、实例周期键、assignment 支部/状态、待办员工/状态、提交版本/状态、进度维度和导出状态；避免列表接口逐支部 N+1 查询。
- 隔离联调使用 `application-redengine-task-e2e.yml`：数据源从环境变量指向 `yit_test`，禁用 Quartz/Flowable schema 更新/调度、Sidecar、SOAP、OBS、锁清理和通知外发，使用独立 Session cookie 与应用实例标识。
- 生产或共享测试环境不得使用本 profile 的回环占位外联地址作为“已完成集成”的证明；真实 OBS、认证、通知和回调必须另行审批并配置隔离命名空间。
