# 红色引擎并发与事务策略

> 红色引擎自管任务与材料状态机，不接 Flowable。实现细节以 Service、Mapper 和数据库约束为准。

## 1. 基本原则

Controller 负责请求绑定和 RED_ENGINE 入口授权，Service 必须重新读取目标实体、校验当前用户和数据范围，再执行状态变更。任务、assignment、提交版本、待办、状态历史和文件关联应在同一业务事务内保持一致。

## 2. 写入事务

| 场景 | 事务要求 |
| --- | --- |
| 党组织新增/修改/删除 | Service 事务；删除前拒绝存在下级组织的节点 |
| 用户党组织绑定 | 映射、当前任务报送员分配和待办同步在同一事务；待办只取消未处理记录 |
| 任务创建发布 | 任务定义、文件类型、目标范围、当前窗口实例、assignment、待办和发布历史按发布服务事务处理 |
| 任务提交/重提 | assignment 当前版本条件更新、提交版本、附件、历史和待办状态同事务 |
| 支部/组织审核 | 当前提交状态条件、状态历史和待办变更同事务 |
| 四维材料桥接 | RE_SUBMIT、提交版本桥接和维度进度同事务 |
| 逾期扣分 | 重新校验候选后写扣分、状态历史和审计，同事务完成 |
| 导出任务创建 | 任务记录和幂等结果事务提交后再交给后台 worker；状态查询/下载只读 |

事务失败必须整体回滚，不能留下只有待办、只有提交版本或只有桥接关系的半状态。文件对象本身由 FileApi 管理，业务事务只保存引用和快照。

## 3. 任务窗口与待办幂等

定时任务只为当前有效窗口创建实例；未来窗口在调度补偿进入当前窗口后生成。实例开始时间以前不展示待办，窗口结束或任务关闭后不再接受提交。任务窗口按北京时间自然日首尾包含计算。

任务发布、窗口补偿和映射同步均按任务/实例/支部/员工业务键查重；唯一约束冲突回读已有记录，不重复建立 assignment 或 TODO。映射变更时只撤销旧支部的未处理报送员待办，已完成待办、提交版本和状态历史保留。

## 4. 状态与乐观并发

提交从 UNREPORTED 或驳回状态创建新的提交版本并将 assignment 置为 BRANCH_PENDING。当前版本只能按下列顺序推进：

UNREPORTED → BRANCH_PENDING → BRANCH_APPROVED → ORG_PENDING → APPROVED

BRANCH_PENDING/ORG_PENDING 可分别转为 REJECTED_BY_BRANCH/REJECTED_BY_ORG；驳回后新版本回到 BRANCH_PENDING。支部通过不自动越过 submit-to-org。已审核、审核中的版本不能被重复提交。

assignment 的 current_version 和提交版本唯一关系用于乐观并发。条件更新影响行数不是一时，或提交版本唯一键冲突时返回刷新/冲突错误；客户端幂等号命中既有状态历史时返回既有提交。

## 5. 四维材料

携带完整任务上下文的首次材料创建当前任务提交 envelope、推进 assignment 和维度进度，再写 RE_SUBMIT 桥接；同一版本的后续维度复用 envelope，只追加桥接并累计一次该维度上传。只有当前版本被驳回后才递增版本。无任务上下文的旧材料不创建任务对象、assignment 或待办。

维度进度按 assignment + dimension_code 唯一维护，重复桥接不重复计数；完成状态不因后续上传回退。

## 6. 逾期和导出并发

逾期执行在写入前重新读取实例、assignment 和当前提交，确认窗口已结束且没有有效提交；同一 assignment 的已执行扣分不能重复产生。首页查询仅展示有效任务和逾期候选。

导出创建以任务、操作者和选项生成幂等标识。PENDING 任务由异步执行器以条件更新抢占为 RUNNING，失败回写 FAILED 并清理未完成的文件对象；只有 SUCCESS 且未过期、归属校验通过才允许下载。

## 7. 调度和依赖

窗口补偿通过治理 JobApi 注册固定的 RED_ENGINE_TASK_WINDOW 任务，执行入口不接受外部 jobKey 或类名。任务域不自行创建调度器、锁服务或对象存储。文件、字典、用户和组织信息必须通过公开 API 获取。
