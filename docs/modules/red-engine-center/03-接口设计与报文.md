# 红色引擎（党建管理）— 接口设计与报文

> 版本：v1.0
> 最后更新：2026-07-19
> 模块编码：red-engine-center
> 统一前缀：`/api/re`
> 统一响应：`ResponseWrapper<T>`（`code`/`message`/`traceId`/`data`/`page`/`timestamp`，见 `common-dev-guide.md`）
> 全部接口已登记 `PT_RESOURCE`（`SYS_CODE='RE'`，`ISMENU=0`，纯 API 资源不建菜单）并声明 `@BizAuth`
> 本文按 `red-engine-center/src/main/java/.../controller/` 下 6 个控制器、共 **23 个端点**全量枚举，字段/校验/错误码均以代码核实（无凭空补写）
> 权限矩阵/字典/技术债等背景信息见模块根 [`red-engine-center/CLAUDE.md`](../../../red-engine-center/CLAUDE.md)，本文不重复维护

## 0. 公共约定

### 0.1 统一响应结构
```json
{
  "code": "0",
  "message": "success",
  "data": { },
  "traceId": "xxx-xxx",
  "timestamp": "2026-07-19T08:00:00Z"
}
```
`ResponseWrapper`（`common-web`）用 `@JsonInclude(NON_NULL)`，`page`/`data` 二选一出现；分页端点走 `data.records`/`data.total`（本模块分页均用 `ResponseWrapper.success(pageResult)`，`data` 直接是 `PageResult<T>`，未使用 `ResponseWrapper.page(...)` 分支，与 customer-marketing 等模块的 `PageResp` 命名不同，字段结构一致：`pageNo`/`pageSize`/`total`/`records`/`totalPages`）。

### 0.2 错误响应结构
```json
{
  "code": "RE-40001",
  "message": "当前用户未绑定党组织，请联系管理员",
  "data": null,
  "traceId": "xxx-xxx",
  "timestamp": "2026-07-19T08:00:00Z"
}
```
`RE-4xxxx` 为**裸字符串错误码**（`new BizException("RE-40001", "...")`），本模块未建 `ReErrorCode` 枚举类，`docs/common-dev-guide.md` 附录 B 模块错误码前缀表未收录 `RE-` 前缀（见根 CLAUDE.md「技术债」⑤）。

### 0.3 分页请求/响应参数（材料上报/审核队列专用，非平台通用 `PageRequest`）
本模块分页端点（`/submits/my`、`/reviews/queue`）直接用 `@RequestParam` 接收 `pageNo`/`pageSize`，**不是**平台标准 `PageRequest` 对象，也无 `sortField`/`sortOrder` 参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| pageNo | int | 1 | 页码（从 1 开始） |
| pageSize | int | 10 | 每页条数（**默认 10**，非平台通用 20；代码未做上限校验，与根 CLAUDE.md「分页懒加载默认 20/最大 100」的通用规范不完全一致，属本模块实现细节，未见截断逻辑） |

响应体 `PageResult<T>`（`common-web`）：
```json
{ "pageNo": 1, "pageSize": 10, "total": 16, "records": [ ] }
```

### 0.4 @BizAuth 注解参数说明
| 参数 | 说明 |
|---|---|
| bizType | 本模块恒为 `BizType.RED_ENGINE`（`common-security` 枚举，`code="RED_ENGINE"`） |
| action | 动作，本模块实际用到：`LIST`/`READ`/`WRITE`/`DELETE`/`CONFIG`/`EXECUTE`/`EXPORT`（`BizAction` 枚举全量另含 TRANSFER/APPROVE/REJECT/IMPORT/RECALC 等，本模块未使用） |

### 0.5 统一响应 Code
- `0` — 成功
- `RE-4xxxx` — 红色引擎业务错误（RE-40001~RE-40007，见「5. 错误码」）
- `AUTH-4xxxx` — 认证/权限错误（如 `@BizAuth` 校验失败）
- `COMMON-4xxxx` — 通用错误（参数校验失败等，来自 `@Valid`/`@NotBlank`/`@NotNull` 违反）

## 4. 两级审核（`ReReviewController`，`/api/re/reviews`）

移植自源 `business.controller.ReviewController`。

### 4.1 GET /api/re/reviews/queue — 审核待审队列

- **@BizAuth**：`bizType=RED_ENGINE, action=LIST`
- **PT_RESOURCE**：`P_RE_REVIEW_Q`（**URL 由种子里的字面量 `/api/re/reviews/queue` 放宽为通配符 `/api/re/reviews/**`**，Task 9 裁决：同一条资源覆盖 4.1 与 4.2 两个 GET 端点，未新增资源登记）

**响应体**：`PageResult<ReSubmit>`（`status=1` 已提交的记录按 `submitDate` 升序分页，最早提交的优先进入审核视野；软删由 `@TableLogic` 自动过滤）

### 4.2 GET /api/re/reviews/{id}/preview — 上报详情预览（审核用）

- **@BizAuth**：`bizType=RED_ENGINE, action=READ`
- **PT_RESOURCE**：`P_RE_REVIEW_Q`（复用，见 4.1）
- **授权角色**：`R_RE_BRREV`、`R_RE_ORGREV`

**路径参数**：`id`（Long）
**响应体**：`ReSubmit`（与 3.3 复用同一 `RE_SUBMIT` 表，不存在时返回 `null`）

### 4.3 POST /api/re/reviews/{id}/approve — 审核通过（含评分）

- **@BizAuth**：`bizType=RED_ENGINE, action=WRITE`
- **PT_RESOURCE**：`P_RE_REVIEW_APPR`
- **授权角色**：`R_RE_BRREV`、`R_RE_ORGREV`
- **@AuditLog**：`action=RE_REVIEW_APPROVE, resourceType=RE_SUBMIT`

**路径参数**：`id`（Long，上报 ID）
**请求体** `ReReviewApproveReqDTO`（`@RequestBody(required=false)`，允许不传或传 `null`）：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|---|---|---|---|---|
| score | BigDecimal | 否 | 无 `@NotNull`（有意保留"仅改状态不评分"的合法用法） | 本次评分；为空或 &le;0 时跳过评分落库，仅推进状态 |
| feedback | String | 否 | 无 | 审核意见 |

**业务规则**：
1. 上报不存在 → `RE-40003`，不触碰 `RE_SCORE`/`RE_SUBMIT`
2. `score>0` 时，校验"同党组织(`orgId`)+同考核项(`itemCode`)+同年度(`scoreYear`=当年)"下 `RE_SCORE` 已有明细的 `finalScore` 累计值 + 本次 `score` 是否超过该上报的 `maxScore`（未配置则回退默认 100）；超限 → `RE-40004`，不落库、不推进状态
3. 校验通过后插入 `RE_SCORE` 明细，`RE_SUBMIT.status` 推进为 `2`（已通过），回填 `reviewFeedback`/`reviewerId`（当前登录审核人工号，源系统未记录，本次补齐）/`reviewDate`
4. `score` 为空或 &le;0 时，状态推进为 `2` 不受影响（状态推进逻辑不依赖评分分支）

**响应体**：`Void`

**错误码**：
- `RE-40003` 提交记录不存在
- `RE-40004` 考核项累计得分已达上限（消息含具体已达分/上限/本次最多可计，如：`考核项[1.1]累计得分已达30分，上限35分，本次最多可计5分`）

**已知限制**（终审 F-1，非阻断）：`insertScoreWithLimitCheck` 走"`selectList` 内存求和 → 校验 → `insert`"，无读锁/唯一约束，并发场景下可绕过 `maxScore`，见模块根 CLAUDE.md「技术债」⑩。

### 4.4 POST /api/re/reviews/{id}/reject — 审核驳回

- **@BizAuth**：`bizType=RED_ENGINE, action=WRITE`
- **PT_RESOURCE**：`P_RE_REVIEW_REJ`
- **授权角色**：`R_RE_BRREV`、`R_RE_ORGREV`
- **@AuditLog**：`action=RE_REVIEW_REJECT, resourceType=RE_SUBMIT`

**路径参数**：`id`（Long）
**请求体** `ReReviewRejectReqDTO`（`@RequestBody(required=false)`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| feedback | String | 否 | 驳回原因/审核意见 |

**业务规则**：**不校验**上报是否存在（源系统同款保真——对不存在的 `id` 静默影响 0 行，不抛异常），直接把状态推进为 `3`（已驳回），回填 `reviewFeedback`/`reviewerId`/`reviewDate`。**`approve`/`reject` 均无前置状态校验**（不要求"仅 `status=1` 才可审核"），对同一 `submitId` 反复审核会重复插入评分行，见根 CLAUDE.md「技术债」②。

**响应体**：`Void`

## 7. RE_SUBMIT 状态机（四态）

```
创建 ──────────────────────────────▶ status=1（已提交，创建即此态，无草稿态入口）
                                        │
                        ┌───────────────┼───────────────┐
                        │ approve                        │ reject
                        ▼                                 ▼
              status=2（已通过）                 status=3（已驳回）
              + 落 RE_SCORE（超上限抛 RE-40004）    + 无前置状态校验（源系统同款保真，
              + reviewerId/reviewDate 回填           可对 2/3 态重复调用并覆盖）
```

- `status=0`（草稿）为 DDL 遗留默认值，**当前无任何代码路径可产生该状态**——`ReSubmitService.createSubmit` 落库直接写 `status=1`，源系统"先存草稿后提交"两段式语义已废弃（YAGNI）。
- `approve`/`reject` 均**不校验**"仅 `status=1` 才可审核"（源系统同款保真，非遗漏）：对已是 `status=2`/`3` 的记录重复调用审核端点仍会被静默覆盖，`approve` 还会因此重复插入 `RE_SCORE` 明细（技术债②）。

## 8. 两级审核流转说明

红色引擎两级审核是**自管状态机**，不接 Flowable（本模块不依赖 `workflow-center`，不持有 `business_key`/`BIZ_PROCESS_MAP`）：

1. **上报（第 0 级，`R_RE_REPORT`/`R_RE_SECR`）**：`POST /api/re/submits` 创建，`orgId` 由当前登录人经 `RE_USER_PARTY_MAP` 强制派生，`status` 直接置 `1`（已提交），无独立提交动作。
2. **审核（`R_RE_BRREV` 支部审核员 / `R_RE_ORGREV` 组织审核员，两角色权限对等、无先后级联关系）**：
   - `GET /api/re/reviews/queue` 拉取 `status=1` 待审队列（按 `submitDate` 升序）
   - `GET /api/re/reviews/{id}/preview` 查看上报详情
   - `POST /api/re/reviews/{id}/approve` 通过并可选携带 `score` 落 `RE_SCORE` 明细（校验 `maxScore` 累计上限），`status→2`
   - `POST /api/re/reviews/{id}/reject` 驳回，`status→3`
3. **两级角色区分体现在数据可见范围而非流程节点顺序**：`R_RE_BRREV`（支部审核员）与 `R_RE_ORGREV`（组织审核员）共享同一条待审队列/同一套 approve/reject 端点（`P_RE_REVIEW_Q`/`P_RE_REVIEW_APPR`/`P_RE_REVIEW_REJ` 三资源均对两角色平等授权），代码层面**没有**"先支部审核通过再进组织审核"的强制串行节点——任一具备审核权限的角色均可对同一条 `status=1` 记录直接终审，"两级"是角色设置上的两类审核人，非流程编排上的两道关卡（与 Flowable 多节点审批流的"层层递进"语义不同，见根 CLAUDE.md「不接 Flowable」定位说明）。
4. **逾期与预警是审核流程外的旁路能力**：`R_RE_ORGREV` 可在驾驶舱对逾期未审的上报（`status∈{0,1}` 且超 7 天）手工执行扣分（`RE-40005` 兜底）；红黄牌预警池基于 `RE_SCORE.final_score` 只读展示，不驱动状态流转。
