## 0. 公共约定

### 0.1 统一响应结构
```json
{
  "code": "0",
  "message": "success",
  "data": { },
  "traceId": "xxx-xxx",
  "timestamp": "2026-07-19T08:00:00Z"
}
```
`ResponseWrapper`（`common-web`）用 `@JsonInclude(NON_NULL)`，`page`/`data` 二选一出现；分页端点走 `data.records`/`data.total`（本模块分页均用 `ResponseWrapper.success(pageResult)`，`data` 直接是 `PageResult<T>`，未使用 `ResponseWrapper.page(...)` 分支，与 customer-marketing 等模块的 `PageResp` 命名不同，字段结构一致：`pageNo`/`pageSize`/`total`/`records`/`totalPages`）。

### 0.2 错误响应结构
```json
{
  "code": "RE-40001",
  "message": "当前用户未绑定党组织，请联系管理员",
  "data": null,
  "traceId": "xxx-xxx",
  "timestamp": "2026-07-19T08:00:00Z"
}
```
`RE-4xxxx` 为**裸字符串错误码**（`new BizException("RE-40001", "...")`），本模块未建 `ReErrorCode` 枚举类，`docs/common-dev-guide.md` 附录 B 模块错误码前缀表未收录 `RE-` 前缀（见模块根 AGENTS.md「已知有效限制」）。

### 0.3 分页请求/响应参数（材料上报/审核队列专用，非平台通用 `PageRequest`）
本模块分页端点（`/submits/my`、`/reviews/queue`）直接用 `@RequestParam` 接收 `pageNo`/`pageSize`，**不是**平台标准 `PageRequest` 对象，也无 `sortField`/`sortOrder` 参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| pageNo | int | 1 | 页码（从 1 开始） |
| pageSize | int | 10 | 每页条数（**默认 10**，非平台通用 20；代码未做上限校验，与根 AGENTS.md 的分页规范不完全一致，属本模块实现细节，未见截断逻辑） |

响应体 `PageResult<T>`（`common-web`）：
```json
{ "pageNo": 1, "pageSize": 10, "total": 16, "records": [ ] }
```

### 0.4 @BizAuth 注解参数说明
| 参数 | 说明 |
|---|---|
| bizType | 本模块恒为 `BizType.RED_ENGINE`（`common-security` 枚举，`code="RED_ENGINE"`） |
| action | 动作，本模块实际用到：`LIST`/`READ`/`WRITE`/`DELETE`/`CONFIG`/`EXECUTE`/`EXPORT`（`BizAction` 枚举全量另含 TRANSFER/APPROVE/REJECT/IMPORT/RECALC 等，本模块未使用） |

### 0.5 统一响应 Code
- `0` — 成功
- `RE-4xxxx` — 红色引擎业务错误（RE-40001~RE-40009，见「10. 错误码」）
- `AUTH-4xxxx` — 认证/权限错误（如 `@BizAuth` 校验失败）
- `COMMON-4xxxx` — 通用错误（参数校验失败等，来自 `@Valid`/`@NotBlank`/`@NotNull` 违反）

## 2. 用户党组织映射（`ReUserPartyMapController`，`/api/re/user-party-maps`）

### 2.1 GET /api/re/user-party-maps — 映射列表

- **@BizAuth**：`bizType=RED_ENGINE, action=LIST`
- **PT_RESOURCE**：`P_RE_MAP_LIST`
- **授权角色**：仅 SYS_ADMIN
- **查询参数**：

| 参数 | 类型 | 默认值/边界 | 匹配语义 |
|---|---|---|---|
| pageNo | int | 默认 1，小于 1 归一为 1 | 页码，从 1 开始 |
| pageSize | int | 默认 10，小于 1 归一为 10，大于 100 截断为 100 | 每页条数 |
| username | String | 可选，首尾空白忽略 | 登录工号 `PT_USER.USERNAME` 包含式模糊匹配 |
| displayName | String | 可选，首尾空白忽略 | 中文姓名 `PT_USER.USERCHNNAME` 包含式模糊匹配 |
| partyOrgId | Long | 可选 | 党组织 ID 精确匹配 |
| partyRole | String | 可选，首尾空白忽略 | 党内角色精确匹配 |

`username` 与 `displayName` 同时传入时为 **AND** 关系；党组织、党内角色与用户条件之间同样为
AND。服务端先通过 auth `UserApi.findUsersByUsernameAndDisplayName` 取得候选 `PT_USER.USER_ID`，再把
候选集合与党组织/角色条件一并交给本模块 MyBatis-Plus 分页，因此过滤发生在分页前，`total` 与
`records` 口径一致；候选为空时直接返回空页，不生成空 `IN`，也不会退化成无条件查询。

**响应体** `PageResult<ReUserPartyMapDTO>`
```json
{
  "code": "0",
  "data": {
    "pageNo": 1,
    "pageSize": 10,
    "total": 1,
    "totalPages": 1,
    "records": [
      {
        "id": 1,
        "userId": "PT_USER_ID_1001",
        "username": "E001",
        "displayName": "张三",
        "partyOrgId": 2,
        "partyRole": "SECRETARY",
        "createTime": "2026-07-18 10:00:00",
        "updateTime": "2026-07-18 10:00:00"
      }
    ]
  }
}
```

当页记录以 `RE_USER_PARTY_MAP.USER_ID` 批量调用 auth `UserApi.getUserByEmpIds`，响应中的
`username` 和 `displayName` 分别是仅供展示的 `PT_USER.USERNAME` 与
`PT_USER.USERCHNNAME`；持久化字段仍为 `userId=PT_USER.USER_ID`。

### 2.2 POST /api/re/user-party-maps — 绑定用户党组织

- **@BizAuth**：`bizType=RED_ENGINE, action=CONFIG`（注意：非 `WRITE`，本模块内唯一使用 `CONFIG` 动作的端点）
- **PT_RESOURCE**：`P_RE_MAP_BIND`（种子注释标"高危"，但 Task 6 评审裁决维持 `reasonRequired=false`，非遗漏）
- **授权角色**：仅 SYS_ADMIN
- **@AuditLog**：`action=RE_MAP_BIND, resourceType=RE_USER_PARTY_MAP, reasonRequired=false`

**请求体** `ReUserPartyMapDTO`（`@Valid @RequestBody`）：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|---|---|---|---|---|
| userId | String | 是 | `@NotBlank(message="userId 不能为空")` | 平台用户 ID（`PT_USER.USER_ID`） |
| username | String | 否 | 请求忽略 | 展示用工号（`PT_USER.USERNAME`），由服务端响应回填 |
| displayName | String | 否 | 请求忽略 | 展示用姓名（`PT_USER.USERCHNNAME`），由服务端响应回填 |
| partyOrgId | Long | 是 | `@NotNull(message="partyOrgId 不能为空")` | 党组织 ID（`RE_PARTY_ORG.id`） |
| partyRole | String | 是 | `@NotBlank(message="partyRole 不能为空")` | 兼容描述字段：`ORG_REVIEWER`/`BRANCH_REVIEWER`/`SECRETARY`/`REPORTER`（不参与授权；真正权限只认平台 `PT_ROLE`） |

前端新增映射时复用 auth 用户列表作为远程下拉，同时展示 `PT_USER.USERNAME`
和 `PT_USER.USERCHNNAME`，但仅提交其对应的
`PT_USER.USER_ID`。服务端仍通过 `UserApi.getUserByEmpId` 二次校验，禁止绕过页面保存不存在的用户，
也禁止保存登录名 `PT_USER.USERNAME`。`partyRole` 仅用于兼容展示，
用户拥有多个党建角色时不要求也不能在该单值字段中表达并集；接口 RBAC 唯一读取
`PT_USER_ROLE → PT_ROLE → PT_ROLE_RESOURCE`。绑定为 `uk_user` 唯一键 upsert 语义
（`bind()` 先查后插/更新，已知有并发窗口下的 `DuplicateKeyException` 兜底重查逻辑）。

绑定成功后，与映射处于同一事务的任务同步会根据平台 `R_RE_REPORT` 角色和最新党支部映射重算
当前未结束的开放实例报送员待办：全部/指定支部任务向新支部补齐待办，不再属于旧支部且未处理的待办置为
`CANCELLED`；指定员工任务仍只能授予明确目标员工。`partyRole` 不参与这个判定，未拥有平台报送员
角色的用户不得因为党组织映射而获得填报待办。未来窗口提前按 `WINDOW_START_AT` 写入待办可用时间，
查询侧到点前不展示；已提交的历史通过提交人关系保持可查，不因映射变更删除。

**响应体**：`Void`

**错误码**：
- `RE-40009` 平台用户不存在，无法绑定党组织

## 3. 材料上报（`ReSubmitController`，`/api/re/submits`）

移植自源 `business.controller.SubmitController`。源系统 `POST /api/submit/{id}/files`（`@Deprecated uploadFile`）本次不落地——附件改走 governance `FileApi`，前端先 `POST /api/files/upload` 直传拿 `fileObjectId`，随创建请求体一并提交。

### 3.1 POST /api/re/submits — 新建材料上报

- **@BizAuth**：`bizType=RED_ENGINE, action=WRITE`
- **PT_RESOURCE**：`P_RE_SUBMIT_ADD`
- **授权角色**：`R_RE_REPORT`、`R_RE_SECR`
- **@AuditLog**：`action=RE_SUBMIT_ADD, resourceType=RE_SUBMIT`

**请求体** `ReSubmitCreateReqDTO`（`@Valid @RequestBody`）：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|---|---|---|---|---|
| dimension | String | 是 | `@NotBlank(message="dimension 不能为空")` | 考核维度（dim1~dim4，字典 `RE_DIMENSION`） |
| itemCode | String | 是 | `@NotBlank(message="itemCode 不能为空")` | 考核项编码（如 `1.1`，字典 `RE_ITEM_CODE`） |
| itemName | String | 是 | `@NotBlank(message="itemName 不能为空")` | 考核项名称 |
| maxScore | BigDecimal | 否 | 无 | 该考核项满分上限；为空时评分校验兜底默认 100 |
| projectName | String | 否 | 无 | 项目名称 |
| submitType | Integer | 是 | `@NotNull(message="submitType 不能为空")` | 上报类型：1月度 2季度 3年度 |
| submitDate | LocalDate | 是 | `@NotNull(message="submitDate 不能为空")` | 上报日期 |
| formData | String | 否 | 无 | 表单数据（JSON 字符串） |
| fileObjectIds | List\<String\> | 否 | 无 | governance `FileApi.upload` 返回的文件对象 ID 列表，服务端逐个写 `RE_SUBMIT_FILE` 并调用 `FileApi.bindFile` |
| taskAssignmentId | Long | 否 | 无 | 四维材料上报接入任务域时的支部分配 ID；须与 `taskId`、`taskInstanceId` 一并作为任务上下文 |
| taskId | Long | 否 | 无 | 四维材料上报接入任务域时的任务定义 ID；服务端仍以 assignment 关系复核，不信任单独传值 |
| taskInstanceId | Long | 否 | 无 | 四维材料上报接入任务域时的任务实例 ID；服务端仍以 assignment 关系复核，不信任单独传值 |

**关键约束**：`orgId`/`submitterId` **不接受前端传入**——服务端从
`CurrentUserApi.getCurrentEmpId()` 取得当前登录人的 `PT_USER.USER_ID`，经
`ReUserPartyMapService.getRequiredPartyOrgId` 强制解析归属党组织，防止越权把上报挂到他人组织名下。

**响应体**：`Long`（新建记录 ID；创建即 `status=1` 已提交，无草稿态入口）

**四维兼容路径按任务上下文分流**：当 `taskId`、`taskInstanceId`、`taskAssignmentId` 三项均存在时，旧入口
在创建 `RE_SUBMIT` 的同一事务内接入任务域。首个材料创建该 assignment 的任务提交 envelope（`RE_TASK_SUBMISSION`
版本）并将待审状态推进为 `BRANCH_PENDING`，同时追加 `RE_TASK_RE_SUBMIT_REL` 桥接和一次四维进度；当前版本仍为
`BRANCH_PENDING` 时，后续维度上报复用同一任务提交版本，只追加对应旧材料桥接并累计一次本次上传的维度进度，
不重复创建 envelope 或推进状态。只有当前版本被支部或组织驳回后，下一次上报才创建递增的新版本。
三项上下文均缺省时是合法的侧栏旧入口：只创建/更新 `RE_SUBMIT`，不伪造 `RE_TASK_SUBMISSION`、
`RE_TASK_BRANCH_ASSIGNMENT`、待办或桥接关系；该记录仍由旧材料审核队列和支部书记首页待办展示。只有任务上下文
齐备且经 assignment/实例关联校验通过时，才允许进入任务路径；任何不完整或不匹配的上下文都不得用来伪造任务关系。

**错误码**：
- `RE-40001` 当前用户未绑定党组织，请联系管理员

### 3.2 GET /api/re/submits/my — 我的上报列表（按党组织）

- **@BizAuth**：`bizType=RED_ENGINE, action=LIST`
- **PT_RESOURCE**：`P_RE_SUBMIT_MY`
- **授权角色**：`R_RE_REPORT`、`R_RE_SECR`（**不含** `R_RE_ORGREV`；已停用的 `R_RE_BRREV` 仅保留历史关系）

**请求参数（Query）**：`pageNo`（默认 1）、`pageSize`（默认 10）

**已知限制**（终审 F-1，非阻断）：`insertScoreWithLimitCheck` 走"`selectList` 内存求和 → 校验 → `insert`"，无读锁/唯一约束，并发场景下可绕过 `maxScore`，见模块根 AGENTS.md「已知有效限制」。

## 7. RE_SUBMIT 状态机（四态）

```
创建 ──────────────────────────────▶ status=1（已提交，创建即此态，无草稿态入口）
                                        │
                        ┌───────────────┼───────────────┐
                        │ approve                        │ reject
                        ▼                                 ▼
              status=2（已通过）                 status=3（已驳回）
              + 落 RE_SCORE（超上限抛 RE-40004）    + 无前置状态校验（源系统同款保真，
              + reviewerId/reviewDate 回填           可对 2/3 态重复调用并覆盖）
```

- `status=0`（草稿）为 DDL 遗留默认值，**当前无任何代码路径可产生该状态**——`ReSubmitService.createSubmit` 落库直接写 `status=1`，源系统"先存草稿后提交"两段式语义已废弃（YAGNI）。
- `approve`/`reject` 均**不校验**"仅 `status=1` 才可审核"（源系统同款保真，非遗漏）：对已是 `status=2`/`3` 的记录重复调用审核端点仍会被静默覆盖，`approve` 还会因此重复插入 `RE_SCORE` 明细（技术债②）。
- `approve`/`reject` 均在状态流转前按持久化 `submitterId` 拒绝本人自审；多角色权限并集不会绕过该实体级守卫。

## 8. 两级审核流转说明

红色引擎两级审核是**自管状态机**，不接 Flowable（本模块不依赖 `workflow-center`，不持有 `business_key`/`BIZ_PROCESS_MAP`）：

1. **上报（第 0 级，`R_RE_REPORT`/`R_RE_SECR`）**：`POST /api/re/submits` 创建，`orgId` 由当前登录人经 `RE_USER_PARTY_MAP` 强制派生，`status` 直接置 `1`（已提交），无独立提交动作。
   附件先走 governance `POST /api/files/upload`，因此两个上报角色另需共享资源 `G_FILE_UPLOAD`；纯审核角色不授予。
2. **审核（`R_RE_BRREV` 支部审核员 / `R_RE_ORGREV` 组织审核员，两角色权限对等、无先后级联关系）**：
   - `GET /api/re/reviews/queue` 拉取 `status=1` 待审队列（按 `submitDate` 升序）
   - `GET /api/re/reviews/{id}/preview` 查看上报详情
   - `POST /api/re/reviews/{id}/approve` 通过并可选携带 `score` 落 `RE_SCORE` 明细（校验 `maxScore` 累计上限），`status→2`
   - `POST /api/re/reviews/{id}/reject` 驳回，`status→3`
   - 两条写命令都先比较持久化 `submitterId` 与当前审核人 `empId`；相同则 `RE-40008`，不允许自审
3. **两级角色区分体现在数据可见范围而非流程节点顺序**：`R_RE_BRREV`（支部审核员）与 `R_RE_ORGREV`（组织审核员）共享同一条待审队列/同一套 approve/reject 端点（`P_RE_REVIEW_Q`/`P_RE_REVIEW_APPR`/`P_RE_REVIEW_REJ` 三资源均对两角色平等授权），代码层面**没有**"先支部审核通过再进组织审核"的强制串行节点——任一具备审核权限的角色均可对同一条 `status=1` 记录直接终审，"两级"是角色设置上的两类审核人，非流程编排上的两道关卡（与 Flowable 多节点审批流的"层层递进"语义不同，见模块根 AGENTS.md「模块定位」）。
4. **逾期与预警是审核流程外的旁路能力**：`R_RE_ORGREV` 可在驾驶舱对逾期未审的上报（`status∈{0,1}` 且超 7 天）手工执行扣分（`RE-40005` 兜底）；红黄牌预警池基于 `RE_SCORE.final_score` 只读展示，不驱动状态流转。

上段的 `R_RE_BRREV`/`R_RE_ORGREV` 对等关系是源系统及初始基础种子的历史事实；角色合并后
`R_RE_BRREV` 已停用，当前支部书记对 legacy `RE_SUBMIT` 的队列、预览和操作授权及范围以第 12 节
为准，不因保留历史关系而恢复旧菜单或旧角色。

## 12. 现行任务域、首页与资源授权契约（2026-09-03）

本节是本次任务域上线后的当前 REST 与 RBAC 对照。资源实际写入由
`docs/superpowers/sql/2026-08-31-redengine-task-rbac-align.sql` 负责，数据库实施仅限获授权的
`yit_test`，不由应用启动或迁移框架自动执行。`@BizAuth` 只声明 `RED_ENGINE` 与动作，URL/HTTP
方法到 `PT_RESOURCE` 的匹配仍由平台资源表完成；所有写操作的实体范围校验仍由 Service 层完成。

### 12.1 任务管理

| 方法与路径 | 请求/响应要点 | `@BizAuth` | `PT_RESOURCE` | 授权角色 |
|---|---|---|---|---|
| `GET /api/re/tasks` | `ReTaskPageQueryDTO` 分页；支持 `title`、`taskNature`、`businessType`、`cycleType`、`status`、发布时间范围 | `LIST` | `P_RE_TASK_LIST` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `POST /api/re/tasks` | `ReTaskCreateReqDTO`；标题、说明、定时/临时、业务类型、周期窗口、文件要求、任务对象；成功即发布 | `WRITE` | `P_RE_TASK_CREATE` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `GET /api/re/tasks/eligible-users` | `ReTaskEligibleUserPageQueryDTO` 分页；返回当前红色引擎数据范围内已启用且已绑定党支部的员工，支持员工 ID/工号/姓名关键字和党支部过滤 | `LIST` | `P_RE_TASK_ELIGIBLE` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `GET /api/re/tasks/{taskId}` | `ReTaskDetailDTO`；返回对象、文件类型及当前任务实例 | `READ` | `P_RE_TASK_GET`（`MENU_RANK_NO=10`） | `R_RE_ORGREV`、`SYS_ADMIN` |
| `GET /api/re/tasks/{taskId}/assignments` | `ReTaskAssignmentPageQueryDTO`；按支部、状态、填报时间分页 | `LIST` | `P_RE_TASK_ASG_LIST` | `R_RE_ORGREV`、`SYS_ADMIN` |

`ReTaskCreateReqDTO` 的 `taskNature` 为 `SCHEDULED`/`TEMPORARY`（兼容请求别名 `PERIODIC`），四大
维度任务使用 `businessType=FOUR_DIMENSION`，其他任务使用 `GENERAL`。定时任务周期为
`WEEK_START`、`WEEK_END`、`MONTH_START`、`MONTH_END`、`QUARTER_START`、`QUARTER_END`，周期窗口
按北京时间自然日计算；临时任务填写 `temporaryStartTime`/`temporaryEndTime`。发布定时任务时，
只有当前日期落在有效窗口内才立即生成实例、分配和待办，未来生效任务由窗口补偿生成；临时任务
立即生成首个实例，响应中的 `todoCount` 仅统计实际创建的报送员待办。四大维度导出或填报所选
明细使用 `itemCodes`，服务层通过治理中心公开 `DictApi.getDictItems("RE_ITEM_CODE")` 校验
启用字典项，不直接访问治理中心表，也不把逻辑字典误写成独立物理表。

`GET /api/re/tasks/eligible-users` 的查询参数为 `pageNo`（默认 1）、`pageSize`（默认 20，最大
100）、`keyword`（可选，匹配平台用户 ID、登录工号或中文姓名）和 `branchId`（可选，党支部
ID）。响应使用统一 `page` 分页封装，记录类型为 `ReTaskEligibleUserDTO`：`employeeId` 是
提交任务对象时应使用的 `PT_USER.USER_ID`，同时返回 `username`、`displayName`、`branchId`
和 `branchName`。服务端先读取本域 `RE_USER_PARTY_MAP`/`RE_PARTY_ORG` 形成可落到党支部的
员工范围，再通过 auth 公开 `UserApi.getUserByEmpIds` 补齐员工信息并只保留 `enabled=true`，
最后执行关键字过滤和分页。该接口独立登记 `P_RE_TASK_ELIGIBLE`，不要求也不授予
`/api/admin/users` 的全局用户管理资源；当前 auth 公开 API 或本域组织映射读取失败时以
`RE-50014` fail-close。

### 12.2 报送员任务处理与附件

| 方法与路径 | 说明 | `PT_RESOURCE` | 授权角色 |
|---|---|---|---|

| `POST /api/re/tasks/submissions` | `ReTaskSubmissionReqDTO`；`assignmentId`、`content`、`fileObjectIds`、幂等号必按 DTO 约束提交；四维任务可携带兼容字段，旧材料桥接按 3.1 兼容路径完成 | `P_RE_TASK_SUBMIT` | `R_RE_REPORT`、`SYS_ADMIN` |

提交状态由任务服务自管：`DRAFT → BRANCH_PENDING → BRANCH_APPROVED → ORG_PENDING → APPROVED`；
支部或组织驳回分别进入 `REJECTED_BY_BRANCH`/`REJECTED_BY_ORG`，重新提交回到
`BRANCH_PENDING`，且沿用原 assignment 记录、版本递增并保留状态历史。四大维度工作台响应提供
`legacyReviewId`/`submitId` 兼容字段，用于继续打开原材料上报和评分入口。任务附件使用治理中心
文件对象 ID，不允许红色引擎直接访问治理表或 OBS。

任务提交字段按任务类型分流：`businessType=FOUR_DIMENSION` 时正文 `content` 可为空，任务 envelope
保存任务上下文并通过 `RE_TASK_RE_SUBMIT_REL` 定位旧材料；四维详情的维度、明细和结构化材料以关联的
`RE_SUBMIT` 为准。临时或普通任务（`businessType=GENERAL`）以当前 `RE_TASK_SUBMISSION` 版本的
`content`/`formData` 作为填报正文，附件由当前版本的任务附件快照提供。

`ReTaskWorkflowAssignmentDTO` 始终只返回 assignment 指向的当前提交版本；`content`/`files` 不得从旧版本混入，
`reviewFeedback` 返回当前版本的 `REVIEW_OPINION`，供驳回后报送员重新填报及两级工作台回显。任务说明与
本次填报内容是两个独立字段，前端必须分栏或带标签展示，不能连续无标识渲染为“两次填报”。

### 12.3 任务处理（支部书记）

支部书记入口的用户可见菜单名称为“任务处理”，仍使用独立的支部任务资源；支部书记只使用该入口，
不继承报送员的四大维度材料上报、报送员任务处理或任务填报写入资源。标准任务路径处理有任务上下文的
assignment；无任务上下文的四维材料直接使用下表的 legacy 审核路径，不通过 `source=material` 改写或
复用标准 task URL。两个路径别名都受同一业务方法的角色、支部书记与党支部归属二次校验保护：

| 方法与路径 | `PT_RESOURCE` | 说明 |
|---|---|---|
| `GET /api/re/reviews/tasks/branch/queue` / `GET /api/re/tasks/branch-review` | `P_RE_WF_BQC` / `P_RE_WF_BQ` | 任务来源的支部待处理/审核中分页队列；支持 `tab`（`PENDING`/`REVIEWING`/`PASSED`/`REJECTED`）及状态、关键字、业务类型、周期、支部、提交时间筛选，服务端在 SQL 分页前按支部书记归属收窄 |

| `POST .../branch/{assignmentId}/reject` / `POST .../branch-review/{assignmentId}/reject` | `P_RE_WF_BRC` / `P_RE_WF_BR` | 驳回意见必填，退回报送员 |
| `POST .../branch/{assignmentId}/submit-to-org` / `POST .../branch-review/{assignmentId}/submit-to-org` | `P_RE_WF_BSC` / `P_RE_WF_BS` | 提交组织审核 |

| `GET /api/re/reviews/{id}/preview` | `P_RE_REVIEW_Q` | legacy 四维材料详情预览；服务端按实体 `orgId` 做支部范围校验 |
| `POST /api/re/reviews/{id}/approve` | `P_RE_REVIEW_APPR` | legacy 四维材料通过（可选评分）；服务端先做实体支部范围及自审校验 |

任务工作流标准路径资源只授予 `R_RE_SECR` 与 `SYS_ADMIN`；legacy 审核资源也必须正式授予
`R_RE_SECR`，当前可调用角色为 `R_RE_SECR` 与 `SYS_ADMIN`，其中 `R_RE_SECR` 的读取和写入必须受
当前书记支部范围约束。标准路径的队列排序值为 `-20`、详情/动作排序值为 `-10`，保证它们先于旧的
`/api/re/reviews/**` 通配资源命中；无任务上下文的材料仍由旧路径处理，不得因支部审核员角色停用而
丢失该合法来源。若投产 DML 尚未补齐 `R_RE_SECR` 与 `P_RE_REVIEW_Q`/`P_RE_REVIEW_APPR`/
`P_RE_REVIEW_REJ` 的关系，书记调用旧路径会得到已联调确认的 `AUTH-40301`；该问题应通过 RBAC
数据变更解决，不能通过把材料伪装为 task assignment 绕过。

支部“任务处理”页面对任务 assignment 与 legacy `RE_SUBMIT` 两个来源分别服务端分页，再在当前页分别
呈现：任务来源调用标准支部任务路径，材料来源调用旧 `/api/re/reviews/queue`、`/{id}/preview`、
`/{id}/approve`、`/{id}/reject` 路径。列表中的每一条任务/材料都必须点击后在当前页弹出详情，不跳转到
其他路由，审核动作也在对应详情中完成。首页 legacy 待办进入该页时可保留 `source=material`（仅表示
`RE_SUBMIT` 来源）与 `submitId` 上下文，由当前页调用 legacy 材料接口并自动打开同一条材料详情；该标识
不是标准 task URL 的兼容或分流参数。两个来源不以 assignment 查询结果互相补造，不把来源分页先在前端合并
后再伪装为服务端分页。

详情内容按任务类型和来源取数：

- 四大维度任务来源以当前 assignment 的 `RE_TASK_SUBMISSION` 版本确定任务上下文，再经
  `RE_TASK_RE_SUBMIT_REL` 读取其关联的旧 `RE_SUBMIT`/桥接材料及材料附件；不能把四维材料正文当作普通任务
  `content`，也不能混入被驳回旧版本。无任务上下文的侧栏旧入口直接作为 legacy 材料来源，读取
  `RE_SUBMIT`（预览走 `/api/re/reviews/{id}/preview`），不伪造 task/instance/assignment；
- 临时或普通任务以当前 `RE_TASK_SUBMISSION` 版本的 `content`/`formData` 展示正文，附件读取该版本的
  `RE_TASK_SUBMISSION_FILE` 快照并通过治理 `FileApi` 下载；
- 无论任务类型，详情读取必须限定当前 assignment 的当前版本，不得混入被驳回的旧版本；未提交正文或附件时
  显示空状态，但不影响任务行可打开和待办操作。legacy 材料不适用 assignment 版本规则，而以其
  `RE_SUBMIT` 实体和服务端支部范围校验为准。

### 12.4 组织审核工作台

| 方法与路径 | `PT_RESOURCE` | 授权角色 |
|---|---|---|
| `GET /api/re/reviews/tasks/org/queue` / `GET /api/re/tasks/org-review` | `P_RE_WF_OQC` / `P_RE_WF_OQ` | `R_RE_ORGREV`、`SYS_ADMIN`；支持与支部工作台相同的 `tab`、状态、关键字、业务类型、周期、支部、提交时间筛选，服务端在 SQL 分页前按组织审核状态过滤 |
| `GET /api/re/reviews/tasks/org/{assignmentId}` / `GET /api/re/tasks/org-review/{assignmentId}` | `P_RE_WF_OGC` / `P_RE_WF_OG` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `POST .../org/{assignmentId}/approve` / `POST .../org-review/{assignmentId}/approve` | `P_RE_WF_OAC` / `P_RE_WF_OA` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `POST .../org/{assignmentId}/reject` / `POST .../org-review/{assignmentId}/reject` | `P_RE_WF_ORC` / `P_RE_WF_OR` | `R_RE_ORGREV`、`SYS_ADMIN` |

组织审核员可查看支部填报内容和附件并执行任务通过/驳回；驳回意见必填并退回报送员。组织审核员同时
拥有任务新增发布、任务支部进度、异步导出、党组织管理和用户党组织映射资源，但不授予报送员的
四大维度材料上报、报送员任务处理菜单资源。无任务上下文的四大维度 legacy 材料由支部书记任务处理和
`SYS_ADMIN` 通过 `P_RE_REVIEW_Q`/`P_RE_REVIEW_APPR`/`P_RE_REVIEW_REJ` 处理；`R_RE_ORGREV` 的历史
资源关系不代表当前可调用能力。新任务的组织审核使用上表的 `P_RE_WF_O*` 资源，不与旧材料正文混用。

“任务处理”页面后打开对应材料详情；查询失败或支部范围无法解析时不得回退为全量 legacy 待办。

### 12.6 任务异步导出

| 方法与路径 | 请求/响应要点 | `PT_RESOURCE` | 授权角色 |
|---|---|---|---|
| `POST /api/re/tasks/{taskId}/exports` | `ReTaskExportReqDTO.itemCodes`；四大维度任务必须先校验启用的明细编码 | `P_RE_TASK_EXP_NEW` | `R_RE_ORGREV`、`SYS_ADMIN` |
| `GET /api/re/task-exports/{exportId}` | 返回 `QUEUED/RUNNING/SUCCEEDED/FAILED/EXPIRED/CANCELLED` 对外状态及可下载标记 | `P_RE_TASK_EXP_GET` | `R_RE_ORGREV`、`SYS_ADMIN` |

子目录，无附件时仅保留 Excel。导出范围、任务归属、路径安全、同名附件去重及明细项快照由服务
层校验；跨模块文件对象仍走治理 `FileApi`。

### 12.7 当前菜单矩阵

`M_RE_RECORDS`（报送员入口）与 `M_RE_BRANCH_WORK`（支部书记入口）在界面上均显示为“任务处理”；
两者的路由、资源和角色授权仍然分离，前者处理本人任务，后者处理所属支部待办。
