# 绩效计算中心 — 并发与事务策略

> 模块: performance-engine-center
> 版本: v1.0
> 最后更新: 2026-04-10

本文档描述绩效计算中心各核心业务在并发、事务、锁、幂等、缓存等方面的设计要求。所有写操作都必须遵守本文档定义的事务边界、锁策略和幂等规则, 以保证数据一致性和系统可靠性。

## 1. sys_control 版本管理并发

### 1.1 并发场景

- 多节点同时接收数据推送, 可能同时尝试创建同一维度同一日期的新版本
- 历史回算任务和新数据导入任务可能同时要求切换 `is_valid`
- 运维人员手动重置版本与系统自动切换冲突

### 1.2 并发保护手段

**数据库约束**:
```sql
UNIQUE KEY uk_scope_date(scope_dim, latest_data_date, current_version)
```
保证同一维度+日期+版本号组合唯一。

**分布式锁** (Redis):
- Key: `perf:sys_control:switch:{scope_dim}`
- Value: `{nodeId}:{threadId}:{timestamp}`
- TTL: 30 秒 (足够一次版本切换事务)
- 释放: Lua 脚本原子校验 value 后删除 (防止误删其他节点的锁)

### 1.3 事务流程

切换有效版本必须在**同一个数据库事务 + 分布式锁**内完成:

```java
@Transactional(rollbackFor = Exception.class)
public void switchValidVersion(String scopeDim, LocalDate dataDate, String version) {
    String lockKey = "perf:sys_control:switch:" + scopeDim;
    String lockValue = nodeId + ":" + Thread.currentThread().getId() + ":" + System.currentTimeMillis();
    try {
        // 1. 获取分布式锁, 获取不到则抛出 CONCURRENT_MODIFY 异常
        boolean locked = redisLockUtil.tryLock(lockKey, lockValue, 30, TimeUnit.SECONDS);
        if (!locked) {
            throw new BizException(ErrorCode.CONCURRENT_MODIFY, "版本切换正在进行, 请稍后重试");
        }
        // 2. 将原有效版本置为无效
        sysControlMapper.invalidateCurrentVersion(scopeDim);
        // 3. 插入或更新新版本为有效 (幂等, 支持重试)
        SysControl record = new SysControl();
        record.setScopeDim(scopeDim);
        record.setLatestDataDate(dataDate);
        record.setCurrentVersion(version);
        record.setIsValid(1);
        sysControlMapper.upsert(record);
        // 4. 清除 Redis 缓存 (让下游读取最新)
        redisTemplate.delete("perf:sys_control:" + scopeDim);
    } finally {
        redisLockUtil.unlock(lockKey, lockValue);
    }
}
```

对应 SQL:
```sql
-- invalidateCurrentVersion
UPDATE sys_control
SET is_valid = 0, updated_by = #{empId}, update_time = NOW()
WHERE scope_dim = #{scopeDim} AND is_valid = 1;

-- upsert (使用 ON DUPLICATE KEY UPDATE)
INSERT INTO sys_control(scope_dim, latest_data_date, current_version, is_valid, updated_by)
VALUES(#{scopeDim}, #{latestDataDate}, #{currentVersion}, 1, #{updatedBy})
ON DUPLICATE KEY UPDATE is_valid = 1, updated_by = #{updatedBy}, update_time = NOW();
```

### 1.4 读端一致性

读端通过 Redis 缓存 `perf:sys_control:{scope_dim}` 缓存当前有效版本, TTL=60 秒, 缓存内容示例:
```json
{
  "scopeDim": "EMP",
  "latestDataDate": "2026-04-09",
  "currentVersion": "20260409-V1"
}
```
版本切换后主动清除缓存, 下一次读取会从 DB 加载最新。

## 2. 指标计算事务

### 2.1 计算流程总览

```
调度触发 (每日 02:00)
  ↓
创建 perf_run_task (task_type=METRIC_RUN)
  ↓
加载当日启用的所有一级指标 (按依赖拓扑排序)
  ↓
逐个指标:
  ├─ 为该指标创建子任务日志
  ├─ 独立事务内执行 SQL/PROC → UPSERT 到结果宽表
  └─ 成功后触发二三级级联刷新 (异步消息)
  ↓
所有一级完成 → 消费级联刷新消息
  ↓
更新主任务状态为 SUCCESS / PARTIAL
```

### 2.2 事务边界

**每个指标独立事务**:
- 指标 A 失败不影响指标 B
- 事务粒度: 一个 SELECT INTO + 一个 INSERT ON DUPLICATE KEY UPDATE
- 大数据量指标分批处理 (每批 5000 行), 每批独立事务

**代码示例**:
```java
public MetricRunResult runSingleMetric(String metricCode, LocalDate dataDate, String version) {
    MetricDef def = metricDefMapper.getByCode(metricCode);
    try {
        // 独立事务执行
        int affectedRows = transactionTemplate.execute(status -> {
            return metricCalcEngine.execute(def, dataDate, version);
        });
        return MetricRunResult.success(metricCode, affectedRows);
    } catch (Exception e) {
        // 记录失败, 但不回滚其他指标
        log.error("metric calc failed: {}", metricCode, e);
        perfRunTaskMapper.insertSubTaskFailed(metricCode, e.getMessage());
        return MetricRunResult.failure(metricCode, e.getMessage());
    }
}
```

### 2.3 级联刷新策略

**异步化**: 一级指标完成后不立即计算二级, 通过内存队列/消息异步触发, 避免长事务。

```
一级指标 A 完成
  ↓
发布事件 MetricCalculatedEvent(A, dataDate, version)
  ↓
事件监听器查询 perf_metric_ref: 找出所有引用 A 的指标 B
  ↓
判断 B 所依赖的所有指标是否已全部完成
  ↓ (全部就绪)
触发 B 的计算 (独立事务)
```

### 2.4 失败处理

- 单个指标失败: 记录错误到 `perf_run_task.error_msg`, 继续下一个
- 主任务最终状态:
  - 所有成功 → `SUCCESS`
  - 部分失败 → `PARTIAL`
  - 全部失败 → `FAILED`
- 失败指标记录到结果预览: `result_preview_json`
- 通知配置的告警接收人 (依赖 `NotifyApi.sendNotification`)

### 2.5 试运行 (DRY_RUN)

试运行特殊处理:
- 只执行 SELECT, 不写入结果宽表
- 取前 20 行写入 `perf_run_task.result_preview_json`
- 必须在只读事务内 (`@Transactional(readOnly = true)`)
- 不产生级联刷新

## 3. KPI 计算事务

### 3.1 并行策略

KPI 计算按员工维度并行:
- 1000 员工分为 10 批, 每批 100 员工
- 批内串行, 批间并行 (线程池大小 4)
- 每个员工独立事务 (避免锁冲突)

### 3.2 幂等写入

使用 `kpi_result` 的 UK(emp_id, cycle_type, cycle_date, as_of_date) 实现幂等:

```sql
INSERT INTO kpi_result(emp_id, scheme_id, cycle_type, cycle_date, as_of_date,
                       data_version, kpi_total_score, detail_json, calc_batch_id)
VALUES(#{empId}, #{schemeId}, #{cycleType}, #{cycleDate}, #{asOfDate},
       #{dataVersion}, #{totalScore}, #{detailJson}, #{calcBatchId})
ON DUPLICATE KEY UPDATE
    scheme_id = VALUES(scheme_id),
    data_version = VALUES(data_version),
    kpi_total_score = VALUES(kpi_total_score),
    detail_json = VALUES(detail_json),
    calc_batch_id = VALUES(calc_batch_id),
    updated_time = NOW();
```

**效果**:
- 每日重算 (同一 `as_of_date`): 直接 UPDATE, 不产生重复记录
- 新日期首次计算: INSERT 新行

### 3.3 历史回算覆盖

历史回算同样通过 UK 覆盖:

```java
@Transactional
public void recalcKpiForPeriod(String cycleType, LocalDate cycleStart, LocalDate cycleEnd,
                                LocalDate asOfDate, String dataVersion, String batchId) {
    // 查询周期内所有员工
    List<String> empIds = empQueryApi.listAllActiveEmpIds();
    for (List<String> batch : Lists.partition(empIds, 100)) {
        kpiCalcService.calcBatch(batch, cycleType, cycleStart, asOfDate, dataVersion, batchId);
    }
}
```

### 3.4 长事务避免

- 禁止"批量计算 → 批量写入"模式 (可能 10 万行一次性提交)
- 强制分批, 每批独立事务 (100 员工/批)
- 主任务状态更新 (`SUCCESS` / `FAILED`) 在最后一步, 独立事务

## 4. 数据导入事务

### 4.1 导入流程

```
1. 上传文件 → POST /api/perf/import/upload (事务外, 只调用 FileApi)
   ↓
2. 预览 → POST /api/perf/import/preview (只读事务, 不写 DB)
   ↓
3. 确认执行 → POST /api/perf/import/{batchId}/execute
   ├─ 事务 1: 创建 perf_import_batch, 状态 IMPORTING
   ├─ 事务 2: 逐行校验 + 写入目标表 (分批, 每批 1000 行)
   └─ 事务 3: 更新 perf_import_batch 终态 (SUCCESS / FAILED / PARTIAL)
```

### 4.2 预览不写库

预览阶段只解析文件 + 校验, 不产生任何数据库写入:

```java
@Transactional(readOnly = true)
public ImportPreviewDTO preview(String batchId) {
    PerfImportBatch batch = importBatchMapper.getByBatchNo(batchId);
    // 下载文件
    InputStream is = fileApi.download(batch.getFileObjectId());
    // 解析 + 校验前 100 行
    return importPreviewer.preview(is, batch.getImportType(), 100);
}
```

### 4.3 行级校验 + 整批回滚

```java
@Transactional(rollbackFor = Exception.class)
public ImportResult execute(String batchId, boolean failFast) {
    PerfImportBatch batch = loadBatch(batchId);
    List<ImportError> errors = new ArrayList<>();
    int success = 0;
    try {
        for (List<ImportRow> chunk : chunks(file, 1000)) {
            for (ImportRow row : chunk) {
                try {
                    validator.validate(row);
                    writer.write(row);
                    success++;
                } catch (ValidationException ve) {
                    errors.add(ImportError.of(row.getLineNo(), ve.getMessage()));
                    if (failFast) {
                        throw new BizException(ErrorCode.IMPORT_FAILED, "第" + row.getLineNo() + "行校验失败");
                    }
                }
            }
        }
        // 更新批次状态
        updateBatchStatus(batchId, errors.isEmpty() ? "SUCCESS" : "PARTIAL", success, errors);
        return new ImportResult(success, errors);
    } catch (Exception e) {
        // 回滚整批
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        updateBatchStatusFailed(batchId, e.getMessage());
        throw e;
    }
}
```

### 4.4 分批提交 (大文件)

对超过 10000 行的文件, 使用 `REQUIRES_NEW` 传播级别实现分批提交:

```java
public ImportResult executeLargeFile(String batchId) {
    // 每批 1000 行独立事务
    for (List<ImportRow> chunk : chunks(file, 1000)) {
        transactionTemplate.execute(status -> {
            try {
                writer.writeBatch(chunk);
                return true;
            } catch (Exception e) {
                status.setRollbackOnly();
                throw e;
            }
        });
    }
}
```

**权衡**: 分批提交允许部分成功, 必须在 `perf_import_batch` 中准确记录已提交的行号范围, 便于错误恢复和补偿。

### 4.5 防重复导入

使用 `file_md5` 检查:

```java
public String uploadAndCreate(MultipartFile file, String importType, String empId) {
    String md5 = DigestUtils.md5Hex(file.getInputStream());
    // 查询最近 24 小时是否有相同 MD5 的导入
    PerfImportBatch existing = importBatchMapper.findRecentByMd5(md5, 24);
    if (existing != null && !"FAILED".equals(existing.getStatus())) {
        throw new BizException(ErrorCode.DUPLICATE_IMPORT, "最近已导入相同文件: " + existing.getBatchNo());
    }
    // 上传到 MinIO
    String fileObjectId = fileApi.upload(file, empId);
    // 创建批次记录
    return createBatchRecord(fileObjectId, md5, importType, empId);
}
```

## 5. 分配关系调整流程事务

### 5.1 申请发起事务

**事务边界**: 发起申请必须在同一事务中完成以下操作:
1. INSERT `perf_alloc_adjust_apply` 主记录
2. INSERT `perf_alloc_adjust_item` 明细
3. 调用 `WorkflowApi.startProcess()` 创建流程实例
4. UPDATE 申请记录写入 `process_instance_id` 和 `business_key`
5. UPDATE 状态为 `IN_APPROVAL`

```java
@Transactional(rollbackFor = Exception.class)
public Long submitAllocAdjust(AllocAdjustSubmitCmd cmd, String empId) {
    // 1. 校验客户有效性 (跨模块 API)
    if (!customerQueryApi.isValidCustomer(cmd.getCustId())) {
        throw new BizException(ErrorCode.CUSTOMER_NOT_FOUND);
    }
    // 2. 校验明细比例之和 = 100 (按比例分配时)
    if ("RATIO".equals(cmd.getAllocDim())) {
        BigDecimal total = cmd.getItems().stream()
            .map(AllocAdjustItemDTO::getRatio)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        if (total.compareTo(new BigDecimal("100.00")) != 0) {
            throw new BizException(ErrorCode.INVALID_RATIO_SUM);
        }
    }
    // 3. 创建主记录
    PerfAllocAdjustApply apply = buildApply(cmd, empId);
    apply.setStatus("DRAFT");
    allocAdjustApplyMapper.insert(apply);
    // 4. 创建明细
    allocAdjustItemMapper.insertBatch(apply.getId(), cmd.getItems());
    // 5. 发起工作流 (business_key = ALLOC_ADJUST:{applyId})
    String businessKey = "ALLOC_ADJUST:" + apply.getId();
    StartProcessCmd startCmd = StartProcessCmd.builder()
        .processKey("alloc_adjust_approve_v1")
        .businessKey(businessKey)
        .starterEmpId(empId)
        .variables(Map.of("applyId", apply.getId(), "custId", cmd.getCustId()))
        .build();
    StartProcessResult result = workflowApi.startProcess(startCmd);
    // 6. 回写流程实例 ID, 更新状态
    allocAdjustApplyMapper.updateProcessInfo(apply.getId(),
        businessKey, result.getProcessInstanceId(), "IN_APPROVAL");
    return apply.getId();
}
```

**异常处理**:
- 如果 `workflowApi.startProcess()` 抛异常 → 整个事务回滚, 申请记录被撤销
- 如果明细插入失败 → 事务回滚

### 5.2 审批监听事务

**事件驱动**: workflow-center 流程完成后发布 `workflow.process.completed` 事件, performance-engine-center 监听。

```java
@EventListener
@Transactional(rollbackFor = Exception.class)
public void onProcessCompleted(ProcessCompletedEvent event) {
    // 只处理分配关系调整流程
    if (!event.getBusinessKey().startsWith("ALLOC_ADJUST:")) {
        return;
    }
    Long applyId = Long.valueOf(event.getBusinessKey().split(":")[1]);
    String status = event.isApproved() ? "APPROVED" : "REJECTED";
    // 1. 更新申请状态 (并发保护: 用 WHERE status='IN_APPROVAL' 乐观锁)
    int updated = allocAdjustApplyMapper.updateStatusConditional(
        applyId, status, "IN_APPROVAL", event.getCompletedTime());
    if (updated == 0) {
        log.warn("alloc adjust apply already processed: {}", applyId);
        return;
    }
    // 2. 审批通过 → 发送通知 (事务成功后)
    if (event.isApproved()) {
        notificationPublisher.publish(() -> {
            notifyApi.sendNotification(NotifyCmd.of(
                event.getStarterEmpId(), "分配关系调整申请已通过", /*...*/));
        });
    }
}
```

**事务后事件**: 使用 `TransactionSynchronizationManager` 注册事务成功后回调, 避免在事务内调用外部系统 (通知、回算任务等)。

### 5.3 次日同步回写

由独立的 `DataSyncJobService` (调度任务) 处理:
- 每日 01:00 扫描 `status=APPROVED` 的申请
- 根据明细写入 `cust_alloc_relation` (闭合原区间, 插入新区间)
- 写入成功后更新 `status=SYNCED`, `sync_time=now()`
- 独立事务, 失败可重试

```java
@Scheduled(cron = "0 0 1 * * ?")
public void syncApprovedAllocAdjust() {
    List<PerfAllocAdjustApply> approved =
        allocAdjustApplyMapper.listByStatus("APPROVED", 1000);
    for (PerfAllocAdjustApply apply : approved) {
        transactionTemplate.execute(status -> {
            syncSingleApply(apply);
            return true;
        });
    }
}

@Transactional
public void syncSingleApply(PerfAllocAdjustApply apply) {
    LocalDate effectiveDate = apply.getEffectiveDate();
    // 1. 闭合原有效区间 (end_date = effectiveDate - 1)
    custAllocRelationMapper.closePreviousRelations(
        apply.getCustId(), apply.getBizKind(), apply.getAccountNo(),
        effectiveDate.minusDays(1));
    // 2. 插入新区间
    List<PerfAllocAdjustItem> items = allocAdjustItemMapper.listByApplyId(apply.getId());
    for (PerfAllocAdjustItem item : items) {
        if (!"DELETE".equals(item.getOperation())) {
            CustAllocRelation relation = buildNewRelation(apply, item, effectiveDate);
            custAllocRelationMapper.insert(relation);
        }
    }
    // 3. 更新申请状态
    allocAdjustApplyMapper.updateStatus(apply.getId(), "SYNCED");
}
```

## 6. 目标修正流程事务

### 6.1 事务流程 (类似分配关系调整)

1. **发起申请**: INSERT `perf_target_adjust_apply` + 快照原目标值 + 调用 `workflowApi.startProcess`
2. **审批监听**: 事务内更新状态, 事务后触发"应用到 perf_target_value" + "历史回算任务"
3. **应用到 perf_target_value**: 独立事务, 更新 `perf_target_value.target_value`
4. **历史回算**: 异步任务, 触发 `RECALC` 类型的 `perf_run_task`

### 6.2 审批通过后的事务链

```java
@EventListener
public void onTargetAdjustCompleted(ProcessCompletedEvent event) {
    if (!event.getBusinessKey().startsWith("TARGET_ADJUST:")) return;
    Long applyId = Long.valueOf(event.getBusinessKey().split(":")[1]);
    // 事务 1: 更新申请状态
    transactionTemplate.execute(status -> {
        targetAdjustApplyMapper.updateStatusConditional(applyId,
            event.isApproved() ? "APPROVED" : "REJECTED", "IN_APPROVAL");
        return true;
    });
    if (!event.isApproved()) return;
    // 事务 2: 应用到 perf_target_value
    transactionTemplate.execute(status -> {
        applyTargetValueChanges(applyId);
        targetAdjustApplyMapper.updateStatusAndApplied(applyId, "APPLIED");
        return true;
    });
    // 事务 3: 触发历史回算 (异步)
    String recalcTaskId = recalcService.triggerRecalc(applyId);
    targetAdjustApplyMapper.updateRecalcTaskId(applyId, recalcTaskId);
}

@Transactional
public void applyTargetValueChanges(Long applyId) {
    PerfTargetAdjustApply apply = targetAdjustApplyMapper.getById(applyId);
    // 使用 ON DUPLICATE KEY UPDATE 更新目标值
    targetValueMapper.upsert(apply.getPlanId(), apply.getSubjectType(),
        apply.getSubjectId(), apply.getCycleKey(), apply.getMetricCode(),
        apply.getNewTargetValue());
}
```

### 6.3 历史回算事务粒度

回算任务按周期 × 员工分批执行, 避免长事务:

```java
public void executeRecalc(String taskId, RecalcParams params) {
    List<LocalDate> cycleDates = generateCycleDates(params);
    for (LocalDate cycleDate : cycleDates) {
        List<String> empIds = findAffectedEmpIds(params, cycleDate);
        for (List<String> batch : Lists.partition(empIds, 100)) {
            // 每 100 员工独立事务
            transactionTemplate.execute(status -> {
                kpiCalcService.recalcBatch(batch, params.getCycleType(), cycleDate,
                    params.getAsOfDate(), params.getDataVersion(), taskId);
                return true;
            });
            // 更新任务进度
            updateTaskProgress(taskId, calcProgress(cycleDate, batch, cycleDates));
        }
    }
}
```

## 7. 历史回算并发

### 7.1 防重复触发

相同参数重复触发返回已有任务 ID (幂等):

```java
public String triggerRecalc(RecalcParams params, String empId) {
    String paramsHash = DigestUtils.md5Hex(JsonUtil.toJson(params));
    String lockKey = "perf:recalc:trigger:" + paramsHash;
    // 使用 Redis SETNX 尝试占位 (TTL = 24 小时)
    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "LOCKED", 24, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(acquired)) {
        // 已有相同参数的回算任务, 返回已有 task_id
        String existingTaskId = redisTemplate.opsForValue().get(lockKey + ":taskId");
        if (existingTaskId != null) {
            return existingTaskId;
        }
        throw new BizException(ErrorCode.DUPLICATE_RECALC, "相同参数的回算任务正在执行");
    }
    // 创建任务记录
    String taskId = createRunTask("RECALC", params, empId);
    redisTemplate.opsForValue().set(lockKey + ":taskId", taskId, 24, TimeUnit.HOURS);
    // 异步提交
    asyncExecutor.submit(() -> executeRecalc(taskId, params));
    return taskId;
}
```

### 7.2 并发限流

- 同一时刻至多 1 个回算任务 (全局) — 使用 Redis 分布式锁
- Key: `perf:recalc:running`, TTL = 4 小时 (超时自动释放)
- 新任务排队等待或返回"系统繁忙"

```java
public boolean tryStartRecalc(String taskId) {
    String lockKey = "perf:recalc:running";
    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, taskId, 4, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(acquired)) {
        String runningTask = redisTemplate.opsForValue().get(lockKey);
        log.warn("recalc already running: {}, new task: {} queued", runningTask, taskId);
        return false;
    }
    return true;
}
```

### 7.3 任务取消

用户手动取消任务:
- 修改 `perf_run_task.status = CANCELLED`
- 任务线程检测到状态变更, 优雅退出 (不处理新批次, 已处理批次不回滚)
- 释放 Redis 锁, 允许新任务启动

## 8. 缓存策略

### 8.1 缓存分类

| Key 模式 | TTL | 数据 | 更新策略 |
|---|---|---|---|
| `perf:sys_control:{scope_dim}` | 60 秒 | 当前有效版本 | 版本切换后主动清除 |
| `perf:metric_def:{metric_code}` | 10 分钟 | 单个指标定义 | 指标更新后主动清除 |
| `perf:metric_def:list:{base_dim}` | 10 分钟 | 某维度指标列表 | 任一指标变更后清除 |
| `perf:kpi_scheme:{scheme_id}` | 5 分钟 | KPI 方案及其项 | 方案更新后清除 |
| `perf:kpi_scheme:list` | 5 分钟 | 启用方案列表 | 方案状态变更后清除 |
| `perf:target_plan:{plan_id}` | 5 分钟 | 目标方案 | 方案更新后清除 |
| `perf:cust_alloc:{cust_id}:{biz_date}` | 1 小时 | 客户某日分配关系 | 分配关系同步后清除 |
| `perf:kpi_result:{emp_id}:{cycle_type}:{cycle_date}:{as_of_date}` | 10 分钟 | 员工 KPI 结果 | KPI 重算后清除 |

### 8.2 缓存失效

统一通过 `CacheManager.evict()` 接口失效, 写操作完成后在事务成功后调用:

```java
@Transactional
public void updateMetric(MetricUpdateCmd cmd) {
    metricDefMapper.update(cmd.toEntity());
    // 事务成功后清除缓存
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                cacheManager.evict("perf:metric_def:" + cmd.getMetricCode());
                cacheManager.evict("perf:metric_def:list:" + cmd.getBaseDim());
            }
        });
}
```

### 8.3 缓存穿透保护

- 空值缓存: 对不存在的 `metric_code` 缓存空对象 (TTL=30 秒)
- 布隆过滤器 (可选): 对高频查询的实体使用 BloomFilter

### 8.4 缓存雪崩保护

- TTL 加随机 10%: 避免同一时刻大量缓存失效
- 热点数据永不过期 + 定时刷新

## 9. 幂等策略

### 9.1 幂等约束清单

| 场景 | 幂等手段 | 说明 |
|---|---|---|
| 数据导入 | `batch_no` + `file_md5` 双重唯一约束 | 同一文件 24h 内只能成功导入一次 |
| 指标计算 | `uk_emp_date_version` 宽表 UK | UPSERT 幂等 |
| KPI 计算 | `uk_emp_cycle_asof` UK | UPSERT 幂等 |
| 版本切换 | `uk_scope_date` UK + 分布式锁 | 防止并发切换 |
| 历史回算触发 | `params_hash` Redis SETNX | 防重复提交 |
| 工作流回调 | `status` 乐观锁 (`WHERE status='IN_APPROVAL'`) | 防重复处理 |
| 任务状态上报 | `taskId` + 目标状态 UK | `DataTaskApi.reportDataTaskStatus` |

### 9.2 任务状态上报幂等

```sql
-- 任务状态更新幂等: 只有当前状态符合预期时才更新
UPDATE perf_run_task
SET status = #{newStatus}, end_time = NOW(), duration_ms = #{durationMs}
WHERE task_id = #{taskId} AND status IN ('PENDING', 'RUNNING');
```

### 9.3 重试安全

所有对外接口在同一事务内必须满足重试安全:
- 使用数据库唯一约束或乐观锁
- 避免使用 `SELECT ... FOR UPDATE` (除非明确需要悲观锁)
- 避免使用自增 ID 作为幂等 key (客户端无法预知)

## 11. 事务传播级别规范

| 场景 | 传播级别 | 说明 |
|---|---|---|
| 常规业务写操作 | `REQUIRED` (默认) | 加入外层事务 |
| 分批写入大数据量 | `REQUIRES_NEW` | 每批独立提交, 避免长事务 |
| 日志记录 (审计、操作日志) | `REQUIRES_NEW` | 主事务失败也要记录 |
| 只读查询 | `SUPPORTS` + `readOnly=true` | 优化 MyBatis 缓存 |
| 异步任务 | `REQUIRES_NEW` | 独立于调用方事务 |
