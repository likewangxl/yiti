# 绩效计算中心 — 功能规格

> 模块编码: `performance-engine-center`
> 模块性质: 核心域 (Core Domain)
> 版本: V1.0
> 关联设计文档: `project_ana.md` 4.4 节 / `project_ana_技术方案与架构拆分.md` 3.2 节

---

## 1. 模块概述

### 1.1 定位

绩效计算中心是整个"银行省分行一体化营销与绩效管理平台"的**核心业务引擎**, 负责把"外部来源的业绩数据"转换为"可用于考核、挂榜、工作台展示的指标与 KPI 得分", 并管理员工/机构/客户三个维度上的全部**指标计算、KPI 方案、目标值、分配关系**等关键业务数据。

模块对平台的核心价值:

1. **统一指标口径** — 所有业务维度下的原始数据汇聚为标准化的"指标值", 避免各业务部门各算各的
2. **KPI 得分生成** — 把零散指标组装成面向员工的综合 KPI 总分
3. **分配关系治理** — 维护客户业绩归属的分配关系, 保证"同一笔业绩不会重复计入不同员工"
4. **历史一致性** — 通过 `sys_control` 数据版本机制保证"某天某维度的 KPI 可追溯"
5. **历史回算能力** — 当分配关系或目标值发生调整时, 可按规则触发未结束年度的历史重算

### 1.2 边界职责

| 类型 | 说明 |
|---|---|
| 负责 | 指标库定义、指标计算(SQL/存储过程/Groovy)、KPI 方案、目标方案、目标值、分配关系、分配关系调整审批、目标修正审批、KPI 计算、历史回算、数据版本控制 |
| 不负责 | 工作台展示 (portal), 客户触达/营销活动 (customer-marketing), 报表展示层 (report-analytics), 审批流定义 (workflow), 底层认证授权 (auth) |
| 被依赖方 | 门户、客户营销、报表分析均只读消费本模块数据 |

### 1.3 核心概念一览

| 概念 | 中文名 | 说明 |
|---|---|---|
| `sys_control` | 数据版本 | 管理每天每维度当前对外有效的数据版本 |
| `perf_metric_def` | 指标定义 | 指标库核心表, 定义 metric 的身份、维度、层级、计算逻辑 |
| `val_slot` | 宽表槽位 | 指标定义落地到宽表的某个 `val_n` 列 (n=1..200) |
| `perf_kpi_scheme` | KPI 方案 | 一组指标 + 权重 + 多项加成, 面向某类角色的考核方案 |
| `perf_target_plan` | 目标方案 | 目标与基础值的版本载体, 绑定 KPI 方案 + 周期 |
| `cust_alloc_relation` | 客户分配关系 | 客户业绩按比例分配给员工的关系表 (RULE/ACCOUNT) |
| `kpi_result` | KPI 结果 | 员工考核周期内的 KPI 总分, 按 `cycle_date+as_of_date` 快照 |
| `perf_run_task` | 运行任务 | 指标计算、KPI 计算、回算等执行的统一日志 |

## 2. 数据版本管理机制 (sys_control)

### 2.1 业务目标

在银行场景中, 一天的原始业绩数据可能多次重跑 (T+1 补数、历史追溯重算等), 而报表和工作台必须给用户看到**同一份、一致的**数据。`sys_control` 解决的就是"当前哪份数据是对外可见的、有效的"这个问题。

### 2.2 字段设计

```
sys_control (
  id               BIGINT PK,
  dim              VARCHAR(16),      -- EMP / ORG / CUST
  latest_data_date DATE,             -- 最新可用的数据日期
  current_version  VARCHAR(32),      -- 当前对外有效的版本号, 如 '20260410-01'
  is_valid         TINYINT(1),       -- 是否是当前唯一对外有效版本
  publish_time     DATETIME,         -- 发布时间
  publish_by       VARCHAR(64),      -- 发布人(系统或用户)
  publish_source   VARCHAR(32),      -- TIMER / IMPORT / RECALC / MANUAL
  remark           VARCHAR(500),
  create_time      DATETIME,
  update_time      DATETIME
)
```

### 2.3 核心规则

1. **每天每维度只能有 1 条 `is_valid=true` 的记录**, 由唯一索引 `UK(dim, latest_data_date, is_valid)` 保证 (需借助函数索引或触发器实现, 因为 `is_valid=false` 允许多条)
2. **维度间独立**: EMP / ORG / CUST 三个维度的版本发布是独立的, 允许 EMP 已到 `2026-04-09`, 而 ORG 还停留在 `2026-04-08`
3. **版本切换原子性**: 从"旧版本"切到"新版本"必须在同一事务内完成 `UPDATE old SET is_valid=0` + `INSERT new SET is_valid=1`
4. **历史可追溯**: 不会物理删除旧 `sys_control` 记录, 通过 `is_valid=0` + `current_version` 做历史查询
5. **发布触发源**: 日终批处理完成(TIMER) / 手工导入完成(IMPORT) / 历史回算完成(RECALC) / 管理员手工发布(MANUAL)

### 2.4 读取策略

- **业务只读接口**(工作台卡片、报表、KPI 查询): 一律读取 `is_valid=1` 的那条, 再从结果宽表过滤对应 `data_date + version`
- **历史数据分析**: 可以指定 `data_date + version` 查指定历史快照

### 2.5 事件

`sys_control` 每次发布成功, 向领域事件总线发布 `performance.sys-control.updated.v1`, 由本模块自身消费以清理指标/ KPI 的 Redis 缓存。

## 3. 指标库管理 (project_ana 4.4.1)

### 3.1 业务概念

指标是考核 KPI 的原子单元。银行典型业务指标如:

- `M_EMP_DEP_AVG_BAL` — 员工名下存款日均余额
- `M_EMP_LOAN_BAL` — 员工名下贷款余额
- `M_ORG_CARD_NEW_CNT` — 机构信用卡新增发卡数
- `M_CUST_AUM` — 客户总资产 (AUM)

所有指标集中在 `perf_metric_def` 表中定义并版本化管理。

### 3.2 指标定义核心字段

| 字段 | 说明 | 必填 | 取值 |
|---|---|---|---|
| metric_code | 指标唯一编码 | 是 | 大写字母+数字+下划线, 全局唯一 |
| metric_name | 指标中文名 | 是 | — |
| metric_name_en | 英文名 | 否 | — |
| description | 指标口径描述 | 否 | 用于卡片悬浮说明 |
| base_dim | 基础维度 | 是 | `EMP` / `ORG` / `CUST` |
| metric_level | 指标层级 | 是 | `1` / `2` / `3` |
| calc_freq | 计算频率 | 是 | `D`(日) / `W`(周) / `M`(月) / `Q`(季) |
| calc_mode | 计算方式 | 是 | `AUTO`(自动) / `MANUAL`(手工导入) |
| calc_logic_type | 计算逻辑类型 | 条件 | `SQL` / `PROC` / `EXPR` / `SUMMARY` |
| sql_text | SQL 语句 | 条件 | 一级+AUTO+SQL 时必填 |
| proc_name | 存储过程名 | 条件 | 一级+AUTO+PROC 时必填 |
| expr_text | Groovy 表达式 | 条件 | 二三级+AUTO+EXPR 时必填 |
| summary_rule | 汇总规则 | 条件 | 机构指标汇总时必填, 格式 `SUM/AVG/MAX/MIN` + 源指标 |
| ref_metric_codes | 引用的下级指标 | 条件 | 二三级指标必填, JSON 数组 |
| val_slot | 宽表槽位 | 是 | 1~200, 表示落在 `val_<slot>` 列 |
| status | 状态 | 是 | **V1.0：`ACTIVE`（启用）/ `DISABLED`（停用）** |
| owner_dept | 归属部门 | 否 | 用于权限与审计 |

### 3.3 指标层级规则 (严格层级)

**V1 强制规定:**

1. 一级指标 (level=1): 计算逻辑是 SQL 或存储过程, 直接从数据仓库抽取聚合
2. 二级指标 (level=2): 只能通过 Groovy 表达式引用**一级指标**, 不允许直接写 SQL
3. 三级指标 (level=3): 只能通过 Groovy 表达式引用**二级指标**, 不允许引用一级或 SQL

**违规场景举例:**

| 场景 | 是否允许 | 原因 |
|---|---|---|
| 三级指标 `F = B + C` (B 二级, C 二级) | 是 | 同级或下级引用 |
| 三级指标 `F = A + B` (A 一级, B 二级) | 否 | 三级跨级引用一级, 抛 `PERF-40003` |
| 二级指标内直接写 SQL | 否 | 二级必须通过 EXPR 引用一级 |
| 一级指标引用其他一级指标 | 否 | 一级必须独立计算 |

该规则在 `MetricDefService` 的保存校验中强制执行。

### 3.4 机构指标-汇总模式

当 `base_dim=ORG` 且 `calc_logic_type=SUMMARY` 时, 该指标的值由"人员一级指标按 `员工 → 机构` 关系汇总"自动计算。

`summary_rule` 格式示例: `SUM:M_EMP_DEP_AVG_BAL` (把全部员工的日均存款余额按机构汇总求和)

支持的汇总函数: `SUM / AVG / MAX / MIN / COUNT`。

### 3.5 宽表存储 (val_n 槽位)

为了同时支持"指标定义灵活扩展"和"高性能查询", 结果不采用 EAV (Entity-Attribute-Value) 模式, 而是用**三张固定宽表 + 200 个 val_n 列**:

- `emp_index_result` — 员工指标宽表, `PK(emp_id, data_date, version)`, 列 `val_1..val_200`
- `org_index_result` — 机构指标宽表, `PK(org_code, data_date, version)`
- `cust_index_result` — 客户指标宽表, `PK(cust_id, data_date, version)`

每个指标注册时必须分配一个**尚未被占用的** `val_slot` (1~200), 并且 `(base_dim, val_slot)` 组成本维度内的唯一键。校验失败抛 `PERF-40004`。

槽位分配策略:

1. 管理员创建指标时系统自动分配下一个可用槽位
2. 管理员也可手动指定槽位 (需后端校验未被占用)
3. 指标 `DISABLED` 后槽位**不可立即复用**, 需管理员手工"释放槽位"(双确认), 避免历史数据语义错位

### 3.6 立即执行与级联刷新

"立即执行"按钮由资财部或系统管理员触发, 语义如下:

1. 若指标是**一级** — 执行 SQL/存储过程, 写入结果宽表对应 `val_<slot>` 列, 成功后**递归刷新**依赖该一级指标的所有二级/三级指标
2. 若指标是**二级** — 执行 Groovy 表达式计算并写入宽表, 成功后递归刷新依赖它的三级指标
3. 若指标是**三级** — 仅执行自己的 Groovy 表达式

级联刷新基于 `perf_metric_ref` 表, 通过深度优先(DFS)遍历下游指标。执行过程会在 `perf_run_task` 中登记任务, `task_type=METRIC_RUN`。

### 3.7 试运行功能

"试运行"按钮允许管理员在不落库的前提下验证指标逻辑:

- 一级: 执行 SQL, 但把结果写入"试运行影子表"或内存结果集
- 二三级: 执行 Groovy 表达式, 临时读取上游一级结果(内存)并计算
- 每次试运行记录到 `perf_run_task`, `task_type=METRIC_TRIAL`, `result_preview_json` 存前 20 条结果样本
- 试运行失败时, `error_msg` 记录堆栈, 供管理员排查

### 3.8 权限约束

- **系统管理员** (`ROLE_SYS_ADMIN`): 全部指标的 CRUD + 试运行 + 立即执行
- **资财部员工** (`ROLE_TREASURY`): 全部指标的 CRUD + 试运行 + 立即执行
- **其他角色**: 只读或无权限

接口必须使用 `@BizAuth(bizType = PERF_CONFIG, action = ...)` 标注, 由 `auth-permission-center` 统一鉴权。

## 4. KPI 规则管理 (project_ana 4.4.2)

### 4.1 业务概念

KPI 方案 (`perf_kpi_scheme`) 是**给某类员工算总分**的配方, 由一组 `perf_kpi_item` (指标项) 组成, 每项给出权重、加成、上下限。

典型 KPI 方案举例: 支行理财经理月度考核方案 = `[存款日均权重0.4, AUM 权重0.3, 理财销售额权重0.2, 客户满意度权重0.1]`。

### 4.2 KPI 方案字段

```
perf_kpi_scheme (
  id            BIGINT PK,
  scheme_code   VARCHAR(64) UK,  -- 方案编码
  scheme_name   VARCHAR(200),
  cycle_type    VARCHAR(16),     -- MONTHLY / QUARTERLY
  open_detail   TINYINT(1),      -- 是否对员工开放得分明细
  remark        VARCHAR(1000),
  status        VARCHAR(16),     -- DRAFT / PUBLISHED / DISABLED
  version       INT,
  create_time   DATETIME,
  create_by     VARCHAR(64),
  update_time   DATETIME,
  update_by     VARCHAR(64)
)
```

### 4.3 KPI 指标项字段

```
perf_kpi_item (
  id          BIGINT PK,
  scheme_id   BIGINT,           -- 归属 KPI 方案
  metric_code VARCHAR(64),      -- 指标编码
  weight      DECIMAL(10,4),    -- 权重 (不要求总和=100)
  multiplier  DECIMAL(10,4),    -- 加成系数, 默认 1
  min_score   DECIMAL(10,4),    -- 单项得分下限
  max_score   DECIMAL(10,4),    -- 单项得分上限
  sort_no     INT,              -- 展示顺序
  UK(scheme_id, metric_code)
)
```

### 4.4 计算公式

**单项得分:**

```
score_i = clamp(
  ((actual_i - base_i) / target_i) * multiplier_i * weight_i,
  min_score_i,
  max_score_i
)
```

**KPI 总分:**

```
KPI_total = Σ(score_i)
```

### 4.5 特殊处理规则

| 场景 | 处理 |
|---|---|
| `target_i ≤ 0` | 该单项得分直接记 0, 不参与公式 |
| `base_i` 未导入或空 | 视为 0 |
| `actual_i` 未计算 | 视为 0, 但在明细中标记"数据缺失" |
| `weight` 为 0 | 允许, 该项不参与计算 |
| 权重总和 | **不要求**等于 100, 允许 60、150 等任意取值 |
| `min_score` / `max_score` 都为空 | 不限制上下限 |

### 4.6 V1 冻结项

- 二次分配 (二级绩效分配): V1 不做, 模型中不增加 `secondary_allocation` 相关表
- 360 环评 (同事互评): V1 不做
- 多维度得分叠加 (如品行分/合规分): V1 不做

## 5. 目标管理 (project_ana 4.4.3)

### 5.1 两层结构

- **目标方案 (`perf_target_plan`)**: 描述"哪一类对象在哪个 KPI 方案下的目标版本", 比如"2026 年度对公客户经理目标 V2"
- **目标值 (`perf_target_value`)**: 描述"某个具体员工/机构/客户, 在某个周期, 在某个指标上的目标值与基础值"

### 5.2 字段

```
perf_target_plan (
  id              BIGINT PK,
  plan_code       VARCHAR(64) UK,
  plan_name       VARCHAR(200),
  kpi_scheme_id   BIGINT,         -- 绑定的 KPI 方案
  target_dim      VARCHAR(16),    -- EMP / ORG
  target_cycle    VARCHAR(16),    -- YEAR / QUARTER / MONTH
  effective_date  DATE,           -- 生效日期
  expire_date     DATE,
  status          VARCHAR(16),    -- DRAFT / PUBLISHED / DISABLED
  create_time     DATETIME,
  create_by       VARCHAR(64)
)

perf_target_value (
  id            BIGINT PK,
  plan_id       BIGINT,
  subject_type  VARCHAR(16),    -- EMP / ORG
  subject_id    VARCHAR(64),    -- 员工 ID / 机构编码
  cycle_key     VARCHAR(16),    -- 如 '2026' / '2026Q2' / '202604'
  metric_code   VARCHAR(64),
  target_value  DECIMAL(20,4),
  base_value    DECIMAL(20,4),
  create_time   DATETIME,
  update_time   DATETIME,
  UK(plan_id, subject_type, subject_id, cycle_key, metric_code)
)
```

### 5.3 录入方式

1. **单条新增** — 管理界面直接录入
2. **Excel 批量导入** — 主流程, 模板字段: `员工工号/机构编码 | 周期 | 指标编码 | 目标值 | 基础值`

### 5.4 目标修正流程

**背景**: 年中调整策略时, 原有目标值不合理, 需要修改但必须保留审计轨迹。

**流程:**

1. 资财部员工发起"目标修正申请" (`perf_target_adjust_apply`), 填写修正项列表、原因、附件
2. 调用 `workflow-center` 的 `WorkflowApi.startProcess`, 流程编码 `perf_target_adjust_v1`
3. 工作流配置: 单节点审批 — 资财部负责人
4. 审批通过后, 本模块监听 `workflow.process.completed.v1` 事件, 由 `TargetAdjustCompletedListener` 执行:
   - 更新 `perf_target_value` 的新值
   - 保留一份变更快照到 `perf_target_adjust_item` 的 `before_value/after_value`
   - 发布 `performance.target-adjustment.approved.v1` 领域事件
5. 本模块自身监听该事件, 触发 KPI 历史回算 (见 8.4)

### 5.5 历史刷新规则

- **未结束年度**: 目标修正生效后, 自动刷新该年度内所有已计算的 KPI
- **已结束年度**: 不刷新, 不重算, 目标只影响新数据
- 判定"已结束"的规则: 年度截止日 + 系统参数 `perf.year-end.freeze-buffer-days` (默认 30 天)

## 6. 数据导入 (project_ana 4.4.4)

### 6.1 统一入口

所有人工上传的绩效相关数据都走 `POST /api/perf/import` 这一接口, 通过参数 `importType` 区分业务场景:

| importType | 业务场景 | 模板结构 |
|---|---|---|
| `INDEX_RESULT` | 指标结果导入 | 明细行: 工号/机构编码/客户编号 + 指标编码 + 指标值 + 时间点 |
| `KPI_RESULT` | KPI 结果直接导入 | 矩阵: 行=员工, 列=指标, 单元格=得分 |
| `TARGET_VALUE` | 目标值导入 | 明细行: 主体类型 + 主体 ID + 周期 + 指标 + 目标 + 基础值 |

### 6.2 导入流程

1. 管理员上传文件 → 后端生成 `file_md5` 并在 `perf_import_batch` 建 `PENDING` 批次
2. 系统校验: 模板列头、必填项、数据类型、关键字段存在性 (工号是否存在于 `emp_info`)
3. 生成预览结果 (前 100 行) 供管理员核对
4. 管理员"确认导入" → 批次状态 `IMPORTING`, 后台异步写入目标表
5. 全部成功 → `SUCCESS`, 部分失败 → `PARTIAL`, 全部失败 → `FAILED`
6. 错误行汇总为错误 Excel, 存入 MinIO, `error_file_object_id` 记录引用
7. `INDEX_RESULT` 导入成功后, 自动触发下游二级、三级指标刷新 (同 3.6 级联刷新)

### 6.3 幂等与防重

- `file_md5` 在 `perf_import_batch` 内做唯一性检查, 24 小时内同 md5 + 同 importType 禁止重复导入
- 管理员可以通过 `forceReimport=true` 强制跳过该检查, 但必须在审计日志中登记强制原因

## 7. 分配关系调整 (project_ana 4.4.5)

### 7.1 业务背景

银行客户的业绩需要分配到具体员工。例如某对公客户的存款贡献 100 万, 其中对客户经理 A 计 70%、对客户经理 B 计 30%。`cust_alloc_relation` 维护这种分配关系。

### 7.2 分配维度

| alloc_dim | 说明 |
|---|---|
| `RULE` | 按业务规则整体分配, `biz_kind` 描述业务种类 (存款/理财/贷款...), 不绑定具体账户 |
| `ACCOUNT` | 按具体账户号分配, `account_no` 必填 |

一个客户同一业务种类下两种维度可以**同时存在**, 但优先级为 `ACCOUNT > RULE`。

### 7.3 调整申请流程

**对公/零售分流:**

- 对公客户: 流程编码 `perf_alloc_adjust_corp_v1`
- 零售客户: 流程编码 `perf_alloc_adjust_retail_v1`, 附件必填 (零售客户调整需提供佐证)

**流程节点设计 (以对公为例):**

1. 发起人 (原/新客户经理)
2. 发起人所属支行行长审批
3. **动态节点**: 原业绩所属人审批 (可选, 配置项 `perf.alloc.origin-owner-approval`)
4. 分行资财部审批
5. 流程结束

**动态节点逻辑:** 当"新分配关系涉及从旧员工划走业绩"时, 如果配置开启, 插入原员工审批节点, 让原员工"知情或驳回"。

### 7.4 强制校验

1. `ratio` 列之和**必须严格等于 100.00**, 误差 0.01 也拒绝 (前端四舍五入避免精度问题)
2. **单行 `ratio ≥ 1.00**, 即最小 1%, 避免无意义的细碎分配
3. 同一 `(custId, bizKind, accountNo)` 下不允许出现重复 `empId`
4. 参与分配的员工必须在 `emp_info` 中存在且在职
5. 调整生效日期不能早于今天 (追溯调整走另一专用流程, V1 不做)

校验失败抛 `PERF-40902`。

### 7.5 线上审批 → 线下操作 → 次日同步闭环

1. 平台完成审批 → 更新 `perf_alloc_adjust_apply.status = APPROVED`
2. 发布 `performance.allocation-adjustment.approved.v1` 事件
3. 资财部根据审批结果, **线下**在 CCRM (对公) / PCRM (零售) 系统做实际的客户关系变更
4. 次日 T+1 时, 外部数据同步系统再次把 CCRM/PCRM 的最新分配关系 dump 到平台, 调用 `POST /api/data-task/status` 上报任务完成
5. 本模块收到上报后, 更新 `cust_alloc_relation` 表并发布 `sys_control` 新版本
6. 完成闭环后, 自动触发 **未结束年度的** KPI 历史回算 (见 8.4)

### 7.6 历史追溯重算

- **未结束年度**: 从调整申请的 `effective_date` 开始到今天, 所有涉及的员工 KPI 全部重算
- **已结束年度**: 冻结不重算, 如果调整涉及已结束年度, 申请表单上**禁止**填写早于年度截止日的 `effective_date`, 前端校验 + 后端校验

## 8. 考核计算 (KPI 得分, project_ana 4.4.6)

### 8.1 计算时机

| 触发源 | 说明 |
|---|---|
| 每日定时任务 | 每天凌晨 02:00, 读取当日最新有效 `sys_control`, 对所有 `MONTHLY`/`QUARTERLY` KPI 方案内的员工执行计算 |
| 手工触发 | 资财部/管理员对指定 `cycle_type` 和员工范围手动触发 |
| 历史回算 | 分配关系调整 / 目标修正触发 |

### 8.2 计算流程

1. 读取 `sys_control WHERE is_valid=1 AND dim='EMP'`, 得到 `latest_data_date + current_version`
2. 遍历启用的 KPI 方案, 对每个方案内的员工:
   a. 从 `emp_index_result` 读取最新有效版本的各项 `actual` 值
   b. 从 `perf_target_value` 读取该员工当前周期的 `target` / `base`
   c. 按 4.4 公式算单项 `score_i`, 再求和得 `KPI_total`
   d. 将结果写入 `kpi_result`, UK 为 `(emp_id, cycle_type, cycle_date, as_of_date)`
   e. `detail_json` 字段存所有单项的 actual/target/base/score 明细
3. 任务结束后在 `perf_run_task` 标记 `SUCCESS`, 发布 `performance.kpi-calc.completed.v1`

### 8.3 快照策略

**核心设计**: `kpi_result` 只存"实际值和得分", **不存目标值快照**。

原因:

- 目标值变更后自动历史回算, 旧的 `kpi_result` 会被覆盖掉
- 不存快照意味着 `kpi_result.detail_json` 里的 target/base 只是计算当时的参考, 下次回算时会被新值覆盖
- 查询时需通过当时的 `cycle_date + perf_target_plan` 推导目标值, 报表需要做此关联

### 8.4 历史刷新触发源

| 触发源 | 生效范围 | 是否自动 |
|---|---|---|
| 分配关系调整审批通过 | 从 `effective_date` 到今天 | 是, 异步任务 |
| 目标修正审批通过 | 涉及的周期内所有快照 | 是, 异步任务 |
| 管理员手工触发 | 管理员指定时间段 | 是, 需要填写 reason |

### 8.5 已结束年度冻结

- 判定规则: `cycle_date.year < current_year` 且 `当前日期 > 年度截止日 + freeze-buffer-days`
- 冻结后: 任何触发源都跳过该年度, 回算任务会在 `perf_run_task.result_preview_json` 标注"N 条记录因年度冻结被跳过"
