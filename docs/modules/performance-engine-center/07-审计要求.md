# 绩效计算中心 — 审计要求

> 模块: performance-engine-center
> 版本: v1.0
> 最后更新: 2026-04-10

本文档定义绩效计算中心所有高危、敏感、重要业务动作的审计规范。所有列出的动作必须通过 `AuditApi.log(AuditLogCmd)` 记录, 接入 system-governance-center 的统一审计链路, 并支持按 `resource_type` + `operator_emp_id` + `request_time` 追溯。

---

## 1. 高危动作清单

本模块需审计的接口按风险等级分为三档:

- **高危** (HIGH): 涉及数据重算、批量写入、权限敏感操作, 必须审计且 `reason` 必填
- **需审计** (MEDIUM): 涉及配置变更、流程发起、单对象写操作, 必须审计
- **读操作** (LOW): 一般不审计, 但导出类读接口按导出数量触发审计

### 1.1 指标管理相关

| 接口 | 动作 | 审计级别 | reason 必填 | 说明 |
|---|---|---|---|---|
| `POST /api/perf/metrics` | WRITE | 需审计 | 否 | 新增指标定义 |
| `PUT /api/perf/metrics/{metricCode}` | WRITE | 需审计 | 建议 | 更新指标定义 (SQL/表达式变更时 reason 必填) |
| `DELETE /api/perf/metrics/{metricCode}` | WRITE | 高危 | 是 | 逻辑删除指标 |
| `PUT /api/perf/metrics/{metricCode}/status` | WRITE | 需审计 | 是 | 启用/停用指标 |
| `POST /api/perf/metrics/{metricCode}/trial-run` | EXECUTE | 高危 | 否 | 试运行, 不写结果表但执行 SQL |
| `POST /api/perf/metrics/{metricCode}/execute` | EXECUTE | 高危 | 是 | 立即执行 (写入结果宽表) |
| `POST /api/perf/metrics/batch-execute` | EXECUTE | 高危 | 是 | 批量执行指标 |

### 1.2 KPI 方案相关

## 3. 特殊审计场景

### 3.1 指标【立即执行】

**必记录字段**:
- `metric_code`
- `data_date`
- `version`
- `val_slot` (受影响的槽位)
- `affectedRows` (写入行数)
- `cascadeRefresh` (是否触发级联)
- 参数 JSON (如过滤条件)
- reason (执行原因)

**特殊要求**: 如果执行过程中使用了与 `perf_metric_def.sql_text` 不同的 SQL (如动态参数覆盖), 必须完整记录实际执行的 SQL。

### 3.2 指标【试运行】

**必记录字段**:
- `metric_code` 或临时 SQL
- 完整的 `sql_text` 或 `expr_text`
- 参数 (如数据日期、过滤条件)
- 执行耗时
- 前 20 条结果预览 (脱敏后)

**日志存储**: 试运行的审计日志 `after` 字段可能较大 (包含完整 SQL + 结果预览), 使用 TEXT 类型存储, 不走 varchar。

### 3.3 sys_control 版本切换

**必记录字段**:
- 原版本 `oldVersion`
- 新版本 `newVersion`
- 维度 `scopeDim`
- 数据日期 `latestDataDate`
- 切换触发源: `AUTO` / `MANUAL` / `RECALC_TRIGGERED`

**注意**: 版本切换属于 `PERMISSION_CHANGE` 类型, 因为它改变了全系统的数据指针。

### 3.4 目标修正导致的历史刷新

目标修正审批通过后触发历史回算, 产生**两条关联的审计日志**:

1. 第一条: `PERF_TARGET_VALUE` 的 WRITE (记录原值 → 新值)
2. 第二条: `KPI_RESULT` 的 RECALC (记录回算范围、受影响员工数)

**关联**: 两条日志共享同一个 `trace_id`, 并在 `after` 中互相引用:
- 第一条 `after.relatedRecalcTaskId`
- 第二条 `after.relatedApplyNo`

### 3.5 分配关系调整

**必记录字段**:
- 原分配关系 (`before` 中完整 JSON)
- 新分配关系 (`after.newItems`)
- 生效日期
- 业务类型
- 客户 ID + 客户名

**注意**: 由于 `before` 和 `after` 都可能较大, 使用 TEXT 类型存储。同步到 `cust_alloc_relation` 时产生第二条关联审计日志 (`action=SYNC`)。

### 3.6 数据导入

**必记录字段**:
- `batchNo`
- `fileName`
- `fileMd5`
- `totalRows` / `successRows` / `errorRows`
- `affectedSubjects` (导入后影响的员工/机构/客户数量)
- 错误汇总 (前 10 条错误)

**注意**: 导入执行和导入回滚必须成对审计。

### 3.7 历史回算

**必记录字段**:
- `cycleType`
- `cycleDateFrom` / `cycleDateTo`
- `affectedEmpCount`
- `triggerSource`: `MANUAL` / `TARGET_ADJUST_APPROVED` / `METRIC_RECALC`
- `relatedApplyNo` (如由审批触发)
- `originalVersion` → `newVersion`

**高风险**: 历史回算是本模块最敏感的动作, 需要双人复核机制 (由 Controller 层 `@BizAuth(requireDoubleCheck=true)` 实现)。

## 4. 审计记录的 before / after 快照要求

### 4.1 WRITE 类动作

- **INSERT**: `before = null`, `after = 新记录 JSON`
- **UPDATE**: `before = 变更前 JSON`, `after = 变更后 JSON`
  - 仅保留发生变化的字段 + 关键业务字段 (如 id、code)
  - 避免把整个大对象序列化
- **DELETE**: `before = 删除前 JSON`, `after = null`

### 4.2 PERMISSION_CHANGE 类动作

必须保留**完整字段快照** (不能简化), 包括:
- 全部字段的旧值 (`before`)
- 全部字段的新值 (`after`)

**示例**: sys_control 版本切换、KPI 方案权重修改。

### 4.3 RECALC 类动作

必须记录**影响范围**:
- 员工数 / 机构数 / 客户数
- 周期数 / 日期范围
- 预期耗时 / 实际耗时
- 输入参数 / 关联的业务来源

### 4.4 EXPORT 类动作

必须记录:
- 查询参数 (不含敏感字段值)
- 导出行数
- 数据范围 (`data_scope`)
- 导出文件对象 ID (便于追溯)

### 4.5 EXECUTE 类动作

必须记录:
- 任务 ID
- 关键业务参数
- 执行结果摘要 (成功/失败/影响行数)
- 耗时

### 4.6 快照字段脱敏

`before` / `after` 中如包含以下字段, 必须在写入审计日志前脱敏:

| 字段 | 脱敏规则 | 示例 |
|---|---|---|
| `password` | 完全屏蔽 | `****` |
| `phone` | 中间 4 位替换 | `138****5678` |
| `idCard` | 只保留前 6 和后 4 | `110101********1234` |
| `bankAccount` | 只保留后 4 | `****5678` |
| `custName` (导出场景可保留, 单操作场景不脱敏) | - | - |

脱敏由 `AuditLogCmd.setBefore()` / `setAfter()` 前调用 `SensitiveUtil.mask()` 完成。

## 5. 审计链路与 TraceID

所有审计日志必须携带 `trace_id`, 用于跨接口、跨模块追溯同一业务链路:

1. 一次 HTTP 请求进入 → 由 `TraceInterceptor` 生成 / 继承 `trace_id`
2. 业务执行中的所有 `AuditApi.log()` 调用都自动携带当前 `trace_id`
3. 异步任务 (如级联刷新、回算) 继承发起时的 `trace_id`
4. 跨模块调用 (通过 `*Api`) 传递 `trace_id`

**追溯场景示例**:
- 目标修正 → 审批通过 → 写入 target_value → 触发 RECALC → 更新 KPI → 发送通知
- 全链路共享同一 `trace_id`, 运维可通过 `SELECT * FROM gov_audit_log WHERE trace_id = ? ORDER BY request_time`

## 6. 审计失败处理

**审计失败不影响业务主流程**:
- `AuditApi.log()` 调用异常时, 只记录 ERROR 级别日志, 不抛出异常
- 审计写入使用独立事务 (`REQUIRES_NEW`), 与业务事务解耦
- 审计失败时写入本地兜底日志文件 (`logs/audit-fallback.log`), 待修复后补写

**关键审计不允许失败**:
- `action=RECALC`、`action=PERMISSION_CHANGE` 属于关键审计, 必须成功写入
- 如果写入失败, **业务操作必须回滚**
- 代码示例:
```java
try {
    auditApi.log(auditCmd);
} catch (Exception e) {
    if (auditCmd.isCritical()) {
        throw new BizException(ErrorCode.AUDIT_FAILED, "关键审计写入失败, 业务操作已回滚");
    }
    log.error("audit log failed (non-critical)", e);
}
```

## 7. 审计日志查询权限

审计日志存储在 `gov_audit_log` 表 (system-governance-center 维护), 查询权限:

- **系统管理员**: 可查询全部审计日志
- **本模块管理员**: 可查询 `resource_type` 以 `PERF_` 开头的审计日志
- **普通用户**: 只能查询自己的操作记录 (`operator_emp_id = currentEmpId`)

通过 `auth-permission-center` 的 `@BizAuth` + `DATA_SCOPE` 实现。

## 8. 审计合规性要求

1. **保留期限**: 审计日志至少保留 **3 年**, 高危动作 (RECALC / PERMISSION_CHANGE) 保留 **5 年**
2. **不可篡改**: 审计日志表 `gov_audit_log` 不允许 UPDATE 和 DELETE, 只允许 INSERT + SELECT
3. **定期备份**: 每周归档上周审计日志到对象存储 (MinIO)
4. **合规审查**: 内审团队可通过 `system-governance-center` 的审计查询接口导出分析
5. **个人信息保护**: 审计日志不得包含完整身份证号、银行卡号等敏感字段, 必须脱敏
