# 绩效计算中心审计要求

> 审计以 Controller 的 AuditLog 注解、统一审计切面和 AuditApi 实现为准；本文不复制报文示例。

## 1. 审计范围

以下动作必须留痕，并记录操作者、时间、traceId、资源、业务主键、请求摘要、结果和失败原因：

| 领域 | 当前动作 |
| --- | --- |
| 指标 | 删除/停用、状态变更、槽位释放、试运行、单指标执行、批量执行 |
| KPI/目标 | 方案与指标项增改删、发布；目标方案/目标值增改删；目标调整申请与撤回 |
| 导入 | 上传、重试、删除批次、下载源文件 |
| 分配 | 创建申请、保存草稿、草稿提交、撤回；审批完成由流程审计和完成事件关联 |
| 计算与版本 | 回算、KPI 计算触发、数据任务状态上报、SYS_CONTROL 初始化/切换/回滚 |
| 导出 | KPI、指标、分配关系和明细导出提交；高敏感分配/明细导出要求原因 |

普通列表、详情、统计和运行任务查询按当前实现不单独写 AuditLog；统一访问日志仍保留必要的 traceId 和耗时。

## 2. 高风险动作

版本指针切换/回滚、历史回算、分配关系与明细导出、批次删除、指标删除/槽位释放等改变数据口径或产生敏感文件的动作必须：

- 使用独立资源和对应的 BizAuth；
- 在请求和 Service 层校验操作者、数据范围和业务对象；
- 要求非空 reason（以当前 DTO/注解为准）；
- 在审计记录中保留目标范围、版本/日期、任务或申请编号及最终状态。

审计记录的 before/after 只保存必要字段，不序列化 SQL 原文、文件内容或完整业务对象。SQL/Groovy 试运行和 SQL 相关参数应按敏感数据规则脱敏。

## 3. 结果与任务关联

异步指标、批量计算、KPI 计算和导出先记录受理/创建，再由任务状态记录执行结果；审计不得把“请求已受理”写成“计算已完成”。线程池拒绝、校验失败、超时和下游调用失败均写明失败原因。

分配/目标审批由 workflow-center 产生流程审计，绩效 listener 在提交后以申请业务键、流程实例和 traceId 关联本地生效记录。拒绝不产生生效数据写入；重复事件只能形成一次生效结果。

## 4. 脱敏与访问

账号、手机号、证件号、银行卡号、金额、SQL 参数、对象存储凭据和文件内容不得以明文写入日志或审计快照。导出审计仅记录任务、筛选条件摘要、行数/文件引用和下载结果，不记录文件正文。

审计查询由治理模块统一控制访问范围；绩效模块不得通过额外表或本地日志绕过统一审计链路。审计写入失败须按公共审计组件的失败策略处理，并保留可定位 traceId。
