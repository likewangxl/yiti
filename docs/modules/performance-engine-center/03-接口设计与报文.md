# 绩效计算中心接口设计与报文

> 统一返回使用 ResponseWrapper；分页使用 PageResult；具体 DTO、校验注解和错误码以源码为准。除文件下载外，接口返回 JSON。

## 1. 通用约定

管理接口位于 /api/perf，通常使用 BizType.PERF_CONFIG；KPI 结果查询/导出使用源码标注的 KPI_CALC；评价接口位于 /api/eval 或 /api/admin/eval，使用 EVAL。Controller 的资源必须在 PT_RESOURCE 登记，Service 仍执行对象权限和数据范围校验。

高风险写操作的请求体包含 reason，并由统一审计切面记录。日期使用 yyyy-MM-dd；分页参数由各 DTO 的默认值和上限处理，不能依据本页自行推导隐藏参数。

### 3.1 KPI 评分结果查询参数与机构范围

`GET /api/perf/kpi-score/results` 使用 `BizType.KPI_CALC` 的 `READ` 授权，继续沿用已有
`PT_RESOURCE` 资源 `P_PERF_KPISCORE_RES`，不新增资源登记。除原有 `dataDate`、`schemeCode`、
`subjectType`、`subjectKeyword`、`pageNo`、`pageSize` 外，新增可选查询参数 `orgCode`：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `orgCode` | String | 机构编码。省略时保持原查询行为；显式传入时去除首尾空白，空白值按参数错误拒绝 |
| `dataDate` | String | `yyyy-MM-dd`。传入 `orgCode` 时必填，结果严格按该日期查询 |
| `schemeCode` | String | KPI 方案编码。传入 `orgCode` 时必填，避免跨方案或空日期查询 |

显式传入 `orgCode` 后，服务先把该机构解析为 `ORG` 主体编码和其员工工号（`getEmpIdsByOrg`
返回的 `USER_ID` 必须经 `getUserByEmpIds` 转为 `PT_USER.USERNAME`），再与当前请求的
`KPI_CALC` 数据范围求交集：`ALL` 也只保留指定机构，`ORG`/`ORG_SUBTREE` 必须包含指定机构，
`SELF` 只保留本人且本人属于指定机构。`subjectType=EMP` 只使用指定机构员工工号，
`subjectType=ORG` 只使用指定机构编码；关键字得到的候选集合还要再次与该交集求交，不能扩大范围。
最终过滤器通过 `PerfKpiScoreMapper` 的 `scope` 下推到 SQL。

请求没有有效的 `KPI_CALC` 数据范围上下文，或机构/用户目录解析返回异常、`null`、空名单时，
服务返回空结果页（fail-close），不能回退为全部范围。机构限定响应增加 `scopeOrgCode`，值为
服务实际采用的规范化机构编码；未传 `orgCode` 的旧请求该字段为 `null`。前端应先核对该字段再展示结果，
不能用机构行的业务机构号替代内部 `orgCode` 判断。

结果日期口径是 `PERF_KPI_SCORE.data_date` 的精确等值匹配；未落库的对象/指标不补零，也不跨日期查找。
计算时实际值缺失按 0 参与计算，目标值记录不存在则跳过该对象/指标，不产生计分明细；已落库的
目标值/基础值空值按计算服务口径视为 0。缺失计分行在结果查询中保持缺失。

## 9. 错误与兼容性

业务错误统一使用 performance 的错误码和 ResponseWrapper，不在文档维护一份独立完整列表。调用方应处理资源未授权、数据范围冲突、版本冲突、任务不存在/过期、校验失败和下游文件/流程失败，并以实际 HTTP 响应为准。

## 10. 分行大屏不可变批次

分行大屏批次是 performance 内部的批量编排能力，任务类型固定为
`BRANCH_DASHBOARD_BATCH`，持久化复用 `PERF_RUN_TASK`，不新增表。手工入口和治理
Quartz 包装都调用同一个 `BranchDashboardBatchService`；Quartz 类为
`com.bank.branch.platform.performance.job.quartz.BranchDashboardBatchQuartzJob`，不加
`@Component`，由治理中心按 `SYS_JOB_CONF`/`JobApi` 注册和触发。不能恢复
`MetricSchedulerService.register()` 或增加 `@Scheduled`。

Service 先在只读事务快照中解析 `OrgGroupApi.listActiveMemberCodes`、当前 ORG 版本、
金融源、客户 `MarketingOrgSnapshotQueryApi` 和 ACTIVE 目标方案，再校验写入前版本与组成员
仍一致。未指定 `dataDate` 时按“今天及以前、组成员和全部 upstreamMetricCodes 均非空”的
最近金融业务日选择；未来日期、缺组成员、缺客户行、目标缺失/重复/非正数以及生产指标单位
缺失均失败。QUARTER 目标按业务日解析周期且有效期必须覆盖业务日。

成功输出只写当前业务日/版本下五个配置槽位（customer、attention、target、orgRate、
groupContribution），槽位必须在 1..400；按机构 upsert 时不会清除无关槽位，也不更新
`SYS_CONTROL`。槽位、`resultPreviewJson` 和任务 SUCCESS 在同一事务提交；计算或 JSON 序列化
失败由独立事务留下 FAILED 任务，不能产生 SUCCESS 快照或半写结果。批次 ID 每次运行可不同，
同日重跑不重复客户/目标等业务关系。

批次 JSON 至少包含 `batchId`、`groupCode`、`dataDate`、`version`、对外状态
`COMPLETE`/`FAILED`/`PARTIAL`、`calculatedAt`、成员快照、`sourceAsOf`、`quality`、指标
口径合同、来源模式、当前 `rows`、历史 `historyRows` 和逐金融日的 `historyCoverage`。
`quality.expected/received` 是成员×金融指标值数量，`expectedSubjects/receivedSubjects`
是机构覆盖数量；`newerIncomplete` 表示选择完整日之前发现的更新但不完整日期。历史仅返回实际
存在的金融行，缺日不补零；机构或字段缺失保留在覆盖信息中。`sourceAsOf` 分开记录
financial/marketing/target/revenue 的截至日、生效日和采集时刻；测试营收来源模式固定为
`TEST_MANUAL`，不由客户数乘常量推导。JSON 不包含客户编号、姓名、手机等 PII。

`application-branch-dashboard-e2e.yml` 只用于隔离的 `yit_test` profile：数据分类必须显式
为 `TEST`，并配置机构组、目标方案、六项 upstream 指标、五个输出指标、历史天数和
`expectedUnits`。它恢复内存 Quartz、保留 `TaskSchedulingAutoConfiguration` 排除，并把
允许的治理 job key 限定为 `BRANCH_DASHBOARD_BATCH`；cron 由治理配置/JobApi 管理。
