## 0. 通用约定

### 0.1 URL 前缀

- 业务接口统一前缀: `/api/perf`
- 外部系统上报接口前缀: `/api/data-task`

### 0.2 请求/响应格式

- Content-Type 统一 `application/json;charset=UTF-8`, 上传接口为 `multipart/form-data`
- 所有响应遵循 `R<T>`:

```json
{
  "code": "0",
  "message": "success",
  "traceId": "abcd1234ef5678",
  "data": { ... }
}
```

- 分页响应遵循 `PageResult<T>`:

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "pageNo": 1,
    "pageSize": 20,
    "total": 128,
    "list": [...]
  }
}
```

### 0.3 鉴权

- 所有接口 (除 G 组外部接口) 经 `common-security` 过滤器鉴权
- 每个接口必须标注 `@BizAuth(bizType, action)`, 对应资源注册到 `PT_RESOURCE`
- `bizType` 取值（2026-07-19 据源码订正，`BizType` 枚举定义于 `common-security`）:
  - `PERF_CONFIG` — **主干（`performance.controller` 包）实际统一使用的唯一 bizType**，覆盖指标/KPI/目标/计算/分配调整/导入/导出/任务日志/版本控制/财务统计展示等全部端点（`grep` 命中 87 处），由 `BizAuthConsistencyArchTest` 守护"单档"约束
  - `KPI_CALC` — 仅 `KpiScoreCalcController` 的 3 个端点使用（`GET /results`、`GET /export-scores`、`GET /export-details`，命中 3 处）
  - `EVAL` — **eval 考核评价/奖励分配子域（`performance.eval.controller` 包）统一使用**，命中 45 处；该包不在 `BizAuthConsistencyArchTest` 的 `@AnalyzeClasses` 扫描范围内，架构测试不校验其单档性
  - ~~`PERF_QUERY`~~ / ~~`PERF_ADJUST`~~ — **历史设计值，全量源码检索零命中，从未落地**，本文档 C.6/E.1 等处曾提及，2026-07-19 一并订正为 `PERF_CONFIG`（下文对应位置已加订正标注）

### 0.4 数据范围

所有"查询"接口通过 `DataScopeHelper` 自动注入数据范围 SQL 片段, 默认按员工/机构权限过滤。

### A.3 POST /api/perf/metrics — 新增指标

**鉴权:** `@BizAuth(bizType = "PERF_CONFIG", action = "WRITE")`

**请求体 `MetricCreateReqDTO`:**

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| metricCode | String | 是 | `@NotBlank @Size(max=64) @Pattern("^[A-Z_0-9]+$")` |
| metricName | String | 是 | `@NotBlank @Size(max=200)` |
| metricNameEn | String | 否 | `@Size(max=200)` |
| description | String | 否 | `@Size(max=1000)` |
| baseDim | String | 是 | `@NotBlank @In({"EMP","ORG","CUST"})` |
| metricLevel | Integer | 是 | `@NotNull @Range(min=1, max=3)` |
| calcFreq | String | 是 | `@NotBlank`, 取值来源字典 `PERF_CALC_FREQ` |
| calcMode | String | 是 | `@In({"AUTO","MANUAL"})` |
| calcLogicType | String | 条件必填 | `AUTO` 时必填, `@In({"SQL","PROC","EXPR","SUMMARY"})` |
| sqlText | String | 条件必填 | `metricLevel=1 && calcMode=AUTO && calcLogicType=SQL` 时必填 |
| procName | String | 条件必填 | `calcLogicType=PROC` 时必填 |
| exprText | String | 条件必填 | `metricLevel in (2,3) && calcMode=AUTO && calcLogicType=EXPR` 时必填 |
| summaryRule | String | 条件必填 | `calcLogicType=SUMMARY` 时必填, 格式 `SUM/AVG/MAX/MIN/COUNT:<metricCode>` |
| refMetricCodes | List\<String\> | 条件必填 | `metricLevel in (2,3)` 时必填, `@Size(min=1, max=20)` |
| valSlot | Integer | 否 | `@Range(min=1, max=200)`, 空则系统自动分配 |
| ownerDept | String | 否 | `@Size(max=64)` |
| remark | String | 否 | `@Size(max=1000)` |

**业务校验:**

1. `metricCode` 未在 `perf_metric_def` 中存在, 否则 `PERF-40901`（指标编码已存在）
2. 层级引用严格匹配: 三级引用的 `refMetricCodes` 必须全部是二级指标, 二级引用必须全部是一级, 否则 `PERF-42201`（指标计算逻辑非法）
3. `valSlot` 在 `(baseDim, valSlot)` 不重复, 否则 `PERF-40901`（指标槽位已占用，复用 METRIC_CODE_DUP 编号）
4. SQL 语法校验: Druid AST 检查仅允许 `SELECT`, 否则 `PERF-42201`
5. Groovy 语法与沙箱校验, 否则 `PERF-42201`（指标计算逻辑非法）
6. 循环依赖检查, 否则 `PERF-42201`（指标计算逻辑非法）

> 错误码以 §K「错误码完整汇总」为准（2026-04-22 对齐）。

**响应 `R<MetricDefRespDTO>`**

### A.6 POST /api/perf/metrics/{metricCode}/execute — 立即执行

**鉴权:** `@BizAuth(bizType = "PERF_CONFIG", action = "EXECUTE")` (高危, 审计)

**请求体 `MetricExecuteReqDTO`:**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| dataDate | String | 是 | 执行的数据日期 |
| cascade | Boolean | 否 | 是否级联刷新下游, 默认 true |
| async | Boolean | 否 | 是否异步提交, 默认 true（2026-07-22 起真正生效，此前该字段被后端忽略、恒同步执行） |

**响应 `R<RunTaskInfoDTO>`:** 返回 `taskId`, 前端轮询 `GET /api/perf/run-tasks/{taskId}` 查询状态

**执行语义（2026-07-22 修订）：**

- `async=true`（默认）：请求线程只做「校验指标 + 解析 `SYS_CONTROL` 版本 + 预建 `PERF_RUN_TASK` 行(PENDING)」，随即返回 `taskId`，真正的计算与级联在 `metricExecuteExecutor` 线程池后台执行。响应 `status=PENDING`；线程池拒绝（队列满/已关闭）时预建行就地标 FAILED、响应 `status=FAILED`。
- `async=false`：保留原全同步语义，返回即终态（`SUCCESS`/`FAILED`/`PARTIAL_FAILED`）。仅供脚本/排障，重指标或级联链长时容易撞网关读超时。
- 任务行刻意在**请求线程**内预建：`started_by` 取自当前会话 ThreadLocal，异步线程拿不到会兜底成 `SYSTEM`，操作人会丢失。

**错误:**

- `PERF-40001` 指标不存在
- `PERF-40014` 状态不允许 (DISABLED 不可执行；V1.1 DRAFT 同样不可执行)
- `PERF-50007` 幂等锁冲突 (同指标正在执行)

### B.3 POST /api/perf/kpi-schemes — 新增 KPI 方案

**鉴权:** `@BizAuth(bizType = "PERF_CONFIG", action = "WRITE")`

**请求体 `KpiSchemeCreateReqDTO`:**

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| schemeCode | String | 是 | `@NotBlank @Pattern("^[A-Z_0-9]+$") @Size(max=64)` |
| schemeName | String | 是 | `@NotBlank @Size(max=200)` |
| cycleType | String | 是 | `@In({"MONTHLY","QUARTERLY","YEARLY"})` |
| openDetail | Boolean | 是 | — |
| empTagScopes | List\<Long\> | 否 | 人员标签 ID 数组（`PERSON_TAG.TAG_ID`），空=不限定全员 |
| remark | String | 否 | `@Size(max=1000)` |
| items | List\<KpiItemCreateReqDTO\> | 否 | 可创建后追加 |

**员工标签范围（2026-07-20 由「员工角色范围」改造而来）：**

- 方案生效的员工范围 = 所选**人员标签**关联员工的**并集**（多选）；留空 = 不限定，全员参与。
- 标签由「系统设置 > 人员标签」维护（governance 模块 `PERSON_TAG` / `PERSON_TAG_REL`），
  perf 侧经 `PersonTagApi` 跨模块获取，落库为标签 ID CSV（`PERF_KPI_SCHEME.emp_tag_scope`）。
- 保存时校验标签均存在，含非法/已删除标签返回 `PERF-42200`（消息附具体项）。
- 计分链路：`KpiScoreCalcService` 用 `PersonTagApi.getUsernamesByTagIds` 解析为工号集合，
  与"有目标值的员工基础集"取交集；标签已删除或标签下无人 → 范围为空 → 该方案不计分（fail-close）。

- **metric_code 兜底**：`indexNo=42 且 metricCode 空 → metric_code="M_0042"`
- **文件内 metric_code 重复**：Excel 内同 code 出现 ≥2 次 → 抛 PERF-42211，错误消息含首次出现行号和重复行号
- **DB 内 metric_code 冲突**：Strategy 在落库前批量 `getByCodes` 探测，已存在则整批拒绝（PERF-42211）
- **行号约定**：Excel 第 1 行是列头；数据第 N 行 = Excel 第 N+1 行；错误消息里的"第 X 行"指 Excel 物理行号（含列头），便于用户表格里直接定位

#### D.6.7 错误码速查（METRIC_DEF 专属）

| 错误码 | 触发场景 |
|---|---|
| `PERF-42211 IMPORT_BATCH_ALL_OR_NONE_FAILED` | 整批校验未通过或落库失败，附详细行号 + 原因 |
| `PERF-42203 IMPORT_COLUMN_MAPPING_INVALID` | Excel 列头与模板不匹配 / Excel 解析失败 / 文件不可读 |
| `PERF-42200 VALIDATION_FAILED` | 单行：必填缺失 / `sourceType ∉ {1,2,3}` / `statusFlag ∉ {0,1}` / metricLevel 越界 |
| `PERF-42201 METRIC_CALC_LOGIC_INVALID` | 单行：来源=2/3 时 `calcRule` 空 |
| `PERF-40021 METRIC_CALC_FREQ_INVALID` | 单行：`scheduleType ∉ {1,2,3,4}` |
| `PERF-40002 BIZ_KIND_INVALID` | `importType` 不在已注册策略列表内 |

> 单行错误（PERF-42200/42201/40021）通过 Strategy 的预扫描收集，最终统一包装成 PERF-42211 抛出；整批回滚后 batch 记录 status=FAILED + remark 写入错误明细，可通过 `GET /api/perf/import/batches/{batchId}/errors` 取出。

## J. 导出接口统一规范（附录）

> **一致性声明**：07-审计要求.md §1.8 / §2.11 / §2.12 列出的 4 个导出接口在本附录补齐 HTTP 定义，消除 03 与 07 之间的空档。本章节同时落地 `docs/common-dev-guide.md §8.2 第 5 条`（"超过 5000 行必须走异步导出"）。

### J.1 同步 / 异步分支规则

绩效数据体量通常较大（KPI 结果按 `emp × metric × cycle` 展开，单次查询命中 5 位数行很常见），因此**推荐优先走异步分支**：

| 命中行数 N | 处理方式 | 响应类型 | 说明 |
|---|---|---|---|
| N ≤ 5000 | 同步流式返回 | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | 小范围快速导出 |
| 5000 < N ≤ 200000 | 异步任务 | `R<ExportTaskRespDTO>` | 绩效数据常见区间，默认走异步 |
| N > 200000 | 拒绝 | `PERF-42207` | 引导增加过滤条件（缩小机构 / 周期范围） |

注意：绩效类导出硬上限为 **200000 行**（区别于其他模块的 100000），原因是 KPI 明细展开后行数更多。

**判定流程**：
1. 进入导出接口先执行 `SELECT count(*)`（含 DATA_SCOPE 过滤）
2. 按行数命中分支
3. 异步分支：写入 `sys_async_task`（governance 提供），同时创建 `perf_run_task (task_type=EXPORT)` 便于绩效侧追溯
4. 异步完成后上传 OBS（2026-07-19 订正：经 governance `FileApi`/`ObsStorageClient` 落地华为云 OBS，非 MinIO），发通知给发起人

### J.2 文件命名规则

格式：`{module}_{business}_{filterHash}_{yyyyMMddHHmmss}.xlsx`

| 片段 | 说明 | 示例 |
|---|---|---|
| `{module}` | 固定 `perf` | `perf` |
| `{business}` | `kpi_results` / `metric_results` / `cust_alloc` / `kpi_detail` | `kpi_results` |
| `{filterHash}` | 请求参数 MD5 前 8 位 | `a3f9b2c4` |
| `{yyyyMMddHHmmss}` | 导出时刻 | `20260410153022` |

示例：`perf_kpi_results_a3f9b2c4_20260410153022.xlsx`

### J.4 列定义规范

每个导出接口必须明确：列顺序、中文列名、字段来源、格式规则。绩效数据涉及金额、比例，统一约束：

## S. eval 考核评价与奖励分配子域（2026-07-19 全新章节，此前零收录）

> **子域概述**：`com.bank.branch.platform.performance.eval` 包，2026-05-29 起开发，共 11 个 Controller。两条并行路径：① 规则驱动评价（标签→规则→任务→打分，`EvalTagController`/`EvalRuleController`/`EvalTaskController`/`EvalScoreController`）；② 手工导入的"待处理任务"，按 `importType` 分 EVAL（评价任务导入，`EvalAssignAdminController`/`EvalAssignBatchController`/`EvalPendingController`）与 REWARD（奖励分配，`EvalRewardAdminController`/`EvalRewardPendingController`），两条路径物理隔离（不同表），仅在 `EvalUnifiedController` 展示层合并列表；此外 `EvalUserTagController` 管理人员标签关联（评价角色，单一角色化模型）。
>
> **鉴权约束（与主干不同）**：全部端点统一 `@BizAuth(bizType = "EVAL", ...)`，不区分 `PERF_CONFIG`/`KPI_CALC`；`BizAuthConsistencyArchTest` 的 `@AnalyzeClasses(packages = "com.bank.branch.platform.performance.controller")` **不扫描** `performance.eval.controller` 包，故本子域端点不受该架构测试的"单档"约束检查。
>
> **错误码**：本子域专用错误码见 §K.6（`PERF-40050`～`PERF-40073`，均定义在 `PerfErrorCode.java` "评价模块" 分组）。
>
> **架构守护观察（代码核实，非本文档缺陷）**：`NoEntityInControllerArchTest` 的 `@AnalyzeClasses(packages = "com.bank.branch.platform.performance")` 名义上覆盖整个模块（含 eval 子包），但其 `isEntity()` 判定硬编码包前缀为 `com.bank.branch.platform.performance.entity`（主干 entity 包），并**不匹配** `com.bank.branch.platform.performance.eval.entity`。因此 eval 子域的 Controller 直接返回 `entity` 包下的类型（如 `EvalTag`/`EvalRule`/`EvalRuleGroup`/`EvalTask`/`EvalTaskTarget`/`EvalUserTag`/`EvalAssignBatch`，下文各表格中出现的响应类型即为此类实体）**不会被该架构测试拦截**，这是与主干"Controller 只返回 RespDTO"约定不一致的现状，供后续架构收紧参考。

### K.7 使用约定

1. 错误码在 `CommonResult.errorCode` 字段返回，`code` 字段为 HTTP 状态码同值
2. 所有高危操作失败（RECALC/CONFIG/EXPORT/IMPORT）必须写审计日志
3. `PERF-40903` 是 sys_control 版本并发冲突的标识，需前端引导用户重试
4. 批量接口（如 KPI 计算、分配关系查询）超上限时返回 `PERF-42206`，前端需分页重试
5. eval 子域（§K.6）与主干共用同一 `PerfErrorCode` 枚举 + 同一 `PerfException`/`GlobalExceptionHandler` 处理链路，不是独立错误码体系
