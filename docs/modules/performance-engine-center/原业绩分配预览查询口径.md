# 业绩调整：原业绩分配预览查询口径

> 适用：新建/编辑分配调整申请，以及申请详情和审批只读回显。查询实现以 performance-engine-center 的 AllocApi/AllocRelationService 为准。

## 1. 调用链

页面在客户和业务种类确定后请求：

GET /api/perf/alloc-adjust/emp-suggest
GET /api/perf/alloc-relations（当前分配/预览）

服务按客户编号、业务种类和分配维度读取当前有效关系，再批量通过 UserApi 补充登录名、姓名和机构显示信息。页面只消费 DTO，不直接查询 CUST_ALLOC_RELATION。

## 2. 当前关系筛选

预览选择 CUST_ALLOC_RELATION 中目标客户和业务种类的关系，分配维度、有效日期和结束日期必须满足当前查询条件。具有来源批次的关系以批次为整体选择；同批次的全部关系行一并返回。来源批次为空的关系按自身主键形成独立组。

批次优先比较 source_process_date，其次比较 created_time，最后使用稳定主键/批次键消歧。这样可避免相同客户同时存在多名分配人时只展示部分行。

## 3. 页面与申请快照

allocList 非空时页面展示只读原分配，并据此决定是否允许选择“交原业绩所属人审批”。没有当前关系时由页面进入手工录入路径。

保存草稿或提交申请时，服务将预览关系复制为申请明细中的 ORIGIN 快照；新分配明细使用 NEW。详情和审批优先读取申请快照，避免申请期间当前关系变化覆盖已提交内容。历史快照缺少 username 时，使用员工编号显示。

审批批准只把 NEW 明细落地为当前分配关系，ORIGIN 仅用于追溯，不重复写入。批准后的关系包含来源申请编号、员工和机构快照，后续查询仍按当前关系选择规则执行。

## 4. 约束

- 客户编号、业务种类和分配维度由服务层校验，不能由前端拼接 SQL。
- 预览查询和申请详情均执行当前用户数据范围校验。
- UserApi 解析不到员工时保留可追溯的员工编号/申请快照，不把无法解析的对象伪装成其他员工。
- 该口径只覆盖原分配预览；审批状态、比例校验和生效事务见 03、06 文档。

## 5. 代码位置

- 前端：xanzc_frontend 中分配调整页面。
- 后端：performance-engine-center 的 AllocAdjustController、AllocRelationController、AllocRelationService、AllocApiImpl。
- 申请明细：PERF_ALLOC_ADJUST_ITEM；当前关系：CUST_ALLOC_RELATION。
