## 1. 模块职责边界

### 1.1 负责

| 领域 | 具体职责 |
|---|---|
| 指标库 | `perf_metric_def`/`perf_metric_ref` 的 CRUD, 层级校验, 槽位分配 |
| 指标计算 | SQL / 存储过程 / Groovy 执行, 立即执行, 级联刷新, 试运行 |
| KPI 规则 | `perf_kpi_scheme`/`perf_kpi_item` 管理, 计算公式引擎 |
| 目标管理 | `perf_target_plan`/`perf_target_value` 管理, Excel 批量导入, 目标修正审批发起 |
| 数据导入 | 指标结果 / KPI 结果 / 目标值的统一导入, 预览, 错误报表 |
| 分配关系 | `cust_alloc_relation` 增删查, 对公/零售调整审批发起 |
| 数据版本控制 | `sys_control` 发布与切换, 缓存失效事件发布 |
| KPI 计算 | 日终批量 KPI 计算任务, 结果写入 `kpi_result` |
| 历史回算 | 跨触发源的统一回算引擎 |
| 外部数据任务上报接收 | `POST /api/data-task/status` 接口 |

### 1.2 不负责

## 4. 分层规范

### 4.1 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| `controller` | 接收 HTTP 请求, 参数校验 (@Valid), 调用 `facade`, 封装 `R<T>` 返回 | 禁止直接调 `service` / `mapper`, 禁止写业务逻辑 |
| `facade` | 编排多个 `service` 完成一个外部用例, 组装返回 DTO | 禁止直接访问 `mapper` |
| `service` | 单一职责的业务逻辑, 事务边界 | 禁止直接 return entity 给 controller |
| `mapper` | 数据访问, 只关心 CRUD 与 SQL | 禁止写业务逻辑, 禁止跨模块 join |
| `entity` | 贫血模型, 仅字段 + getter/setter | 禁止写业务方法 |

### 4.2 事务边界

- 默认事务边界在 `service` 层 public 方法上
- 跨 service 调用时, 最外层的 `facade` 或 `service` 承担总事务
- 使用 `@Transactional(rollbackFor = Exception.class)` 显式声明
- **KPI 计算**: 单员工一事务, 全局用异步批处理, 避免大事务
- **历史回算**: 按周期分批事务, 单批 500 条

### 4.3 跨模块调用

**唯一规则**: 本模块调用其他模块, 只通过对方的 `*Api` 或 `*QueryApi` 接口, 禁止:

- 直接 `@Autowired` 对方的 `service` 或 `mapper`
- 直接读对方的表
- 在 MyBatis XML 中 join 其他模块的表

**典型调用示例:**

```java
@Service
public class AllocAdjustService {
    @Autowired private WorkflowApi workflowApi;                        // workflow-center
    @Autowired private CustomerQueryApi customerQueryApi;              // customer-marketing-center
    @Autowired private NotificationApi notificationApi;                // system-governance-center
    @Autowired private AuditApi auditApi;                              // system-governance-center

    @Transactional(rollbackFor = Exception.class)
    public String startAdjust(AllocAdjustCreateReqDTO req, String empId) {
        // 1. 校验客户存在
        CustomerInfoDTO cust = customerQueryApi.getCustomerInfo(req.getCustId())
            .orElseThrow(() -> new BizException(PerfErrorCode.CUST_NOT_FOUND));
        
        // 2. 本地持久化申请单
        PerfAllocAdjustApply apply = buildApply(req, empId);
        allocAdjustApplyMapper.insert(apply);
        
        // 3. 发起工作流
        String processCode = cust.isCorp() 
            ? "perf_alloc_adjust_corp_v1" 
            : "perf_alloc_adjust_retail_v1";
        String processInstanceId = workflowApi.startProcess(
            StartProcessCmd.builder()
                .processCode(processCode)
                .businessKey(apply.getApplyNo())
                .variables(buildProcessVariables(apply))
                .starter(empId)
                .build()
        );
        
        // 4. 记录审计
        auditApi.record(AuditCmd.highRisk("PERF_ALLOC_ADJUST_SUBMIT", apply.getApplyNo()));
        
        return apply.getApplyNo();
    }
}
```

## 5. 核心服务内部设计

### 5.1 SysControlService

职责: 版本发布、切换、查询。核心方法:

```java
public class SysControlService {
    /** 发布新版本, 同一事务内切换 is_valid 标记 */
    @Transactional
    public void publish(BaseDim dim, LocalDate dataDate, String version, PublishSource source, String publishBy);

    /** 查询当前有效版本 */
    public Optional<SysControl> getCurrentValid(BaseDim dim);

    /** 查询历史版本 */
    public List<SysControl> listHistory(BaseDim dim, LocalDate dataDate);

    /** 回滚到上一个版本 (高危, 仅系统管理员) */
    @Transactional
    public void rollback(BaseDim dim, LocalDate dataDate, Long targetVersionId, String reason);
}
```

发布事务内必须同时:

1. `UPDATE sys_control SET is_valid=0 WHERE dim=? AND is_valid=1`
2. `INSERT INTO sys_control (..., is_valid=1)`
3. `eventPublisher.publishEvent(new SysControlUpdatedEvent(dim, newVersion))`

### 5.2 MetricCalcService 与 CascadeRefreshService

指标计算流程:

```
executeImmediately(metricCode)
  → metricDefService.getByCode(metricCode)
  → switch(metricLevel)
      L1: sqlExecutorService.execute(sqlText | procName) → writeResult
      L2/L3: groovyExecutorService.execute(exprText, context) → writeResult
  → cascadeRefreshService.refreshDownstream(metricCode)
      → for each downstream metric: executeImmediately (递归)
```

**环路检测**: 每次级联刷新都要检查循环依赖, 防止 A→B→A 死循环。通过"已访问集"在 `perf_metric_ref` 上做 DFS 判定。

### 5.3 SqlExecutorService

一级指标执行 SQL 的安全要求:

1. SQL 只能是 `SELECT` 或存储过程调用, **禁止** `INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER`
2. SQL 解析使用 Druid `SQLParserUtils`, 遍历 AST 检查类型
3. 只读从库数据源: 通过 `@DS("perf_read")` 切换到指标计算专用的只读库
4. 执行超时 5 分钟, 超过报 `PERF-50001`
5. 执行前后写 `perf_run_task` 记录 `started_at / ended_at / status / error_msg`

### 5.4 GroovyExecutorService

二三级指标 Groovy 执行的安全沙箱:

1. 使用 `GroovyShell` + `SecureASTCustomizer` 禁用以下包:
   - `java.io.*`, `java.net.*`, `java.lang.reflect.*`, `java.lang.Runtime`, `java.lang.ProcessBuilder`
   - `javax.script.*`
2. 脚本最大执行时间 30 秒 (通过 `Thread.interrupt` 实现)
3. 脚本可用的上下文变量:
   - `empId` / `orgCode` / `custId` (当前计算对象)
   - `dataDate` (当前数据日期)
   - `ref(metricCode)` — 函数, 读取引用指标值
   - `Math` / `BigDecimal`
4. 脚本不能 `import`, `import` 关键字在 AST 阶段被拒绝

示例表达式:

```groovy
// 二级指标 M_EMP_DEP_WEIGHTED 的计算
def bal = ref('M_EMP_DEP_AVG_BAL') ?: 0
def pct = ref('M_EMP_DEP_GROWTH_PCT') ?: 0
return bal * (1 + pct / 100)
```

### 5.5 KpiCalcService

KPI 计算的伪代码:

```java
public void calcAll(LocalDate dataDate) {
    PerfRunTask task = perfRunTaskService.begin(RunTaskType.KPI_RUN, dataDate);
    try {
        SysControl control = sysControlService.getCurrentValid(BaseDim.EMP)
            .orElseThrow(() -> new BizException(PerfErrorCode.SYS_CONTROL_NOT_FOUND));
        
        List<PerfKpiScheme> schemes = kpiSchemeService.listPublished();
        for (PerfKpiScheme scheme : schemes) {
            List<String> empIds = resolveEmpIdsForScheme(scheme);
            ListUtils.partition(empIds, 500).forEach(batch -> 
                threadPool.submit(() -> calcBatch(scheme, batch, dataDate, control.getCurrentVersion()))
            );
        }
        
        threadPool.awaitTermination();
        perfRunTaskService.success(task.getId(), resultPreview);
        eventPublisher.publish(new KpiCalcCompletedEvent(dataDate));
    } catch (Exception e) {
        perfRunTaskService.fail(task.getId(), e.getMessage());
        throw e;
    }
}

@Transactional
private void calcBatch(PerfKpiScheme scheme, List<String> empIds, LocalDate dataDate, String version) {
    for (String empId : empIds) {
        Map<String, BigDecimal> actuals = empIndexResultMapper.selectSlotsByEmpId(empId, dataDate, version, scheme.getRequiredSlots());
        Map<String, TargetBase> targets = targetValueService.getTargets(empId, scheme, currentCycleKey(scheme));
        
        BigDecimal total = BigDecimal.ZERO;
        List<KpiItemDetail> details = new ArrayList<>();
        for (PerfKpiItem item : scheme.getItems()) {
            BigDecimal actual = actuals.getOrDefault(item.getMetricCode(), BigDecimal.ZERO);
            TargetBase tb = targets.get(item.getMetricCode());
            BigDecimal score;
            if (tb == null || tb.getTargetValue().compareTo(BigDecimal.ZERO) <= 0) {
                score = BigDecimal.ZERO;  // target<=0 按 0 分
            } else {
                BigDecimal base = tb.getBaseValue() != null ? tb.getBaseValue() : BigDecimal.ZERO;  // base 未导入按 0
                BigDecimal raw = actual.subtract(base)
                    .divide(tb.getTargetValue(), 6, RoundingMode.HALF_UP)
                    .multiply(item.getMultiplier())
                    .multiply(item.getWeight());
                score = clamp(raw, item.getMinScore(), item.getMaxScore());
            }
            total = total.add(score);
            details.add(KpiItemDetail.of(item, actual, score));
        }
        
        kpiResultService.upsert(empId, scheme.getCycleType(), currentCycleDate(scheme), dataDate, version, total, details);
    }
}
```

### 5.6 HistoryRecalcService

历史回算引擎接受以下参数:

- `cycleType` (MONTHLY/QUARTERLY/YEARLY)
- `cycleDateFrom` / `cycleDateTo`
- `scope` (EMP_IDS / ORG_CODES / ALL)
- `reason` (必填, 审计用)
- `triggerSource` (ALLOC_ADJUST / TARGET_ADJUST / MANUAL)

执行过程:

1. 判定"已结束年度", 把冻结年度从 `[from, to]` 中移除
2. 构造 `perf_run_task`, `task_type=RECALC`
3. 对每个 cycle_date, 调 `KpiCalcService.calcSpecificCycle`
4. 成功后发布 `performance.kpi-calc.completed.v1` (带 `recalc=true` 标记)

### 5.7 PerfImportService

导入统一入口处理流程:

1. 接收 multipart 文件 → 计算 md5
2. 查重, 生成 `perf_import_batch (PENDING)`
3. 异步: 按 `importType` 路由到 `PerfImportExecutor` 的具体策略
4. 执行器内部:
   - INDEX_RESULT → 解析明细行 → 按维度写入 `emp_index_result` / `org_index_result` / `cust_index_result` → 触发级联刷新
   - KPI_RESULT → 解析矩阵 → 写入 `kpi_result`
   - TARGET_VALUE → 解析明细行 → 写入 `perf_target_value`
5. 汇总错误行 → 生成错误 Excel → 上传 MinIO → 更新批次状态

## 8.1 V1.7 指标级调度链路（2026-04-30 交付）

### 架构图

```
PerfMetricDef CRUD                              system-governance-center
    ↓                                             ↓
MetricDefService.create/update/delete ──hook──▶ JobApi.registerJob/unregisterJob
    ↓                                             ↓
afterCommit                                     JobService 写 sys_job_conf + 注入 Quartz
    ↓                                             ↓
MetricSchedulerService                          QRTZ_TRIGGERS（每指标 1 行）
    ↓ (启动同步 / Health Check 兜底)            ↓
                                                 Quartz 集群（QRTZ_LOCKS 行锁防重）
                                                 ↓ cron 触发
                                                 MetricExecuteQuartzJob.execute
                                                 ↓ JobDataMap.metricCode
MetricCalcService.calcMetric ←─────────────────  ↓
    ↓ 主体集合 SubjectFetcher (EXPR/GROOVY)
    ↓ foreach subject + per-subject try/catch
    ↓ 写宽表 emp/org/cust_index_result
    ↓ status: SUCCESS / PARTIAL_FAILED / FAILED
publishEvent(MetricCalcCompletedEvent) ──────▶ KpiCascadeListener
                                                 ↓ @Async + Redis SETNX 30s
                                                 KpiCalcService.calcScheme
                                                 (cycleType → cycleDate)
```

### 关键组件

| 组件 | 路径 | 说明 |
|---|---|---|
| `MetricSchedulerService` | service/MetricSchedulerService.java | 启动同步 + register/unregister + isSchedulable 6 分支判定 |
| `MetricSchedulerHealthCheck` | service/MetricSchedulerHealthCheck.java | @Scheduled 每 10 分钟兜底补偿 + @ConditionalOnProperty 启停开关 |
| `MetricExecuteQuartzJob` | job/quartz/MetricExecuteQuartzJob.java | 通用包装类，按 JobDataMap.metricCode 派发到 calcMetric |
| `MetricCronResolver` | service/MetricCronResolver.java | cronExpr 优先；空则按 calc_freq 推导（DAY=02:00 / WEEK=Mon 02:00 / MONTH=1 日 02:00 / QUARTER=季度首月 1 日 02:00 / YEAR=1 月 1 日 02:00） |
| `SubjectFetcher` | service/SubjectFetcher.java | EXPR/GROOVY 类型主体集合 SQL 取数 + SqlValidator 黑名单 |
| `SubjectStats` | service/dto/SubjectStats.java | 主体明细统计（total/success/failed/failedSamples/jobKey/triggerType） |
| `KpiCascadeListener` | listener/KpiCascadeListener.java | 事件驱动 KPI 重算（AFTER_COMMIT + @Async + Redis SETNX 30s 防重） |
| `KpiCascadeAsyncConfig` | config/KpiCascadeAsyncConfig.java | 专用线程池（core=2/max=4/queue=200/CallerRunsPolicy） |
| `MetricCalcCompletedEvent` | event/MetricCalcCompletedEvent.java | 11 字段事件载荷 |

### 关键不变式

- 每条 ACTIVE+AUTO 指标 ⇔ sys_job_conf 1 行 ⇔ QRTZ_TRIGGERS 1 行（1:1:1）
- 双写日志：sys_job_run_log（治理可见） + perf_run_task（业务参数 + 明细计数），靠 perf_run_task.params_json.jobKey 关联
- DailyKpiCalcJob 已删除（V1_7_1 清理 sys_job_conf 行）；KPI 改为事件驱动
- MANUAL / DISABLED / PROC / SUMMARY 类型不注册（isSchedulable 判定）

### 事件传递语义（V1.7 best-effort）

- MetricCalcService.calcMetric 设计为非事务最外层方法（每个 mapper 走自己的短事务）
- 事件发布发生在所有写库后，AFTER_COMMIT + fallbackExecution=true 立即异步触发
- 边界风险：calcMetric 写状态成功 → 事件 publish 之前 JVM 崩溃 → 事件丢失，KPI 永远不会重算
- 当前架构靠 MetricSchedulerHealthCheck 每 10 分钟扫描的间接补偿
- V1.7+ 如需强一致，再引入"事件落库 + Quartz 补偿扫描"模式
