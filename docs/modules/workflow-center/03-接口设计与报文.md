# 工作流中心 -- 接口设计与报文

> 版本：V1.3 | 最后更新：2026-08-11（V1.0 基线 2026-04-02）
> 本文档定义所有 HTTP 接口的字段级精度，可直接用于开发。
> **2026-08-11 增量说明**：新增跨模块只读聚合 `WorkflowQueryApi.getActiveTaskCandidates`，不新增 REST 路由；其返回当前活动任务实际 assignee/candidate 对应的员工姓名与工号，无活动任务时返回空列表，详见 `04-对外API契约.md` §3。
> **实现边界**：当前该查询的节点级消费按串行、单活动 `userTask` 假设；返回扁平员工列表，不携带任务/节点分组。并行网关、多实例或同一流程多活动任务尚未形成节点级契约，不应据此判定某一具体节点的审批人。
> **2026-07-19 回填说明**：本次对照 `controller/` 源码全量核实并补齐 2026-04 快照之后新增的控制器契约——审批流程设计器（`FlowDesignController`）、流程命令（`ProcessCommandController`）、审批流监控（`ProcessMonitorController`）、两阶段任务转交（`TaskTransferController`），并订正若干与代码不符的字段/校验注解/错误码描述（详见各分组内 "字段更新" 提示块）；未特别标注的既有章节内容保持不变。

## 接口分组总览

| 分组 | 路由前缀 | Controller | 说明 |
|:---|:---|:---|:---|
| A. 待办/已办查询 | `/api/workflow/tasks` | `TaskController` | 待办列表、已办列表、任务详情 |
| B. 任务操作 | `/api/workflow/tasks/{taskId}/*` | `TaskController` | 签收、审批、驳回（旧单阶段转交已下线，见 B.4） |
| C. 流程查询 | `/api/workflow/processes`、`/api/workflow/process-map` | `ProcessController` / `ProcessMapController` | 流程实例详情、进度图(PNG)、进度图(结构化JSON)、审批日志、流程映射 |

## A. 待办/已办查询

### A.1 GET /api/workflow/tasks -- 查询待办列表（分页）

**权限说明**：无需 `@BizAuth`（待办天然按当前用户过滤，待办可见范围由 Flowable + 本系统候选组解析控制）。

#### 请求参数（Query）

| 参数 | 类型 | 必填 | 校验 | 说明 |
|:---|:---|:---|:---|:---|
| bizType | String | 否 | 枚举值 | 按业务类型过滤：LEAD / LOAN / SUPPORT / TOUCH / TARGET_ADJUST / ALLOC_ADJUST |
| keyword | String | 否 | @Size(max=100) | 按标题模糊搜索。**当前实现差异**：`TodoQueryService` 尚未真正对该参数做过滤，传入不生效 |
| pageNo | int | 否 | @Min(1) | 页码，默认 1 |
| pageSize | int | 否 | @Min(1) @Max(100) | 每页条数，默认 20 |

#### TaskRespDTO 字段定义

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| taskId | String | Flowable 任务ID |
| processInstanceId | String | 流程实例ID |
| businessKey | String | 业务键 |
| bizType | String | 业务类型 |
| bizId | String | 业务对象ID |
| title | String | 流程标题 |
| startUser | String | 发起人工号 |
| startUserName | String | 发起人姓名 |
| startOrgName | String | 发起人机构名称 |
| startTime | String(ISO 8601) | 流程发起时间 |
| taskName | String | 节点名称（如"公司部审核"） |
| taskCreateTime | String(ISO 8601) | 到达节点时间 |

## B. 任务操作

### B.1 POST /api/workflow/tasks/{taskId}/claim -- 签收

**权限说明**：BizType 通过 business_key 前缀动态解析，校验当前用户在候选组范围内。

#### 路径参数

| 参数 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| taskId | String | 是 | Flowable 任务ID |

#### 请求体

无（或空 JSON `{}`）

#### 成功响应

```json
{
  "code": 200,
  "message": "签收成功",
  "traceId": "TRC_20260402150003_004",
  "data": null
}
```

#### 错误响应示例（订正，见下方错误码核实说明）

**WF-40403 任务不存在：**
```json
{
  "code": 404,
  "message": "任务不存在",
  "traceId": "TRC_20260719120000_004",
  "errorCode": "WF-40403",
  "data": null
}
```

**WF-40913 任务转交待认领中，不可办理：**
```json
{
  "code": 409,
  "message": "任务转交待认领中，不可办理",
  "traceId": "TRC_20260719120000_005",
  "errorCode": "WF-40913",
  "data": null
}
```

**WF-40904 任务已被签收：**
```json
{
  "code": 409,
  "message": "任务已被签收",
  "traceId": "TRC_20260402150003_007",
  "errorCode": "WF-40904",
  "data": null

```

> **错误码核实与订正（2026-07-19，源码 `TaskOperationService.claimTask` + `WfErrorCode.java`）**：`claimTask` 实际按序抛出 `WF-40403`（任务不存在，`TASK_NOT_FOUND`）→ `WF-40913`（转交待认领锁定中，`TASK_TRANSFER_LOCKED`，2026-07-13 两阶段转交上线后新增）→ `WF-40904`（已被签收，`TASK_ALREADY_CLAIMED`）。原文档标注的 `WF-40902`（"任务不存在或已完成"）与 `WF-40903`（"无权签收，当前用户非候选人"）在当前 `WfErrorCode` 枚举中含义分别为 `TASK_NOT_OWNED`（任务非当前用户）与 `NOT_TASK_ASSIGNEE`（非任务办理人），并非签收路径实际抛出的语义/代码，本次订正为真实实现；`claimTask` 当前也**不**做"候选人身份"层面的显式拒绝（未签收即可被任意登录用户 claim，仅拦不存在/已签收/转交锁定三种情形）。

| source | 写入时机 |
|:---|:---|
| `START` | 流程启动，记发起人主机构 |
| `ASSIGN` | 任务创建且已有具体受理人，记受理人主机构 |
| `CANDIDATE` | 任务创建且为**候选人模式**（受理人为 NULL），记按机构归属（SELF/PARENT/L2/AUTO）解析出的**审批机构**（2026-07-22 新增） |

> **仍不记的情况**：「不限机构」的候选组（`addCandidateGroup` 分支）没有确定的审批机构，不写快照——否则会把无关机构带进监控范围。此类流程对 `ORG` 范围仅凭发起/签收机构可见。

#### 校验链与错误码（任一不通过即抛异常，不写库）

| 顺序 | 校验内容 | 错误码 |
|:---|:---|:---|
| 1 | 任务存在 | `WF-40403` `TASK_NOT_FOUND` |
| 2 | 不能转交/指派给被转出者本人或发起人自己 | `WF-40918` `TRANSFER_SELF_NOT_ALLOWED`（"不能将任务转交给本人"） |
| 3 | 该任务无正在生效的待认领转交（单活约束） | `WF-40910` `TRANSFER_ALREADY_PENDING`（"该任务已有待认领的转交"） |
| 4 | 接收人 ∈ 发起人所在机构（机构-用户 1:1，主机构编码须相等） | `WF-40911` `TRANSFER_RECEIVER_NOT_IN_ORG`（"接收人不在本机构"） |
| 5 | 接收人 ∈ 该节点可办理者 | `WF-40912` `TRANSFER_RECEIVER_NOT_CANDIDATE`（"接收人无该节点办理资格"） |

> **转交 / 指派两种语义（2026-07-20 放开未签收转交）**：本端点按任务当前 `assignee` 自动区分——
> `assignee` 非空 = **转交**（`fromEmpId` 记原办理人，办理权从 A 转给 B）；`assignee` 为空（候选组任务尚无人签收）
> = **指派**（`fromEmpId` 落 `null`，由发起人从候选池直接指定办理人，典型场景为秘书岗分派机构负责人会签任务）。
> 两者共用同一条两阶段链路与"发起即锁定"语义。此前第 2 项校验为"任务必须已签收"（`WF-40917`），
> 与审批链路口径不一致（PC 端 approve 前自动 claim、手机端 `approveTaskByEmp` 不校验 assignee），
> 导致未签收的会签任务无法分派，现已移除；`WF-40917` 码位保留但不再抛出。
>
> `fromEmpId`（被转出者）取当前任务 `assignee`，**不是**发起人——秘书代为发起转交时，发起人可能不同于被转出的实际办理人。DB 侧还有唯一索引（`uk_active_task`）兜底单活约束，先查后插的竞态窗口败者会被 `DuplicateKeyException` 兜成同样的 `WF-40910`。

| 2 | 原 Flowable 任务仍存在（可能已被撤单/驳回/无会话审批完成删除） | `WF-40916` `TRANSFER_TASK_GONE`（命中时把转交记录乐观置为 `INVALIDATED` 终态） |
| 3 | 当前登录用户即接收人 | `WF-40303` `TRANSFER_NOT_RECEIVER`（"只有接收人可认领"） |
| 4 | 乐观状态流转成功（并发下可能已被抢先流转） | `WF-40915` `TRANSFER_STATE_CHANGED`（"转交状态已变更"） |

认领成功后：改 Flowable 任务 `assignee` → 同步 `biz_process_map.current_assignee` → 记参与机构快照（`WfProcessOrgService.record(pid, empId, "TRANSFER")`）→ 任务加认领评论留痕 → 通知发起人。

#### TransferItemDTO 字段定义（H.2/H.5 收发件箱共用）

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| id | String | 转交记录ID |
| processInstanceId | String | Flowable 流程实例ID |
| taskId | String | 任务ID |
| businessKey | String | 业务键（可能为空） |
| bizType | String | 业务类型（可能为空） |
| nodeKey | String | 节点定义 Key |
| nodeName | String | 节点名称 |
| fromEmpId | String | 原办理人工号（被转出者，任务 assignee） |
| initiatorEmpId | String | 发起人工号（可能是原办理人本人，也可能是代为发起的秘书） |
| toEmpId | String | 接收人工号 |
| orgCode | String | 发起人机构编码 |
| status | String | 转交状态：PENDING_ACCEPT / ACCEPTED / REJECTED / CANCELLED / INVALIDATED |
| transferReason | String | 转交原因（发起时填写） |
| rejectReason | String | 拒绝理由（仅 REJECTED 状态有值） |
| initiatedTime | LocalDateTime | 发起时间 |
| decidedTime | LocalDateTime | 决策时间（认领/拒绝/撤回的时间，PENDING_ACCEPT 状态为空） |

> **补充说明（2026-07-19）**：`status` 实际枚举比 H 分组文字描述多一个 `INVALIDATED`（原任务已不存在导致转交被动失效的终态），H.2/H.5 收发件箱查询未过滤该状态时仍可能查到，前端展示需覆盖此分支。

### H.4 POST /api/workflow/transfers/{id}/decline -- 拒绝转交

无 `@BizAuth`（服务层内部校验：仅接收人本人可拒绝）。
**审计**：`@AuditLog(action = "TRANSFER_DECLINE", resourceType = "WORKFLOW_TASK", reasonRequired = true)`

#### 路径参数

| 参数 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| id | String | 是 | 转交记录ID |

#### 请求体 TransferDecisionReqDTO

| 字段 | 类型 | 必填 | 校验 | 说明 |
|:---|:---|:---|:---|:---|
| reason | String | 是 | @NotBlank @Size(max=500) | 拒绝理由 |

#### 校验链与错误码

同 H.3 步骤 1/2，另加：

| 校验内容 | 错误码 |
|:---|:---|
| 当前登录用户即接收人 | `WF-40304` `TRANSFER_DECLINE_NOT_RECEIVER`（"只有接收人可拒绝"） |
| 拒绝理由非空（Controller `@Valid` 已挡，Service 层防御性兜底） | `WF-40001` `TRANSFER_REJECT_REASON_REQUIRED` |
| 乐观状态流转成功 | `WF-40915` `TRANSFER_STATE_CHANGED` |

拒绝成功后同时通知发起人与原办理人（`fromEmpId`）。

#### 成功响应

```json
{ "code": 200, "message": "success", "traceId": "TRC_20260719120000_062", "data": null }
```

### H.6 POST /api/workflow/transfers/{id}/cancel -- 撤回转交

无 `@BizAuth`（服务层内部校验：仅发起人本人可撤回）。
**审计**：`@AuditLog(action = "TRANSFER_CANCEL", resourceType = "WORKFLOW_TASK")`

#### 路径参数

| 参数 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| id | String | 是 | 转交记录ID |

#### 校验链与错误码

同 H.3 步骤 1，另加：

| 校验内容 | 错误码 |
|:---|:---|
| 当前登录用户即发起人（秘书代发起场景下归属 `initiatorEmpId` 而非 `fromEmpId`） | `WF-40305` `TRANSFER_CANCEL_NOT_INITIATOR`（"只有发起人可撤回"） |
| 乐观状态流转成功 | `WF-40915` `TRANSFER_STATE_CHANGED` |

撤回成功后通知接收人。

#### 成功响应

```json
{ "code": 200, "message": "success", "traceId": "TRC_20260719120000_063", "data": null }
```
