# 工作流中心 — 并发与事务策略

> 本文档定义 workflow-center 模块在流程发起、任务签收、任务办理、流程结束等关键环节的事务边界和并发控制策略。
> 核心原则：**单库单 Schema 本地事务 + Flowable 内置乐观锁 + 应用层幂等**

---

## 1. 流程发起事务边界

### 1.1 事务范围

流程发起是一个**单事务**操作，包含以下步骤，全部在同一个数据库事务中完成：

```
@Transactional
public void startProcess(StartProcessCmd cmd) {
    // 1. 校验 business_key 唯一性（SELECT + uk_business_key 约束兜底）
    // 2. 创建 biz_process_map 记录（INSERT）
    // 3. 调用 Flowable RuntimeService.startProcessInstanceByKey()
    //    - Flowable 在同一事务中写入 ACT_RU_EXECUTION / ACT_RU_TASK 等表
    // 4. 回写 process_instance_id 到 biz_process_map（UPDATE）
}
```

### 1.2 事务保证

| 保证项 | 实现方式 |
|---|---|
| 业务映射与流程实例强一致 | 同一个 `@Transactional` 事务，任何环节失败整体回滚 |
| 防重复发起 | `uk_business_key` 唯一约束 + 应用层前置检查 |
| 数据库连接复用 | 单库单 Schema，Flowable 共享 DataSource，无分布式事务 |
| 回滚策略 | Flowable 异常自动触发 Spring 事务回滚，biz_process_map INSERT 同步回滚 |

### 1.3 调用方事务传播

业务模块（如 business-application-center）调用 `WorkflowApi.startProcess()` 时：

```
@Transactional  // 调用方事务
public void submitLoanApplication(LoanSubmitCmd cmd) {
    // 1. 保存/更新业务主表（如 loan_application）
    loanMapper.updateStatus(cmd.getId(), "SUBMITTED");

    // 2. 发起流程（参与调用方事务，REQUIRED 传播）
    workflowApi.startProcess(new StartProcessCmd(
        "loan_approve_v1",
        BizType.LOAN,
        cmd.getId(),
        currentUserApi.getCurrentEmpId()
    ));
    // 若流程发起失败，业务主表更新也会回滚
}
```

**关键设计**：`WorkflowApi.startProcess()` 使用默认的 `@Transactional(propagation = REQUIRED)`，参与调用方的事务。这保证了"业务主表状态变更"与"流程实例创建"的原子性。

## 2. 任务签收(Claim)并发控制

### 2.1 并发场景

候选组待办模式下，多个用户可能同时看到同一个待办任务并尝试签收。

### 2.2 并发控制机制

```
@Transactional
public void claimTask(String taskId, String empId) {
    // 1. 查询任务（Flowable 从 ACT_RU_TASK 读取）
    Task task = taskService.createTaskQuery().taskId(taskId).singleResult();
    if (task == null) {
        throw new BizException("WF-40401", "任务不存在或已完成");
    }

    // 2. 校验任务未被签收
    if (task.getAssignee() != null) {
        if (task.getAssignee().equals(empId)) {
            return; // 幂等：自己已签收，直接返回成功
        }
        throw new BizException("WF-40901", "任务已被其他人签收");
    }

    // 3. 调用 Flowable claim（内置乐观锁）
    //    Flowable 在 UPDATE ACT_RU_TASK SET ASSIGNEE_ = ? WHERE ID_ = ? AND REV_ = ?
    //    若并发冲突，REV_ 不匹配，Flowable 抛出 FlowableOptimisticLockingException
    taskService.claim(taskId, empId);

    // 4. 同步刷新 biz_process_map（同事务）
    bizProcessMapMapper.updateCurrentAssignee(processInstanceId, empId);
}
```

### 2.3 并发保证

| 保证项 | 实现方式 |
|---|---|
| 同一任务只允许一人签收 | Flowable `TaskService.claim()` 内置乐观锁（`REV_` 字段） |
| 并发签收互斥 | 第二个签收请求因 `REV_` 不匹配抛出 `FlowableOptimisticLockingException` |
| 签收与映射表一致 | `claim` 和 `updateCurrentAssignee` 在同一事务中 |
| 幂等处理 | 同一用户重复签收返回成功 |

### 2.4 异常处理

```java
try {
    taskService.claim(taskId, empId);
} catch (FlowableOptimisticLockingException e) {
    // 并发签收冲突，重新查询任务状态
    Task updatedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    if (updatedTask != null && empId.equals(updatedTask.getAssignee())) {
        return; // 实际是自己签收成功了
    }
    throw new BizException("WF-40901", "任务已被其他人签收");
} catch (FlowableObjectNotFoundException e) {
    throw new BizException("WF-40401", "任务不存在或已完成");
}
```

## 3. 任务办理(Approve/Reject)并发控制

### 3.1 并发场景

任务已签收后，理论上只有签收人可以办理。但需防范以下异常场景：
- 用户在两个浏览器标签页同时点击"同意"
- 网络重试导致重复请求

### 3.2 并发控制机制

```
@Transactional
public void approveTask(String taskId, ApproveCmd cmd) {
    // 1. 查询并校验任务
    Task task = taskService.createTaskQuery().taskId(taskId).singleResult();
    if (task == null) {
        throw new BizException("WF-40401", "任务不存在或已完成");
    }

    // 2. 校验 assignee（只有签收人可办理）
    String currentEmpId = currentUserApi.getCurrentEmpId();
    if (!currentEmpId.equals(task.getAssignee())) {
        throw new BizException("WF-40302", "非当前任务处理人，无法办理");
    }

    // 3. 保存审批意见到 ACT_HI_COMMENT
    taskService.addComment(taskId, task.getProcessInstanceId(),
        "APPROVE", cmd.getOpinion());

    // 4. 设置流程变量（审批结果）
    Map<String, Object> variables = new HashMap<>();
    variables.put("approved", true);
    variables.putAll(cmd.getFormData());

    // 5. 完成任务（Flowable 内置乐观锁）
    //    若任务已被 complete，Flowable 抛出 FlowableObjectNotFoundException
    taskService.complete(taskId, variables);

    // 6. 刷新 biz_process_map（清除 assignee，流程可能已到下一节点）
    refreshProcessMap(task.getProcessInstanceId());
}
```

### 3.3 并发保证

| 保证项 | 实现方式 |
|---|---|
| 同一任务不可被并行 complete | Flowable `taskService.complete()` 执行时，先检查 `ACT_RU_TASK` 中是否存在该任务 |
| 重复 complete 报错 | 第二次调用时任务已从 `ACT_RU_TASK` 删除，Flowable 抛出 `FlowableObjectNotFoundException` |
| assignee 校验 | 应用层强制校验当前操作人 == task.assignee |
| 审批意见不丢失 | `addComment` 在 `complete` 之前，即使 `complete` 失败意见也会随事务回滚 |

## 4. 流程结束事件发布

### 4.1 事件发布时机

使用 Spring `@TransactionalEventListener`，保证在**事务提交后**才发布事件，避免消费方读到未持久化的数据。

```java
/**
 * Flowable 流程结束监听器
 * 在 BPMN endEvent 触发时执行（仍在 Flowable 事务中）
 */
@Component
public class ProcessEndListener implements ExecutionListener {

    @Override
    public void notify(DelegateExecution execution) {
        // 更新 biz_process_map 状态为 COMPLETED（同事务）
        bizProcessMapService.completeProcess(
            execution.getProcessInstanceId(),
            LocalDateTime.now()
        );

        // 注册事务提交后事件
        ApplicationEventPublisher publisher = SpringContextHolder.getBean(ApplicationEventPublisher.class);
        publisher.publishEvent(new ProcessCompletedEvent(
            execution.getProcessInstanceId(),
            execution.getVariable("businessKey").toString(),
            UUID.randomUUID().toString()  // eventId，用于消费方幂等
        ));
    }
}
```

### 4.2 事件消费方

```java
@Component
public class ProcessCompletedEventHandler {

    /**
     * AFTER_COMMIT：事务提交后执行
     * 保证 biz_process_map 状态已持久化
     */
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onProcessCompleted(ProcessCompletedEvent event) {
        // 1. 幂等检查（按 eventId 去重）
        if (eventIdempotentService.isDuplicate(event.getEventId())) {
            return;
        }

        // 2. 通知业务模块（如更新业务主表状态）
        // 通过 Spring Event 广播，各业务模块自行监听

        // 3. 发送通知（调用 NotifyApi）
        notifyApi.sendNotification(new NotificationCmd(
            event.getStartUser(),
            "流程已完成",
            "您发起的流程已审批完成",
            event.getBizType(),
            event.getBizId(),
            "/workflow/detail/" + event.getProcessInstanceId()
        ));
    }
}
```

### 4.3 事件可靠性保证

| 保证项 | 实现方式 |
|---|---|
| 状态持久化先于事件发布 | `@TransactionalEventListener(phase = AFTER_COMMIT)` |
| 消费方幂等 | 按 `eventId` 去重（Redis SETNX，TTL=24h） |
| 消费失败不影响主流程 | 事件消费在独立事务中，失败不回滚主事务 |
| 事件丢失风险 | V1 接受极端场景下事件丢失（如应用在 AFTER_COMMIT 前宕机）；V2 可引入事件表补偿 |

## 5. biz_process_map 一致性保证

### 5.1 唯一约束防护

| 约束 | 字段 | 防护场景 |
|---|---|---|
| `uk_business_key` | `business_key` | 防止同一业务实体重复发起流程 |
| `uk_process_instance` | `process_instance_id` | 防止同一流程实例重复映射 |

### 5.2 状态同步策略

`biz_process_map` 中的 `current_assignee`、`candidate_groups`、`process_status` 字段需要与 Flowable 引擎表保持同步：

| 字段 | 同步时机 | 实现方式 |
|---|---|---|
| `current_assignee` | 签收(Claim) / 办理(Approve/Reject) / 转交(Transfer) | 在 Flowable 操作的**同一事务**中更新 |
| `candidate_groups` | TaskListener 设置候选组时 | TaskListener 中同步更新（同事务） |
| `process_status` | 流程结束时 | ProcessEndListener 中更新为 `COMPLETED`（同事务） |
| `end_time` | 流程结束时 | ProcessEndListener 中写入当前时间（同事务） |

### 5.3 一致性修复

尽管设计上保证了同事务更新，但为防止极端场景下的数据不一致，提供以下修复机制：

```
-- 检查一致性 SQL（运维用，非自动执行）
-- 找出 biz_process_map 状态为 RUNNING 但 Flowable 已无运行实例的记录
SELECT bpm.id, bpm.business_key, bpm.process_status
FROM biz_process_map bpm
LEFT JOIN ACT_RU_EXECUTION are ON bpm.process_instance_id = are.PROC_INST_ID_
WHERE bpm.process_status = 'RUNNING'
  AND are.PROC_INST_ID_ IS NULL;
```

## 6. 红绿灯计算

### 6.1 计算策略

| 属性 | 说明 |
|---|---|
| 触发方式 | 定时任务，每 30 分钟执行一次 |
| 计算范围 | 所有 `process_status = 'RUNNING'` 的流程的当前活动任务 |
| 计算方式 | 只读操作，不加写锁 |
| 工作日计算 | 调用 `CalendarApi.isWorkingDay()` / `CalendarApi.countWorkingDays()` 计算工作日小时数 |

### 6.2 计算流程

```
@Scheduled(cron = "0 */30 * * * ?")
public void calculateTaskTrafficLight() {
    // 1. 查询所有运行中的流程映射
    List<BizProcessMap> runningList = bizProcessMapMapper
        .selectByStatus("RUNNING");

    // 2. 批量查询 Flowable 运行时任务
    for (BizProcessMap bpm : runningList) {
        List<Task> tasks = taskService.createTaskQuery()
            .processInstanceId(bpm.getProcessInstanceId())
            .list();

        for (Task task : tasks) {
            // 3. 查询超时规则
            WfTimeoutRule rule = timeoutRuleMapper.selectByProcessAndNode(
                bpm.getProcessDefinitionKey(),
                task.getTaskDefinitionKey()
            );
            if (rule == null) continue;

            // 4. 计算工作日小时数（排除节假日和周末）
            int workingHours = calendarApi.countWorkingDays(
                task.getCreateTime().toLocalDate(),
                LocalDate.now()
            ) * 8; // 每工作日按8小时计

            // 5. 判定红绿灯
            TrafficLight light;
            if (workingHours >= rule.getTimeoutHours()) {
                light = TrafficLight.RED;
            } else if (rule.getWarningHours() != null
                       && workingHours >= rule.getWarningHours()) {
                light = TrafficLight.YELLOW;
            } else {
                light = TrafficLight.GREEN;
            }

            // 6. 缓存结果到 Redis（供查询接口使用）
            redisTemplate.opsForHash().put(
                "wf:traffic-light:" + bpm.getProcessInstanceId(),
                task.getId(),
                light.name()
            );
        }
    }
}
```

### 6.3 性能考量

| 考量点 | 策略 |
|---|---|
| 扫描量控制 | 只扫描 `process_status = 'RUNNING'` 的记录 |
| 数据库压力 | 只读操作，不竞争写锁 |
| CalendarApi 调用优化 | 批量获取当年工作日集合（`getWorkingDays`），本地计算，避免逐条调用 |
| 结果缓存 | 计算结果存入 Redis Hash，TTL=35min（覆盖下一次计算周期） |
| 并发安全 | 定时任务单节点执行（通过 `@SchedulerLock` 或 Redis 分布式锁） |

## 7. 幂等策略

### 7.1 各操作幂等保证

| 操作 | 幂等机制 | 重复调用行为 |
|---|---|---|
| 发起流程 | `uk_business_key` 唯一约束 | 抛出 `DuplicateKeyException`，捕获后返回已存在的流程信息 |
| 签收(Claim) | 应用层判断 `task.assignee == currentUser` | 返回成功（不抛异常） |
| 办理(Approve/Reject) | Flowable 任务完成后从 `ACT_RU_TASK` 删除 | 抛出 `FlowableObjectNotFoundException`，捕获后查询历史判断是否已办理 |
| 转交(Transfer) | 应用层判断目标 assignee 是否一致 | 若目标一致则返回成功 |
| 事件消费 | `eventId` Redis SETNX 去重 | 跳过重复事件，返回成功 |

### 7.2 重复请求判定流程

```java
// 通用幂等判定：办理操作
public void handleApproveIdempotent(String taskId) {
    Task task = taskService.createTaskQuery().taskId(taskId).singleResult();
    if (task == null) {
        // 任务不在运行时表，检查历史
        HistoricTaskInstance historicTask = historyService.createHistoricTaskInstanceQuery()
            .taskId(taskId)
            .singleResult();
        if (historicTask != null && historicTask.getEndTime() != null) {
            // 任务已完成，幂等返回
            log.info("任务 {} 已完成，幂等返回", taskId);
            return;
        }
        throw new BizException("WF-40401", "任务不存在");
    }
    // 正常处理...
}
```

## 8. 事务隔离级别

### 8.1 全局配置

```yaml
spring:
  datasource:
    hikari:
      transaction-isolation: TRANSACTION_READ_COMMITTED
```

| 配置项 | 值 | 原因 |
|---|---|---|
| 事务隔离级别 | `READ_COMMITTED` | MySQL InnoDB 默认级别，避免脏读；配合 Flowable 乐观锁可防止并发问题 |

### 8.2 Flowable 乐观锁说明

Flowable 在 `ACT_RU_TASK`、`ACT_RU_EXECUTION` 等运行时表中维护 `REV_`（revision）字段：
- 每次 UPDATE 操作时 WHERE 条件包含 `REV_ = ?`
- UPDATE 成功后 `REV_ = REV_ + 1`
- 若 WHERE 匹配不到行（`REV_` 已被其他事务修改），抛出 `FlowableOptimisticLockingException`

这种机制保证了：
1. 同一任务不会被并发签收/办理
2. 同一执行路径不会被并发推进
3. 无需使用 `SELECT ... FOR UPDATE` 等悲观锁

## 9. 事务边界总览

| 操作 | 事务边界 | 事务传播 | 并发控制 | 幂等 |
|---|---|---|---|---|
| 发起流程 | 业务主表 + biz_process_map + Flowable | REQUIRED（参与调用方） | uk_business_key 唯一约束 | 唯一约束捕获 |
| 签收(Claim) | ACT_RU_TASK + biz_process_map | REQUIRED | Flowable 乐观锁(REV_) | 判断 assignee |
| 办理(Approve/Reject) | ACT_RU_TASK + ACT_HI_COMMENT + biz_process_map | REQUIRED | Flowable 乐观锁 + 任务存在性 | 查历史表 |
| 转交(Transfer) | ACT_RU_TASK + biz_process_map | REQUIRED | 校验当前 assignee | 判断目标一致 |
| 流程结束 | biz_process_map(同事务) + 事件发布(AFTER_COMMIT) | 随 Flowable 事务 | 无并发风险 | eventId 去重 |
| 红绿灯计算 | 无写事务（只读） | 无 | 单节点执行锁 | 覆盖式写入缓存 |
