# 工作流中心——并发与事务策略

## 1. 总原则

工作流引擎的运行时状态由 Flowable 管理，本模块的业务映射、配置、机构快照和转交状态由
本模块管理。任何操作都不能通过先改 `BIZ_PROCESS_MAP` 再猜测引擎结果来替代引擎命令。
关键引擎命令、映射更新和转交状态更新应遵循同一命令事务语义；失败时必须返回明确业务
错误，不能把并发失败伪装为成功。

Flowable 自身的乐观锁保护执行、任务和变量；本模块通过业务键锁、唯一约束和状态条件更新
补充业务并发控制。数据库 schema 的物理索引以目标库核对为准。

## 2. 流程启动

`ProcessStartService.startProcess` 使用 Spring `@Transactional`。当前顺序和一致性要求：

1. 从 RepositoryService 读取最新可用流程定义，找不到即失败；
2. 按 `businessKey` 对 `BIZ_PROCESS_MAP` 执行 `selectForUpdate`；已有 `RUNNING` 映射
   拒绝启动，终态映射按重启策略复用；
3. 在同一命令事务中通过 RuntimeService 启动实例，写入业务变量和发起人/机构变量；
4. 写入或更新映射，再查询首个任务并返回；
5. 记录机构快照和发布启动侧事件。

没有历史映射的并发首次启动可能同时看不到行，业务键唯一约束负责兜底，败者转换为
`WF-40901`。引擎启动或映射写入失败必须整体回滚；机构快照写入是旁路，失败由
`WfProcessOrgService` 记录并不阻断主命令。

## 3. 流程取消/撤回

REST `ProcessCommandService.cancelProcess` 先验证映射为 `RUNNING`、当前员工为申请人或
系统管理员，再确认运行时实例存在。删除运行时实例前读取当前活动任务的 assignee，随后
更新映射为 `CANCELLED` 并发布 `ProcessWithdrawnEvent`。

当前方法本身未标注外层 `@Transactional`；Flowable 命令由引擎事务管理，映射更新和事件
发布仍必须保持可追踪。若部署要求“引擎删除与映射更新严格原子”，应在代码和事务代理层
另行评审，不能由文档假定已经具备该保证。

## 4. 任务办理

### 4.1 签收

签收路径先查运行时任务、检查 `WF_TASK_TRANSFER` 是否有 `PENDING_ACCEPT`，再调用
`TaskService.claim`，更新映射当前处理人并记录机构快照。当前方法未标注外层
`@Transactional`；引擎命令自身受 Flowable 事务管理，映射/快照失败语义以现有服务实现
为准。签收并发由 Flowable 的 assignee 状态和 `WF-40904` 保护，待接收锁返回 `WF-40913`。

候选资格必须在服务层按运行时身份链接和本系统权限确认；列表字段 `claimable` 不参与
安全决策。若补齐候选校验，应保持与查询、审批和转交使用同一解析口径。

### 4.2 审批通过

会话版 `approveTask` 标注 `@Transactional`，顺序为：任务存在性/转交锁/处理人或候选人
校验，写 `APPROVE` 评论，合并节点表单数据并写 `approved=true`，完成任务，记录机构
快照并发布内部办理事件。变量必须在引擎推进网关或多实例之前写入。

无会话 `approveTaskByEmp` 由外部渠道传入员工 ID，不依赖登录上下文，也不要求先签收；
调用方必须先认证和授权。当前 facade 方法未单独标注 `@Transactional`，依靠引擎命令和
被调用操作的现有事务语义，不能在跨模块契约中承诺额外原子性。

### 4.3 驳回

会话版 `rejectTask` 标注 `@Transactional`。服务层要求非空意见，先写 `REJECT` 评论，
再删除运行时流程实例，将映射更新为 `CANCELLED`，发布
`ProcessCompletedEvent(outcome=REJECTED)`。这条路径是显式终止，不是运行时任意跳转。

无会话驳回同样由外部渠道认证并传入员工 ID，底层服务检查任务、意见和转交锁。评论必须
在删除任务前写入，避免引擎级联删除后历史留痕失败。

## 5. 两阶段转交

`TaskTransferService.initiate/accept/decline/cancel` 均标注 `@Transactional`。

### 5.1 发起

发起事务依次校验任务存在、没有活动待转交、接收人和发起人主机构一致、接收人属于该
节点可办理者且不是本人，然后插入 `WF_TASK_TRANSFER(PENDING_ACCEPT)` 并写任务评论。
未签收任务的 `fromEmpId` 可空，表示候选池定向指派；发起时不改变 Flowable assignee。

数据库活动任务唯一约束（如 `active_task_key`）兜住“先查后插”的竞争窗口；唯一键冲突
转换为 `WF-40910`。成功插入后原任务进入待接收锁，禁止签收、审批、驳回和再次转交。

### 5.2 接受/拒绝/取消

接受、拒绝和取消都先加载仍为 `PENDING_ACCEPT` 的记录并校验当前员工身份。底层任务不
存在时先将记录条件更新为 `INVALIDATED`，再返回任务失效错误。状态变更使用
`updateStatusIfPending`：

- 接受成功才设置 Flowable assignee、更新映射、写机构快照、评论并通知发起人；
- 拒绝写拒绝理由、评论并通知发起人/原处理人；
- 取消只由发起人执行，关闭请求并通知接收人。

条件更新返回 0 表示并发方已经决策，返回 `WF-40915`，不得继续调用引擎或发送后续副作用。
状态离开 `PENDING_ACCEPT` 后活动锁自然解除；终态记录保留供历史查询。

通知调用属于治理模块旁路能力。文档不承诺通知与引擎状态的跨系统原子性；失败处理按
治理通知接口和当前服务实现执行，并需可观测。

## 6. 查询、监控和 SLA

- 查询只读运行时/历史和本模块投影，不以查询结果回写引擎；
- 监控先解析 `DataScopeContext`，未知、空值和不支持的范围 fail close，再结合
  `WF_PROCESS_ORG` 机构快照过滤；
- `WF_PROCESS_ORG` 幂等插入，写入异常不阻断启动、分配、签收、审批或转交主操作；
- SLA 在任务查询时调用治理 `CalendarApi` 计算工作日，不建立定时扫描、缓存或第二套日历；
- 无超时规则为 `GREEN`，达到预警阈值为 `YELLOW`，达到超时阈值为 `RED`。

## 7. 事件和回滚边界

工作流代码通过 `ApplicationEventPublisher` 发布公开完成/撤回事件及内部办理事件。公开
事件不携带引擎对象，也不提供事件表、outbox 或固定“提交后才发布”的额外承诺；消费者
应按平台事件约定幂等，并在自身事务中更新业务主表。若需要跨库可靠投递，应由平台级
事件方案另行设计，不能在本模块文档中虚构实现。

引擎事务回滚只保证纳入同一 Spring/Flowable 命令事务的操作；通知、机构快照等旁路效果
应具备失败日志和重试/补偿观测。任何新增写路径都必须说明事务代理是否生效、并发条件、
回滚结果和事件重复处理方式。

## 8. 验收要点

- 并发启动只能保留一个运行中实例，唯一键竞争返回明确错误；
- 重复签收、重复办理、重复转交决策不能覆盖先成功状态；
- 待接收锁覆盖所有任务办理入口；
- 接受转交的 assignee、映射和快照顺序可审查，底层任务消失能失效收敛；
- 驳回评论先于流程终止，完成/撤回事件语义与映射状态分离；
- 监控范围和候选解析 fail close；
- 未经代码/数据库评审，不以本文新增事务、缓存、调度或幂等实现。
