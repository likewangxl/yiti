# 工作流中心 -- 功能规格

> 版本：V1.0 | 最后更新：2026-04-02

---

## 1. 模块概述

### 1.1 定位

工作流中心（`workflow-center`）是系统**唯一的 Flowable 7.x 集成边界**，属于支撑域模块。所有业务模块（`customer-marketing-center`、`business-application-center`、`performance-engine-center`、`portal-content-center`）不得直接调用 Flowable `RuntimeService / TaskService / HistoryService / RepositoryService / ManagementService`，也不得直接读写 Flowable 引擎表（`ACT_*`）。

### 1.2 核心职责

| 职责 | 说明 |
|:---|:---|
| 流程发起与管理 | 接收业务模块的 `startProcess` 请求，启动 Flowable 流程实例，写入/更新 `biz_process_map` |
| 待办 / 已办管理 | 提供统一待办列表、已办列表查询，支持分页、按业务类型过滤、关键字搜索 |
| 签收（Claim） | 候选组任务的签收/领取，维护 assignee 与候选组状态同步 |
| 转交（Transfer） | 任务在候选范围内的转交，含原因记录与审计 |
| 审批 / 驳回 | 统一办理入口，调用 Flowable `TaskService` 完成/驳回任务 |
| 节点候选人管理 | 维护 `wf_node_candidate_conf`，解析候选组集合 |
| 节点表单权限 | 维护 `wf_node_form_conf`，控制节点级字段可见/可编辑/必填 |
| 红绿灯 SLA | 维护 `wf_timeout_rule`，定时计算超时状态 |
| 流程映射 | 维护 `biz_process_map`，建立业务键与流程实例的映射关系 |
| 流程事件发布 | 流程完成/取消后发布领域事件，供业务模块消费 |
| 流程参与者判定 | 当前由模块内部逻辑完成；未来可抽成 `WorkflowParticipantService`，但尚未作为对外 Java 契约落地 |

### 1.3 不负责的事项

- **不**保存业务主单数据（线索、资产投放申请、中场支持申请等由各业务模块持有）
- **不**直接更新业务表状态（业务模块消费流程事件后自行回写）
- **不**实现业务表单校验逻辑（表单校验由业务模块在提交流程前完成）
- **不**作为权限权威源（权限权威源为 `auth-permission-center` 的 `PT_* / EXT_*` 体系）

## 2. 待办管理

### 2.1 待办来源

所有待办信息**100% 由 Flowable 流程产生**。当流程流转到某个节点时，Flowable 创建 `ACT_RU_TASK`，系统将其展示在对应用户的待办列表中。

### 2.2 待办列表字段

| 字段 | 来源 | 说明 |
|:---|:---|:---|
| taskId | ACT_RU_TASK.ID_ | Flowable 任务ID |
| processInstanceId | ACT_RU_TASK.PROC_INST_ID_ | 流程实例ID |
| businessKey | biz_process_map.business_key | 业务键 |
| bizType | biz_process_map.biz_type | 业务类型（LEAD/LOAN/SUPPORT 等） |
| bizId | biz_process_map.biz_id | 业务对象ID |
| title | 流程变量 title | 流程标题 |
| startUser | biz_process_map.start_user | 发起人工号 |
| startUserName | auth-permission-center 查询 | 发起人姓名 |
| startOrgName | auth-permission-center 查询 | 发起人机构名称 |
| startTime | biz_process_map.start_time | 流程发起时间 |
| taskName | ACT_RU_TASK.NAME_ | 节点名称 |
| taskCreateTime | ACT_RU_TASK.CREATE_TIME_ | 到达节点时间 |
| assignee | ACT_RU_TASK.ASSIGNEE_ | 当前处理人（已签收） |
| candidateGroups | ACT_RU_IDENTITYLINK | 候选组（未签收时展示） |
| slaStatus | 计算字段 | 红绿灯状态：GREEN / YELLOW / RED |
| warningTime | 计算字段 | 黄灯预警时间点 |
| timeoutTime | 计算字段 | 红灯超时时间点 |
| claimable | 计算字段 | 是否可领取（true = 当前用户在候选组中且任务未被签收） |

### 2.3 待办可见范围

待办列表仅展示满足以下**任一条件**的任务：

1. **`assignee = 当前用户`**：已签收/已分配的任务，展示为"待办理"
2. **`candidateUser = 当前用户`**：明确指定当前用户为候选人的任务，展示为"可领取"
3. **`candidateGroup` 与当前用户候选组有交集**：当前用户所属角色/岗位/组织对应的候选组包含任务的 candidateGroup，展示为"可领取"

### 2.4 候选组解析规则（关键）

> **V1 不以 Flowable IDM 作为权限权威源。** 候选组必须基于本系统权限模型解析。

**待办查询不能仅依赖 `taskCandidateOrAssigned(empId)` 这类 Flowable 黑盒查询**，原因：

- Flowable IDM 中没有本系统的角色/岗位/组织数据
- 候选组的语义（如"公司部审核员"）映射到本系统的角色+组织边界组合
- 当前实现通过 `CurrentUserApi.getCurrentCandidateGroupKeys()` 与任务候选组做匹配；旧稿中的 `WorkflowParticipantService.resolveCandidateGroups(empId)` 仍属规划态名称

**解析流程：**
```
1. 从 auth-permission-center 获取当前用户的角色列表、组织信息
2. 根据 wf_node_candidate_conf 中的候选规则，计算用户属于哪些候选组
3. 查询 assignee=empId 的任务 UNION 查询 candidateGroup IN (用户候选组集合) 的任务
4. 对候选组任务标记 claimable=true
```

### 2.5 候选组待办展示

- 候选组待办展示为 **"可领取"** 状态
- 列表中 assignee 字段显示为空或"待领取"
- 提供【签收】按钮，点击后转为本人待办

## 3. 已办管理

### 3.1 已办可见范围

1. **历史 assignee 为当前用户的任务**：从 `ACT_HI_TASKINST` 中查询 `ASSIGNEE_ = 当前用户` 且已完成的任务
2. **`WORKFLOW_PARTICIPANT` 可查看流程历史**：流程参与者（发起人、历史处理人、候选人）可只读查看流程的所有审批日志和进度信息

### 3.2 已办列表字段

在待办列表字段基础上，额外包含：

| 字段 | 来源 | 说明 |
|:---|:---|:---|
| completeTime | ACT_HI_TASKINST.END_TIME_ | 办理完成时间 |
| approvalResult | 流程变量 approvalResult | 审批结果：APPROVE / REJECT |
| opinion | 审批意见 | 办理时填写的意见 |

### 3.3 Flowable History Level 要求

**V1 强制要求 Flowable history-level >= `audit`**，以确保：
- 历史任务实例（`ACT_HI_TASKINST`）完整记录
- 历史参与者（`ACT_HI_IDENTITYLINK`）可用于参与者判定
- 流程变量历史（`ACT_HI_VARINST`）可用于审批结果回溯

## 4. 签收（Claim）

### 4.1 业务规则

| 规则项 | 说明 |
|:---|:---|
| 前置条件 | 任务必须处于候选组状态（`assignee` 为空） |
| 签收人约束 | 签收人必须属于任务的候选组（通过本系统权限模型验证） |
| 签收效果 | 签收后 `assignee` 变为签收人，任务从"可领取"变为"待办理" |
| 并发控制 | 同一任务只能被一人签收，后签收者返回 409（WF-40904 任务已被签收） |
| 审计要求 | 签收为敏感操作，需记录审计日志：领取人/时间/节点/流程实例/business_key |

### 4.2 Flowable API 调用

```
TaskService.claim(taskId, empId)
```

### 4.3 签收后同步操作

签收成功后**必须同步刷新** `biz_process_map`：
- `current_assignee` 更新为签收人工号
- `candidate_groups` 保留原始候选组（不清空，用于转交时验证接收人范围）
- `updated_time` 更新为当前时间

---

## 5. 审批（Approve）

### 5.1 业务规则

| 规则项 | 说明 |
|:---|:---|
| 操作人约束 | 仅当前 `assignee` 可执行审批 |
| 权限校验三重保障 | 必须**同时**满足：(1) DATA_SCOPE 校验 (2) 节点字段权限校验 (3) 业务状态守卫 |
| 节点必填字段 | 根据 `wf_node_form_conf` 中的 `required_fields` 校验，缺失则返回 WF-42202 |
| 审批意见 | 可选填写，最大 500 字符 |
| 表单数据 | 根据节点配置提交可编辑字段数据，存入流程变量 |

### 5.2 Flowable API 调用

```
TaskService.complete(taskId, empId, variables)
```

variables 至少包含：
- `approvalResult`: "APPROVE"
- `opinion`: 审批意见（可为空）
- 节点表单数据中的可编辑字段

### 5.3 审批后同步操作

- 刷新 `biz_process_map`（current_task_id / current_node_id / current_assignee / candidate_groups 更新为下一节点信息）
- 如果是流程最后一个节点，触发流程完成事件

## 6. 驳回（Reject）

### 6.1 V1 实现方案

**V1 通过 BPMN 显式配置的驳回分支实现**，不将运行时任意跳转作为默认驳回方案。

具体机制：
1. 每个需要驳回的节点在 BPMN 中配置排他网关（Exclusive Gateway）
2. 网关条件基于流程变量 `approvalResult` 判断：
   - `approvalResult == "APPROVE"` -> 流转到下一个审批节点
   - `approvalResult == "REJECT"` -> 流转到驳回结束节点（或回到发起人修改节点，视流程定义而定）
3. 办理时通过 `TaskService.complete(taskId, empId, variables)` 提交，variables 中设置 `approvalResult = "REJECT"`

### 6.2 业务规则

| 规则项 | 说明 |
|:---|:---|
| 操作人约束 | 仅当前 `assignee` 可执行驳回 |
| 驳回原因 | **必填**，最大 500 字符 |
| 驳回效果 | 由 BPMN 排他网关决定流转目标（通常为流程结束或回到发起人修改） |

## 7. 转交（Transfer）

### 7.1 发起人约束

| 角色 | 权限 |
|:---|:---|
| 当前 assignee | 可发起转交 |
| 任务管理员 / 系统管理员 | 可强制转交（异常兜底） |

### 7.2 接收人约束（三重校验）

接收人必须**同时满足**以下条件：

1. **属于候选集合**：接收人属于该节点的 `wf_node_candidate_conf` 配置的候选范围（角色/组织/指定用户）
2. **满足组织边界**：接收人满足节点配置的组织边界约束（默认同机构/同部门）
3. **具备最小必要读权限**：接收人对该 `business_key` 对应的业务数据具备最小必要的读取权限

### 7.3 Flowable API 调用

```
TaskService.setAssignee(taskId, targetEmpId)
```

### 7.4 审计要求

转交必须记录以下审计信息：

| 审计字段 | 说明 |
|:---|:---|
| taskId | 任务ID |
| processInstanceId | 流程实例ID |
| nodeKey | 节点ID |
| businessKey | 业务键 |
| fromEmpId | 原处理人工号 |
| toEmpId | 接收人工号 |
| reason | 转交原因（必填） |
| operatorEmpId | 操作人工号（可能与 from 不同，如管理员强制转交） |
| operateTime | 操作时间 |

### 7.5 红绿灯计时规则

**转交不得重置红绿灯计时**。任务的 `taskCreateTime`（到达节点时间）保持不变，SLA 计算继续从任务创建时间起算。

## 8. 红绿灯超时预警

### 8.1 配置粒度

以 **`(流程定义 Key, 节点 ID)`** 为最小配置单元，存储在 `wf_timeout_rule` 表中。

| 配置项 | 说明 |
|:---|:---|
| process_definition_key | 流程定义 KEY（如 `loan_approve_v1`） |
| node_key | 节点 ID（如 `task_credit_review`） |
| warning_hours | 黄灯阈值（工作小时数），到达后状态变为 YELLOW |
| timeout_hours | 红灯阈值（工作小时数），到达后状态变为 RED，必须大于 warning_hours |

### 8.2 计算机制

**定时任务（每 30 分钟执行一次）批量扫描所有进行中的任务节点**：

```
1. 查询所有 status=RUNNING 的 biz_process_map 记录
2. 对每条记录，获取当前任务节点的 taskCreateTime（到达节点时间）
3. 调用 system-governance-center 的工作日历接口，剔除非工作日
4. 计算工作时间差 = 当前时间 - taskCreateTime（仅计算工作日工作时间）
5. 与 wf_timeout_rule 中的阈值比较，确定 SLA 状态：
   - 工作时间差 < warning_hours -> GREEN（正常）
   - warning_hours <= 工作时间差 < timeout_hours -> YELLOW（预警）
   - 工作时间差 >= timeout_hours -> RED（超时）
```

### 8.3 状态展示位置

| 展示位置 | 说明 |
|:---|:---|
| 待办列表 | slaStatus 字段，以颜色标识展示 |
| 任务处理页面 | 任务概览区展示黄灯预警时间、红灯超时时间具体时间点 |
| 客户详情历史 TAB | 资产投放历史、中场支持历史中的"节点状态"列展示红绿灯 |

### 8.4 边界条件

- 已完成的任务不参与扫描
- 转交后红绿灯计时不重置（以 `taskCreateTime` 为准）
- 工作日历变更后，下一次定时扫描自动生效

## 9. 节点表单权限

### 9.1 配置模型

每个节点通过 `wf_node_form_conf` 绑定一套表单字段配置：

| 配置项 | 类型 | 说明 |
|:---|:---|:---|
| form_fields | JSON | 该节点展示的所有字段集合（全量字段定义） |
| editable_fields | JSON 数组 | 该节点可编辑的字段列表 |
| required_fields | JSON 数组 | 该节点必填的字段列表 |

### 9.2 字段权限规则

| 用户角色 | 权限 |
|:---|:---|
| 流程参与者（WORKFLOW_PARTICIPANT） | **只读**：可查看 form_fields 中的所有字段，不可编辑 |
| 当前节点 assignee | **可编辑**：可编辑 editable_fields 中的字段；必填 required_fields 中的字段 |
| 候选人（未签收） | **不可编辑**：即使在候选组中，未签收前只能查看不能编辑 |

### 9.3 办理权判定

**节点办理权必须以 Flowable runtime task 为准**，不得仅依据业务表中的 `assigned_emp_id` 等字段推导。具体判定链路：

```
1. 通过 taskId 查询 ACT_RU_TASK，确认任务存在且未完成
2. 确认 ACT_RU_TASK.ASSIGNEE_ = 当前用户
3. 通过 wf_node_form_conf 获取节点表单配置
4. 校验提交数据是否满足 required_fields
5. 校验提交数据是否仅包含 editable_fields 中的字段
```

## 10. 流程发起标准

### 10.1 发起顺序（强制）

业务模块提交流程类 `WRITE` 接口时，**必须按以下顺序执行**：

```
步骤 1：业务模块完成 RBAC 权限校验（PT_RESOURCE 鉴权）
步骤 2：业务模块完成 DATA_SCOPE 数据范围校验
步骤 3：业务模块完成业务状态守卫校验（如线索状态必须为 DRAFT）
步骤 4：业务模块完成表单校验（必填字段、字典值、唯一性等）
步骤 5：业务模块保存/更新业务主表数据
步骤 6：业务模块调用 WorkflowApi.startProcess(StartProcessCmd) 发起流程
步骤 7：workflow-center 校验 business_key 唯一性与流程定义有效性
步骤 8：workflow-center 调用 IdentityService.setAuthenticatedUserId(startUser)
步骤 9：workflow-center 使用 RuntimeService.createProcessInstanceBuilder() 启动流程
步骤 10：workflow-center 写入/更新 biz_process_map
步骤 11：业务模块回写业务主表状态（如 lead_status = IN_APPROVAL）
```

> 步骤 6-10 在同一个事务中执行（嵌入式 Flowable 共用应用数据源）。

### 10.2 StartProcessCmd 参数

| 字段 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| bizType | String | 是 | 业务类型（LEAD / LOAN / SUPPORT / TOUCH 等） |
| bizId | String | 是 | 业务对象ID |
| businessKey | String | 是 | 格式 `BIZ_TYPE:{id}`，如 `LEAD:12345` |
| processDefinitionKey | String | 是 | 流程定义 KEY（如 `lead_approve_v1`） |
| startUser | String | 是 | 发起人工号 |
| startOrgId | String | 是 | 发起人机构代码 |
| title | String | 是 | 流程标题（展示在待办列表） |
| variables | Map<String,Object> | 否 | 额外流程变量 |

### 10.3 校验规则

workflow-center 在启动流程前进行以下校验：

1. **流程定义存在且已发布**：`processDefinitionKey` 必须在 Flowable 中存在且状态为激活，否则返回 `WF-40401`
2. **business_key 唯一**：`biz_process_map` 中不存在相同 `business_key` 且 `status=RUNNING` 的记录，否则返回 `WF-40901`

## 11. 流程结束与事件

### 11.1 事件发布机制

**V1 使用事务后事件**（`@TransactionalEventListener(phase = AFTER_COMMIT)`）。

| 层级 | 职责 |
|:---|:---|
| Flowable 监听器 | 刷新 `biz_process_map`（status / end_time 等）、记录流程侧元数据、准备通知上下文 |
| 事务内 | 以上操作与 Flowable 引擎操作在同一事务中 |
| 事务提交后 | 发布对外领域事件 `workflow.process.completed.v1` |
| 业务模块 | 消费事件后自行回写最终状态（如 `lead_status = APPROVED`） |

### 11.2 事件清单

| 事件名称 | 发布时机 | 消费方 |
|:---|:---|:---|
| `workflow.process.completed.v1` | 流程实例结束（正常完成/取消） | customer-marketing-center, business-application-center, performance-engine-center, portal-content-center |
| `workflow.task.created.v1` | 新待办任务创建 | portal-content-center（生成通知） |
| `workflow.task.completed.v1` | 单个任务节点完成 | portal-content-center（更新通知） |

### 11.3 流程结束通知

流程结束后，系统应向以下人员发送通知：
- 发起人：告知流程最终结果（通过/驳回/取消）
- 最后处理人：告知流程已结束
- 相关参与人（可选）：根据业务需要扩展

## 12. 业务流程映射（biz_process_map）

### 12.1 表结构

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| id | VARCHAR(32) | 映射ID（主键） |
| business_key | VARCHAR(100) | 业务键，**V1 必须唯一**（UK） |
| biz_type | VARCHAR(50) | 业务类型：LEAD / LOAN / SUPPORT / TOUCH / TARGET_ADJUST / ALLOC_ADJUST |
| biz_id | VARCHAR(100) | 业务对象ID |
| process_definition_key | VARCHAR(100) | 流程定义 KEY |
| process_instance_id | VARCHAR(64) | Flowable 流程实例ID（UK） |
| current_task_id | VARCHAR(64) | 当前任务ID（运行中才有） |
| current_node_id | VARCHAR(64) | 当前节点 BPMN Node ID |
| current_assignee | VARCHAR(32) | 当前处理人工号 |
| candidate_groups | TEXT | 当前节点候选组（JSON 数组） |
| start_user | VARCHAR(32) | 发起人工号 |
| start_time | DATETIME | 流程发起时间 |
| end_time | DATETIME | 流程结束时间 |
| process_status | VARCHAR(50) | 流程状态：RUNNING / COMPLETED / CANCELLED |
| created_time | DATETIME | 记录创建时间 |
| updated_time | DATETIME | 记录更新时间 |

### 12.2 索引

|:---|:---|:---|
| uk_business_key | business_key | UNIQUE |

| idx_start_user | start_user | 普通 |
| idx_current_assignee | current_assignee | 普通 |

### 12.3 核心用途

1. **待办/已办列表查询**：通过 `biz_process_map` 关联业务信息，展示待办列表中的业务类型、标题、发起人等
2. **WORKFLOW_PARTICIPANT 判定**：通过 `start_user`、`current_assignee` 等字段判断参与者关系
3. **BizType 动态解析**：通过 `business_key` 前缀定位业务域，再映射到真实权限 `BizType`
4. **流程审计与历史追溯**：完整记录流程全生命周期的状态变化

## 13. 客户并行流程规则

### 13.1 核心规则

**V1 允许一个客户同时存在多个进行中的流程。**

例如：同一客户可以同时存在进行中的触达任务和中场支持流程。

### 13.2 发起提示

发起新流程时，系统**必须检查**该客户是否存在其他进行中的流程：
- 如果存在，在页面给出明确提示：**"该客户当前已有进行中的【XX 流程】，请确认是否继续发起？"**
- 该提示**仅用于告知与二次确认，不做拦截**
- 用户确认后可继续发起

### 13.3 V1 约束说明

- **不做互斥锁**：不限制同一客户同时只能有一个流程
- **不做去重限制**：不限制同一客户同类型流程的并行数量
- **风险由业务方承担**：并行带来的重复触达与数据并发风险由业务方自行承担

### 14.4 BizType 解析规则（V1 冻结）

`/api/workflow/tasks/**` 统一办理入口**不得固定映射为单一 BizType**，必须先由 `taskId -> business_key` 定位业务域，再结合任务节点类型或入口视图映射真实权限 BizType：

| business_key 前缀 | 默认 BizType | 特殊规则 |
|:---|:---|:---|
| `LEAD:*` | LEAD | -- |
| `TOUCH:*` | TOUCH_TASK | -- |
| `LOAN:*` | LOAN | -- |
| `SUPPORT:*` | SUPPORT | 承接部门秘书派单节点与支持人员办理节点使用 SUPPORT_DEPT |
| `TARGET_ADJUST:*` | PERF_CONFIG | -- |
| `ALLOC_ADJUST:*` | PERF_CONFIG | -- |
