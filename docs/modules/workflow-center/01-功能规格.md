# 工作流中心——功能规格

## 1. 定位与边界

`workflow-center` 是系统唯一的 Flowable 集成边界。业务模块只通过本模块
`api/` 下的 `WorkflowApi`、`WorkflowQueryApi`、`TodoQueryApi` 和公开事件协作，
不得直接调用 Flowable 服务、读取 `ACT_*` 表或依赖本模块内部实现。

本模块负责：

- 启动、查询、办理、撤回和取消流程实例；
- 统一待办、已办、流程历史、节点和流程图查询；
- Flowable 任务候选解析、签收和审批；
- 两阶段任务转交及其状态、通知和审计；
- 节点候选人、表单字段、超时规则和设计器流程配置；
- `BIZ_PROCESS_MAP` 业务键映射、`WF_PROCESS_ORG` 机构快照；
- 在流程完成或撤回时发布跨模块公开事件。

本模块不持有业务主单，不回写业务模块私有表，不承担业务表单业务校验，也不取代
`auth-permission-center` 的用户、组织和权限权威。

## 2. 流程实例与业务映射

### 2.1 业务键和生命周期

业务模块在保存主单、完成自身状态和权限校验后调用 `WorkflowApi.startProcess`。
业务键必须在业务域内稳定且唯一，推荐格式为 `BIZ_TYPE:bizId`。同一业务键只能有一
个 `RUNNING` 实例；已结束实例可按业务策略重新发起，映射记录由工作流中心维护。

启动时写入或更新 `BIZ_PROCESS_MAP`，至少关联：业务键、业务类型、业务 ID、流程定义
键、流程实例 ID、发起人、标题、当前处理人/候选组、流程状态和起止时间。启动用户和
机构由当前用户上下文补齐，调用方不应以请求体伪造。

当前状态使用：

| 状态 | 含义 |
| --- | --- |
| `RUNNING` | 流程仍有运行时实例或待处理任务 |
| `COMPLETED` | 流程自然结束；下游审批结论通常为 `APPROVED` |
| `CANCELLED` | 流程被撤回、取消或驳回终止；下游结论可为 `REJECTED` |

`processStatus` 是流程生命周期，不能与事件 `outcome` 或表单变量 `approved` 混用。
`WorkflowApi.getProcessOutcome` 在历史变量可确定结论时返回 `APPROVED`、`REJECTED`，
否则返回空值；调用方应先确认映射状态。

### 2.2 流程定义

运行时流程定义由 Flowable Repository/Runtime/Task/History 服务管理。当前 classpath
BPMN 配置目录由应用配置决定，仓库内可见的静态定义为：

- `lead_approve_v1.bpmn20.xml`：发起、审核、审批/拒绝分支和结束；
- `loan_approve_v1.bpmn20.xml`：多级审核、排他网关和审批/拒绝结束。

设计器流程以 `flowKey` 保存图模型，发布时生成 `DSN_<flowKey>` 流程定义键；已发布
流程的运行实例仍绑定其定义版本，修改图模型不能改变在途实例的定义。设计器发布是
完整图替换，必须先通过节点、边、候选和条件校验。

## 3. 待办和已办

### 3.1 待办

待办来源是 Flowable 运行时任务和身份链接。查询结果按当前员工过滤：

- 已分配任务只对 `assignee` 对应员工可办理；
- 未分配任务依据运行时 `USER:`、`ROLE:`、`ORG:` 身份链接及本系统候选组解析，
  命中当前员工的候选用户/候选组时显示为可领取；
- 候选组语义来自本系统权限和组织数据，不以 Flowable IDM 作为权限权威；
- 空员工、未知候选组或权限查询异常必须返回空结果或拒绝，不能放大可见范围。

待办查询提供页码、业务类型和关键字参数；返回 `TaskRespDTO`，包含任务/流程 ID、
业务键、业务类型和 ID、标题、发起人及机构展示信息、节点、到达时间、处理人、候选组、
SLA 状态和 `claimable`。`claimable` 是展示提示，办理接口仍必须在服务层重做鉴权。

### 3.2 已办

已办基于 Flowable 历史任务和本模块历史映射查询。结果包含待办基础字段以及办理完成
时间、审批结果和意见。流程历史、节点进度、流程图和任务详情是只读查询；业务模块
不得绕过工作流查询接口读取 `ACT_HI_*`。

Flowable history level 至少为 `audit`，以支持历史任务、身份链接、评论和流程变量的
回溯。流程参与者查询只返回有历史参与记录或当前用户候选组命中的业务键，并受调用
方传入的流程键前缀、时间窗口和数量上限约束。

## 4. 任务办理

### 4.1 签收

未分配任务可调用 `POST /api/workflow/tasks/{taskId}/claim`。签收成功后由 Flowable
设置 `assignee`，并同步 `BIZ_PROCESS_MAP.currentAssignee`；候选组快照保留，便于后续
转交资格判断。任务已签收、任务不存在或有待接收转交时分别返回相应业务错误。

候选资格必须在服务层基于运行时身份链接和权限数据核验。当前代码的签收路径还需与
统一候选校验门禁保持一致；文档中的 `claimable` 不能作为安全授权。

### 4.2 审批

`POST /api/workflow/tasks/{taskId}/approve` 接收可选意见和节点表单/路由变量。服务层
校验当前员工是任务处理人或有效候选人、任务未被转交锁定，并将审批意见、表单数据和
`approved=true` 写入 Flowable 后完成任务。变量必须在多实例或网关路由计算前写入。

节点表单配置由 `WF_NODE_FORM_CONF` 提供可见、可编辑和必填字段集合；业务主单的领域
校验仍由业务模块负责。当前审批实现将 `formData` 作为流程变量传入，前端展示权限和
服务层资源/业务权限必须分开判断。

### 4.3 驳回

`POST /api/workflow/tasks/{taskId}/reject` 要求非空意见。当前驳回路径终止运行时实例、
将映射置为 `CANCELLED`，并发布 `ProcessCompletedEvent(outcome=REJECTED)`；它不是一
个任意运行时跳转。若流程需要“退回修改”，应在 BPMN/设计器图中显式建模分支和条件。

## 5. 两阶段任务转交

### 5.1 状态和接口

转交是“发起—接收方决策”流程，而不是直接替换 assignee：

1. 当前处理人（未签收任务时为当前合法候选人）提交接收员工和必填原因，生成
   `PENDING_ACCEPT` 记录；
2. 接收方可接受或拒绝，发起方可在待决策时取消；
3. 接受后才设置 Flowable assignee、更新映射和机构快照；拒绝/取消只结束转交请求。

待接收期间原任务被锁定，不能签收、审批、驳回或再次发起转交。底层任务已消失时转交
记录标记为 `INVALIDATED` 并报告任务已失效。状态更新使用乐观条件，重复决策不能覆盖
已处理状态。

### 5.2 资格和审计

接收人必须由服务端依据运行时候选身份链接（无链接时才可使用节点候选配置兜底）解析，
且与发起人的主机构满足当前组织边界。接收员工不能是发起人本人。未签收任务允许将
`fromEmpId` 置空，表示候选任务的定向分配。

转交接口：

- `POST /api/workflow/monitor/tasks/{taskId}/transfer` 发起；
- `GET /api/workflow/monitor/tasks/{taskId}/transfer-candidates` 查询候选；
- `GET /api/workflow/monitor/processes/{processInstanceId}/transfers` 查询流程历史；
- `GET /api/workflow/transfers/inbox`、`/outbox` 查询收件箱/发件箱；
- `POST /api/workflow/transfers/{id}/accept|decline|cancel` 完成接收方或发起方决策。

发起、接受、拒绝和取消都必须保留原因、操作人、节点、接收人、状态和时间，并通过
独立资源授权与审计链路保护。

## 6. 监控、表单和 SLA

### 6.1 流程监控

`GET /api/workflow/monitor/processes` 按状态、业务类型、关键字和发起人分页查询。
机构数据范围由统一 `DataScopeContext` 提供：`ALL`、本机构或机构树按范围过滤；未知、
空值、无法解析的范围和不支持的范围 fail close。监控查询只读 `BIZ_PROCESS_MAP`，并
通过 `WF_PROCESS_ORG` 机构快照扩大到流程参与机构；快照记录失败不能阻断主流程操作。

### 6.2 节点配置

管理员可按流程定义键和节点维护：

- 候选类型和值、审批机构范围；
- 表单字段、可编辑字段、必填字段；
- 预警小时数和超时小时数。

运行时任务候选身份链接优先于静态配置。并行审批必须保持“组间 AND、组内 OR”，
`GROUP_ALL` 不能被压平成全局任意一人。

### 6.3 SLA

任务查询时根据 `WF_TIMEOUT_RULE` 和治理模块 `CalendarApi` 工作日计算红黄绿状态：
无规则为 `GREEN`，超过超时阈值为 `RED`，达到预警阈值为 `YELLOW`，其余为 `GREEN`。
工作流中心不自建 Quartz 调度器、缓存或另一套日历实现；需要调度时遵循治理模块边界。

## 7. 事件和跨模块协作

对外公开事件仅位于 `workflow.api.event`：

| 事件 | 发布时机 | 关键语义 |
| --- | --- | --- |
| `ProcessCompletedEvent` | 流程自然完成或审批驳回终止 | `outcome` 为 `APPROVED`/`REJECTED`，`reason` 可空 |
| `ProcessWithdrawnEvent` | 申请人/授权人撤回流程 | 包含撤回人、撤回时当前处理人（可空）和意见 |

事件中的 `outcome` 与 `BIZ_PROCESS_MAP.processStatus` 独立。下游监听器必须幂等，并按
自身事务更新业务主表；不得依赖工作流内部监听器、内部事件或 Flowable 表。

业务模块调用顺序、权限、数据范围、表单校验和失败补偿由各自模块负责。工作流中心
只公开稳定 API/DTO/事件，具体实现、Mapper、Entity 和内部 Service 不构成跨模块契约。

## 8. 当前验收要点

- 业务键运行中唯一，映射状态与 Flowable 实例一致；
- 待办/已办只显示调用者有权访问的任务，办理时再次服务端鉴权；
- 审批变量先于网关/多实例路由写入，驳回与完成事件结论不混淆；
- 转交的待接收锁、组织/候选校验、乐观状态更新和失效标记有效；
- 监控范围 fail close，机构快照写入失败不影响主操作；
- REST 资源、管理员配置、设计器发布和转交操作均有独立授权及必要审计；
- Flowable 运行时和历史由工作流中心封装，其他模块无直接引擎依赖。
