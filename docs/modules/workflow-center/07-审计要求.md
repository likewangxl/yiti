# 工作流中心——审计要求

## 1. 审计边界

工作流操作同时产生两类留痕：

1. Flowable 历史任务、评论、身份链接和变量，用于流程进度和审批历史查询；
2. 平台治理审计，用于操作者、资源、请求和高危变更的合规追踪。

两者用途不同，任何一类都不能替代另一类。业务模块的主单状态和业务审计由业务模块
负责；工作流中心不直接修改业务私有表。

## 2. 高危 REST 操作

### 2.1 当前显式审计覆盖

`TaskTransferController` 当前通过 `@AuditLog` 覆盖：

| 操作 | 路径 | action/resourceType | 原因 |
| --- | --- | --- | --- |
| 发起转交 | `POST /api/workflow/monitor/tasks/{taskId}/transfer` | `TRANSFER` / `WORKFLOW_TASK` | 必填 |
| 接受转交 | `POST /api/workflow/transfers/{id}/accept` | `TRANSFER_ACCEPT` / `WORKFLOW_TASK` | 可选 |
| 拒绝转交 | `POST /api/workflow/transfers/{id}/decline` | `TRANSFER_DECLINE` / `WORKFLOW_TASK` | 必填 |
| 取消转交 | `POST /api/workflow/transfers/{id}/cancel` | `TRANSFER_CANCEL` / `WORKFLOW_TASK` | 可选 |

发起时记录任务、流程、来源/接收人和转交原因；拒绝记录拒绝原因；接受/取消记录决策
操作者和状态。转交状态本身仍以 `WF_TASK_TRANSFER` 为准，审计记录用于追踪请求上下文。

### 2.2 必须纳入审计的操作

以下操作是独立资源授权和审计设计的要求：

- 流程提交、撤回/取消、签收、审批和驳回；
- 管理员候选人、节点表单和超时规则新增/修改；
- 设计器草稿保存、删除、发布和内置流程导入；
- 转交候选名单查询、转交历史查询等敏感监控读操作。

当前源码显式 `@AuditLog` 主要集中在转交端点；其余端点若未接入通用切面或服务级审计，
不能在文档或验收报告中宣称已经完成审计覆盖，应由实现任务补齐并单独验证。审计切面
默认在方法成功返回后记录，失败操作如需留痕必须设计服务级失败审计链路。

## 3. 记录内容

平台审计应使用 common AOP 与治理审计处理器，至少能关联：

- `traceId`、时间、操作者员工/机构、IP、User-Agent；
- 业务类型、动作、资源类型/ID、请求 URL/方法和脱敏参数；
- 响应状态、耗时、错误信息（如失败审计链路已启用）；
- 操作原因，以及配置变更需要的 before/after 快照或新增/移除集合。

请求参数中的手机号、证件号、账号、金额、凭据、完整表单和其他敏感字段必须按平台
规则脱敏。审批意见、转交原因、业务键和流程变量也不得原样写入普通应用日志；日志
仅保留定位所需的最小摘要。

审计表的保留、访问、导出和脱敏策略服从 `system-governance-center` 及合规要求；本模块
不另建审计表、不定义固定保留年限。

## 4. Flowable 历史留痕

### 4.1 评论和动作

任务办理在引擎历史中记录节点、操作人、动作、意见和时间：

- 审批通过写 `APPROVE` 评论；空审批意见使用服务端默认留痕文案；
- 驳回写必填 `REJECT` 评论，随后终止流程；
- 签收、转交发起/接受/拒绝等任务操作写对应评论；
- 流程完成/驳回的业务结论通过公开事件传递，不从评论文本猜测。

Flowable history level 至少为 `audit`。`GET /api/workflow/processes/{id}/history` 只经
工作流服务读取历史，返回 `ApprovalLogDTO`，不把 `ACT_HI_*` 暴露给调用方。

### 4.2 结论和状态

`ProcessCompletedEvent.outcome` 使用 `APPROVED`/`REJECTED`；
`BIZ_PROCESS_MAP.processStatus` 使用 `RUNNING`/`COMPLETED`/`CANCELLED`。驳回会话在
流程终止前写评论并发布 `REJECTED` 事件；撤回发布 `ProcessWithdrawnEvent`。两组值不能
混为同一个审计字段。

## 5. 权限、失败与幂等

- 审计入口与业务资源分离，不能因前端隐藏按钮而省略服务层目标实体校验；
- 查询、详情、监控、转交历史和审计读取都遵循统一认证和数据范围；未知范围 fail close；
- 转交决策先以条件状态更新确定唯一胜者，再进行引擎变更/通知；重复请求记录冲突结果；
- 机构快照是旁路投影，写入失败记录告警但不能伪造“主操作已失败”；
- 事件消费者和审计补偿按业务键/流程实例或转交 ID 幂等，不依赖应用日志去重；
- 审计写入失败是否回滚主操作取决于通用切面或服务级审计配置，新增高危路径必须明确这一点。

## 6. 验收清单

- 逐个 REST 方法都有资源注册，管理员、监控和转交动作有独立权限；
- 转交四个动作的 `action`、资源类型、原因要求和状态可追溯；
- 提交、办理、驳回、撤回、配置和设计器发布的审计覆盖已通过源码/运行态核对；
- Flowable 历史能还原节点动作和意见，流程结论能由事件/变量确定；
- 普通日志和审计参数无明文敏感数据；
- 失败操作、并发冲突、重复事件和通知失败的处理边界有证据，不以“接口返回 200”代替审计验收。
