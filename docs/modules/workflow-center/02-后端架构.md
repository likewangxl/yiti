# 工作流中心——后端架构

## 1. 架构决策

### 1.1 唯一引擎边界

`workflow-center` 是系统唯一直接使用 Flowable 的模块。Flowable 的运行时、任务、身份
链接、历史、仓储和管理服务只能在本模块内部出现；其他模块不得依赖 Flowable 类型、
`ACT_*` 表、工作流 Mapper/Entity 或内部 Service。

跨模块只暴露 `workflow.api` 下稳定的 `WorkflowApi`、`WorkflowQueryApi`、`TodoQueryApi`
及 `workflow.api.event` 的公开事件和 DTO。业务模块保存自己的业务数据并负责业务状态、
表单和数据范围校验，流程中心只维护流程状态与业务键映射。

### 1.2 依赖方向

```text
业务模块 ──> workflow.api
workflow-center ──> common + auth-permission-center + system-governance-center
workflow-center ──> Flowable 引擎
```

工作流中心不得反向依赖业务模块，也不作为业务模块之间的查询中转层。认证、用户、组织、
数据范围、审计、通知和工作日日历复用平台公共 API；不在工作流中心复制这些能力。

## 2. 分层与职责

保持 `api / controller / facade / service / mapper / entity / config` 分层：

| 层 | 责任与边界 |
| --- | --- |
| `api` | 跨模块接口、命令/查询 DTO、公开事件；不暴露引擎对象 |
| `controller` | REST 入参校验、统一响应和资源注解；不直接操作引擎表 |
| `facade` | 对外 API 的适配和跨模块调用边界；协调工作流服务 |
| `service` | 流程启动、任务办理、转交、查询、监控、设计器发布和配置校验 |
| `mapper/entity` | 本模块映射表的持久化；Flowable 表只经引擎服务访问 |
| `config` | 引擎与平台集成配置；不建立第二套引擎或权限配置 |

Service 的公共方法说明业务不变量和失败语义；复杂逻辑说明原因。DTO 是契约的一部分，
实现类、Mapper 和实体不是跨模块依赖面。

## 3. Flowable 集成

### 3.1 引擎与配置

Flowable starter 提供引擎自动配置；工作流模块不重复创建 Runtime/Task/History 等引擎
Bean。当前应用配置要求：

- `history-level: audit`，用于历史任务、评论、身份链接和变量回溯；
- BPMN 扫描位置由应用配置的 classpath BPMN 前缀和后缀决定；
- Flowable IDM 关闭，用户、角色、组织和候选组由认证权限中心提供；
- 引擎与本模块表使用平台配置的数据源和事务管理；
- schema 初始化/更新配置只服从部署环境治理，不在代码中引入 Flyway 或版本迁移。

引擎表属于 Flowable 所有；本模块的 `BIZ_PROCESS_MAP`、配置表、机构快照和转交表由本
模块维护。业务模块不能直接 join 任一方的私有表。

### 3.2 流程键和变量

业务流程以稳定 `businessKey` 启动，格式和运行中唯一约束由启动服务保证。设计器发布的
流程定义键为 `DSN_<flowKey>`，启动方通过 `WorkflowApi.resolveDesignerProcDefKey`
读取已发布键；未发布不能静默回退到另一流程。

审批意见、`approved` 和节点表单/路由变量必须在任务完成前写入引擎。网关、条件和多实例
只读取已写入的流程变量，不通过业务模块直读表补算。

### 3.3 设计器发布

设计器图由流程定义、节点、边、审批人和条件组成。发布流程固定为：读取完整图、校验
可达性和条件、生成 BPMN、部署 Flowable、更新本模块发布元数据和候选配置。保存/更新
采用完整图替换；已发布导入定义标记为只读，草稿删除不能影响已启动实例。

在途实例绑定启动时的流程定义版本。发布新版本只影响后续启动，除非另有经过评审的迁移
方案；工作流文档不把迁移历史或未来迁移脚本视为当前契约。

## 4. 任务、候选人与机构快照

### 4.1 候选解析

Flowable 任务身份链接是运行时事实；`USER:`、`ROLE:`、`ORG:` 等候选值通过认证权限
中心解析。节点候选配置是无运行时链接时的受控兜底和管理员配置来源。未知员工、组织、
角色或解析异常必须 fail close。

审批组的逻辑保持“组间 AND、组内 OR”；`ANY`、`ALL`、`GROUP_ALL` 是流程节点的业务
语义，不能由查询层压平成单一候选集合。

### 4.2 机构快照与监控

`WfProcessOrgService` 是 `WF_PROCESS_ORG` 的唯一写入口。启动、候选分配、签收、审批、
转交等运行路径按实际发现记录机构，写入失败只记录告警，不回滚 Flowable 主操作。监控
查询从统一 `DataScopeContext` 获取范围，再使用机构快照过滤 `BIZ_PROCESS_MAP`；未知或
无法解析范围返回空结果。

## 5. 任务转交架构

任务转交由独立服务和表承载，采用 `PENDING_ACCEPT`、`ACCEPTED`、`REJECTED`、`CANCELLED`
及底层任务消失后的 `INVALIDATED` 状态。数据库保证同一活动任务只有一个待接收请求，
状态决策使用带当前状态条件的更新。

发起转交只创建待决策记录，不立即改变 Flowable assignee；待决策期间原任务操作被锁定。
接受时在同一业务操作中设置 assignee、更新映射、写机构快照和通知发起人；拒绝/取消只
关闭请求。接收人资格、主机构边界、本人排除和转交原因均在服务层校验。

## 6. 事务与一致性原则

- 启动、审批、驳回和转交的关键引擎命令与本模块映射更新必须保持同一命令事务语义；
- Flowable 自身的乐观锁负责运行时任务/执行并发；重复办理返回业务错误，不伪装成成功；
- `BIZ_PROCESS_MAP` 的业务键唯一性与行锁共同防止并发重复启动；
- 转交状态采用数据库条件更新，任务不存在时显式失效；
- 机构快照和通知属于旁路效果，不应破坏主流程命令；其失败按平台治理记录；
- 对外事件载荷只位于 `api.event`。消费者必须幂等并在自身事务中处理，不假设工作流内部
  Service 或引擎事务边界。

## 7. 平台能力复用

| 能力 | 归属 | 工作流中心使用方式 |
| --- | --- | --- |
| 当前用户、用户、组织和候选组 | `auth-permission-center` | 解析当前员工、主机构、角色/组织候选及展示信息 |
| 数据范围、认证、RBAC、统一响应和追踪 | `common`/认证权限中心 | REST 门禁、服务层二次校验、监控范围和调用上下文 |
| 工作日日历 | `system-governance-center` | `CalendarApi` 计算任务 SLA |
| 通知 | `system-governance-center` | 转交决策和任务分配通知 |
| Quartz 调度 | `system-governance-center` | 工作流不自建调度器；只有治理模块可注册调度 |

不能以缓存、ThreadLocal 或另一套本地表替代这些平台权威。无会话 API 的 `*ByEmp` 方法
由调用方负责外部认证和授权，工作流服务按显式员工 ID执行既定业务校验。

## 8. 运行配置和验收边界

启动入口是 `bootstrap`；端口、数据源、Flowable 和平台集成配置以
`bootstrap/src/main/resources/application*.yml` 为准。变更工作流 Controller、API、
DTO、错误码或资源时，应同步接口文档、`PT_RESOURCE` 并运行契约检查。

架构验收至少确认：其他模块无 Flowable/私有表依赖；业务键唯一；候选和监控 fail close；
转交锁和乐观状态有效；事件和审计路径可追溯；配置、设计器发布和历史查询使用当前
引擎配置。具体 HTTP 报文见 `03-接口设计与报文.md`，跨模块 Java 契约见
`04-对外API契约.md`。
