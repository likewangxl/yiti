# 客户营销中心 — 审计要求

> 本文档定义客户营销中心所有需审计的高危动作、审计记录格式、必填字段、审计级别和特殊审计要求。
> 审计实现统一通过 `@BizAuth` 注解自动触发，审计日志写入 `PT_AUDIT_LOG` 表。
> 敏感字段（手机号、身份证、金额）在 after/before 快照中必须脱敏后存储。

---

## 1. 高危动作清单

### 1.1 按业务域分类

#### 1.1.1 线索管理

| 接口 | HTTP 方法 | URL | 动作 | 级别 | reason 必填 |
|---|---|---|---|---|---|
| 创建线索草稿 | POST | /api/leads | WRITE | 普通 | 否 |
| 提交线索审批 | POST | /api/leads/{id}/submit | WRITE | 敏感 | 否 |
| 批量导入线索（执行） | POST | /api/leads/import | IMPORT | **高危** | **是** |
| 删除线索草稿 | DELETE | /api/leads/{id} | DELETE | 敏感 | 否 |
| 线索审批通过（回调） | - | (Flowable ServiceTask) | APPROVE | 敏感 | 否 |
| 线索审批驳回（回调） | - | (Flowable ServiceTask) | REJECT | 敏感 | 否 |

#### 1.1.2 标签管理

| 接口 | HTTP 方法 | URL | 动作 | 级别 | reason 必填 |
|---|---|---|---|---|---|

| 更新标签 | PUT | /api/tags/{id} | UPDATE | 普通 | 否 |

| 停用标签 | POST | /api/tags/{id}/disable | UPDATE | 普通 | 否 |
| 标签批量打标（单个客户） | POST | /api/customers/{id}/tags | WRITE | 普通 | 否 |
| 标签客户批量导入 | POST | /api/tags/{id}/customers/import | IMPORT | **高危** | **是** |
| 标签客户导出 | GET | /api/tags/{id}/customers/export | EXPORT | **高危** | 否 |

#### 1.1.3 客户主档与池管理

| 接口 | HTTP 方法 | URL | 动作 | 级别 | reason 必填 |
|---|---|---|---|---|---|
| 客户列表导出 | GET | /api/customers/export | EXPORT | **高危** | 否 |
| 跨机构客户全量历史查询 | GET | /api/customers/{id}/history | READ | **特殊跨域** | 否 |
| 客户转交维护人 | POST | /api/customers/{id}/transfer | TRANSFER | **高危** | **是** |
| 客户删除申请 | POST | /api/customers/{id}/delete-apply | DELETE | **高危** | **是** |
| 客户删除审批通过（回调） | - | (Flowable ServiceTask) | DELETE | **高危** | 否 |

#### 1.1.4 认领与触达

| 接口 | HTTP 方法 | URL | 动作 | 级别 | reason 必填 |
|---|---|---|---|---|---|
| 客户认领 | POST | /api/customer-pool/{custId}/claim | WRITE | 敏感 | 否 |
| 取消认领 | POST | /api/claims/{claimId}/cancel | WRITE | 敏感 | **是** |
| 触达任务成功 | POST | /api/touch-tasks/{id}/success | WRITE | 敏感 | 否 |
| 触达任务取消 | POST | /api/touch-tasks/{id}/cancel | WRITE | 敏感 | **是** |
| 触达任务批量分配 | POST | /api/admin/touch-tasks/batch-assign | UPDATE | 敏感 | **是** |
| 管理员触达任务导出 | GET | /api/admin/touch-tasks/export | EXPORT | **高危** | 否 |

#### 1.1.5 跨机构营销

| 接口 | HTTP 方法 | URL | 动作 | 级别 | reason 必填 |
|---|---|---|---|---|---|
| 提交跨机构营销申请 | POST | /api/cross-org-marketing | WRITE | **敏感跨机构** | **是** |
| 跨机构营销审核通过 | POST | /api/cross-org-marketing/{id}/approve | APPROVE | **敏感跨机构** | **是** |
| 跨机构营销审核退回 | POST | /api/cross-org-marketing/{id}/reject | REJECT | **敏感跨机构** | **是** |

三项端点分别使用 `@AuditLog` 动作 `CREATE_CROSS_ORG_MARKETING`、
`APPROVE_CROSS_ORG_MARKETING`、`REJECT_CROSS_ORG_MARKETING`，且均设置
`reasonRequired=true`。`CrossOrgApplyCreateReqDTO.reason` 是申请原因；
`CrossOrgReviewReqDTO.reason` 在 approve 请求中是审批意见，在 reject 请求中是退回原因。
统一审计切面从请求 DTO 的 `getReason()` 提取文本写入 `PT_AUDIT_LOG.reason`；审批意见不写入
`CROSS_ORG_MARKETING_APPLY`，本功能不新增 DDL。

### 1.2 审计级别说明

| 级别 | 说明 | 留存期 | 告警 |
|---|---|---|---|
| 普通 | 常规写操作 | 1 年 | 无 |
| 敏感 | 涉及客户关系变更、流程操作 | 2 年 | 每日报表 |
| **高危** | 批量导入导出、删除、转交 | **5 年** | **实时 SMS + 次日报表** |
| **特殊跨域** | 跨机构访问 | **5 年** | 月度专项审计 |

## 3. 跨机构历史访问审计（特殊要求）

### 3.1 业务场景

- 总行/省分行运营人员需要查看某客户在全行范围内的历史行为数据
- 常规数据范围（DataScope）仅允许查看本机构认领的客户
- 通过独立接口 `GET /api/customers/{id}/history` 开放跨机构只读查询
- 该接口必须单独授权，单独审计

### 3.2 必须记录的字段

| 字段 | 类型 | 说明 |
|---|---|---|
| cust_id | 必须 | 被查询的客户ID |
| operator_emp_id | 必须 | 操作人工号 |
| operator_org_id | 必须 | 操作人所属机构 |
| operator_role | 必须 | 操作人角色（须为 TOTAL_BANK_ADMIN 或 PROVINCE_ADMIN） |
| access_time | 必须 | 访问时间 |
| viewed_tabs | 必须 | 访问的 TAB 范围（JSON数组） |
| cross_org_count | 必须 | 数据涉及的机构数量（用于统计跨域程度） |
| total_records | 必须 | 返回的记录总数 |
| reason | 可选 | 访问原因（建议必填，便于后续审计溯源） |

### 3.3 访问 TAB 列表

| TAB 标识 | 说明 |
|---|---|
| basic | 客户基础信息 |
| lead_history | 线索历史版本链 |
| claim_history | 历史认领记录（所有机构） |
| touch_log | 历史触达日志（所有机构） |
| touch_task | 历史触达任务（所有机构） |

### 3.4 审计日志示例

见 §2.15。

### 3.5 追溯与报表

- **月度专项审计**：每月 1 日生成上月跨机构访问报表，发送到合规/审计部门邮箱
- **异常检测**：同一操作人 1 小时内访问超过 20 个客户 → 触发实时告警
- **留存**：5 年，不可删除

### 3.6 数据脱敏

跨机构历史查询返回的字段不做脱敏（管理员需要完整信息），但审计日志中的 `after` 字段仅记录元数据（custId/recordsCount），不记录具体客户字段，防止审计日志本身成为敏感数据泄露源。

## 4. 触达日志幂等与审计

### 4.1 幂等与审计的关系

- 同一 `client_uuid` 首次成功提交：触发审计日志（action=TOUCH_LOG_SUBMIT）
- 同一 `client_uuid` 后续重复提交：**不产生**新的审计日志（返回已存在的日志ID，视为无变更）
- 审计去重依据：审计服务对 `eventId` 字段做幂等（eventId = business_key + request_id + action）

### 4.2 审计事件 ID 格式

```
AUDIT_EVENT:{action}:{business_key}:{client_uuid}
示例：AUDIT_EVENT:TOUCH_LOG_SUBMIT:TOUCH:TT_001:abc123def
```

### 4.3 触达日志提交审计

虽然触达日志提交是高频操作，但仍需审计（银行外勤合规要求）。记录级别设为"普通"，留存 1 年。

```json
{
  "action": "TOUCH_LOG_SUBMIT",
  "resource_type": "TOUCH_LOG",
  "resource_id": "TL_001",
  "business_key": "TOUCH:TT_001",
  "operator_emp_id": "E10001",
  "operator_org_id": "ORG_001",
  "request_time": "2026-03-06T15:28:00+08:00",
```

```java
@BizAuth(

    return ApiResult.ok(claimService.claim(custId));
```

### 5.2 敏感字段脱敏规则

在审计日志 `before/after` 的 JSON 快照中：

| 字段 | 脱敏规则 |
|---|---|
| contact_mobile | 保留前 3 位和后 4 位，中间 * 替代（如 `138****5678`） |
| unified_credit_code | 保留前 4 位和后 4 位（如 `9144****1234`） |
| credit_amount | 保留万元位（如 `500万元` 展示为 `500万`） |
| credit_exposure_amount | 同上 |
| 操作人姓名 | 只保留姓氏（如 `张*`） |

### 5.3 自动化脱敏

通过 `@DesensitizeField` 注解 + Jackson 序列化器在审计快照生成时自动脱敏：

```java
public class CustLeadAuditDTO {
    @DesensitizeField(type = DesensitizeType.MOBILE)
    private String contactMobile;

    @DesensitizeField(type = DesensitizeType.CREDIT_CODE)
    private String unifiedCreditCode;

    @DesensitizeField(type = DesensitizeType.AMOUNT_WAN)
    private BigDecimal creditAmount;
}
```

### 5.4 审计失败处理

- 审计写入失败**不影响业务主事务**（异步写入）
- 异步队列使用 Redis Stream，消费失败进死信队列
- 死信队列由定时任务每 5 分钟扫描重试，连续失败 3 次触发告警

```java
@Transactional(rollbackFor = Exception.class)
public void businessMethod() {
    // ... 业务逻辑 ...
    // 最后一步：发送审计事件（异步）
    auditEventPublisher.publish(AuditEvent.builder()
        .action("CLAIM")
        ...
        .build());
}
```

### 5.5 审计日志检索

管理员后台提供审计日志检索接口（属于 system-governance-center 的 AuditController）：

- 按 operator_emp_id 查询某人的所有操作
- 按 resource_type + resource_id 查询某客户的所有变更
- 按 action + level 筛选

## 7. 留存与归档

| 动作类型 | 留存期 | 归档策略 |
|---|---|---|
| 普通写操作 | 1 年 | 归档到冷存储，可按需恢复 |
| 敏感写操作 | 2 年 | 归档到冷存储 |
| 高危操作 | 5 年 | 归档到专用审计库，不可删除 |
| 跨机构访问 | 5 年 | 同上 |

### 7.1 归档脚本

```sql
-- 每月 1 日归档前 13 个月的普通审计日志
INSERT INTO audit_log_archive
SELECT * FROM pt_audit_log
WHERE level = 'NORMAL'
  AND created_time < DATE_SUB(NOW(), INTERVAL 13 MONTH);

DELETE FROM pt_audit_log
WHERE level = 'NORMAL'
  AND created_time < DATE_SUB(NOW(), INTERVAL 13 MONTH);
```

### 7.2 不可删除保证

高危和跨机构审计日志使用独立数据库实例 + 只读账号 + 审计日志权限控制，禁止任何人（包括 DBA）直接 DELETE/TRUNCATE。
