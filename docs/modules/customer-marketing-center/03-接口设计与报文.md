| 参数 | 说明 |
|---|---|
| bizType | 业务类型（TAG/LEAD/CUSTOMER/CUSTOMER_POOL/CLAIM/TOUCH_TASK/TOUCH_REPORT） |
| action | 动作（LIST/READ/WRITE/DELETE/TRANSFER/IMPORT/EXPORT） |

## A.6 POST /api/tags/{id}/customers/import — 标签关联客户批量导入

> **2026-07-19 订正（实现机制完全不同）**：真实端点是 `TagCustomerController.importCustomers`，
> **不是 Excel 上传 + 预览/确认二段式流程**，而是一次性 JSON 请求体直接传入客户 ID 列表，
> 服务端"先删后插"覆盖式写入，**没有 PREVIEW 模式，没有 confirmToken，没有 addCount/deleteCount/keepCount 统计**。

**权限**：`@BizAuth(bizType = TAG, action = IMPORT)`（源码未加 `highRisk = true`，但配置了 `@AuditLog(action = "IMPORT", resourceType = "TAG_CUSTOMER")`）
**描述**：覆盖式导入标签关联的客户列表——先 `deleteByTagId` 清空该标签全部旧关联，再批量插入本次传入的 `custIds`（`TagCustomerService.importCustomers`）
**Content-Type**：`application/json`

### 请求体 `TagCustomerImportReqDTO`
| 字段 | 类型 | 必填 | 校验 | 说明 |
|---|---|---|---|---|
| custIds | List\<String\> | 是 | `@NotEmpty` | 待导入的客户 ID 列表，覆盖式（完全替换旧关联） |

```json
{ "custIds": ["5001", "5002", "5003"] }
```

### 响应体
```json
{ "code": "0", "data": null }
```

### 业务规则（源码）
1. 标签必须存在，否则 `CUST-40401`
2. `custIds` 非空时逐一校验必须存在于 `CUST_MASTER`（先去重再比对），任一缺失则整批回滚，不做部分成功
3. `custIds` 为空列表时，仅清空旧关联，不报错

### 错误码
- `CUST-40401` 标签不存在（原文档写 `CUST-42202` 用于此场景，实为标签导入客户数据校验失败码）
- `CUST-42202` 客户 ID 列表中存在不属于 `CUST_MASTER` 的 ID（整批回滚）

> **2026-07-19 订正（未落地附录 K 规范）**：真实实现是简单同步 CSV 导出，**没有同步/异步分支，没有

### A.10.1 GET /api/tags/{id}/customers/import-template

- 下载 `xlsx` 模板，列为：客户名称、纳税人识别号（统一社会信用代码）、标签名称、标签说明。

### A.10.2 POST /api/tags/{id}/customers/import-file

**Content-Type**：`multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | File | 是 | `xlsx/xls`，最大 10MB，最多 5000 条 |
| mode | String | 是 | `APPEND` 追加；`REPLACE` 全量替换 |

- 统一社会信用代码作为客户唯一标识，必须能匹配 `CUST_MASTER`，且客户名称必须与主档一致。
- 文件中的标签名称必须与当前标签一致；重复统一代码按幂等处理并计入 `skippedCount`。
- 任一行有误时 `success=false`，`errors` 返回 Excel 行号、统一代码与错误原因，整批不入库。
- `APPEND` 保留原有有效关系；`REPLACE` 仅在整批校验通过后失效旧关系，再激活/写入本次客户。
- 关系存在性查询、历史关系恢复和多值 `INSERT` 均分批执行，每条批量 SQL 最多 500 行，不做逐客户查询/写入。
- 仅 `APPROVED + ACTIVE` 标签可执行，权限为 `TAG / IMPORT`，写操作记录导入审计日志。

## A.11 跨机构营销 `/api/cross-org-marketing`

- `GET /validate?custId=`：按客户 ID 或客户号执行四项规则。
- `POST /`：提交申请并通知原主办及原主办机构。请求体为 `CrossOrgApplyCreateReqDTO`，`custId` 必填，`reason` 必填且最多 500 字；申请原因同时写入申请业务表和审计记录。
- `GET /`、`GET /{id}`：申请列表与详情；普通用户只见本人，审核角色/管理员可见全量。
- `POST /{id}/approve`：审核通过，**请求体必传** `CrossOrgReviewReqDTO`，`reason` 为必填审批意见（最多 500 字）；通过后只创建申请人的触达任务。审批意见由统一 `@AuditLog` 审计切面提取并写入 `PT_AUDIT_LOG.reason`，不新增或写入跨机构申请业务表。
- `POST /{id}/reject`：审核退回，**请求体必传** `CrossOrgReviewReqDTO`，`reason` 为必填退回原因（最多 500 字），写入申请业务表的 `reject_reason` 并写入审计记录。
- 三个写/审核端点分别使用 `@AuditLog`：`CREATE_CROSS_ORG_MARKETING`、`APPROVE_CROSS_ORG_MARKETING`、`REJECT_CROSS_ORG_MARKETING`，均为 `reasonRequired=true`；审计切面从请求 DTO 的 `getReason()` 提取原因。

# K. 导出接口统一规范（附录）

本章节为本模块导出接口设定统一的同步/异步分支规则、文件命名、异步任务 DTO、列定义原则、错误码与审计要求，
目标是落地 `docs/common-dev-guide.md §8.2 第 5 条`（"超过 5000 行必须走异步导出"）。

> **2026-07-19 订正（重要，已知技术债）**：本模块当前实际有 **4 个**导出接口——A.7（标签客户导出）、
> D.6（客户导出）、H.3（管理后台触达明细导出）、H.7（触达报告导出，此前完全未收录）。**这 4 个真实
> 实现全部是同步 CSV 流式写出，均未落地本附录规范**：没有 5000/100000 行阈值判断、没有异步任务、
> 没有 `ExportTaskRespDTO`、没有 MinIO 上传、没有 §K.4 的字典翻译/金额精度/脱敏规则、文件名不遵循
> §K.2 格式。以下 K.1~K.7 内容保留作为设计目标/后续演进方向，**不代表任何导出接口的当前真实行为**——
> 各接口的真实响应格式、表头列、文件名请参阅 A.7/D.6/H.3/H.7 各自小节的"2026-07-19 订正"说明。

## K.1 同步 / 异步分支规则

| 命中行数 N | 处理方式 | 响应类型 | 说明 |
|---|---|---|---|
| N ≤ 5000 | 同步流式返回 | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | 直接 HTTP 流式写出，前端触发浏览器下载 |
| 5000 < N ≤ 100000 | 异步任务 | `R<ExportTaskRespDTO>` | 后端返回任务 ID，前端轮询任务状态 |
| N > 100000 | 拒绝 | `CUST-42207` | 引导用户增加过滤条件 |

**判定流程**：
1. 进入导出接口先执行一次 `SELECT count(*)` 取精确命中行数（走 DATA_SCOPE + cust_claim 过滤）
2. 按行数命中分支
3. 异步分支：写入 `sys_async_task`（governance 提供），状态 `PENDING → RUNNING → SUCCESS / FAILED`
4. 异步完成后：上传 Excel 到 MinIO，持久化 `file_object_id`，调用 `NotifyApi.sendUserNotify(empId, "导出完成", downloadUrl)`
5. 发布事件 `customer.export.completed.v1`（可选，供审计汇总消费）

## L.7 使用约定

1. 错误码通过 `new BizException(code, message)` 抛出，由全局异常处理器转换为统一响应结构（`ResponseWrapper`）
2. 所有高危操作（`@AuditLog(reasonRequired = true)` 标注的端点）失败也应留痕，即使被错误码拦截；具体
   端点是否配置了 `reasonRequired = true` 见 §J 矩阵"高危(reasonRequired)"列
3. "占位/否"标记的错误码当前不会真实出现，前端不需要为其编写专门的错误提示分支（编写了也不会触发）
4. 文档交叉引用：各接口的具体错误码触发条件见本文档对应接口段落；`CustomerErrorCode` 枚举源码是
   唯一权威来源，本表随源码变化需同步更新
