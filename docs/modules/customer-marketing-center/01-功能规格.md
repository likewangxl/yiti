## 1. 模块概述

### 1.1 模块定位
**客户营销中心（customer-marketing-center）** 是分行业务平台的**核心域模块**，覆盖客户营销全生命周期：

```
标签管理 → 线索录入 → 线索审批 → 客户入池 → 机构认领 → 首次触达 → 触达日志/拍照 → 触发中场支持
```

### 1.2 核心能力域
| 能力域 | 说明 | 关联表 |
|---|---|---|
| 标签管理 | 全行统一标签字典、标签关联客户批量覆盖式导入 | `cust_tag` / `cust_tag_rel` |
| 线索管理 | 单条录入、批量导入、版本化编辑、审批 | `cust_lead` / `lead_import_batch` |
| 客户主档 | 统一客户视图、跨机构历史只读 TAB | `cust_master` |
| 客户池 | 待认领池、已认领客户 | `cust_claim` |
| 认领管理 | 争抢认领、取消认领 | `cust_claim` |
| 触达任务 | 首次触达、二次触达、日志+拍照 | `touch_task` / `touch_log` |
| 触达管理视图 | 机构汇总 + 全行明细 + 导出 | 聚合查询 |

### 1.3 职责边界（Do / Don't）

#### ✅ 本模块负责
1. 客户标签字典管理与客户打标
2. 线索的录入、审批、编辑、删除（生成审批单据与状态机，**不直接调 Flowable**）
3. 客户主档 CRUD（基于线索审批通过后自动生成）
4. 认领关系维护
5. 触达任务的创建、完成、取消
6. 触达日志与照片的存储（照片存 MinIO，路径存 JSON）
7. 客户只读查询能力对外暴露（被多个模块依赖）

#### ❌ 本模块不负责
1. **Flowable 引擎操作**：只通过 `workflow-center` 提供的 `WorkflowApi` 发起/查询流程
2. **资产投放审批**：归 `business-application-center`
3. **中场支持审批**：归 `business-application-center`
4. **绩效计算**：归 `performance-engine-center`
5. **产品字典维护**：归 `portal-content-center`
6. **通讯录维护**：归 `portal-content-center`
7. **员工组织结构维护**：归 `auth-permission-center`

### 1.4 用户角色与可见范围

## 2. 标签管理（对应 project_ana 4.2.1）

### 2.1 功能清单
1. 标签列表查询（分页 + 搜索 + 状态筛选）
2. 标签新增 / 编辑 / 启停
3. 标签关联客户批量导入（覆盖式）
4. 标签关联客户导出
5. 启用标签列表（所有登录用户可见，用于选择器）

### 2.2 字段定义 — cust_tag
| 字段 | 类型 | 必填 | 唯一 | 说明 |
|---|---|---|---|---|
| id | BIGINT | 是 | PK | 主键 |
| tag_name | VARCHAR(100) | 是 | 全行唯一 | 标签名称（展示名） |
| tag_category | VARCHAR(50) | 否 | — | 标签分类（行业/规模/价值/风险等） |
| tag_priority | INT | 是 | — | 展示优先级（0~1000，越小越靠前） |
| status | VARCHAR(20) | 是 | — | ENABLED/DISABLED |
| description | VARCHAR(500) | 否 | — | 描述 |
| created_by | VARCHAR(32) | 是 | — | 创建人 ID |
| created_at | DATETIME | 是 | — | 创建时间 |
| updated_by | VARCHAR(32) | 是 | — | 更新人 ID |
| updated_at | DATETIME | 是 | — | 更新时间 |

### 2.3 全行唯一约束
- `tag_name` 全行唯一（忽略大小写）：新增/编辑时必须校验，冲突返回 `CUST-40002`

### 2.4 禁用状态规则
- **禁用状态标签不可见**：不出现在任何选择器（`GET /api/tags/enabled` 不返回）
- 禁用**不删除**已关联关系：历史记录展示时仍显示标签名，但带"已停用"标注
- 禁用前提：无**阻塞性依赖**（规则简单：直接允许禁用，运行期展示兜底）

### 2.5 标签关联客户批量导入（覆盖式）

#### 2.5.1 流程概览
```
上传Excel → 预览校验 → 二次确认 → 覆盖式导入 → 返回结果
```

#### 2.5.2 覆盖式规则
- **幂等键**：客户名称（`cust_name`）
- **覆盖逻辑**：
  - 如果 Excel 中出现某客户 → 在该标签下保留/新增 `cust_tag_rel`
  - 如果 Excel 中**未出现**某客户 → 从该标签下移除 `cust_tag_rel`（物理删除本标签关联）
- **单标签覆盖**：仅影响本次导入的目标标签，不影响其它标签

#### 2.5.3 5 步安全控制
1. **Step1 文件校验**：格式（.xlsx）、大小 ≤ 10MB、模板列头
2. **Step2 行级校验**：客户名称非空、客户存在（`cust_master`）
3. **Step3 预览返回**：totalRows / validRows / errorRows / errorList / 待新增数 / 待删除数
4. **Step4 二次确认**：前端展示影响面 → 用户确认后返回 `confirmToken`
5. **Step5 整批事务**：任一行校验失败 → 整批回滚 → 返回行级错误清单

#### 2.5.4 失败回滚
- 行级校验任一失败 → **整批回滚**（不做部分成功）
- 返回错误明细（rowNo + field + errorMessage）

### 2.6 启用标签列表（选择器接口）
- 所有登录用户可见
- 返回：`id / tag_name / tag_category / tag_priority`
- 按 `tag_priority` 升序 → `tag_name` 升序
- 仅返回 `status=ENABLED` 记录
- 建议缓存（TTL 5 分钟，标签变更时 `evict`）

### 3.4 单条录入流程

#### 3.4.1 业务流程
```
新建草稿 → 编辑草稿（可反复） → 提交审批 → 审批中 → 审批通过/驳回
                                   ↓               ↓
                              business_key     APPROVED → 创建 cust_master
                              LEAD:{leadId}    REJECTED → 允许复制新线索
```

#### 3.4.2 幂等校验（cust_name）
- **提交审批时**校验：
  - 若 `cust_master` 已存在同名客户（状态=有效）→ 拒绝，返回 `CUST-40901`
  - 若其他线索正在 `PENDING_APPROVAL` 同名 → 拒绝，返回 `CUST-40901`
  - 若其他线索已 `APPROVED` 且 `is_latest=1` → 拒绝（走"编辑"流程而非新建）
- **草稿阶段不校验**：允许用户先填再改

#### 3.4.3 business_key 规则
- 单条：`LEAD:{leadId}` 例如 `LEAD:1001`
- 在提交审批时写入 `cust_lead.business_key`
- 由 `workflow-center` 发起流程时传入，供后续审批回写使用

### 3.5 批量导入流程

#### 3.5.1 业务流程
```
上传Excel → 预览 → 二次确认 → 创建批次(CREATED) → 行级校验 → 整批INSERT cust_lead
                                                    ↓ 任一失败 → 整批回滚
                                                  创建流程(business_key=LEAD:IMP_{batchId})
                                                    ↓
                                                  批次状态 PENDING_APPROVAL
                                                    ↓
                                                  整批审批 → APPROVED/REJECTED
```

#### 3.5.2 批次状态机
```
[CREATED] ──提交审批──→ [PENDING_APPROVAL] ──通过──→ [APPROVED] (终态)
                              │
                              └──驳回──→ [REJECTED] (终态)
```
- **CREATED**：批次已创建，校验未通过前的中间态（通常仅内部可见）
- **PENDING_APPROVAL**：流程已发起，等待审批
- **APPROVED**：审批通过，**不可重提**
- **REJECTED**：审批驳回，**不可重提**（必须重新导入新批次）

#### 3.5.3 批次级 cust_name 幂等规则
**触发整批失败的 3 种场景**：
1. **文件内重复**：Excel 内部有 2 行及以上 `cust_name` 相同
2. **已存在审批中同名**：文件内某行与其他批次内的 `cust_lead` 存在 `cust_name + lead_status=PENDING_APPROVAL` 冲突
3. **已存在有效客户**：文件内某行与 `cust_master` 存在 `cust_name` 冲突（状态=有效）

**任一命中 → 整批失败 + 回滚 + 返回行级错误定位**

#### 3.5.4 不允许重提
- 批次一旦进入 `PENDING_APPROVAL`，无论流程结果如何 → 此批次终态固定
- 需要重新处理 → 必须**重新导入**生成新批次

### 3.6 线索状态机

> **2026-04-28 修正**：实际 `LeadStatus.java` 枚举为 5 值 `DRAFT / SUBMITTED / IN_APPROVAL / APPROVED / REJECTED`。下图中 `PENDING_APPROVAL` 是 `SUBMITTED + IN_APPROVAL` 两态的合并展示（前端点提交后入 `SUBMITTED`，Flowable 任务受理后转 `IN_APPROVAL`），业务规则上等价于一个"审批中"虚状态；本节正文中其余 `PENDING_APPROVAL` 字样含义同此。

```
[DRAFT] ──提交审批──→ [PENDING_APPROVAL] ──通过──→ [APPROVED]
   │                         │                          │
   │                         └──驳回──→ [REJECTED]      │
   │                                                      │
   └──草稿删除──→ 物理删除                          ┌──(编辑)──┐
                                                    │  生成新版本 │
                                                    │  PREV指向旧 │
                                                    │  回到 DRAFT │
                                                    └──────────┘
```

### 3.7 审批通过后自动创建 cust_master
- **监听器**：`LeadApprovedListener` 监听 `customer.lead.approved.v1` 事件
- **创建规则**：
  - 如果 `lead_op=CREATE` → 新建 `cust_master`
  - 如果 `lead_op=UPDATE` → 更新 `cust_master` 对应字段（保留原 `id`）
  - 如果 `lead_op=DELETE` → 将 `cust_master` 标记为已删除（软删除）
- **批量审批通过**：循环处理 `cust_lead` 批次内所有记录，事务一致性
- **触发进入待认领池**：`cust_master` 创建后自动进入待认领池（通过 `cust_claim` 为空判定）

### 4.3 基础可见性冻结口径（关键）

**强制规则**：客户列表与详情的**可见性 100% 按 `cust_claim` 有效认领关系判定**，与 `cust_master.owner_org_id` 无关。

#### 4.3.1 客户经理（SELF_CREATED/ORG）
```sql
-- 可见条件：该员工所在机构对该客户有有效认领关系
EXISTS (
  SELECT 1 FROM cust_claim cc
  WHERE cc.cust_id = cm.id
    AND cc.org_id = :current_emp_org_id
    AND cc.claim_status = 'CLAIMED'
)
```

#### 4.3.2 经营机构负责人（ORG_SUBTREE）
```sql
-- 可见条件：本机构下属子树内任一机构对该客户有有效认领关系
EXISTS (
  SELECT 1 FROM cust_claim cc
  WHERE cc.cust_id = cm.id
    AND cc.org_id IN (:current_emp_org_subtree)
    AND cc.claim_status = 'CLAIMED'
)
```

#### 4.3.3 分行公司部/零售部（ALL）
- 无可见性过滤，所有 `status=VALID` 客户可见

#### 4.3.4 严禁的反模式
- ❌ **禁止**用 `cust_master.owner_org_id = :current_org` 作为可见性判定条件
- ❌ **禁止**在 SQL 中同时用 owner_org_id 和 claim 做 OR
- ✅ `owner_org_id` 只在**来源追溯**场景使用（如详情页展示"录入机构"）

### 4.4 编辑规则（生成新版本并重审）

#### 4.4.1 触发条件
- 仅对 `cust_master.status=VALID` 且用户有 `CUSTOMER.WRITE` 权限
- 当前客户**无其他在途审批**（同一客户只允许一条 PENDING_APPROVAL 线索）

#### 4.4.2 流程
```
点击"编辑" → 复制当前 cust_master 字段到新的 cust_lead
            → lead_op=UPDATE
            → source_cust_id=原 cust_master.id
            → prev_lead_id=原 cust_lead.id（最新版本）
            → version_no = max(version_no) + 1
            → is_latest=0 (旧版本更新)
            → 新记录 is_latest=1
            → 状态=DRAFT
         →  用户确认后 → 提交审批
         → 审批通过 → 更新 cust_master（保留 ID 不变）
```

#### 4.4.3 版本链路
```
cust_master(id=100, lead_id=1005)
  ↑ 最新绑定
cust_lead(id=1001, v1, is_latest=0) ← prev_lead_id=NULL
cust_lead(id=1003, v2, is_latest=0) ← prev_lead_id=1001
cust_lead(id=1005, v3, is_latest=1) ← prev_lead_id=1003
```

### 4.5 转交规则（TRANSFER）

#### 4.5.1 约束
- **同机构转交**：接收人 `orgCode` 必须与当前客户的有效 `cust_claim.org_id` 相同
- **角色限制**：接收人必须具备"客户经理"角色
- **状态校验**：当前客户无本机构在途的触达/中场支持/资产投放流程
- **审计**：独立记录 `cust_transfer_log`（本次版本预留，暂存 `audit_log`）

#### 4.5.2 流程
```

                           → 发布事件 customer.claim.transferred.v1
```

### 4.6 删除规则（DELETE）

#### 4.6.1 前置校验
- **无在途流程**：
  - `cust_claim` 相关的触达任务无 `PENDING/IN_PROGRESS`
  - 无 `business_application_center` 的在途流程（调用 `BusinessApplicationQueryApi.hasRunningProcess`）
- **无已认领关系**（可选策略）：或允许存在认领关系但一并清除（版本确认：**必须无已认领关系**）

#### 4.6.2 流程
```

         → business_key=LEAD:{newLeadId}
         → 调用 WorkflowApi.startProcess 发起流程
         → 审批通过 → cust_master.status=DELETED
                    → 发布 customer.customer.deleted.v1 事件

```

### 4.7 跨机构全量展示特例（只读 TAB）

#### 4.7.1 使用场景
在客户详情页中，提供**独立 TAB** 展示该客户的**跨机构全量历史**：
- 跨机构触达历史
- 跨机构资产投放历史
- 跨机构中场支持历史

#### 4.7.2 严格约束

#### 状态图

```
                  ┌──────────────────────────────────────┐
                  │          【初始】                    │
                  │   由认领 / 重新发起触达 自动创建     │

              │              │        │             │
     首次追加触达日志         │     7 天未操作       │ cust_claim
     (POST /logs)             │      （SLA 内）     │  取消认领
              ↓              │        ↓             ↓

    触达成功  │ 触达取消  (7天+1天仍未完成)
    (POST /success)  (POST /cancel)  └───────────┐
          │     │                                 ↓
          ↓     ↓                    ┌──────────────────────┐
     ┌─────────┐ ┌────────────┐      │  SLA_EXPIRED          │
     │ SUCCESS │ │ CANCELLED  │      │  （超期未完成）      │
     │ （终态） │ │ （终态）    │      │  task_status 不变，  │
     └─────────┘ └────────────┘      │  sla_warning=1，     │
                                     │  触发告警             │
                                     └──────────────────────┘
```

#### 状态转移矩阵

| 当前状态 | 事件 | 触发条件 | 目标状态 | 副作用 |
|---|---|---|---|---|
| **（无）** | 客户认领 | `POST /customer-pool/{custId}/claim` 成功 | `PENDING` | 插入 `touch_task (task_type=FIRST_TOUCH)`，`sla_deadline = created_at + 7d`，`sla_warning=0` |
| **（无）** | 重新发起触达 | `POST /claims/{id}/re-touch` 且前次触达终态 | `PENDING` | 插入 `touch_task (task_type=FOLLOW_UP)`，新的 `sla_deadline` |
| `PENDING` | 追加触达日志 | `POST /touch-tasks/{id}/logs` 成功（首次） | `IN_PROGRESS` | `UPDATE task_status='IN_PROGRESS'` + INSERT `touch_log` |
| `PENDING` | 触达成功 | `POST /touch-tasks/{id}/success`（可直接跳过 IN_PROGRESS） | `SUCCESS` | 见 §7.5.3 |
| `PENDING` | 触达取消 | `POST /touch-tasks/{id}/cancel` | `CANCELLED` | 见 §7.6 |
| `PENDING` | 取消认领 | `POST /claims/{id}/cancel`（上层操作） | `CANCELLED` | 关闭该任务，`cancel_reason='取消认领'` |
| `PENDING` | SLA 预警（-1 天） | 定时任务扫描 `sla_deadline < NOW() + 1d AND sla_warning = 0` | `PENDING`（不变） | `UPDATE sla_warning=1`，发通知给 assignee 和其上级 |
| `PENDING` | SLA 超期 | 定时任务扫描 `sla_deadline < NOW() AND task_status='PENDING'` | `PENDING`（不变） | 发 `customer.touch.sla_expired.v1` 事件，写审计日志，记录到管理视图"超期列表" |
| `IN_PROGRESS` | 追加触达日志 | `POST /touch-tasks/{id}/logs` 后续调用 | `IN_PROGRESS`（不变） | 仅 INSERT `touch_log`，状态保持 |
| `IN_PROGRESS` | 触达成功 | `POST /touch-tasks/{id}/success` | `SUCCESS` | 见 §7.5.3 |
| `IN_PROGRESS` | 触达取消 | `POST /touch-tasks/{id}/cancel` | `CANCELLED` | 见 §7.6 |
| `IN_PROGRESS` | 取消认领 | `POST /claims/{id}/cancel` | **拒绝** | 6.2.1 前置校验要求"在途任务不得取消认领"，返回 `CUST-40901` |
| `IN_PROGRESS` | SLA 超期 | 同上 | `IN_PROGRESS`（不变） | 同 PENDING 的超期处理 |
| `SUCCESS` | 任何事件 | — | **终态，不可迁移** | 任何修改操作返回 `CUST-40902` 终态保护 |
| `CANCELLED` | 任何事件 | — | **终态，不可迁移** | 同上 |

#### SLA 规则

| 项 | 值 | 说明 |
|---|---|---|
| SLA 周期 | 7 天 | `sla_deadline = created_at + 7d`（工作日历由 governance 提供） |
| 预警触发 | SLA 截止前 1 天 | 定时任务每天 09:00 扫描，发通知 |
| 超期触发 | SLA 截止后 | 定时任务每天 09:30 扫描，发事件+审计+管理视图标红 |
| 超期后的可操作性 | 仍可触达成功/取消 | **超期不阻塞完成**，只做标记和告警 |
| 状态字段 | `task_status` + `sla_warning` | 两者独立，超期不改 `task_status` |

**重要**：超期 (`SLA_EXPIRED`) **不是独立的状态值**，而是通过 `task_status='PENDING'/'IN_PROGRESS' AND sla_deadline < NOW()` 派生计算。状态字段只存 4 个合法值：`PENDING / IN_PROGRESS / SUCCESS / CANCELLED`。

#### 终态保护

写操作必须在 Service 层做状态校验：

```java
// TouchTaskService.touchSuccess(taskId, cmd)
TouchTaskEntity task = touchTaskMapper.selectByIdForUpdate(taskId);
if (task == null) throw new BizException("CUST-40404", "触达任务不存在");
if (!Set.of("PENDING", "IN_PROGRESS").contains(task.getTaskStatus())) {
    throw new BizException("CUST-40902", "触达任务已处于终态：" + task.getTaskStatus());
}
// ... 执行成功流程
```

#### 并发控制

| 场景 | 控制方式 | 说明 |
|---|---|---|
| 移动端重复提交 | `touch_log` UK(touch_task_id, client_uuid) | 见 §7.8 |
| 同时点击"成功"和"取消" | `SELECT ... FOR UPDATE` | 悲观锁，先到先得 |
| 定时任务与用户操作竞争 | `WHERE task_status = 'PENDING'` 条件 UPDATE | 超期标记时用乐观条件 |
| 认领取消时的在途校验 | `SELECT ... FROM touch_task WHERE cust_id=? AND org_id=? AND task_status IN ('PENDING','IN_PROGRESS') FOR UPDATE` | 见 §6.2.1 |

#### 定时任务清单

| 任务 | Cron | 扫描逻辑 | 动作 |
|---|---|---|---|
| SLA 预警 | `0 0 9 * * *` | `sla_deadline BETWEEN NOW() AND NOW()+1d AND sla_warning=0 AND task_status IN ('PENDING','IN_PROGRESS')` | `sla_warning=1`，发通知 |
| SLA 超期 | `0 30 9 * * *` | `sla_deadline < NOW() AND task_status IN ('PENDING','IN_PROGRESS')` | 发事件 `customer.touch.sla_expired.v1` |
| 历史归档 | `0 0 2 1 * *` | `task_status IN ('SUCCESS','CANCELLED') AND updated_time < NOW() - 1y` | 迁移到 `touch_task_archive` 表（V2 启用） |

定时任务配置通过 governance 的 `sys_job_conf` 统一管理，本模块在初始化数据中登记 Job 定义。

- **不拦截**：后端不做阻断

### 9.2 在途流程类型
| 流程类型 | 来源模块 | BizType |
|---|---|---|
| 线索审批 | customer-marketing-center | LEAD |
| 触达任务 | customer-marketing-center | TOUCH_TASK |
| 资产投放审批 | business-application-center | LOAN_APPROVAL |
| 中场支持审批 | business-application-center | MIDFIELD_SUPPORT |

### 9.3 查询接口
- `CustomerQueryApi.hasRunningProcess(custId, bizType)` — 单类型
- `CustomerQueryApi.listRunningProcesses(custId)` — 全量类型（新增）

  - 触达导出
