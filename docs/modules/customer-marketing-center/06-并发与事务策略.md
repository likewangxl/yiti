# 客户营销中心 — 并发与事务策略

> 本文档定义客户营销中心的事务边界、并发控制、幂等策略、锁粒度和缓存策略。
> 事务注解统一使用 `@Transactional(rollbackFor = Exception.class)`；默认隔离级别 READ_COMMITTED。
> 所有跨模块调用（WorkflowApi、FileApi、AuditApi）必须放在业务事务**最后一步**，失败回滚业务数据。

---

## 1. 线索管理事务

### 1.1 创建草稿 — 单事务

```java
@Transactional(rollbackFor = Exception.class)
public String createDraft(LeadCreateCmd cmd) {
    // 1. 字段校验 (基础校验 + 重名校验)
    validate(cmd);
    // 2. 插入 cust_lead 记录 (lead_status=DRAFT)
    String leadId = IdGenerator.uuid();
    CustLead lead = buildLead(cmd, leadId, "DRAFT");
    custLeadMapper.insert(lead);
    return leadId;
}
```

**边界**：单表 INSERT，无外部调用。

### 1.2 提交审批 — 业务更新 + WorkflowApi 同事务

```java
@Transactional(rollbackFor = Exception.class)
public void submitForApproval(String leadId) {
    // 1. 锁行读取 (防并发提交)
    CustLead lead = custLeadMapper.selectForUpdate(leadId);
    Assert.state(lead.getLeadStatus().equals("DRAFT") 
              || lead.getLeadStatus().equals("REJECTED"),
              "仅草稿或驳回状态可提交审批");
    // 2. 更新线索状态 DRAFT/REJECTED -> SUBMITTED
    lead.setLeadStatus("SUBMITTED");
    lead.setBusinessKey("LEAD:" + leadId);
    custLeadMapper.updateById(lead);
    // 3. 启动审批流程 (同事务)
    StartProcessCmd startCmd = StartProcessCmd.builder()
        .processDefKey("lead_approve_v1")
        .businessKey(lead.getBusinessKey())
        .initiator(currentUserApi.getCurrentEmpId())
        .variables(Map.of("leadId", leadId))
        .build();
    WorkflowLaunchResp resp = workflowApi.startProcess(startCmd);
    // 4. 回写 process_instance_id
    custLeadMapper.updateProcessInstanceId(leadId, resp.getProcessInstanceId());
    // 5. 更新状态 SUBMITTED -> IN_APPROVAL
    custLeadMapper.updateStatus(leadId, "IN_APPROVAL");
}
```

**边界**：Service 层包一个事务，WorkflowApi 调用失败整体回滚。

**并发风险**：多次点击提交按钮。通过 SELECT ... FOR UPDATE 行锁 + 状态机校验防止。

### 1.3 批量导入 — 预览不写库，执行时分段提交

#### 1.3.1 预览阶段（只读，无事务）

```java
public ImportPreviewResult preview(String fileId) {
    // 1. 下载文件 (FileApi)
    byte[] bytes = fileApi.download(fileId);
    // 2. 解析 Excel (内存计算)
    List<LeadImportRow> rows = parseExcel(bytes);
    // 3. 校验每行 (查重、字典、格式)
    List<LeadImportRow> errorRows = validateRows(rows);
    // 4. 返回预览结果 (不写库)
    return new ImportPreviewResult(rows.size(), errorRows);
}
```

#### 1.3.2 执行阶段 — 严格整批回滚模式

```java
@Transactional(rollbackFor = Exception.class)
public String executeImport(String fileId, String reason) {
    // 1. 再次解析 + 校验 (防预览后源文件变化)
    List<LeadImportRow> rows = validateAndParse(fileId);
    if (hasError(rows)) {
        throw new BizException("文件包含错误行，请修正后重新导入");
    }
    // 2. 插入 lead_import_batch (status=CREATED)
    String batchId = createBatch(fileId, rows.size());
    // 3. 分段插入 cust_lead (每1000行一次批量 insert)
    //    注意：分段仅为性能优化，整个过程仍在同一事务内
    for (List<LeadImportRow> chunk : Lists.partition(rows, 1000)) {
        List<CustLead> leads = chunk.stream()
            .map(r -> buildLead(r, batchId, "DRAFT"))
            .toList();
        custLeadMapper.batchInsert(leads);
    }
    // 4. 更新批次状态 CREATED -> PENDING_APPROVAL
    batchMapper.updateStatus(batchId, "PENDING_APPROVAL");
    // 5. 启动批量审批流程
    String businessKey = "LEAD:IMP_" + batchId;
    WorkflowLaunchResp resp = workflowApi.startProcess(
        StartProcessCmd.builder()
            .processDefKey("lead_import_approve_v1")
            .businessKey(businessKey)
            .initiator(currentUserApi.getCurrentEmpId())
            .variables(Map.of("batchId", batchId, "reason", reason))
            .build());
    batchMapper.updateProcessInstanceId(batchId, resp.getProcessInstanceId());
    return batchId;
}
```

**策略**：任一行校验失败 → 整批事务回滚，返回所有错误信息。

**大批量优化**：
- 单次导入上限 5000 行（配置项 `customer.lead.import.max-rows`）
- 超过上限返回 400 错误提示拆分导入
- 事务超时：60 秒（`@Transactional(timeout = 60)`）

### 1.4 审批回调事务

审批通过/驳回是 Flowable 流程驱动的回调，在 ServiceTask 中通过 Spring Bean 调用：

```java
@Transactional(rollbackFor = Exception.class)
public void onApproved(String leadId) {
    CustLead lead = custLeadMapper.selectForUpdate(leadId);
    lead.setLeadStatus("APPROVED");
    custLeadMapper.updateById(lead);

    // 根据 lead_op 执行不同动作
    if ("CREATE".equals(lead.getLeadOp())) {
        createCustMasterFromLead(lead);
    } else if ("UPDATE".equals(lead.getLeadOp())) {
        applyUpdateToCustMaster(lead);
    } else if ("DELETE".equals(lead.getLeadOp())) {
        deleteCustMaster(lead);
    }
}
```

## 2. lead_import_batch 批次状态机

### 2.1 状态图

```
           创建批次
              ↓
          [CREATED]
              ↓  提交审批
      [PENDING_APPROVAL]
          ↙         ↘
  审批通过          审批驳回
      ↓              ↓
  [APPROVED]     [REJECTED]
  (终态)         (终态)
```

### 2.2 约束

1. **状态切换必须在业务事务内**：UPDATE 语句与相关业务操作同事务。
2. **终态不可退回**：APPROVED / REJECTED 为终态，禁止再次变更。
3. **状态校验**：所有状态转换 SQL 使用 CAS 方式防并发：

```sql
UPDATE lead_import_batch
SET status = 'PENDING_APPROVAL',
    process_instance_id = #{procId},
    updated_by = #{empId},
    updated_time = NOW()
WHERE id = #{id}
  AND status = 'CREATED';  -- CAS 关键条件
```

Java 层判断影响行数：

```java
int affected = batchMapper.updateStatusCas(id, "CREATED", "PENDING_APPROVAL");
if (affected == 0) {
    throw new BizException("批次状态已变更，请刷新重试");
}
```

### 2.3 批次-线索一致性

- 批次审批通过时：所有关联的 cust_lead 记录状态一并更新为 APPROVED，并触发客户主档创建。
- 批次审批驳回时：所有关联的 cust_lead 记录状态一并更新为 REJECTED。
- 通过 `custLeadMapper.batchUpdateStatusByBatchId(batchId, oldStatus, newStatus)` 一次更新，同事务。

## 3. 线索版本管理并发

### 3.1 生成新版本的事务

```java
@Transactional(rollbackFor = Exception.class)
public String createNewVersion(String sourceCustId, LeadUpdateCmd cmd) {
    // 1. 查询当前最新版本 (带乐观锁)
    CustLead current = custLeadMapper.selectLatestBySourceCust(sourceCustId);
    if (current == null) {
        throw new BizException("未找到源客户对应的线索");
    }
    // 2. 更新旧版本 is_latest=0 (CAS 使用 version_no 乐观锁)
    int affected = custLeadMapper.updateIsLatestCas(
        current.getId(), current.getVersionNo(), 0);
    if (affected == 0) {
        throw new BizException("线索版本已被其他操作修改，请刷新重试");
    }
    // 3. 插入新版本 (version_no+1, is_latest=1)
    String newLeadId = IdGenerator.uuid();
    CustLead newLead = buildLead(cmd, newLeadId, "DRAFT");
    newLead.setLeadOp("UPDATE");
    newLead.setSourceCustId(sourceCustId);
    newLead.setPrevLeadId(current.getId());
    newLead.setVersionNo(current.getVersionNo() + 1);
    newLead.setIsLatest(1);
    custLeadMapper.insert(newLead);
    return newLeadId;
}
```

**SQL 乐观锁更新**：

```sql
UPDATE cust_lead
SET is_latest = 0,
    updated_time = NOW()
WHERE id = #{id}
  AND version_no = #{versionNo}
  AND is_latest = 1;
```

### 3.2 并发场景

**场景**：A、B 两个客户经理同时修改同一客户的线索信息。
- A 读取 current.versionNo=2
- B 读取 current.versionNo=2
- A 提交事务成功：is_latest 变为 0，插入 version_no=3 的新记录
- B 提交事务时 CAS 失败（version_no 条件不满足）
- 系统返回"版本冲突，请刷新重试"

### 3.3 审批驳回时的版本回退

```java
@Transactional(rollbackFor = Exception.class)
public void onRejected(String leadId) {
    CustLead rejected = custLeadMapper.selectById(leadId);
    // 1. 驳回的记录 is_latest=0
    custLeadMapper.updateIsLatestDirect(leadId, 0);
    // 2. 前一版本 is_latest=1 (仅 UPDATE/DELETE 类型需要)
    if (rejected.getPrevLeadId() != null) {
        custLeadMapper.updateIsLatestDirect(rejected.getPrevLeadId(), 1);
    }
    // 3. 更新状态 IN_APPROVAL -> REJECTED
    custLeadMapper.updateStatus(leadId, "REJECTED");
}
```

**注意**：驳回后 `is_latest` 回退到前一版本；如果用户想再次修改，应基于"源客户"创建新版本（从当前 cust_master 开始新的编辑链）。

## 4. 客户认领并发控制

### 4.1 唯一约束防重复

`cust_claim` 表 `UK(cust_id, org_id)` 天然防止同一客户被同一机构重复认领。

### 4.2 认领事务

```java
@Transactional(rollbackFor = Exception.class)
public ClaimResult claim(String custId) {
    String empId = currentUserApi.getCurrentEmpId();
    String orgId = currentUserApi.getCurrentOrgCode();
    // 1. 查询客户是否存在且未删除
    CustMaster cust = custMasterMapper.selectByIdForUpdate(custId);
    Assert.state(cust != null && cust.getDeleted() == 0, "客户不存在");
    // 2. 检查是否已被本机构认领 (INSERT IGNORE 容错)
    CustClaim newClaim = CustClaim.builder()
        .id(IdGenerator.uuid())
        .custId(custId)
        .orgId(orgId)
        .claimedBy(empId)
        .maintainerEmpId(empId)
        .claimStatus("CLAIMED")
        .claimTime(LocalDateTime.now())
        .build();
    int inserted = custClaimMapper.insertIgnore(newClaim);
    if (inserted == 0) {
        // 已存在，检查是否是 CANCELLED 状态可复活
        CustClaim existing = custClaimMapper.selectByCustOrg(custId, orgId);
        if ("CANCELLED".equals(existing.getClaimStatus())) {
            // 复活：UPDATE 回 CLAIMED
            custClaimMapper.reactivate(existing.getId(), empId);
            newClaim = existing;
        } else {
            throw new BizException("该客户已被本机构认领");
        }
    }
    // 3. 创建 FIRST_TOUCH 触达任务 (同事务)
    String touchTaskId = createFirstTouchTask(custId, orgId, empId);
    // 4. 启动触达流程
    WorkflowLaunchResp resp = workflowApi.startProcess(
        StartProcessCmd.builder()
            .processDefKey("touch_process_v1")
            .businessKey("TOUCH:" + touchTaskId)
            .initiator(empId)
            .variables(Map.of("taskId", touchTaskId, "custId", custId))
            .build());
    touchTaskMapper.updateProcessInstanceId(touchTaskId, resp.getProcessInstanceId());
    return new ClaimResult(newClaim.getId(), touchTaskId);
}
```

**SQL 复活认领**：

```sql
UPDATE cust_claim
SET claim_status = 'CLAIMED',
    claimed_by = #{empId},
    maintainer_emp_id = #{empId},
    claim_time = NOW(),
    cancel_time = NULL,
    cancel_reason = NULL,
    updated_time = NOW()
WHERE id = #{id}
  AND claim_status = 'CANCELLED';
```

### 4.3 争抢模式并发

**设计取舍**：允许多机构并发认领同一客户，这是银行业务的常态（多支行同时争取客户）。

- 每个机构独立 UK(cust_id, org_id)，彼此不冲突
- 不同机构不互相独占，各自运营各自的客户关系
- 业务层面通过 `cust_claim` 查询所有认领机构，前端展示"已被 N 家机构认领"提示

### 4.4 认领 + 触达任务同事务

- 认领成功必须同时创建触达任务（业务强一致）
- 任一步骤失败整体回滚，不允许出现"已认领但无触达任务"的中间态

### 4.5 并行流程检查

认领前需要检查该客户是否处于删除审批中：

```java
// 只读查询，不加锁
boolean hasPendingDelete = custLeadMapper.existsPendingDeleteLead(custId);
if (hasPendingDelete) {
    throw new BizException("该客户正在删除审批中，暂不可认领");
}
```

## 5. 取消认领并发

### 5.1 取消认领事务

```java
@Transactional(rollbackFor = Exception.class)
public void cancelClaim(String claimId, String reason) {
    String empId = currentUserApi.getCurrentEmpId();
    // 1. 读取认领记录
    CustClaim claim = custClaimMapper.selectByIdForUpdate(claimId);
    Assert.state(claim != null && "CLAIMED".equals(claim.getClaimStatus()),
                 "认领记录不存在或已取消");
    // 2. 检查无在途流程 (读操作, 不加锁但要求最终一致)
    List<String> pendingTasks = touchTaskMapper.findPendingByCustOrg(
        claim.getCustId(), claim.getOrgId());
    if (!pendingTasks.isEmpty()) {
        throw new BizException("存在未完成的触达任务，无法取消认领");
    }
    // 3. CAS 更新 CLAIMED -> CANCELLED
    int affected = custClaimMapper.cancelClaimCas(
        claimId, "CLAIMED", "CANCELLED", empId, reason);
    if (affected == 0) {
        throw new BizException("认领状态已变更，请刷新重试");
    }
}
```

### 5.2 时间窗口竞态处理

**风险**：步骤 2 读取时没有未完成任务，但步骤 3 更新前有新任务创建。

**业务接受**：此时间窗口极短（毫秒级），业务上可接受；极端情况次日由定时任务检测修正：

```java
// 定时任务：检测异常认领状态（已取消但仍有未完成任务）
@Scheduled(cron = "0 30 0 * * ?")  // 每日凌晨 00:30
public void detectOrphanTouchTasks() {
    List<String> orphans = custClaimMapper.findCancelledWithPendingTasks();
    for (String claimId : orphans) {
        log.warn("检测到异常状态：认领已取消但仍有未完成任务 claimId={}", claimId);
        alertApi.sendAlert("ORPHAN_CLAIM", claimId);
    }
}
```

### 5.3 严格模式（可选增强）

对监管严格场景可引入分布式锁，粒度 `cust_id + org_id`：

```java
String lockKey = "claim:cancel:" + claim.getCustId() + ":" + claim.getOrgId();
RLock lock = redissonClient.getLock(lockKey);
if (!lock.tryLock(3, 30, TimeUnit.SECONDS)) {
    throw new BizException("系统繁忙，请稍后重试");
}
try {
    // 重新加锁内的校验 + 更新
    executeCancelWithinLock(claim);
} finally {
    lock.unlock();
}
```

## 6. 触达任务并发

### 6.1 FIRST_TOUCH 创建

与 claim 操作同事务，已在 §4.2 说明。

### 6.2 触达完成/取消的互斥

**机制**：通过 Flowable `runtime.task` 完成任务；Flowable 本身保证同一任务只能被完成一次。

```java
@Transactional(rollbackFor = Exception.class)
public void success(String taskId, TouchSuccessCmd cmd) {
    String empId = currentUserApi.getCurrentEmpId();
    // 1. 锁行读取触达任务
    TouchTask task = touchTaskMapper.selectByIdForUpdate(taskId);
    Assert.state("PENDING".equals(task.getTaskStatus()), "任务状态不可完成");
    Assert.state(empId.equals(task.getAssigneeEmpId()), "仅任务执行人可完成");
    // 2. 保存触达日志 (幂等)
    saveTouchLog(taskId, cmd);
    // 3. CAS 更新任务状态 PENDING -> SUCCESS
    int affected = touchTaskMapper.updateStatusCas(
        taskId, "PENDING", "SUCCESS");
    if (affected == 0) {
        throw new BizException("任务状态已变更");
    }
    // 4. 完成 Flowable runtime task
    List<TaskDTO> flowTasks = workflowQueryApi.queryTasksByBusinessKey(
        "TOUCH:" + taskId, empId);
    for (TaskDTO ft : flowTasks) {
        workflowApi.complete(CompleteTaskCmd.builder()
            .taskId(ft.getTaskId())
            .empId(empId)
            .variables(Map.of("touchResult", "SUCCESS"))
            .build());
    }
}
```

### 6.3 批量分配的并发

管理员批量分配触达任务：

```java
@Transactional(rollbackFor = Exception.class)
public void batchAssign(List<String> taskIds, String newAssigneeEmpId) {
    // 循环处理，每个 taskId 独立 CAS
    for (String taskId : taskIds) {
        int affected = touchTaskMapper.updateAssigneeCas(
            taskId, "PENDING", newAssigneeEmpId);
        if (affected == 0) {
            // 记录跳过的任务，继续处理其他任务（不回滚已处理的）
            log.warn("任务 {} 状态已变更，跳过分配", taskId);
            continue;
        }
        // 同步 Flowable 任务受理人
        workflowApi.reassignTask("TOUCH:" + taskId, newAssigneeEmpId);
    }
}
```

**注意**：此处循环处理允许部分成功（business requirement），事务边界为单次批量操作。

## 7. 触达日志幂等

### 7.1 UK(touch_task_id, client_uuid) 防重

移动端网络不稳定时可能重复提交同一日志。前端生成 UUID 作为 `client_uuid`，重试使用相同 UUID。

### 7.2 幂等插入

```java
@Transactional(rollbackFor = Exception.class)
public String saveTouchLog(String taskId, TouchLogCmd cmd) {
    TouchLog log = TouchLog.builder()
        .id(IdGenerator.uuid())
        .touchTaskId(taskId)
        .clientUuid(cmd.getClientUuid())
        .logTime(LocalDateTime.now())
        .logContent(cmd.getContent())
        .photoUrls(JSON.toJSONString(cmd.getPhotoUrls()))
        .createdBy(currentUserApi.getCurrentEmpId())
        .ownerOrgId(currentUserApi.getCurrentOrgCode())
        .build();
    int inserted = touchLogMapper.insertIgnore(log);
    if (inserted == 0) {
        // 已存在：查询返回已存在的记录 ID
        TouchLog existing = touchLogMapper.selectByTaskUuid(
            taskId, cmd.getClientUuid());
        return existing.getId();
    }
    return log.getId();
}
```

**SQL**：

```sql
INSERT IGNORE INTO touch_log (id, touch_task_id, client_uuid, ...)
VALUES (#{id}, #{touchTaskId}, #{clientUuid}, ...)
```

### 7.3 幂等审计

同一 `client_uuid` 重复提交只产生一条 `touch_log` 记录和**一条**审计日志（首次成功插入时触发，后续 INSERT IGNORE 返回 0 行不触发审计）。

## 8. 客户删除审批流程

### 8.1 发起删除事务

```java
@Transactional(rollbackFor = Exception.class)
public String applyDelete(String custId, String reason) {
    String empId = currentUserApi.getCurrentEmpId();
    // 1. 校验当前用户是否维护该客户
    CustClaim claim = custClaimMapper.selectActiveMaintainer(
        custId, currentUserApi.getCurrentOrgCode(), empId);
    Assert.state(claim != null, "仅维护人可发起删除");
    // 2. 校验无未完成触达任务
    if (touchTaskMapper.countPendingByCust(custId) > 0) {
        throw new BizException("存在未完成触达任务，无法发起删除");
    }
    // 3. 创建 DELETE 类型线索 (走版本管理流程)
    String leadId = createDeleteLead(custId, reason, empId);
    // 4. 启动删除审批流程
    String businessKey = "LEAD_DELETE:" + leadId;
    WorkflowLaunchResp resp = workflowApi.startProcess(
        StartProcessCmd.builder()
            .processDefKey("lead_delete_approve_v1")
            .businessKey(businessKey)
            .initiator(empId)
            .variables(Map.of("leadId", leadId, "custId", custId, "reason", reason))
            .build());
    custLeadMapper.updateProcessInstanceId(leadId, resp.getProcessInstanceId());
    return leadId;
}
```

### 8.2 审批通过回调事务

```java
@Transactional(rollbackFor = Exception.class)
public void onDeleteApproved(String leadId) {
    CustLead deleteLead = custLeadMapper.selectById(leadId);
    String custId = deleteLead.getSourceCustId();
    // 1. 更新线索状态 IN_APPROVAL -> APPROVED
    custLeadMapper.updateStatus(leadId, "APPROVED");
    // 2. 逻辑删除客户主档
    custMasterMapper.logicDelete(custId);
    // 3. 取消所有该客户的认领关系
    custClaimMapper.batchCancelByCust(custId, "客户已删除");
    // 4. 取消所有未完成的触达任务
    touchTaskMapper.batchCancelPendingByCust(custId, "客户已删除");
    // 5. 事件发布：CUSTOMER_DELETED
    eventPublisher.publish(new CustomerDeletedEvent(custId, leadId));
}
```

### 8.3 审批驳回

```java
@Transactional(rollbackFor = Exception.class)
public void onDeleteRejected(String leadId) {
    // 1. 线索状态 IN_APPROVAL -> REJECTED
    custLeadMapper.updateStatus(leadId, "REJECTED");
    // 2. 版本回退：前一版本 is_latest=1
    CustLead lead = custLeadMapper.selectById(leadId);
    custLeadMapper.updateIsLatestDirect(leadId, 0);
    if (lead.getPrevLeadId() != null) {
        custLeadMapper.updateIsLatestDirect(lead.getPrevLeadId(), 1);
    }
    // 3. 客户主档无变化
}
```

## 9. 缓存策略

### 9.1 缓存清单

| 缓存键 | 类型 | TTL | 失效策略 |
|---|---|---|---|
| `cust:tag:list:active` | List | 10 min | 标签 CRUD 时主动清除 |
| `cust:tag:detail:{tagId}` | Hash | 10 min | 标签更新时 DEL |
| `cust:master:{custId}` | Hash | 5 min | 客户主档更新时 DEL |
| `cust:claim:count:{custId}` | String | 2 min | 认领变化时 DEL |
| `touch:task:assignee:{empId}:pending` | List | 1 min | 任务状态变化时 DEL |

### 9.2 不缓存的数据

- **待认领客户池**：实时性要求高，每次查询直接走 DB
- **触达任务列表（带分页筛选）**：变化频繁，缓存收益低
- **线索列表**：同上
- **触达日志**：只读历史数据，应用层本地缓存即可

### 9.3 缓存失效场景

#### 场景 A — 启用标签列表

```java
@Cacheable(cacheNames = "custTagList", key = "'active'")
public List<CustTagDTO> listActiveTags() {
    return custTagMapper.selectByStatus("ACTIVE");
}

@CacheEvict(cacheNames = {"custTagList", "custTagDetail"}, allEntries = true)
@Transactional(rollbackFor = Exception.class)
public void createTag(CustTagCreateCmd cmd) { ... }
```

#### 场景 B — 客户主档缓存

```java
@Cacheable(cacheNames = "custMaster", key = "#custId")
public CustMasterDTO getCustMaster(String custId) { ... }

@CacheEvict(cacheNames = "custMaster", key = "#custId")
@Transactional
public void updateCustMaster(String custId, ...) { ... }
```

### 9.4 缓存一致性要求

- 采用 **Cache-Aside** 模式：先更新 DB 再删除缓存
- 删除缓存失败时降级为"等 TTL 自然过期"，记录告警日志
- 禁止 Write-Through（Redis 挂掉会阻塞事务）

### 9.5 热点数据保护

- 启用标签列表是典型热点，单点击穿可能导致 DB 压力
- 使用 Redisson `RLock` 做单飞（single-flight）查询：

```java
public List<CustTagDTO> listActiveTags() {
    List<CustTagDTO> cached = redisTemplate.opsForValue().get(CACHE_KEY);
    if (cached != null) return cached;
    // 单飞查询
    RLock lock = redissonClient.getLock("cust:tag:list:lock");
    if (lock.tryLock(0, 5, TimeUnit.SECONDS)) {
        try {
            cached = redisTemplate.opsForValue().get(CACHE_KEY);
            if (cached != null) return cached;
            List<CustTagDTO> fromDb = custTagMapper.selectByStatus("ACTIVE");
            redisTemplate.opsForValue().set(CACHE_KEY, fromDb, 10, TimeUnit.MINUTES);
            return fromDb;
        } finally { lock.unlock(); }
    }
    // 抢锁失败：重试一次读取
    Thread.sleep(50);
    return redisTemplate.opsForValue().get(CACHE_KEY);
}
```

## 10. 幂等策略汇总

| 操作 | 幂等键 | 实现方式 |
|---|---|---|
| 线索新建 | X-Request-Id (前端传递) | Redis SETNX 5 分钟TTL；命中则返回已生成的 leadId |
| 线索批量导入 | 客户名称（cust_name） | 导入前查重 `SELECT id FROM cust_lead WHERE cust_name=? AND is_latest=1` |
| 标签客户导入 | 客户名称（cust_name） | 同上，仅匹配已存在客户主档 |
| 客户认领 | UK(cust_id, org_id) | INSERT IGNORE；已存在且 CANCELLED 状态可复活 |
| 触达日志提交 | client_uuid | UK(touch_task_id, client_uuid) + INSERT IGNORE |
| 触达任务完成 | taskId | CAS 更新 status PENDING→SUCCESS；Flowable 任务完成天然幂等 |
| 认领取消 | claimId | CAS 更新 status CLAIMED→CANCELLED |
| 客户删除发起 | custId | 同一客户只允许一条 IN_APPROVAL 状态的 DELETE 线索 |

### 10.1 X-Request-Id 防重复提交

```java
public String createDraft(LeadCreateCmd cmd, HttpServletRequest request) {
    String requestId = request.getHeader("X-Request-Id");
    if (requestId == null) {
        return doCreateDraft(cmd);  // 无幂等键，直接创建
    }
    String redisKey = "cust:lead:create:" + requestId;
    String existing = redisTemplate.opsForValue().get(redisKey);
    if (existing != null) {
        return existing;  // 幂等命中，返回已创建的 leadId
    }
    String leadId = doCreateDraft(cmd);
    redisTemplate.opsForValue().set(redisKey, leadId, 5, TimeUnit.MINUTES);
    return leadId;
}
```

### 10.2 删除发起防重复

```sql
-- 查询是否有未完成的删除线索
SELECT id FROM cust_lead
WHERE source_cust_id = #{custId}
  AND lead_op = 'DELETE'
  AND lead_status IN ('DRAFT','SUBMITTED','IN_APPROVAL')
  AND is_latest = 1
LIMIT 1;
```

若存在，返回错误："已存在进行中的删除申请"。

## 11. 锁粒度总结

| 锁类型 | 应用场景 | 锁粒度 | 超时 |
|---|---|---|---|
| 行锁 (SELECT FOR UPDATE) | 线索状态转换、客户主档更新、认领取消 | 单行 | 事务结束 |
| 乐观锁 (version_no) | 线索版本生成 | 单行 | 无 |
| CAS (CASE WHEN) | 状态机 CAS 更新 | 单行 | 无 |
| 唯一约束 | 认领防重、触达日志防重 | 索引键 | 无 |
| Redisson 分布式锁 | 热点缓存单飞、严格认领取消（可选） | Key级别 | 5~30秒 |
