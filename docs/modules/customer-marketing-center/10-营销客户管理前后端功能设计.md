# 客户营销中心——六页面前后端功能设计

> 目标设计稿 v1.0；编制日期：2026-08-26
> 本文描述目标功能、页面交互、后端服务逻辑和规划中的 REST 契约，属于规划稿，未表示当前代码、接口或数据库已经实现。
> 数据库字段和表以 05-表结构DDL.md 的目标模型为准；本文不提供可执行 DDL。结构实施须由 DBA 按审批结果完成。

## 1. 设计边界和统一原则

### 1.1 本次范围

本设计覆盖以下六个页面：

1. 营销客户列表：管理员查看和维护全部营销客户主档，并维护主办权。
2. 我的客户：客户经理查看主办权归属于自己的客户，并向其他客户经理转交。
3. 线索录入：手工线索记录和批量导入记录分 Tab 展示。
4. 线索审批：待审批和本人审批记录分 Tab 展示，按线索逐条审批。
5. 营销客户标签：按标签查看客户，追加导入或全量替换，新增标签和模板导入。
6. 标签客户审核：按标签聚合展示标签审批和标签所属客户审批，支持单条、多条和全部审批。

本文不改变以下边界：

- 客户主档由客户营销域持有，统一社会信用代码是业务唯一键，主键是自增客户 ID。
- 审批中的线索不提前写入客户主档；线索审批通过后才新增或受控更新客户主档。
- 线索是独立营销事项，不建设上一版本、版本号和最新版本链。
- 认领池不是物理表，按线索、客户主档、分配方式、认领关系和主办权组合查询。
- 不接入 CCRM，不在本模块建设 CCRM 原始接入表。
- 外部客户经理关系表是每日全量快照，只读；每日任务只刷新客户主档中已有客户的 AUTO 主办信息。
- 触达历史事实使用 MARKETING_TOUCH_WORKLOG 和 MARKETING_TOUCH_WORKLOG_PICTURE；历史工作日志的 task_id 允许为空，新产生工作日志由服务层要求关联任务。

### 1.2 术语

| 术语 | 定义 |
| --- | --- |
| 客户主档 | MARKETING_CUSTOMER_INFO 中以统一社会信用代码一企一档的客户当前态。 |
| 线索 | MARKETING_LEAD_INFO 中一次独立的营销事项及其完整提交快照。 |
| 在途线索 | lead_status 为 DRAFT、SUBMITTED 或 IN_APPROVAL 的线索。 |
| 导入成功 | 文件行完成校验并生成线索，或在导入处理阶段完成；不代表审批通过。 |
| 审批通过 | 线索或标签客户完成业务审批，允许新增/更新主档或写入正式标签关系。 |
| 主办权为无 | 客户主档 main_manager_id、main_org_id 均为空，ownership_status=UNASSIGNED。无主办客户对全行客户经理可见，但不等于公共待认领池，也不等于所有人可修改。 |
| 有效主办权 | 客户主档 ownership_status=ASSIGNED，且 main_manager_id 对应有效客户经理。 |
| 正式标签关系 | MARKETING_CUSTOMER_TAG_REL 中 active=1 的关系；审批完成前不得写入或激活。 |

### 1.3 统一前后端约定

- 所有接口使用平台统一 ApiResponse 和分页响应，返回 traceId；具体公共结构以 common-dev-guide.md 为准。
- 登录人、登录机构和角色从 CurrentUserApi 获取，前端传入的 empId、orgId 只能作为展示或筛选条件，不能作为权限依据。
- 所有列表、详情、导入、下载和写操作都在后端应用数据范围；前端隐藏按钮不构成授权。
- 业务 Controller 的规划接口使用 @BizAuth，资源登记到 PT_RESOURCE；高危操作使用独立资源和独立审计动作。
- 客户名称、地址、行业等字典字段使用本模块与平台统一字典；员工选择使用员工/机构公开查询 API，不能让前端手工填写任意工号。
- 分页默认 pageNo=1、pageSize=20，最大 pageSize=100；“全部通过”以当前查询条件命中的全部可审批明细为准，不以当前页面已加载行数默默代替。
- 列表默认按业务时间倒序；批量导入明细的失败、异常、警告行排在有效行之前，同一状态按原始行号升序。

## 2. 角色、数据范围和通用权限

### 2.1 角色职责

| 角色 | 页面一 | 页面二 | 页面三 | 页面四 | 页面五 | 页面六 |
| --- | --- | --- | --- | --- | --- | --- |
| 营销管理员/公司部管理人员 | 全部客户查询、编辑、转交、取消主办 | 可查看管理视图 | 可查看导入处理结果并处理异常 | 按审批角色办理 | 标签维护、导入和全量替换 | 标签及客户审批 |
| 客户经理 | 按授权范围只读客户 | 只能看本人主办客户并转给其他有效客户经理 | 新增手工线索、查看本人手工记录、上传批次、处理本人导入确认 | 仅当被工作流授权为审批人时办理 | 按授权读取标签和客户群，不能绕过审批生效 | 仅当被工作流授权为审核人时办理 |
| 线索审批人 | 只读审批所需的当前客户信息 | 不适用 | 不适用 | 查看全部授权待办；审批记录只看本人实际办理记录 | 不适用 | 仅按审批角色查看授权事项 |
| 标签审批人 | 不适用 | 不适用 | 不适用 | 不适用 | 查看待审批标签 | 查看标签审批并联动客户审批 |
| 系统任务账号 | 不直接使用页面 | 不直接使用页面 | 处理导入异步任务 | 通过 WorkflowApi 回调更新状态 | 处理异步导入/替换收敛 | 不直接使用页面 |

实际角色代码、机构数据范围和菜单资源需在 auth-permission-center 中配置。上表是业务能力边界，不是绕过 RBAC 的默认授权。

### 2.2 数据范围规则

1. 页面一只向营销管理员或被授权的管理人员开放。管理员查询范围为 ALL；其他管理角色由 BizScopeApi 解析为授权机构范围。
2. 页面二查询条件必须包含 main_manager_id=当前登录人工号、record_status=ACTIVE、ownership_status=ASSIGNED。
3. 页面三第一个 Tab 必须包含 entry_emp_id=当前登录人工号且 lead_source=MANUAL；不能用 cust_id 或统一社会信用代码分组。
4. 页面三第二个 Tab 默认只显示当前登录人的导入批次；营销管理员可按权限查看全量或机构范围批次。
5. 页面四待审批按 WorkflowApi 返回的候选人/候选组授权查询；不能以“创建人是自己”代替审批权限。审批记录按 Flowable 历史任务中的实际办理人工号过滤。
6. 页面五标签和客户群遵循 TAG/CUSTOMER 数据范围；标签审批和导入权限由独立资源控制。
7. 页面六待审批按工作流候选权限和业务数据范围过滤；审批记录默认是当前登录人实际办理的标签/客户审批记录。

## 3. 页面一：营销客户列表

### 3.1 页面目标和数据来源

页面名称：营销客户列表。
主要数据来源：MARKETING_CUSTOMER_INFO；主办变更补充读取 MARKETING_CUSTOMER_TRANSFER_LOG 和 MARKETING_CUSTOMER_TRANSFER_TARGET；有效标签和最近触达信息按需关联查询。

页面展示营销客户主档的当前信息，不展示未经审批的线索作为客户主档。客户主档查询不依赖 CCRM。

### 3.2 查询条件

支持单条件或组合条件：

| 条件 | 查询说明 |
| --- | --- |
| 企业名称 | 模糊查询，建议使用标准化或前缀索引策略；不得以名称作为唯一键。 |
| 统一社会信用代码 | 精确查询，先标准化大小写和空白。 |
| 客户号 | 精确查询，可为空的未开户客户不因无客户号被排除。 |
| 主办客户经理 | 员工选择器，支持工号和姓名检索。 |
| 主办状态 | ASSIGNED、UNASSIGNED、UNKNOWN、CONFLICT。 |
| 开户状态 | 已开户、未开户、未知。 |
| 行业/集团/客户类型/企业性质 | 字典多选。 |
| 重点客户 | 是/否。 |
| 维护模式 | AUTO、MANUAL。 |
| 资料更新时间 | 时间范围。 |

查询条件、排序字段和数据范围由后端重新校验；不得接受前端传入的 SQL 片段或任意列名。

### 3.3 列表字段

建议列：

- 客户 ID、客户号、企业名称、统一社会信用代码。
- 法定代表人、联系人、联系电话、注册地址、经营地址。
- 行业、集团名称、客户类型、企业性质、是否重点客户。
- 开户状态、授信金额、授信敞口金额、触达限制。
- 当前主办客户经理、主办机构、主办状态、主办来源、维护模式。
- 最近有效触达时间、资料版本、最后更新时间。
- 操作：查看详情、编辑、转交主办权；无主办状态显示“指定主办”，不显示认领按钮。

金额和联系方式按页面权限脱敏；编辑页面在权限不足时只读展示。

### 3.4 详情和编辑

详情页分为基本信息、经营/授信信息、开户和主办信息、标签、触达摘要、变更记录摘要。

管理员可直接修改以下允许维护字段：

- 企业名称、法定代表人、联系人、联系电话。
- 注册地址、实际经营地址、经营范围。
- 行业、集团信息、客户类型、企业性质、重点客户标志。
- 客户描述、授信金额、授信敞口金额、触达限制。

以下字段不能通过普通编辑接口修改：

- 主键 id、统一社会信用代码、客户号。
- 开户状态和完成开户人；开户状态只能由开户确认/业务流程受控更新。
- main_manager_id、main_org_id、ownership_status、ownership_source、ownership_maintain_mode；主办权必须通过专用转交接口修改。
- 客户标签正式关系；必须通过标签导入/审核流程变更。

保存时必须提交 lock_version。成功后返回最新 profile_version、lock_version 和更新时间；发生版本冲突时不覆盖他人修改。

### 3.5 转交主办权

管理员操作：

1. 点击“转交主办权”打开弹窗，展示当前主办人、机构、开户状态和维护模式。
2. 选择一个有效客户经理，或选择“无主办”。
3. 填写转交原因，确认影响范围。
4. 提交后后端重新读取客户主档并执行并发校验。

转交到其他客户经理时：

- transfer_action=TRANSFER，写入 MARKETING_CUSTOMER_TRANSFER_LOG 和唯一 PRIMARY 的 TARGET。
- 更新客户主档 main_manager_id、main_org_id、ownership_status=ASSIGNED。
- ownership_source=MANUAL，ownership_maintain_mode=MANUAL，记录人工维护原因。

设置为无主办时：

- transfer_action=UNASSIGN。
- primary_to_manager_id、primary_to_org_id 必须为空，不生成 TARGET 明细。
- 更新 main_manager_id、main_org_id 为空，ownership_status=UNASSIGNED。
- ownership_source=MANUAL、ownership_maintain_mode=MANUAL，防止次日 AUTO 同步直接恢复。
- 不自动生成公共待认领线索，也不删除历史认领或触达记录。

### 3.6 页面一后端逻辑

查询服务按主档当前态分页返回，所有字段的名称、机构和员工展示值由服务层补齐。写服务流程如下：

1. 读取当前登录上下文并校验 CUSTOMER.WRITE 或 CUSTOMER.TRANSFER 权限。
2. 按 id 加载客户，校验 record_status=ACTIVE 和数据范围。
3. 资料编辑检查允许字段、数据字典、金额范围和 lock_version。
4. 主办转交检查目标员工有效、目标员工为客户经理、目标机构可解析；UNASSIGN 仅管理员可用。
5. 在一个事务中以乐观锁更新主档、写转交主记录/目标记录、写审计。
6. 更新失败返回版本冲突或目标无效，不重复写转交记录。

### 3.7 页面一规划接口

| 方法 | 规划路径 | 用途 | 权限 |
| --- | --- | --- | --- |
| GET | /api/marketing/customers | 分页查询全部营销客户 | CUSTOMER/LIST |
| GET | /api/marketing/customers/{id} | 查询客户详情 | CUSTOMER/READ |
| PUT | /api/marketing/customers/{id}/profile | 修改允许维护的客户资料 | CUSTOMER/WRITE |
| POST | /api/marketing/customers/{id}/transfer | 指定、转交或取消主办权（由 transferAction 区分） | CUSTOMER/TRANSFER，高危 |
| GET | /api/marketing/customers/{id}/transfer-logs | 查询转交摘要 | CUSTOMER/READ |

以上路径是规划契约名，落地时需同步 03-接口设计与报文.md、PT_RESOURCE 和 Controller 的 @BizAuth。

## 4. 页面二：我的客户

### 4.1 页面目标和查询

页面名称：我的客户。数据仍直接来自 MARKETING_CUSTOMER_INFO，不从认领表拼出主办客户。

固定后端条件：

- main_manager_id=当前登录人工号。
- ownership_status=ASSIGNED。
- record_status=ACTIVE。

支持企业名称、统一社会信用代码、客户号、开户状态、行业、重点客户、标签和最近触达时间查询。页面不得允许用户通过修改查询参数查看其他员工主办客户。

### 4.2 列表和详情

列表字段沿用页面一的客户主档字段，增加：

- 主办开始/最近转交时间。
- 当前维护模式。
- 正在进行的触达任务数和最近任务状态。
- 开户状态及开户完成客户经理（按权限展示）。

点击详情展示客户主档当前态、有效标签、本人可见的触达摘要和转交入口。未主办、冲突或已失效的客户不出现在本页面。

### 4.3 转交限制

客户经理只能将当前自己主办的客户转交给其他有效客户经理：

- 目标客户经理必填，不能选择“无”。
- 目标员工必须有效且不能等于当前登录人。
- 当前登录人必须仍是客户主档 main_manager_id；页面打开后主办权发生变化时提交失败并提示刷新。
- 需要填写转交原因。
- 不允许由本页面改变开户状态、统一社会信用代码或客户正式标签。

成功转交后，原客户立即从当前登录人的列表消失，进入新主办人的“我的客户”；ownership_maintain_mode 改为 MANUAL，次日自动同步不覆盖。

### 4.4 页面二后端事务

1. 通过 CurrentUserApi 取得当前员工。
2. 加锁或以 lock_version CAS 读取客户。
3. 校验当前主办人等于当前员工且客户仍有效。
4. 校验目标员工为有效客户经理并解析主机构。
5. 同一事务更新主档、写 TRANSFER_LOG（TRANSFER）和 PRIMARY TARGET，写审计。
6. 若存在以旧主办人作为接收人的未完成任务，按业务规则更新任务归属；不能静默删除工作日志。
7. 返回新主办人和客户最新版本。

### 4.5 页面二规划接口

| 方法 | 规划路径 | 用途 |
| --- | --- | --- |
| GET | /api/marketing/customers/mine | 查询本人主办客户 |
| GET | /api/marketing/customers/mine/{id} | 查询本人有权查看的详情 |
| POST | /api/marketing/customers/{id}/transfer | 转交给其他客户经理 |

管理员恢复 AUTO 是管理能力，归入页面一或管理员专用接口：

| 方法 | 规划路径 | 用途 |
| --- | --- | --- |
| POST | /api/marketing/customers/{id}/ownership/restore-auto | 恢复自动同步并立即按最新快照刷新 |

## 5. 页面三：线索录入

### 5.1 页面总原则

页面三有两个 Tab，但数据粒度不同：

- Tab 一是手工线索记录，粒度为一条 MARKETING_LEAD_INFO；每条线索一行，不聚合。
- Tab 二是批量导入批次，粒度为一条 MARKETING_LEAD_IMPORT_BATCH；点击批次详情后按 MARKETING_LEAD_IMPORT_DETAIL 展示原始行。

同一企业在不同时间产生多条已结束营销线索是正常情况，Tab 一不会将它们合并为一行，也不会在点击详情时默认聚合展示该企业全部线索。详情只展示当前选中的这条线索快照、当前客户主档和字段差异；如需查历史，使用独立的线索查询/审计能力，不改变本页面粒度。

### 5.2 Tab 一：手工线索记录

#### 5.2.1 列表查询

固定条件：

- entry_emp_id=当前登录人工号。
- lead_source=MANUAL。
- record_status=ACTIVE。

不按 cust_id、cust_name 或 unified_credit_code GROUP BY。排序为 entry_time DESC、id DESC。

建议列：

| 列 | 含义 |
| --- | --- |
| 线索编号 | lead_no |
| 企业名称 | 线索提交快照 cust_name |
| 统一社会信用代码 | 标准化后的统一社会信用代码 |
| 线索类型 | NEW_ACCOUNT 或 EXISTING_MARKETING |
| 客户匹配情况 | NEW_CUSTOMER、MATCHED_EXISTING_UNOPENED、MATCHED_EXISTING_OPENED |
| 提交时开户状态 | is_account_opened_snapshot |
| 提交时主办提示 | main_manager_id_snapshot、main_org_id_snapshot |
| 分配方式 | PUBLIC、SCOPE、OWNER |
| 录入时间 | entry_time |
| 线索状态 | DRAFT、SUBMITTED、IN_APPROVAL、APPROVED、REJECTED、CANCELLED |
| 审批结果/时间 | reviewed_by、reviewed_time、reject_reason |
| 操作 | 查看详情、编辑草稿、提交审批 |

线索已审批通过后再次产生的新营销事项，应作为新行展示；不得因为已有客户主档而合并或覆盖原线索记录。

#### 5.2.2 新增和客户反显

新增页面先录入统一社会信用代码，服务端按标准化统一社会信用代码查询：

1. 命中在途线索时立即阻止新增，并返回原线索编号、状态、原录入人、机构和录入时间。
2. 未命中在途线索但命中 MARKETING_CUSTOMER_INFO 时，页面反显当前客户主档资料、开户状态、客户号、主办人和机构。
3. 命中存量未开户客户，默认 lead_type=EXISTING_MARKETING；允许客户经理确认本次营销字段。
4. 命中存量已开户客户，仍允许营销；必须显著提示“该客户已开户”和当前主办归属，由录入人确认后继续。
5. 未命中客户主档时，按 NEW_ACCOUNT 填写企业详细信息。

反显的数据是录入初始值，不代表已经更新主档。用户提交的企业名称、联系人、地址、授信敞口等完整数据写入线索快照；审批通过前不得修改客户主档。

#### 5.2.3 主办权提示

如果存量客户有有效主办权：

- 强制 distribution_mode=OWNER。
- 保存主办人和机构快照，并为 OWNER 建立一条接收人范围记录。
- 录入人不是主办人时，给出“主办权归属”提示，提供继续并推送主办人、发起跨机构营销申请或取消录入的选择。
- 不允许将该线索改成 PUBLIC 或 SCOPE 来绕开主办权。

如果存量已开户客户无主办或主办冲突，默认不开放公共认领，由管理员先处理主办异常；录入页可保存为待处理草稿，但提交时必须选择管理员处理路径或由有权限人员指定 OWNER。

#### 5.2.4 手工录入状态和操作

状态流程：

新建 → DRAFT → 提交 → SUBMITTED → 流程受理 → IN_APPROVAL → APPROVED 或 REJECTED；草稿允许删除或取消，终态线索不复用原记录。

保存草稿时：

- 校验基础字段和格式，不要求客户主档已经存在。
- 记录 entry_emp_id、entry_org_id、entry_time。
- 对统一社会信用代码做在途去重提示；草稿本身也占用 active_dedup_key，防止同一时间多条在途线索。

提交审批时：

- 再次校验在途去重和当前客户主档。
- 保存提交快照、主办快照、标签快照和 base_customer_profile_version。
- 通过 WorkflowApi.startProcess 发起单条线索流程，业务键规划为 LEAD:{leadId}。
- 只有流程启动成功后才将线索置为 SUBMITTED/IN_APPROVAL；启动失败事务回滚。

建议列：

#### 5.3.2 OBS 文件

上传原文件、错误明细文件和重新导入所需的文件均通过 system-governance 的 FileApi 管理，FileApi 内部使用平台的 OBS 存储客户端：

- 上传成功后只在业务表保存 file_object_id、文件名、摘要和媒体类型，不保存可长期公开的 OBS URL。
- 下载接口先校验批次权限，再由 FileApi 生成短时下载地址或流式输出；前端不直接访问 OBS Bucket。
- 文件名按平台安全策略处理，防止路径穿越和脚本内容；下载响应设置正确的文件名和 Content-Disposition。
- 错误明细下载由服务端生成并登记 error_file_id；生成内容包含原始行号、失败原因和可修正字段，不泄露无权查看的客户数据。
- 原文件和错误文件的留存、病毒扫描、大小和类型限制由治理中心统一执行。

#### 5.3.3 行级校验和状态

导入按行处理，不因一行失败拒绝整个文件：

| 行状态 | 说明 | 后续处理 |
| --- | --- | --- |
| VALID | 字段和业务校验通过 | 生成 MARKETING_LEAD_INFO |
| WARNING | 可生成线索但需要人工确认，例如文件携带的主办人与当前主档不一致 | 进入 WAITING_CONFIRM，等待只处理正常行或放弃重传 |
| REJECTED | 命中在途线索等业务拒绝 | 只保留在导入明细，展示失败原因 |
| ERROR | 模板、格式、企业身份或字典校验异常 | 只保留在导入明细，展示失败原因 |

每个明细保留原始行号、原始企业字段、标准化统一社会信用代码、匹配客户 ID、命中的在途线索 ID/原录入人信息、生成线索 ID、错误码和错误原因。

明细默认排序：

1. REJECTED；
2. ERROR；
3. WARNING；
4. VALID；
5. 同一状态按 row_no 升序。

#### 5.3.4 批次处理流程

流程：

上传 OBS 文件 → 创建批次 → 解析和行级校验 → 根据是否存在 WARNING 决定直接处理或先待确认。

- 全部行成功生成线索：导入处理状态为 COMPLETED，可继续提交线索审批。
- 全部行失败或没有可生成线索：状态为 ALL_FAILED，不创建空审批批次。
- 有有效行且存在 WARNING 或需要人工确认的主办冲突：状态为 WAITING_CONFIRM。此时只保存批次和明细，所有行均不生成线索，避免用户放弃重传后遗留在途数据。
- 仅有 REJECTED/ERROR 行不需要确认，状态为 ALL_FAILED 或按产品定义显示“失败”。
- 文件解析异常、OBS 失败或系统异常时保留可重试的批次状态；线索生成依赖明细 handling_status 和 active_dedup_key 幂等防重。

WAITING_CONFIRM 页面必须提供两个明确动作：

1. “仅处理正常数据”：确认处理 VALID 行，跳过 WARNING/REJECTED/ERROR 行；批次进入 COMPLETED，随后可对生成线索提交审批。
2. “放弃并重新导入”：批次进入 ABANDONED，保留原明细和文件，用户下载原文件或错误文件修改后创建新批次。原批次不可被重复确认、不可复用为新批次。

用户确认时可填写备注。确认接口使用批次 lock_version/状态 CAS，避免重复点击导致重复生成线索。

#### 5.3.5 重复和主办权规则

- 同一统一社会信用代码的 DRAFT、SUBMITTED、IN_APPROVAL 只能有一条有效在途线索。
- 文件内同码重复行逐行标记 REJECTED，并在原因中指出冲突行号。
- 命中其他批次或其他人员的在途线索时，返回原线索编号、状态、录入人、机构和时间，提示当前操作人；不创建新线索。
- 命中已存在客户主档不是拒绝理由；审批页必须展示客户当前开户和主办信息。
- 文件携带主办人仅作为请求和提示。不能通过批量导入直接覆盖客户主档主办权；与当前主档不一致时进入 WARNING/WAITING_CONFIRM 或按管理员处理路径。

## 6. 页面四：线索审批

### 6.1 Tab 和审批粒度

页面名称：线索审批，包含“待审批”和“审批记录”两个 Tab。

- 待审批以一条 MARKETING_LEAD_INFO 为审批粒度，页面可按客户字段展示，但审批动作必须落到具体 lead_id。
- 批量导入只表示来源批次，不作为不可拆分的审批单据；批次内有效线索可以逐条审批。
- 待审批展示所有当前审批角色有权办理的 SUBMITTED/IN_APPROVAL 线索。
- 审批记录只展示当前登录人通过 Flowable 历史任务实际办理过的线索；不能只按 reviewed_by 推断完整历史。
- 为避免同一TAG_IMPORT客户同时出现在两个审批页，本页只处理lead_source=MANUAL/LEAD_IMPORT；TAG_IMPORT产生的客户审批只在页面六办理，但复用同一客户主档装配和线索幂等状态推进服务。

### 6.2 待审批列表

建议查询条件：

- 企业名称、统一社会信用代码、客户号。
- 线索来源 MANUAL、LEAD_IMPORT。
- 线索类型、开户状态、当前主办人、录入机构、录入人、提交时间。
- 批次号和标签导入批次号。

建议列：

- 线索编号、企业名称、统一社会信用代码、客户匹配情况。
- 录入人/机构/时间、线索来源、客户号。
- 当前主档开户状态、当前主办客户经理和机构。
- 线索提交开户状态、分配方式、标签快照。
- 提交时间、当前流程节点、操作：查看、通过、驳回。

### 6.3 审批详情

详情必须同时展示：

1. 线索提交快照：企业名称、统一社会信用代码、联系人、地址、行业、客户类型、授信金额和敞口金额等。
2. 当前客户主档：如果 cust_id 已存在，展示当前名称、联系人、地址、开户状态、客户号和主办权。
3. 差异视图：线索快照值、当前主档值、变更字段和资料版本。
4. 主办权提示：已有主办的存量客户必须显著提示，审批通过不自动改主办。
5. 在途触达/开户提示：涉及已有开户或完成开户的任务时展示只读状态。
6. 标签快照和导入批次明细（来源为导入时）。

### 6.4 审批动作

审批通过：

- 重新读取 lead 和当前客户主档，不以列表快照执行。
- NEW_ACCOUNT 且未命中主档：新增 MARKETING_CUSTOMER_INFO，回填 lead.cust_id。
- EXISTING_MARKETING：按允许字段更新已存在主档，保留 id、客户号、统一社会信用代码、开户状态和主办权。
- 如果 base_customer_profile_version 与当前 profile_version 不一致，返回资料冲突，要求审批人刷新并重新确认；不覆盖当前主档。
- 根据 distribution_mode 和业务条件更新线索池状态/认领关系，但未审批线索不得提前入池。
- 事务成功后更新 lead 状态、审批人/时间，提交审批通过事件或工作流回调。

审批驳回：

- 必须填写驳回原因。
- 只将当前线索置为 REJECTED，不改变客户主档和正式标签关系。
- 释放 active_dedup_key，允许后续创建新的营销事项；旧线索保留供历史查询。

审批动作必须幂等：已 APPROVED/REJECTED 的线索重复回调返回既有结果，不重复新增主档、标签关系或认领记录。

## 7. 页面五：营销客户标签

### 7.1 页面目标和列表粒度

页面名称：营销客户标签，按正式标签维度展示客户群。

主列表来自 MARKETING_CUSTOMER_TAG，客户数量来自 MARKETING_CUSTOMER_TAG_REL 中 active=1 的正式关系统计。点击标签进入客户群列表，客户信息来自 MARKETING_CUSTOMER_INFO 和有效标签关系。

标签页支持：

- 按名称、分类、启用状态、审批状态查询。
- 新增标签。
- 按模板导入。
- 进入标签客户群查看客户详情。
- 选择追加导入或全量替换导入。
- 查看该标签的导入批次、待审批数量和最近一次生效时间。

禁用或未审批标签不出现在普通营销选择器；历史审批记录保留标签名称快照。

### 7.2 标签客户群

客户群列表建议列：

- 客户号、企业名称、统一社会信用代码、开户状态。
- 主办人/机构、行业、客户类型、授信敞口。
- 标签生效时间、标签关系来源、最近导入批次。
- 操作：查看客户详情、查看导入/审批来源。

查询只返回正式关系 active=1。处于标签导入审批中的客户不伪装成正式客户群成员，可在“待审批客户”入口查看。

### 7.3 新增标签

新增标签弹窗字段：

- 标签名称、分类、类型、优先级、描述、有效期。

规则：

- 标签名称全行唯一，忽略大小写和首尾空白。
- 新建标签先写 MARKETING_CUSTOMER_TAG.approval_status=PENDING，不直接进入可用标签。
- 启动标签审批流程；审批通过后 status 才可按权限启用。
- 标签驳回必须保存原因；驳回标签不能接收正式关系。
- 同一标签名称存在审批中申请时提示原申请编号和申请人，不重复创建。

### 7.4 追加导入

追加导入以目标标签和一个导入批次为单位：

1. 选择已存在且已审批、已启用的标签。
2. 下载并填写模板，上传文件到 OBS。
3. 服务端解析每行企业身份和客户字段，命中客户主档则反显当前资料。
4. 每个有效客户创建一条 TAG_IMPORT 导入明细，并生成一条用于客户审批的线索或审批事项。
5. 审批通过后，受控更新客户主档（如有资料变化），再新增/恢复 MARKETING_CUSTOMER_TAG_REL。
6. 单个客户被驳回不影响其他客户已经完成的审批；追加批次汇总为部分通过、全部通过或存在驳回。

已存在标签不需要重新审批标签本身，但导入客户仍必须逐客户审批。已存在客户不是拒绝条件，审批页显示其开户和主办信息。

### 7.5 全量替换导入

全量替换也是一个独立批次，模式为 REPLACE。上传阶段只生成批次和明细，不改变现有正式客户群。

安全生效条件：

- 目标标签审批状态为 APPROVED。
- 批次全部有效客户均完成客户审批并通过。
- 批次不存在未处理的有效客户、校验错误或待人工确认。
- 任一有效客户被拒绝，批次状态为 REPLACE_BLOCKED，正式关系完全不变。
- 标签同一时刻只能有一个未结束的 REPLACE 批次；追加批次可以按锁和业务规则排队或拒绝。

全部通过后，在一个受锁保护的事务中：

1. 锁定目标标签及当前生效关系集合。
2. 将旧关系中不在本批次有效客户集合内的关系置为失效并写失效时间。
3. 新增或恢复本批次全部客户关系。
4. 将批次置为 COMPLETED 并记录生效时间。

前端在全量替换确认页必须显示将新增、保留和移除的数量；数量来自后端预览令牌，执行时仍须重新计算，不能只相信前端。

## 8. 页面六：标签客户审核

### 8.1 Tab 和展示粒度

页面名称：标签客户审核，包含“待审批”和“审批记录”两个 Tab。

待审批以标签维度展示一行标签摘要，展开或点击“待审批客户”显示该标签下的待审批客户数和客户明细。标签审批和客户审批来自不同的业务对象，但在同一页面关联展示：

- 标签审批对象：MARKETING_CUSTOMER_TAG。
- 客户审批对象：MARKETING_CUSTOMER_TAG_IMPORT_DETAIL 关联的 lead_id/客户审批状态；如需复用统一流程，工作流业务对象为对应 MARKETING_LEAD_INFO。

不把未审批客户写入 MARKETING_CUSTOMER_TAG_REL；正式标签客户群只展示已生效关系。

### 8.2 待审批 Tab

标签维度表格建议列：

- 标签名称、标签分类、导入模式 APPEND/REPLACE。
- 导入批次号、导入文件名、导入人、导入时间。
- 标签审批状态、待审批客户数、已通过数、已拒绝数、异常数。
- 全量替换预期新增/移除数量和当前生效状态。
- 操作：标签通过、待审批客户、查看批次详情。

按钮规则：

- 标签为 PENDING 时显示“标签通过”；已通过或已驳回时按状态显示，不重复提供通过。
- 有待审批客户时显示“待审批客户”；没有待审批客户时显示数量为 0。
- REPLACE 批次即使标签通过，也不能在客户全部通过前生效。
- 当前人不是工作流候选人时不返回操作按钮，后端仍必须再次校验。

### 8.3 待审批客户抽屉

点击“待审批客户”打开抽屉，默认展示该标签、批次和客户列表；支持按企业名称、统一社会信用代码、客户匹配情况、开户状态、主办人、审批状态筛选。

客户明细字段：

- 导入企业字段快照和原始行号。
- 命中的客户号、当前客户主档信息。
- 统一社会信用代码、企业名称、联系人、地址、行业、客户类型、授信敞口。
- 当前开户状态、当前主办人/机构和主办权提示。
- 客户审批状态、来源线索、失败原因、拒绝原因、资料版本。
- 差异字段：导入值、主档当前值、审批通过后拟更新值。

抽屉支持：

- 单选客户审批通过或驳回。
- 勾选多个客户后批量审批通过/驳回；驳回必须填写统一原因或逐条原因。
- “全部通过”由后端按当前标签和筛选条件重新解析全部可审批明细，再按受控批大小分段调用与单条审批相同的幂等服务；返回逐条成功/跳过/失败统计，不信任前端传入的总数。

### 8.4 标签未审批时的联动

当客户审批人点击客户“审批通过”，而该客户所属标签 approval_status 仍为 PENDING 时：

1. 后端不直接完成客户通过，返回 CUST-40905 TAG_APPROVAL_REQUIRED，附带 tagId、tagName、batchId 和本次 detailId 列表。
2. 前端弹窗提示：“标签【XXX】尚未审批，是否先通过标签审批请求？”
3. 用户取消：保留客户待审批状态，不产生任何主档或正式关系变更。
4. 用户确认：调用标签通过接口；服务端重新校验当前人标签审批权限、标签状态和版本。
5. 前端保留原选中detailId，并以同一批量审批请求重试，增加 approveTag=true；后端在审批标签后继续处理原选中客户。
6. 后端重新读取并校验这些 detailId；已被其他人处理的明细返回逐条结果，不重复审批。
7. 客户审批完成后，按追加或全量替换规则决定是否写正式关系。

后端不信任前端保留的detailId，每次都重新校验当前人的标签/客户审批权限、标签和明细状态及版本。approveTag=true只表示当前人确认先审批标签，不能跳过后端校验。

### 8.5 审批记录 Tab

默认展示当前登录人实际办理过的标签审批和客户审批记录，建议列：

- 审批对象类型、标签、导入批次、客户、审批动作。
- 原状态、结果、审批人、审批时间、意见/拒绝原因。
- 全量替换批次的最终生效状态。

管理员若需要查询全行历史，必须使用额外授权和数据范围参数；不能通过修改 reviewerId 查询他人个人审批记录。

## 9. 状态机和跨页面业务链路

### 9.1 线索状态

DRAFT → SUBMITTED → IN_APPROVAL → APPROVED
DRAFT → CANCELLED
SUBMITTED/IN_APPROVAL → REJECTED

只有 APPROVED 线索才能：

- 新增客户主档或受控更新现有客户主档。
- 按分配方式进入线索池组合查询。
- 产生客户认领关系或后续触达。

### 9.2 线索批次状态

导入处理状态：

IMPORTING → VALIDATED → COMPLETED
VALIDATED → WAITING_CONFIRM → COMPLETED
WAITING_CONFIRM → ABANDONED
VALIDATED/WAITING_CONFIRM → ALL_FAILED（没有可处理的有效行）

线索审批状态与导入处理状态独立展示：

NOT_SUBMITTED → SUBMITTED → IN_APPROVAL → APPROVED/REJECTED

批次终态不能重新确认或重复生成线索；重新处理必须创建新批次。

### 9.3 标签和标签导入状态

标签：

PENDING → APPROVED
PENDING → REJECTED
APPROVED → DISABLED（停用不删除历史关系）

标签导入明细的校验和客户审批状态分开保存：

VALID → PENDING → APPROVED/REJECTED
ERROR/REJECTED → NOT_REQUIRED

追加批次：

IMPORTING → VALIDATED → IN_APPROVAL → COMPLETED

逐条审批期间批次仍保持 IN_APPROVAL，通过 approved_count/rejected_count 和 customer_approval_status 表示部分完成；已通过的 APPEND 明细可逐条生效。

全量替换批次：

IMPORTING → VALIDATED → IN_APPROVAL → READY_TO_LOAD → COMPLETED
IN_APPROVAL/READY_TO_LOAD → REPLACE_BLOCKED（任一有效客户被拒绝或生效前再校验不通过）
任何未生效阶段 → CANCELLED

REPLACE_BLOCKED 的正式关系必须与执行前完全一致。

### 9.4 存量已开户客户再次营销

已有开户状态不阻止新线索。提交和审批时始终显示开户信息：

- 有有效主办：线索 OWNER 路由，审批通过后客户仍在主办人的已认领客户池；不进入公共待认领池。
- 无主办/主办冲突：默认由管理员处理，不自动开放公共认领。
- 录入人不是主办人：必须提示主办归属，可继续推送主办人或走跨机构营销申请。

### 9.5 触达成功开户后的收敛

触达任务状态 SUCCESS 本身不等于开户完成。取得客户号或开户确认审批通过后，服务在一个业务事务中：

1. 更新客户主档开户状态、开户完成员工和时间，必要时写 opening_touch_task_id。
2. 将完成开户的员工设置为主办人，写 OPEN_ACCOUNT 来源的转交记录。
3. 将同客户其他 PENDING/IN_PROGRESS 触达任务置为 CANCELLED，原因 CUSTOMER_OPENED_BY_OTHER。
4. 取消其他有效认领关系，关闭仍 AVAILABLE 的公共线索。
5. 后续再录入该客户时展示新的主办归属并按 OWNER 路由。

页面一、二只展示收敛后的客户当前态；触达和开户来源保留在各自事实/审计记录中。

## 10. 后端分层和服务逻辑

### 10.1 推荐分层

- Controller：参数校验、统一响应、@BizAuth、文件上传/下载入口。
- Facade：编排跨表事务和 WorkflowApi/FileApi/Auth API。
- Service：客户、主办、线索、导入、标签、审批和替换领域规则。
- Mapper：单表 CRUD 使用 MyBatis-Plus；分页组合查询、批量更新和带乐观条件更新使用明确的 Mapper SQL。
- Event/Callback：接收 WorkflowApi 的公开完成事件，按 business_key 幂等回写业务表。

customer-marketing-center 不直接引用 workflow-center 内部 Mapper、Flowable Service 或 ACT_RU_/ACT_HI_ 表；通过 WorkflowApi 发起、办理和查询。

### 10.2 客户主档和主办权

- 客户主档唯一匹配按标准化统一社会信用代码；名称仅作查询条件。
- 允许编辑字段和主办字段分离，避免普通资料修改意外覆盖主办权。
- AUTO 客户由每日外部全量快照任务更新；MANUAL 客户跳过。
- 恢复 AUTO 时立即读取最新快照，成功、无匹配、多主办和员工解析失败分别更新 ASSIGNED、UNASSIGNED、CONFLICT/UNKNOWN。
- 同步任务不创建客户，不覆盖 MANUAL，不删除转交日志。

### 10.3 线索导入和审批

- 解析文件必须在服务端完成；预览结果只作提示，最终执行重新校验。
- 每批次、每行均有稳定业务 ID；使用 batch_id + row_no 防重。
- 生成线索时依赖 active_dedup_key 唯一约束和服务层重查，数据库冲突统一转换为重复线索错误。
- 审批通过使用主档 lock_version/profile_version；任一资料版本冲突只阻止当前线索，不回滚已经完成的其他线索审批。
- 回调以 lead_id/business_key 幂等；重复回调不重复写主档。

### 10.4 标签导入和审批

- MARKETING_CUSTOMER_TAG_IMPORT_BATCH 是一标签一批次的头；DETAIL 是逐客户审批和结果的唯一事实。
- 新标签和既有标签都必须产生导入批次；既有标签省略标签审批，但不能省略客户审批。
- 新客户和存量客户统一使用客户审批明细；新客户审批通过后新增主档，存量客户按资料版本受控更新。
- 正式 TAG_REL 只由审批收敛服务写入/恢复；预导入旧表 MARKETING_TOUCH_CUSTOMER_TAG_SOURCE 的 loaded_flag 不能替代客户审批状态。
- 全量替换通过标签锁和批次状态 CAS 保证只执行一次；执行前再次计算本批次有效客户集合。

### 10.5 数据范围和二次授权

每个 Service 写操作都要基于数据库重读的实体做二次校验：

- 客户资料修改和主办转交：检查当前权限、主档状态、当前主办和 lock_version。
- 手工线索：检查 entry_emp_id、草稿状态和录入权限。
- 导入批次：检查 import_emp_id/机构范围和批次状态。
- 审批：检查 WorkflowApi 候选权限、当前任务状态和业务对象状态。
- 标签：检查标签权限、标签 approval_status、导入批次所属范围和客户明细状态。

## 11. 并发、事务和幂等

### 11.1 事务边界

| 场景 | 一个事务必须包含 |
| --- | --- |
| 客户资料修改 | 重读主档、版本校验、更新资料、审计 |
| 主办转交/取消 | 重读主档、权限校验、更新主档、写转交记录/目标、审计 |
| 手工线索提交 | 去重、保存快照、启动流程映射、更新线索状态 |
| 批量导入有效行 | 批次状态、逐行校验结果、有效线索生成；大文件按有界分片并以行状态幂等 |
| 线索审批通过 | 锁线索/主档、资料版本校验、新增或更新主档、回填 cust_id、更新线索、事件/审计 |
| 标签审批 | 锁标签、校验版本、更新标签审批状态、流程回写和审计 |
| 标签客户审批 | 锁明细、主档资料版本校验、更新明细、必要时主档更新和正式关系载入 |
| 全量替换 | 锁标签和替换批次、重算集合、失效/新增关系、更新批次生效状态 |

跨表操作必须保证异常回滚；耗时的文件解析、OBS 上传和工作流启动采用可重试的状态机，不在事务中持有长时间数据库锁。

### 11.2 乐观锁和唯一性

- 客户主档使用 lock_version；资料审批使用 base_customer_profile_version 对比 profile_version。
- 线索 active_dedup_key 在途状态取统一社会信用代码，终态置空；数据库唯一约束和应用预检查同时生效。
- 导入明细唯一 batch_id + row_no；同一文件重复上传以 checksum 提示，但不能仅以文件摘要决定业务成功。
- 客户标签关系以 cust_id + tag_id 唯一；正式关系使用 active/失效时间表达生命周期，不物理删除。
- 同一标签同一时刻只允许一个未结束 REPLACE；可使用唯一业务锁或 LockManager，锁超时必须可恢复。

### 11.3 幂等键和重试

- 客户资料和转交使用请求号、lock_version 和业务对象状态组合防重。
- 线索流程使用 LEAD:{leadId}；导入批次使用 batch_no/business_key；工作流回调以 business_key 和状态 CAS 幂等。
- 导入确认使用 batch_id + confirm_action + 服务端一次性确认令牌；终态重复确认返回既有结果。
- 标签客户审批使用 detail_id + 审批动作；批量审批逐条返回成功、已处理、版本冲突和失败原因。
- OBS 上传重试使用文件对象 ID/摘要，不重复创建业务批次或客户关系。

## 13. 审计和日志

以下动作必须通过平台审计记录 before/after、操作人、机构、请求号、traceId、结果和原因：

- 客户资料修改。
- 管理员转交主办、取消主办、恢复 AUTO。
- 手工线索创建、提交、取消、批量导入和导入确认。
- 线索审批通过、驳回及工作流回调。
- 标签新增、修改、停用。
- 标签客户追加导入、全量替换预览/确认/生效/阻断。
- 标签审批、客户单条/批量/全部审批。
- 原文件和错误文件下载。

审计要求：

- 客户名称、统一社会信用代码、联系人、地址、敞口等按照平台敏感字段策略记录必要快照；手机号、金额和账号等按现行规则脱敏。
- 导入审计保存批次、文件对象 ID、摘要、总行数、有效/失败/待确认数量、确认动作和结果。
- 全量替换审计保存生效前后关系数量、批次、标签、操作人和阻断原因。
- 应用日志不得打印完整原始文件、OBS 凭证或未脱敏客户数据。
- 审计失败按平台策略阻止高危操作或进入可告警补偿队列，不得静默吞掉。

| 客户 | MARKETING_CUSTOMER_CLAIM | 线索认领和取消；不作为页面二主办列表唯一来源。 |
| 客户 | MARKETING_CUSTOMER_TAG / TAG_REL | 页面五正式标签和客户群；审批前不写 TAG_REL。 |
| 线索 | MARKETING_LEAD_INFO | 页面三 Tab 一逐条记录、页面四审批对象；无版本链。 |
| 线索 | MARKETING_LEAD_IMPORT_BATCH / DETAIL | 页面三 Tab 二批次、逐行结果和 OBS 文件引用。 |
| 触达 | MARKETING_TOUCH_TASK / WORKLOG / PICTURE 等 | 客户触达和开户收敛；不作为六页面主数据来源。 |
| 标签导入 | MARKETING_CUSTOMER_TAG_IMPORT_BATCH | 标签追加/替换批次、文件、统计、审批和生效汇总。 |
| 标签导入 | MARKETING_CUSTOMER_TAG_IMPORT_DETAIL | 逐客户快照、匹配、线索、审批状态、关系载入结果。 |

05-表结构DDL.md 需要与本设计同步确认以下字段语义：

- MARKETING_CUSTOMER_TRANSFER_LOG 增加 transfer_action；UNASSIGN 时目标员工字段可为空且不写 TARGET。
- MARKETING_LEAD_INFO 的 lead_source 至少区分 MANUAL、LEAD_IMPORT、TAG_IMPORT，并能关联 TAG_IMPORT 明细；entry_emp_id、entry_time 必须可查询。
- MARKETING_LEAD_INFO 保留 customer_match_status、开户快照、主办快照、base_customer_profile_version 和 active_dedup_key，不恢复 prev_lead_id/version_no/is_latest 版本链。
- MARKETING_LEAD_IMPORT_BATCH/DETAIL 能记录 WAITING_CONFIRM、确认动作/人/时间、行级 WARNING 和 handling_status；批次导入处理状态与线索审批状态要能分别展示。
- MARKETING_CUSTOMER_TAG_IMPORT_BATCH/DETAIL 能记录 APPEND/REPLACE、OBS 文件对象、目标标签、逐客户审批、生成线索和正式关系生效结果。
- MARKETING_CUSTOMER_TAG 必须能保存标签审批状态及流程关联；若流程关联只由 BIZ_PROCESS_MAP 保存，需明确业务键和回查规则。
- MARKETING_TOUCH_CUSTOMER_TAG_SOURCE 只作为预导入/历史兼容结构，loaded_flag 仅表示是否载入正式关系，不能代替标签客户审批状态。

以上是目标模型同步要求，不是 DDL，也不表示这些结构已经在目标数据库实施。

## 15. 验收标准和后续同步

### 15.1 页面验收

- 页面一只能由管理员在授权范围内查看全部主档；资料编辑和主办操作有独立权限；“无主办”对全行可见但不进入公共池。

- 页面六按标签展示待审批摘要，抽屉支持单条、多条、全部；标签未审批时按“先标签、后选中客户”继续办理，重复点击不重复生效。

## 16. 2026-08-27 客户池与跨机构营销实施契约

本次实施按“0811 会议纪要优先、2026-08-26 目标表设计约束数据源、V2_DEMO 补充页面字段与交互”的顺序收敛，范围仅覆盖待认领线索池、已认领线索池和跨机构营销。

### 16.1 待认领线索池

- 列表是 `MARKETING_LEAD_INFO` 与 `MARKETING_CUSTOMER_INFO` 的组合查询，不新建客户池表。
- 只返回 `lead_status=APPROVED`、`distribution_mode=PUBLIC`、`pool_status=AVAILABLE`、客户主档有效且无有效主办的线索。
- 同一公开线索允许不同员工分别认领；只排除当前员工已存在的有效认领关系。防重维度为 `source_lead_id + claimed_by`。
- 页面展示线索编号、类型、客户资料、标签快照、分配方式、当前有效认领人数和下发时间；详情和认领均优先使用 `sourceLeadId`。

### 16.2 已认领线索池

- 数据事实来源是 `MARKETING_CUSTOMER_CLAIM`，不把主办关系、业绩关系或跨机构触达授权伪装为认领关系。
- `UNTOUCHED/TOUCHED` 在服务端筛选；任务展示、最新任务字段和触达状态唯一读取 `MARKETING_TOUCH_TASK`。
- 来源筛选使用线索分配方式 `PUBLIC/SCOPE/OWNER`。跨机构审批只授予申请人触达权，不进入已认领池。
- SCOPE 和 OWNER 线索审批通过后，为每个接收人建立独立认领关系，并以该认领关系为来源各生成一条 `MARKETING_TOUCH_TASK`。

### 16.3 跨机构营销

- 客户检索入口使用客户号；四项规则只读取 `MARKETING_CUSTOMER_INFO` 和 `MARKETING_CUSTOMER_PERFORMANCE_REL_SNAPSHOT`，未知规则或数据源不匹配时失败关闭。
- 申请保存四项校验快照并进入 `IN_APPROVAL`；审核角色和普通申请人的列表/详情数据范围分离。
- 审批通过仅生成申请人的 `CROSS_ORG` 触达任务，不变更客户主办人、主办机构、认领关系或业绩归属。
- `MARKETING_CROSS_ORG_APPLY.generated_touch_task_id` 与 `MARKETING_TOUCH_TASK.id` 均为 BIGINT；按 `source_type=CROSS_ORG + source_biz_id=申请ID` 回查，审批重试不得重复生成任务。

本节描述代码契约，不代表目标表已在任何数据库执行建表或完成生产迁移。
