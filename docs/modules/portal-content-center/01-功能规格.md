# 门户与内容中心 — 功能规格

> 文档版本: v1.0
> 对应项目文档: `project_ana.md` 4.1 节
> 模块定位: 通用域 / 只读聚合 / 无业务状态

## 1. 模块概述

### 1.1 模块定位
`portal-content-center`（门户与内容中心）是银行省分行一体化营销与绩效管理平台中的**通用域模块**，为全平台提供门户聚合、信息导航、通讯录、产品资料、文档下载等前台展示能力。

### 1.2 核心职责
- **工作台聚合**：聚合待办、通知、指标卡片、快捷入口，为 PC 和 H5 提供一站式门户页面
- **网址导航**：为 PC 端提供常用业务系统网址导航
- **分行通讯录**：员工信息查询、维护、搜索，产品负责人反向关联
- **产品资料库**：全行产品信息维护与查询，支持中场支持筛选
- **文档下载**：科技部统一管理的常用文档分类下载

### 1.3 设计原则
1. **只做只读聚合**：门户工作台只聚合其他模块数据，不持有业务状态
2. **通用基础服务**：产品、通讯录、文档等作为基础数据，被业务模块依赖
3. **双端支持**：PC 和 H5 双端可用（网址导航除外，仅 PC）
4. **数据驱动**：前台展示由后台数据驱动，支持个性化配置
5. **Fail Close**：权限校验失效时默认拒绝访问

### 1.4 与其他模块的关系
本模块**被依赖方**：
- `customer-marketing-center`（调用 ProductApi 查询产品信息）
- `business-application-center`（调用 ProductApi 查询支持中场支持的产品列表）

本模块**依赖方**：
- `common`（公共基础设施）
- `auth-permission-center`（S 强依赖：CurrentUserApi、BizScopeApi、OrgApi）
- `system-governance-center`（S 强依赖：DictApi、NotifyApi、FileApi）
- `workflow-center`（S 强依赖：WorkflowQueryApi 查询待办/已办）
- `performance-engine-center`（W 弱依赖：MetricApi 查询指标卡片，降级允许）

## 2. 工作台聚合（对应 project_ana 4.1.1）

### 2.1 业务目标
为员工提供一站式入口，一次登录即可掌握所有需要处理的待办事项、接收到的通知、个人业务指标和常用流程入口，减少在多个系统间跳转的成本。

### 2.2 展示范围
- **终端支持**：PC 端和 H5 端均展示
- **展示形式**：卡片式布局，按"待办、通知、指标、快捷入口"四大区域分布
- **刷新机制**：用户每次进入工作台时调用聚合接口刷新数据，无需后端推送

### 2.3 四大展示区域

#### 2.3.1 待办列表
- **数据来源**：`workflow-center` 模块，调用 `WorkflowQueryApi.queryTasks(empId)`
- **展示内容**：
  - 流程名称（流程定义的中文名，例如"资产投放审批"）
  - 流程发起人姓名
  - 流程发起时间
  - 当前任务标题（例如"二级审批"）
  - 红绿灯状态（`GREEN` 正常 / `YELLOW` 即将超时 / `RED` 已超时）
  - 超时信息（距离超时还有 X 小时，或已超时 X 小时）
- **展示数量**：工作台展示最近 5 条，点击"更多"跳转到流程中心的"我的待办"页
- **交互**：点击待办条目直接跳转到对应流程审批页

#### 2.3.2 通知列表
- **数据来源**：`system-governance-center` 模块，调用 `NotifyApi.queryNotifications(empId)`
- **展示内容**：
  - 通知标题
  - 通知摘要（前 100 字符）
  - 发送时间
  - 已读/未读状态（红点标记）
  - 关联的业务类型和业务 ID
- **展示数量**：工作台展示最近 5 条，点击"更多"跳转到通知中心
- **交互**：点击未读通知自动标记为已读，同时跳转到对应业务详情页

#### 2.3.3 指标卡片
- **数据来源**：`performance-engine-center` 模块，调用 `MetricApi.queryMetricCards(empId, metricCodes)`
- **卡片数量**：V1 版本固定 4 个卡片
- **卡片内容**：
  - 指标名称
  - 当前值
  - 目标值
  - 完成率（百分比）
  - 趋势（与上期对比的上升/下降/持平图标）
- **V1 固定卡片清单**（H5 端）：
  1. 我的待办数量
  2. 未读通知数量
  3. 我的本月 KPI 总分
  4. 我的进行中触达任务数
- **降级策略**：当 `performance-engine-center` 不可用时，指标卡片区域显示"数据加载中"占位符，不影响其他区域展示

#### 2.3.4 新增流程入口（快捷入口）
- **数据来源**：`portal_shortcut` 表
- **分类**：
  - `SYSTEM`：系统预设，不可删除（例如"新增线索"、"资产投放"、"中场支持"）
  - `CUSTOM`：用户自定义，可添加/删除/排序
- **展示内容**：
  - 入口图标
  - 入口名称
  - 跳转链接（`INTERNAL` 平台内页面 / `EXTERNAL` 外部链接）
- **个性化**：每个员工可配置自己的快捷入口，通过 `emp_id` 隔离

### 2.4 聚合接口特性
- **一次请求**：工作台页面通过单个 REST 接口（`GET /api/portal/workspace`）一次性返回全部四个区域数据
- **失败隔离**：任一区域调用失败时不影响其他区域，失败区域返回空列表+错误码
- **性能目标**：工作台聚合接口 P95 < 500ms
- **权限控制**：天然按当前用户（`CurrentUserContext.getEmpId()`），无需 `@BizAuth`

## 3. 网址导航（对应 project_ana 4.1.2）

### 3.1 业务目标
为员工提供常用业务系统的统一入口，避免员工需要记忆多个系统的 URL。

### 3.2 展示范围
- **终端支持**：仅 PC 端展示（H5 不展示）
- **展示形式**：图标网格布局，按 `nav_category` 分组展示
- **数据来源**：`portal_nav` 表

### 3.3 前台展示功能
- **分组展示**：按 `nav_category` 字段分组（例如"业务系统"、"办公系统"、"管理工具"）
- **排序规则**：每个分组内按 `sort_order` 升序排列
- **状态过滤**：仅展示 `status = ACTIVE` 的导航
- **点击行为**：新标签页打开 `nav_url`

### 3.4 后台管理功能
**权限要求**：仅科技部授权用户可访问后台管理

- **新增导航**：填写导航名称、URL、图标、分类、排序值
- **编辑导航**：修改已有导航信息
- **删除导航**：逻辑删除（更新 `status = DISABLED`）
- **拖拽排序**：支持同分类内拖拽调整顺序，批量更新 `sort_order`
- **启用/禁用**：切换 `status` 值

### 3.5 数据字段（portal_nav 表）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| nav_name | VARCHAR(100) | 导航名称 |
| nav_url | VARCHAR(500) | 跳转地址 |
| nav_icon | VARCHAR(100) | 图标标识 |
| nav_category | VARCHAR(50) | 分类（例如"业务系统"） |
| sort_order | INT | 排序号 |
| status | VARCHAR(20) | ACTIVE / DISABLED |
| created_by | VARCHAR(32) | 创建人 |
| updated_by | VARCHAR(32) | 更新人 |
| created_time | DATETIME | 创建时间 |
| updated_time | DATETIME | 更新时间 |

## 4. 分行通讯录（对应 project_ana 4.1.3）

### 4.1 业务目标
提供全行员工信息查询和维护功能，支持员工之间的快速联系、业务转派时的对象查找、产品负责人反向关联等场景。

### 4.2 展示范围
- **终端支持**：PC 端和 H5 端均展示
- **展示形式**：PC 端表格展示，H5 端列表卡片展示

### 4.3 完整字段定义（addrbook_employee 表）
| 字段 | 类型 | 必填 | 说明 | 数据来源 |
|---|---|---|---|---|
| emp_id | VARCHAR(32) | 是 | 员工工号（主键，唯一） | 与 PT_USER 1:1 映射 |
| emp_name | VARCHAR(100) | 是 | 员工姓名 | PT_USER.user_name |
| mobile | VARCHAR(20) | 否 | 手机号 | 员工自维护 |
| email | VARCHAR(100) | 否 | 邮箱 | 员工自维护 |
| org_code | VARCHAR(32) | 是 | 机构编码 | EXT_ORG_INFO |
| org_name | VARCHAR(200) | 是 | 机构全称 | EXT_ORG_INFO |
| position | VARCHAR(100) | 否 | 岗位 | 来自 POSITION 字典 |
| self_desc | VARCHAR(1000) | 否 | 自我描述 | 员工自维护 |
| responsible_product_ids | JSON | 否 | 负责产品 ID 列表 | 来自产品资料库 |
| status | VARCHAR(20) | 是 | ACTIVE/RESIGNED | 系统维护 |
| maintainer_emp_id | VARCHAR(32) | 否 | 最后维护人工号 | 系统写入 |
| deleted | TINYINT | 是 | 逻辑删除标记 | 系统维护 |
| created_time | DATETIME | 是 | 创建时间 | 系统维护 |
| updated_time | DATETIME | 是 | 最后更新时间 | 系统维护 |

### 4.4 字段数据来源与关系
- **基础信息（emp_id、emp_name、org_code）**：由 `auth-permission-center` 的 `PT_USER` 表初始化，本表作为 1:1 扩展
- **组织信息（org_code、org_name）**：来自 `EXT_ORG_INFO`（系统治理中心维护的外部组织结构）
- **岗位（position）**：来自 `system-governance-center` 的 `POSITION` 字典
- **负责产品（responsible_product_ids）**：来自 `product_info` 表，且产品必须满足 `status = ACTIVE` AND `support_for_support_request = true`
- **最后维护人（maintainer_emp_id）**：记录最后一次编辑本记录的员工工号，用于审计

### 4.5 维护权限规则
**V1 默认权限策略**：
| 角色 | 可编辑范围 | 权限类型 |
|---|---|---|
| 员工本人 | 仅本人记录 | `ADDRBOOK` 的 `SELF` 数据范围 |
| 组织负责人 | 本组织所有员工记录 | `ADDRBOOK` 的 `ORG` 数据范围 |
| 其他员工 | 仅查看 | `ADDRBOOK` 的 `ALL` 读权限 |

**后端二次校验（在 Service 层执行）**：
- 保存员工信息时，Service 必须在基于实体的层面再次校验：
  - 若 `operatorEmpId == targetEmpId`，则通过
  - 若 `operatorEmpId` 是 `targetEmpId.orgCode` 所在组织的负责人，则通过
  - 否则抛出 `PORTAL-40301 无权编辑本人以外的通讯录`

### 4.6 搜索功能
- **搜索范围**：`emp_id` 和 `emp_name` 字段的模糊匹配
- **支持维度**：
  - 按工号/姓名模糊搜索
  - 按机构（`org_code`）精确过滤
  - 按岗位（`position`）精确过滤
- **排序规则**：按 `org_code` 升序 + `emp_name` 拼音升序

### 4.7 60天自动更新提醒机制
- **触发方式**：定时任务，每日凌晨 02:00 扫描一次
- **扫描规则**：查询 `updated_time < NOW() - INTERVAL 60 DAY` 且 `status = ACTIVE` 的员工
- **提醒方式**：
  - 通过 `NotifyApi.sendNotification()` 向员工本人发送 H5 站内通知
  - 通过 `NotifyApi.sendEmail()` 向员工邮箱发送邮件
- **提醒内容**：标题"您的通讯录信息已超过 60 天未更新"，正文提示员工进入个人中心维护
- **频率控制**：同一员工 15 天内只提醒一次，防止骚扰

### 4.8 与 PT_USER/EXT_ORG_INFO 的关系
- `addrbook_employee` 与 `PT_USER` 是 **1:1 扩展关系**，`emp_id` 作为关联字段
- 当 `PT_USER` 新增员工时，由 `auth-permission-center` 发布 `auth.user.created.v1` 事件，本模块监听事件自动创建 `addrbook_employee` 记录
- 当员工离职时，`PT_USER` 发布 `auth.user.resigned.v1` 事件，本模块更新 `status = RESIGNED`
- `org_code` 和 `org_name` 从 `OrgApi.getOrg(orgCode)` 实时查询，不冗余存储最新值

### 4.9 负责产品与产品资料库的双向同步
**场景**：员工 A 在个人通讯录中选择了"产品 P1"作为负责产品，系统必须同步更新 `product_info.responsible_emp_ids` 字段，将 A 加入 P1 的负责人列表。

**同步流程**：
1. 员工保存通讯录时，计算 `responsible_product_ids` 的新增项和移除项
2. 对于新增产品，调用 Service 层方法将当前员工加入 `product_info.responsible_emp_ids`
3. 对于移除产品，将当前员工从 `product_info.responsible_emp_ids` 中移除
4. 发布 `portal.product.responsible-updated.v1` 事件，供缓存失效

**一致性保证**：
- 通讯录保存和产品负责人同步必须在同一事务内完成
- 若同步失败，通讯录保存整体回滚

## 5. 产品资料库（对应 project_ana 4.1.4）

### 5.1 业务目标
提供全行产品的统一查询和维护能力，为营销人员提供产品介绍入口，为业务申请模块提供"支持中场支持"的产品筛选。

### 5.2 展示范围
- **终端支持**：PC 端和 H5 端均展示
- **展示形式**：PC 端表格展示，H5 端列表卡片展示

### 5.3 完整字段定义（product_info 表）
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 主键 |
| product_code | VARCHAR(64) | 是 | 产品代码（唯一） |
| product_name | VARCHAR(255) | 是 | 产品名称 |
| product_category | VARCHAR(50) | 是 | 产品类别（来自 PRODUCT_CATEGORY 字典） |
| description | TEXT | 否 | 产品说明（富文本） |
| support_for_support_request | TINYINT | 是 | 是否支持中场支持（0/1） |
| owner_org_id | VARCHAR(32) | 否 | 归属组织 ID（数据范围字段） |
| product_dept_org_code | VARCHAR(32) | 是 | 产品部门机构编码（维护组织） |
| file_object_id | VARCHAR(64) | 否 | 附件对象 ID（对接 FileApi） |
| responsible_emp_ids | JSON | 否 | 产品负责人工号列表 |
| status | VARCHAR(20) | 是 | ACTIVE/DISABLED |
| deleted | TINYINT | 是 | 逻辑删除标记 |
| created_by | VARCHAR(32) | 是 | 创建人 |
| updated_by | VARCHAR(32) | 是 | 更新人 |
| created_time | DATETIME | 是 | 创建时间 |
| updated_time | DATETIME | 是 | 更新时间 |

### 5.4 维护权限规则
**V1 默认权限策略**：
| 角色 | 可编辑范围 | 权限类型 |
|---|---|---|
| 中后台维护组织员工 | 本组织归属的产品 | `PRODUCT` 的 `ORG` 数据范围 |
| 系统管理员 | 所有产品 | `PRODUCT` 的 `ALL` 写权限 |
| 其他员工 | 仅查看 | `PRODUCT` 的 `ALL` 读权限 |

**判断规则**：
- `PRODUCT` 表的 `product_dept_org_code` 字段与 `ORG` 数据范围匹配
- 员工所在组织 `org_code` 等于 `product_dept_org_code` 时，视为有编辑权限
- 后端 Service 层必须二次校验，防止 URL 越权

### 5.5 产品负责人反向关联机制
**设计思路**：
- 产品负责人不由产品维护端录入，而是由通讯录员工端"认领"
- 员工在通讯录中选择"我负责的产品"，系统自动将该员工加入产品的 `responsible_emp_ids`
- 一个产品允许多个负责人

**查询方式**：
- 查询产品详情时，`responsible_emp_ids` 字段直接返回负责人工号列表
- 若需要负责人详细信息（姓名、联系方式），调用 `AddressBookApi.getEmployees(empIds)` 批量获取

**同步时机**：
- 员工保存通讯录时触发（见 4.9 节）
- 员工离职时，从所有产品的 `responsible_emp_ids` 中移除（监听 `auth.user.resigned.v1` 事件）

### 5.6 支持中场支持的产品筛选
**业务场景**：`business-application-center` 的"中场支持申请"页面需要展示"当前支持中场支持"的产品列表供申请人选择。

**查询接口**：`ProductApi.listSupportAvailableProducts()`

**查询条件**：
```sql
SELECT * FROM product_info
WHERE support_for_support_request = 1
  AND status = 'ACTIVE'
  AND deleted = 0
ORDER BY product_name
```

**缓存策略**：该接口高频调用，建议缓存 TTL 5 分钟，缓存 key 为 `portal:product:support-available:all`。

### 5.7 60天产品确认通知
- **触发方式**：定时任务，每日凌晨 02:30 扫描一次
- **扫描规则**：查询 `updated_time < NOW() - INTERVAL 60 DAY` 且 `status = ACTIVE` 的产品
- **提醒对象**：产品的维护组织（`product_dept_org_code`）对应的部门秘书
- **提醒方式**：通过 `NotifyApi.sendNotification()` 发送通知
- **提醒内容**：标题"产品《XXX》已超过 60 天未更新，请确认或更新产品信息"
- **频率控制**：同一产品 15 天内只提醒一次

## 6. 常用文档下载（对应 project_ana 4.1.5）

### 6.1 业务目标
为全行员工提供常用文档（如规章制度、操作手册、模板表单）的统一下载入口。

### 6.2 管理规则
- **管理方**：科技部指定人员上传、分类、更新、删除
- **使用方**：全行员工均可下载
- **支持目录分类**：`doc_category` 字段作为分类键，例如"规章制度"、"操作手册"、"业务模板"

### 6.3 完整字段定义（doc_info 表）
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 主键 |
| doc_title | VARCHAR(255) | 是 | 文档标题 |
| doc_category | VARCHAR(50) | 是 | 文档分类 |
| file_object_id | VARCHAR(64) | 是 | 文件对象 ID（对接 FileApi） |
| status | VARCHAR(20) | 是 | ACTIVE/DISABLED |
| created_by | VARCHAR(32) | 是 | 创建人工号 |
| updated_by | VARCHAR(32) | 是 | 更新人工号 |
| created_time | DATETIME | 是 | 创建时间 |
| updated_time | DATETIME | 是 | 更新时间 |

### 6.4 维护权限规则
**V1 默认权限策略**：
| 角色 | 权限 |
|---|---|
| 科技部员工 | `DOC.ALL` 可写（上传、编辑、删除） |
| 其他员工 | `DOC.ALL` 只读（仅下载） |

### 6.5 文件存储对接
- 文件本体存储在 MinIO，通过 `FileApi.upload(file)` 返回 `fileObjectId`
- 文档表只记录 `fileObjectId`，不存储文件内容
- 下载时调用 `FileApi.getDownloadUrl(fileObjectId)` 获取临时下载链接（TTL 30 分钟）

## 7. 工作台指标卡片规则

### 7.1 V1 固定卡片（H5 端 4 个）
| 卡片编号 | 卡片名称 | 指标代码 | 数据来源 | 计算口径 |
|---|---|---|---|---|
| 1 | 我的待办数量 | `METRIC_TODO_COUNT` | workflow-center | `WorkflowQueryApi.countTasks(empId)` |
| 2 | 未读通知数量 | `METRIC_UNREAD_NOTIFY` | system-governance-center | `NotifyApi.countUnread(empId)` |
| 3 | 我的本月 KPI 总分 | `METRIC_MONTHLY_KPI` | performance-engine-center | `MetricApi.getMonthlyKpi(empId)` |
| 4 | 我的进行中触达任务数 | `METRIC_ONGOING_REACH` | customer-marketing-center | `MetricApi.getOngoingReachCount(empId)` |

### 7.2 PC 端卡片扩展
- PC 端在 H5 基础上可扩展更多卡片（V1 保持一致，V2 再扩展）
- 卡片是否展示受 RBAC 控制，例如"我的本月 KPI"只对有 KPI 考核资格的员工展示

### 7.3 数据口径说明
- **受 RBAC 控制**：没有某指标权限的员工不展示该卡片
- **受数据范围控制**：`MetricApi` 内部基于 `BizScopeApi` 进行数据范围过滤
- **降级策略**：`performance-engine-center` 不可用时，相关卡片显示"-"或"数据加载中"
- **缓存策略**：每个员工的指标数据缓存 10 分钟

## 8. 60天更新提醒机制（统一说明）

### 8.1 定时任务配置
| 任务名称 | 执行时间 | 扫描对象 | 通知对象 |
|---|---|---|---|
| 通讯录更新提醒 | 每日 02:00 | `addrbook_employee.updated_time < NOW() - INTERVAL 60 DAY` | 员工本人（邮件 + H5） |
| 产品更新确认 | 每日 02:30 | `product_info.updated_time < NOW() - INTERVAL 60 DAY` | 维护部门秘书（H5） |

### 8.2 实现方式
- 使用 Spring `@Scheduled` 注解的定时任务
- 定时任务类：`UpdateReminderService`
- 扫描结果进入提醒队列，通过 `NotifyApi` 统一发送

### 8.3 频率控制
- 每个提醒对象 15 天内同一类型的提醒只发送一次
- 通过 Redis key `portal:reminder:addrbook:{empId}` 和 `portal:reminder:product:{productId}` 设置 TTL 15 天去重
