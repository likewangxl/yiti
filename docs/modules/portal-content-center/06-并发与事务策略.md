# 门户与内容中心 — 并发与事务策略

> 模块：portal-content-center
> 版本：V1.0
> 最后更新：2026-04-10

---

## 0. 总体原则

1. **读多写少**：本模块 95% 流量为工作台聚合查询和通讯录/产品列表，优先保证读性能与降级能力
2. **写操作小粒度短事务**：避免跨多表大事务；跨模块同步全部走事件驱动，不放入主事务
3. **一致性优先级**：产品编辑的附件、审计字段、Owner 机构必须强一致；JSON 字段的双向同步允许最终一致
4. **Fail Close**：权限缓存失效、数据范围解析失败时默认拒绝操作（与 auth 模块一致）

## 1. 工作台聚合接口 `POST /api/portal/workbench/aggregate`

### 1.1 事务要求

- **无写操作，无事务**（`@Transactional(propagation = Propagation.NEVER)` 或直接不加注解）
- 禁止在聚合接口中执行任何 `INSERT/UPDATE/DELETE`

### 1.2 并行查询策略

**使用 `CompletableFuture` + 固定线程池并行获取 6 个子查询结果：**

```java
@Service
public class WorkbenchFacade {
    private final ExecutorService workbenchExecutor;  // 核心 8，最大 16，有界队列 100

    public WorkbenchAggregateRespDTO aggregate(String empId) {
        long t0 = System.currentTimeMillis();
        // 6 路并行
        CompletableFuture<List<TaskDTO>> todoFuture = 
            CompletableFuture.supplyAsync(() -> workflowQueryApi.queryTasks(empId, null, topPage), workbenchExecutor)
                .orTimeout(800, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> { log.warn("todo fallback", ex); return Collections.emptyList(); });

        CompletableFuture<Integer> unreadNotifyFuture = 
            CompletableFuture.supplyAsync(() -> notifyApi.countUnread(empId), workbenchExecutor)
                .orTimeout(500, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> 0);

        CompletableFuture<List<MetricCardDTO>> metricFuture = 
            CompletableFuture.supplyAsync(() -> metricApi.getUserMetricCards(empId), workbenchExecutor)
                .orTimeout(1000, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> Collections.emptyList());

        CompletableFuture<List<ShortcutDTO>> shortcutFuture = 
            CompletableFuture.supplyAsync(() -> shortcutService.listForEmp(empId), workbenchExecutor)
                .orTimeout(300, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> Collections.emptyList());

        CompletableFuture<List<NavDTO>> navFuture = 
            CompletableFuture.supplyAsync(() -> navService.listActive(), workbenchExecutor)
                .orTimeout(300, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> Collections.emptyList());

        CompletableFuture<Integer> todoCountFuture =
            CompletableFuture.supplyAsync(() -> workflowQueryApi.countTasks(empId), workbenchExecutor)
                .orTimeout(500, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> 0);

        // allOf 等待全部完成（已 exceptionally 兜底，不会抛出）
        CompletableFuture.allOf(todoFuture, unreadNotifyFuture, metricFuture,
                                 shortcutFuture, navFuture, todoCountFuture).join();

        WorkbenchAggregateRespDTO resp = new WorkbenchAggregateRespDTO();
        resp.setTodoList(todoFuture.join());
        resp.setTodoCount(todoCountFuture.join());
        resp.setUnreadNotifyCount(unreadNotifyFuture.join());
        resp.setMetricCards(metricFuture.join());
        resp.setShortcuts(shortcutFuture.join());
        resp.setNavs(navFuture.join());
        resp.setAggregateCostMs(System.currentTimeMillis() - t0);
        return resp;
    }
}
```

### 1.3 降级策略

| 子查询 | 超时阈值 | 降级返回 | 前端提示 |
|---|---|---|---|
| workflow 待办列表 | 800 ms | 空列表 | "待办服务暂不可用，请稍后刷新" |
| workflow 待办数 | 500 ms | `-1`（前端识别为未知） | 角标不显示 |
| notify 未读数 | 500 ms | `0` | 角标隐藏 |
| metric 指标卡 | 1000 ms | 空列表 | "指标数据加载中" |
| shortcut 快捷入口 | 300 ms | 空列表 | 显示兜底系统级默认项（内存常量） |
| nav 导航 | 300 ms | 空列表 | 显示缓存（若有） |

**关键约束：**
- 单个子查询失败 **不阻塞** 其他部分展示（核心降级原则）
- 聚合接口整体超时 1.5 秒（Controller 层通过 `AsyncContext` 控制），超时则返回已完成部分 + 降级部分
- 每个子查询在失败时记录 `WARN` 级日志（带 traceId + 耗时），不记录 ERROR 避免噪音
- 返回 `WorkbenchAggregateRespDTO` 时必须带 `degradedParts: List<String>` 字段告知前端哪些块降级了

### 1.4 线程池配置

```yaml
portal:
  workbench:
    executor:
      core-size: 8
      max-size: 16
      queue-capacity: 100
      keep-alive-seconds: 60
      thread-name-prefix: portal-wb-
      rejection-policy: CALLER_RUNS   # 队列满则由调用线程直接执行（降级为串行）
```

**说明**：`CALLER_RUNS` 策略保证在极端流量下仍然可以响应（退化为顺序执行，响应慢但不拒绝）。

## 2. 通讯录维护

### 2.1 编辑本人信息 `PUT /api/employees/{empId}/self`

**事务范围**：单表更新 + 审计日志写入（同事务）

**传播级别**：`REQUIRED`

**隔离级别**：默认（`READ_COMMITTED`）

**冲突场景：**
- 员工本人在两个设备同时编辑自己的资料 → 使用乐观锁
- 管理员在编辑他人（调整维护人）时员工本人同时在编辑 → 使用乐观锁 + 字段隔离

### 2.2 乐观锁实现

**基于 `updated_time` 的 CAS：**

```xml
<!-- AddrbookEmployeeMapper.xml -->
<update id="updateBySelfWithCheck">
    UPDATE addrbook_employee
    SET self_desc = #{selfDesc},
        mobile    = #{mobile},
        email     = #{email},
        responsible_product_ids = #{responsibleProductIdsJson},
        updated_by   = #{operatorEmpId},
        updated_time = CURRENT_TIMESTAMP
    WHERE emp_id       = #{empId}
      AND deleted      = 0
      AND updated_time = #{expectedUpdatedTime}
</update>
```

**Service 层处理：**

```java
@Transactional(rollbackFor = Exception.class)
public void updateSelfInfo(String empId, UpdateSelfInfoCmd cmd) {
    // 1. 读取当前记录（带 updated_time 作为乐观锁版本）
    AddrbookEmployee current = mapper.selectByEmpId(empId);
    if (current == null || current.getDeleted() == 1) {
        throw new BizException(ErrorCode.EMPLOYEE_NOT_FOUND);
    }
    // 2. 业务校验（略）
    // 3. CAS 更新
    int rows = mapper.updateBySelfWithCheck(empId, cmd, current.getUpdatedTime());
    if (rows == 0) {
        throw new BizException(ErrorCode.CONCURRENT_UPDATE_CONFLICT,
                "通讯录信息已被他人修改，请刷新后重试");
    }
    // 4. JSON 字段变更触发双向同步事件（见第 3.3 节）
    publishResponsibleProductChangedIfNeeded(empId, current, cmd);
}
```

### 2.3 字段隔离规则（本人 vs 管理员优先级）

**本人优先字段（本人编辑时强制生效，管理员编辑时不覆盖）：**
- `self_desc`
- `responsible_product_ids`

**管理员/同步优先字段：**
- `emp_name`、`org_code`、`org_name`、`position`、`status` — 仅 PT_USER 同步事件可写
- `maintainer_emp_id` — 仅管理台可写

**混合字段（任何合法操作人可写，最后写入生效）：**
- `mobile`、`email`

**实现：** 通过 `UpdateSelfInfoCmd` / `UpdateByAdminCmd` 两套不同的 Command 对象和 Mapper 方法物理隔离可写字段。

### 2.4 responsible_product_ids 更新与产品表同步的事务边界

**关键决策：不放在同一本地事务内**

**理由：**
1. 多张表同时加行锁容易导致死锁（产品负责人维护接口并发时）
2. 跨表更新行数多时（一个员工负责 20 个产品），事务时长超标
3. 使用事件驱动可天然支持重试与补偿

**实现流程：**

```
[本地事务 A]
  1. 校验新列表合法性
  2. UPDATE addrbook_employee SET responsible_product_ids = ?, updated_time = now()
  3. 写审计日志
  4. 写 sys_event_outbox（事务消息，状态 PENDING）
[本地事务 A 提交]

[异步 Worker 扫描 outbox]
  5. 发布 portal.employee.responsible-products-updated.v1 到事件总线
  6. 将 outbox 记录状态标记为 SENT

[事件消费者 ProductResponsibleSyncListener]
  7. [本地事务 B] 对每个 removed/added 的 productId 更新 product_info.responsible_emp_ids
  8. 消费失败进入 DLQ（死信队列），由运维处理
```

**事务消息表 `sys_event_outbox`** 由 common 基础设施提供，详见 `docs/common-dev-guide.md`。

## 3. 产品资料维护

### 3.1 产品新增/编辑 `POST/PUT /api/products`

**事务范围**：单表更新（product_info） + 审计日志 + 附件关联元数据 + 事件 outbox

**传播级别**：`REQUIRED`

**写前校验（在事务外完成，失败快速返回）：**
1. `BizScopeApi.checkWritePermission(empId, PRODUCT, ownerOrgId, createdBy)` 通过
2. `product_code` 不重复（事务外 SELECT 初判 + 数据库唯一约束兜底）
3. `responsible_emp_ids` 中所有 emp_id 在 addrbook 中存在且在职
4. `file_object_id` 若有，调用 `FileApi.getFileInfo()` 验证存在
5. `product_category` 在字典中存在

### 3.2 product_code 唯一性并发控制

**双重保障：**
- Service 层先查重（`SELECT count(*) FROM product_info WHERE product_code = ? AND deleted = 0`）
- 数据库层 `uk_product_code_deleted` 唯一索引作为兜底（防止查重到 INSERT 间的竞态）
- 捕获 `DuplicateKeyException` 转换为 `BizException(ErrorCode.PRODUCT_CODE_DUPLICATE)`

```java
@Transactional(rollbackFor = Exception.class)
public String createProduct(CreateProductCmd cmd) {
    // 1. 前置校验（略）
    // 2. INSERT
    try {
        mapper.insert(productPO);
    } catch (DuplicateKeyException e) {
        throw new BizException(ErrorCode.PRODUCT_CODE_DUPLICATE,
                "产品编码 " + cmd.getProductCode() + " 已存在");
    }
    // 3. 若有负责人列表，发布同步事件（outbox 模式）
    if (CollectionUtils.isNotEmpty(cmd.getResponsibleEmpIds())) {
        outboxWriter.write(new ProductResponsibleUpdatedEvent(
                productPO.getId(), Collections.emptyList(), cmd.getResponsibleEmpIds()));
    }
    return productPO.getId();
}
```

### 3.3 产品负责人双向同步（详细时序）

**场景：维护人将产品 `P001` 的负责人从 `[E01, E02]` 改为 `[E02, E03]`**

```
┌─────────────────┐      ┌──────────────┐      ┌──────────────────┐
│ ProductFacade   │      │ Local DB     │      │ EventBus         │
└────────┬────────┘      └──────┬───────┘      └────────┬─────────┘
         │                      │                       │
         │ BEGIN TX             │                       │
         ├─────────────────────>│                       │
         │                      │                       │
         │ SELECT product       │                       │
         │ (for update)         │                       │
         ├─────────────────────>│                       │
         │<─────────────────────│                       │
         │                      │                       │
         │ 计算 removed=[E01]   │                       │
         │ added=[E03]          │                       │
         │                      │                       │
         │ UPDATE product SET   │                       │
         │ responsible_emp_ids  │                       │
         ├─────────────────────>│                       │
         │                      │                       │
         │ INSERT outbox        │                       │
         ├─────────────────────>│                       │
         │                      │                       │
         │ COMMIT TX            │                       │
         ├─────────────────────>│                       │
         │                      │                       │
         │                      │ [outbox poller]       │
         │                      │  publish event        │
         │                      ├──────────────────────>│
         │                      │                       │
         │                      │                       │ dispatch
         │                      │<──────────────────────│
         │                      │                       │
         │ [ProductResponsibleSyncListener]              │
         │   BEGIN TX                                    │
         │   FOR empId in [E01]:                         │
         │     UPDATE addrbook REMOVE P001               │
         │   FOR empId in [E03]:                         │
         │     UPDATE addrbook ADD P001                  │
         │   COMMIT TX                                   │
```

**防重入机制：**
- 事件 payload 携带 `source: PRODUCT_SIDE`，消费者仅更新 addrbook，不再反向发事件
- `addrbook_employee` 侧的同一接口发送事件时携带 `source: ADDRBOOK_SIDE`

**并发冲突处理：**
- 消费者使用乐观锁更新：`UPDATE addrbook_employee SET ... WHERE emp_id = ? AND updated_time = ?`
- 失败时重试 3 次（间隔 100/500/2000ms），仍失败进入 DLQ

### 3.4 产品删除前置检查

**软删接口 `DELETE /api/products/{id}`**

```java
@Transactional(rollbackFor = Exception.class)
public void deleteProduct(String productId, String operatorEmpId) {
    ProductInfo product = mapper.selectById(productId);
    if (product == null || product.getDeleted() == 1) {
        throw new BizException(ErrorCode.PRODUCT_NOT_FOUND);
    }

    // 1. 权限校验
    bizScopeApi.checkWritePermission(operatorEmpId, BizType.PRODUCT,
            product.getOwnerOrgId(), product.getCreatedBy());

    // 2. 前置检查：是否有员工仍将此产品列为负责产品
    int refCount = addrbookMapper.countEmployeesReferringProduct(productId);
    if (refCount > 0) {
        throw new BizException(ErrorCode.PRODUCT_STILL_REFERRED,
                "仍有 " + refCount + " 名员工将该产品列为负责产品，请先清理");
    }

    // 3. 软删
    mapper.softDeleteById(productId, operatorEmpId);

    // 4. 解除文件关联
    if (StringUtils.isNotBlank(product.getFileObjectId())) {
        fileApi.detachBizRelation(product.getFileObjectId(), "PRODUCT", productId);
    }

    // 5. 写高危审计
    auditLog.record("PRODUCT_DELETE", productId, product);
}
```

**关键设计：**
- 前置检查在事务内进行，避免"检查通过 → 并发新增引用 → 删除"的 TOCTOU 问题
  - 若性能允许，可对 `addrbook_employee` 的引用行加共享锁（SELECT ... LOCK IN SHARE MODE），代价是高并发下锁等待
  - 兼容方案：软删后增加"禁止新增引用"的产品状态位（`deleted=1` 时查询自动排除）
- 文件解除关联在业务事务内执行；若 FileApi 调用失败则回滚整个删除操作

## 4. 文档管理

### 4.1 上传文档 `POST /api/admin/documents/upload`

**两步提交风险**：`MinIO 上传` 与 `doc_info 写表` 不可原子

**流程设计：**

```
1. MinIO 上传（governance.FileApi.upload） → 获得 fileObjectId
2. [本地事务 BEGIN]
3. INSERT doc_info (file_object_id = fileObjectId)
4. [本地事务 COMMIT]
5. 返回成功
```

**失败处理：**

| 失败阶段 | 处理 |
|---|---|
| MinIO 上传失败 | 直接返回错误，无事务开启，无脏数据 |
| doc_info 写入失败 | **立即** 调用 `FileApi.deleteFile(fileObjectId)` 回滚 MinIO；若清理也失败则写 `sys_orphan_file_log` 等待定时任务清理 |
| 事务提交失败（数据库故障） | 捕获异常后清理 MinIO；进入 sys_orphan_file_log |

**代码示例：**

```java
public String uploadDoc(MultipartFile file, String title, String category, String operatorEmpId) {
    // 1. 上传 MinIO（governance 模块内部已保证一致性）
    FileObjectDTO fileObj = fileApi.upload(file, operatorEmpId);
    try {
        // 2. 本地事务内写 doc_info
        return doUploadDocInTx(fileObj.getId(), title, category, operatorEmpId);
    } catch (Exception ex) {
        // 3. 回滚 MinIO
        try {
            fileApi.deleteFile(fileObj.getId());
        } catch (Exception cleanupEx) {
            log.error("orphan file clean failed, fileId={}", fileObj.getId(), cleanupEx);
            orphanFileLogger.log(fileObj.getId(), "DOC_UPLOAD_TX_FAILED");
        }
        throw ex;
    }
}

@Transactional(rollbackFor = Exception.class)
protected String doUploadDocInTx(String fileObjectId, String title, String category, String operatorEmpId) {
    DocInfo doc = new DocInfo();
    doc.setId(IdUtil.generateShortUuid());
    doc.setDocTitle(title);
    doc.setDocCategory(category);
    doc.setFileObjectId(fileObjectId);
    doc.setStatus("ACTIVE");
    doc.setCreatedBy(operatorEmpId);
    docMapper.insert(doc);
    return doc.getId();
}
```

### 4.2 删除文档 `DELETE /api/admin/documents/{id}`

**事务范围**：单表软删（status=DISABLED） + 解除文件关联

**流程：**
```java
@Transactional(rollbackFor = Exception.class)
public void deleteDoc(String docId, String operatorEmpId) {
    DocInfo doc = docMapper.selectById(docId);
    if (doc == null || "DISABLED".equals(doc.getStatus())) {
        throw new BizException(ErrorCode.DOC_NOT_FOUND);
    }
    // 1. 软删 doc_info
    docMapper.updateStatus(docId, "DISABLED", operatorEmpId);
    // 2. 解除文件关联（不物理删除文件，交给孤儿清理任务）
    fileApi.detachBizRelation(doc.getFileObjectId(), "DOC", docId);
    // 3. 高危审计
    auditLog.record("DOC_DELETE", docId, doc);
}
```

**物理删除策略**：V1 不提供物理删除接口，所有软删的 `file_object` 由 `FILE_ORPHAN_CLEANUP` 定时任务在保留 90 天后清理。

## 5. 幂等策略

### 5.1 客户端重复提交防护

| 接口 | 幂等手段 | 幂等窗口 |
|---|---|---|
| 新增导航 `POST /api/admin/nav` | 客户端 UUID + Redis `SETNX` | 10 秒 |
| 新增快捷入口 `POST /api/shortcut` | 同上 | 10 秒 |
| 新增产品 `POST /api/products` | `product_code` 数据库唯一约束 | 永久 |
| 新增通讯录（同步） | `emp_id` 主键幂等 | 永久 |
| 上传文档 `POST /api/admin/documents/upload` | 客户端 UUID + Redis | 30 秒 |

**Redis 幂等 Key 格式：**
```
idempotent:portal:{action}:{userId}:{clientUuid}
值：接口返回的 respDTO JSON
TTL：窗口期（10/30s）
```

**实现方式**：使用 common-aop 提供的 `@Idempotent(windowSeconds = 10)` 注解，详见 `common/CLAUDE.md`。

### 5.2 事件消费者幂等

- `ProductResponsibleSyncListener` 处理 `portal.product.responsible-updated.v1`：
  - 幂等键：`eventId`（事件总线自动生成）
  - 处理前 `SELECT` 当前 JSON → 计算差集 → 如果 `removed`/`added` 为空则直接 ACK
  - 使用乐观锁更新，失败重试 3 次
- `AddressBookUserSyncListener` 处理 PT_USER 相关事件：
  - 幂等键：`eventId` + `empId`
  - INSERT 使用 `INSERT ... ON DUPLICATE KEY UPDATE`

### 5.3 定时任务幂等

- `ADDR_BOOK_FULL_SYNC` 每日对账：每条记录使用 `ON DUPLICATE KEY UPDATE`，允许重复执行
- `PRODUCT_REMIND` 60 天提醒：通知发送前先查 `sys_notification_log` 判重（同一产品 7 天内不重复提醒）

### 6.1 缓存项清单

| `portal:shortcut:emp:{empId}` | 员工个人快捷入口 | 5 分钟 | 个人变更后 delete | String (JSON) |
| `portal:product:support-available:list` | 支持中场申请的产品列表 | 5 分钟 | 产品新增/编辑/删除后 delete | String (JSON) |

| `portal:addrbook:search:{hash}` | 通讯录搜索结果 | 1 分钟 | 不主动失效（依赖 TTL） | String (JSON) |

### 6.2 缓存更新策略

**Cache-Aside 模式（标准）：**
```java
// 读
public List<NavDTO> listActive() {
    String cacheKey = "portal:nav:active:list";
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return JsonUtil.parseArray(cached, NavDTO.class);
    }
    List<NavDTO> data = navMapper.selectAllActive().stream()
            .map(NavConverter::toDTO)
            .collect(Collectors.toList());
    redisTemplate.opsForValue().set(cacheKey, JsonUtil.toJson(data), Duration.ofMinutes(10));
    return data;
}

// 写
@Transactional(rollbackFor = Exception.class)
public void updateNav(String id, UpdateNavCmd cmd) {
    navMapper.update(id, cmd);
    // 使用事务同步器在事务成功后再 delete 缓存，避免"缓存删除但事务回滚"的脏数据
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            redisTemplate.delete("portal:nav:active:list");
            redisTemplate.delete(buildCategoryKey(cmd.getCategory()));
        }
    });
}
```

### 6.3 缓存穿透与雪崩防护

**穿透（查不存在的数据）：**
- 单产品详情查询：查 DB 为空时写入 `null` 占位（TTL 60 秒）
- 通讯录员工详情：同上

**击穿（热点 Key 失效瞬间大量请求）：**
- 工作台聚合相关缓存使用 Redis 分布式锁 `SETNX` + 短 TTL（3 秒）控制单 JVM 内单次回源

**雪崩（大量 Key 同时失效）：**
- 所有 TTL 值加 `±10%` 随机抖动
- `portal:addrbook:search:*` 独立一层随机范围 `50-80 秒`

### 6.4 缓存一致性红线

- **强一致要求**：`portal:product:detail:{productId}` 必须在产品编辑 commit 后立即失效（`afterCommit` 触发 delete）
- **最终一致**：工作台聚合相关缓存允许最多 10 秒延迟
- **跨节点失效**：单机 Redis 天然全局可见；若未来引入本地 Caffeine 缓存，必须通过 Redis Pub/Sub 广播失效

## 7. 60 天更新提醒定时任务

### 7.1 任务设计

| 任务 Key | Cron | 扫描对象 | 提醒条件 |
|---|---|---|---|
| `ADDR_BOOK_REMIND` | `0 0 9 1 * ?`（每月 1 日 9 点） | addrbook_employee | `updated_time < now() - 60 天` AND `deleted=0` AND `status=ACTIVE` |
| `PRODUCT_REMIND` | `0 0 9 1 */2 ?`（每 2 个月 1 日 9 点） | product_info | `updated_time < now() - 60 天` AND `deleted=0` AND `status=ACTIVE` |

### 7.2 分批扫描策略

**避免单次加载全量数据（万条级）**：

```java
@Component
public class AddressBookRemindJob {

    private static final int BATCH_SIZE = 500;

    public void run() {
        long t0 = System.currentTimeMillis();
        Date threshold = DateUtil.addDays(new Date(), -60);
        String lastEmpId = "";  // 游标
        int batchNo = 0;
        int totalRemind = 0;

        while (true) {
            List<AddrbookEmployee> batch = mapper.scanStaleEmployees(threshold, lastEmpId, BATCH_SIZE);
            if (batch.isEmpty()) break;
            batchNo++;
            log.info("ADDR_BOOK_REMIND batch #{}, size={}", batchNo, batch.size());

            for (AddrbookEmployee emp : batch) {
                try {
                    sendRemindAsync(emp);
                    totalRemind++;
                } catch (Exception ex) {
                    log.warn("remind fail empId={}, msg={}", emp.getEmpId(), ex.getMessage());
                }
            }
            lastEmpId = batch.get(batch.size() - 1).getEmpId();

            // 每批次之间短暂 sleep，避免瞬时 DB/通知系统压力
            try { Thread.sleep(200); } catch (InterruptedException ignored) {}
        }
        log.info("ADDR_BOOK_REMIND done, batches={}, remindCount={}, cost={}ms",
                batchNo, totalRemind, System.currentTimeMillis() - t0);
    }
}
```

**Mapper SQL：**
```xml
<select id="scanStaleEmployees" resultMap="BaseResultMap">
    SELECT * FROM addrbook_employee
    WHERE deleted = 0
      AND status = 'ACTIVE'
      AND updated_time &lt; #{threshold}
      AND emp_id &gt; #{lastEmpId}
    ORDER BY emp_id ASC
    LIMIT #{limit}
</select>
```

### 7.3 异步通知发送

**通知发送不放在扫描主循环中同步执行**：

```java
private void sendRemindAsync(AddrbookEmployee emp) {
    notifyAsyncExecutor.execute(() -> {
        // 1. 发送前判重（7 天内同员工不重复）
        String dedupKey = "remind:addrbook:" + emp.getEmpId();
        Boolean first = redisTemplate.opsForValue().setIfAbsent(dedupKey, "1", Duration.ofDays(7));
        if (Boolean.FALSE.equals(first)) return;

        // 2. 发送通知（目标是维护人，若无则发给员工本人）
        String targetEmpId = StringUtils.defaultIfBlank(emp.getMaintainerEmpId(), emp.getEmpId());
        NotificationCmd cmd = NotificationCmd.builder()
                .templateCode("ADDR_BOOK_STALE_REMIND")
                .targetEmpId(targetEmpId)
                .bizType("ADDR_BOOK")
                .bizId(emp.getEmpId())
                .params(Map.of("empName", emp.getEmpName(),
                               "lastUpdate", DateUtil.format(emp.getUpdatedTime())))
                .build();
        notifyApi.sendNotification(cmd);
    });
}
```

**线程池：**
```yaml
portal:
  notify:
    executor:
      core-size: 4
      max-size: 8
      queue-capacity: 1000
      rejection-policy: CALLER_RUNS
```

### 7.4 任务并发与容错

- **多实例部署**：使用 Flowable/XXL-Job/Quartz Cluster 的分布式锁，保证同一时刻只有一个节点执行
- **任务失败**：单个员工提醒失败不影响整体，最终日志输出失败数
- **监控**：任务结束写 `sys_job_run_log`（governance），含 `batches/totalScanned/remindCount/failedCount/costMs`
- **告警**：`failedCount > 总数 * 10%` 时触发运维告警

## 8. 事务超时与死锁处理

### 8.1 超时配置

| 事务类别 | 超时 | 说明 |
|---|---|---|
| 通讯录编辑 | 3 秒 | 单表 + 事件 outbox |
| 产品编辑 | 5 秒 | 含附件元数据 |
| 产品删除 | 10 秒 | 含前置检查跨表 |
| 文档上传 | 10 秒 | 含 MinIO 调用 |
| 导航/快捷入口编辑 | 3 秒 | 单表 |
| 通讯录同步（批量） | 60 秒 | 批处理场景允许长事务 |

**统一声明：**
```java
@Transactional(rollbackFor = Exception.class, timeout = 5)
```

### 8.2 死锁场景与规避

**场景 1：双向同步并发**
- A 协程：更新 product_info(P1) → 尝试更新 addrbook(E1)
- B 协程：更新 addrbook(E1) → 尝试更新 product_info(P1)
- **规避**：双向同步不在同一事务，全部走事件，避免共享锁

**场景 2：产品批量负责人调整**
- 事务内按随机顺序 update 多个员工 → 不同并发请求可能锁顺序不同
- **规避**：对 emp_id 列表排序后顺序 update（`Collections.sort(empIds)` 强制字典序），死锁概率降为 0

**场景 3：产品删除 + 员工编辑并发**
- 规避：通过乐观锁（updated_time）检测，失败快速返回让前端重试

### 8.3 死锁异常处理

```java
@Transactional(rollbackFor = Exception.class)
public void batchUpdateResponsibleProducts(List<String> empIds, String productId, boolean add) {
    List<String> sortedIds = new ArrayList<>(empIds);
    Collections.sort(sortedIds);  // 统一锁顺序
    try {
        for (String empId : sortedIds) {
            updateOneEmployeeResponsibleProducts(empId, productId, add);
        }
    } catch (DeadlockLoserDataAccessException ex) {
        log.warn("deadlock detected, retrying, empIds={}", sortedIds);
        throw new BizException(ErrorCode.CONCURRENT_CONFLICT_RETRY,
                "并发冲突，请重试");
    }
}
```

**重试由 Spring Retry + `@Retryable(DeadlockLoserDataAccessException.class, maxAttempts = 3)` 在调用方实现**。

## 9. 读写分离建议（V2）

V1 不启用读写分离，所有读写走主库。V2 规划：

- 通讯录搜索、产品列表、导航列表走只读副本
- 延迟 < 500ms 可接受（用户刚编辑后的回显除外）
- 写后立即读场景通过 `@ForceMaster` 注解强制走主库
