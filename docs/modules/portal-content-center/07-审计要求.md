# 门户与内容中心 — 审计要求

> 模块：portal-content-center
> 版本：V1.0
> 最后更新：2026-04-10

> 本文档遵循 `docs/common-dev-guide.md` 中的统一审计规范。portal 模块使用 `common-aop` 提供的 `@BizAudit` 注解声明审计点，由 AOP 自动写入 `sys_audit_log` 表。

---

## 0. 审计日志存储

**日志表**：`sys_audit_log`（由 system-governance-center 管理，详见 governance 模块文档）

**日志级别：**
- `HIGH` — 高危，必须审计，需保留 5 年
- `MEDIUM` — 中等，必须审计，保留 2 年
- `LOW` — 一般写操作，审计可选，保留 1 年
- `NONE` — 不审计（查询类、聚合类、本人日常编辑）

**统一字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | varchar(32) | 审计日志主键 |
| `trace_id` | varchar(64) | 全链路追踪 ID |
| `module` | varchar(32) | 模块名，portal 固定填 `portal-content-center` |
| `action` | varchar(64) | 动作码，见第 1 节 |
| `action_level` | varchar(16) | HIGH/MEDIUM/LOW |
| `resource_type` | varchar(32) | 资源类型 (NAV/SHORTCUT/EMPLOYEE/PRODUCT/DOC) |
| `resource_id` | varchar(64) | 资源主键 |
| `operator_emp_id` | varchar(32) | 操作人工号 |
| `operator_name` | varchar(100) | 操作人姓名（冗余，便于查看） |
| `operator_org_code` | varchar(50) | 操作人所在机构 |
| `operator_ip` | varchar(64) | 客户端 IP |
| `operator_ua` | varchar(500) | User-Agent |
| `http_method` | varchar(8) | GET/POST/PUT/DELETE |
| `request_uri` | varchar(500) | 请求路径 |
| `request_params` | text | 请求参数 JSON |
| `before_snapshot` | text | 修改前快照 JSON（仅高危动作） |
| `after_snapshot` | text | 修改后快照 JSON（仅高危动作） |
| `result` | varchar(16) | SUCCESS/FAIL |
| `fail_reason` | text | 失败原因 |
| `cost_ms` | int | 接口耗时 |
| `audit_time` | datetime | 审计时间 |

## 1. 高危动作清单

| 接口路径 | HTTP 方法 | 动作码 | 级别 | 资源类型 | 审计说明 |
|---|---|---|---|---|---|
| `GET /api/products/export` | GET | `PRODUCT_EXPORT` | HIGH | PRODUCT | 产品数据导出，记录过滤条件与导出行数 |
| `DELETE /api/admin/nav/{id}` | DELETE | `NAV_DELETE` | MEDIUM | NAV | 删除导航（软删） |
| `DELETE /api/products/{id}` | DELETE | `PRODUCT_DELETE` | HIGH | PRODUCT | 产品软删，记录关联负责人与附件 |
| `DELETE /api/admin/documents/{id}` | DELETE | `DOC_DELETE` | HIGH | DOC | 文档软删，记录文件对象 ID |
| `PUT /api/employees/{empId}` | PUT | `EMPLOYEE_EDIT_BY_OTHER` | MEDIUM | EMPLOYEE | **仅当 operator ≠ empId 时审计** |
| `PUT /api/products/{id}` | PUT | `PRODUCT_EDIT` | MEDIUM | PRODUCT | 产品编辑，记录前后快照 |
| `POST /api/products` | POST | `PRODUCT_CREATE` | MEDIUM | PRODUCT | 产品新增 |
| `POST /api/admin/documents/upload` | POST | `DOC_CREATE` | MEDIUM | DOC | 文档新增 |
| `POST /api/admin/nav` | POST | `NAV_CREATE` | LOW | NAV | 新增导航 |
| `PUT /api/admin/nav/{id}` | PUT | `NAV_EDIT` | LOW | NAV | 编辑导航 |
| `PUT /api/products/{id}/responsible` | PUT | `PRODUCT_RESPONSIBLE_CHANGE` | HIGH | PRODUCT | 变更产品负责人 |
| `PUT /api/employees/{empId}/maintainer` | PUT | `EMPLOYEE_MAINTAINER_CHANGE` | MEDIUM | EMPLOYEE | 变更通讯录维护人 |

**未列出的接口默认为 `NONE` 级别不审计**（如工作台聚合、员工搜索、产品列表等纯查询接口）。

## 3. 特殊审计场景

### 3.1 通讯录编辑他人信息

**场景识别**：
- Service 层在处理 `PUT /api/employees/{empId}` 时，比对 `operatorEmpId` 与路径 `empId`
- **不相等** → 按 `EMPLOYEE_EDIT_BY_OTHER`（MEDIUM）记录
- **相等** → 按 `EMPLOYEE_EDIT_SELF`（NONE，不强制审计）

**记录要求：**
- 必须包含完整的 `beforeSnapshot` 与 `afterSnapshot`
- 敏感字段（mobile）必须脱敏后存储
- 操作人与被编辑人在同一条记录内清晰可见（operator 字段 + resourceId）

**权限联动：**
- 编辑他人必须先通过 `BizScopeApi.checkWritePermission()` 校验
- 权限校验失败同样记录审计，`result=FAIL` 且 `failReason` 说明

### 3.2 产品删除的追溯快照

**删除前必须捕获以下完整信息：**
- 产品基本信息（id、product_code、product_name、status）
- 关联附件 ID（`fileObjectId`）
- 负责人列表（`responsibleEmpIds`）
- 维护部门（`productDeptOrgCode`）
- 创建时间与最后更新时间

**目的：** 万一误删需要恢复，从审计日志 `beforeSnapshot` 即可还原所有关联关系（附件、负责人）。

### 3.3 产品导出的特殊字段

`PRODUCT_EXPORT` 需要额外记录：

| 字段 | 说明 | 是否必填 |
|---|---|---|
| `exportFormat` | 导出格式（XLSX/CSV） | 是 |
| `exportedRowCount` | 实际导出行数 | 是 |
| `exportedColumns` | 导出包含的列清单 | 否 |
| `filterConditions` | 完整过滤条件 JSON | 是 |
| `dataScope` | 应用的数据范围（ALL/ORG_SUBTREE/ORG_SELF） | 是 |
| `estimatedDataSize` | 预估数据量（KB） | 否 |

**阈值告警**：单次导出行数 > 5000 时触发运维告警（不阻塞业务）。

### 3.4 产品负责人变更的前后对比

`PRODUCT_RESPONSIBLE_CHANGE` 必须清晰体现：
- `before`：原负责人列表
- `after`：新负责人列表
- `removed`：被移除的负责人
- `added`：新增的负责人

**目的**：便于管理员追溯"谁把 E10001 从产品负责人中移除"类问题。

### 3.5 文档删除的文件对象保留

**`DOC_DELETE` 审计记录必须包含 `fileObjectId`：**
- 文档软删后，`file_object` 仍保留 90 天
- 90 天内如需恢复，凭审计日志的 `fileObjectId` 可找回原文件

## 4. 非高危写操作的审计策略

### 4.1 不审计的场景

以下操作不强制记审计日志（`action_level=NONE`）：

| 场景 | 理由 |
|---|---|
| 通讯录本人编辑本人 `self_desc`、`mobile`、`email` | 日常频繁操作，高价值审计应关注"他人编辑" |
| 个人快捷入口 `CUSTOM` 的增删改 | 纯个人设置，无跨用户影响 |
| 工作台聚合查询 | 纯查询，频率极高 |
| 通讯录搜索/产品列表/导航列表 | 查询类 |
| 产品 `listSupportAvailableProducts` | 查询类 |
| 产品详情查看 | 查询类 |
| 文档下载 | 仅记日志，不强制审计 |

**注意：** 不审计 ≠ 不记日志。常规操作仍在 `application.log` 和 `access.log` 中留痕，便于运维定位，仅不进入 `sys_audit_log`。

### 4.2 审计实现方式

**基于 AOP 的声明式审计：**

```java
@RestController
public class ProductController {

    @BizAudit(
        action = "PRODUCT_DELETE",
        level = AuditLevel.HIGH,
        resourceType = "PRODUCT",
        resourceIdExpr = "#productId",
        captureBeforeSnapshot = true,
        snapshotLoaderBean = "productSnapshotLoader"
    )
    @DeleteMapping("/api/products/{productId}")
    public Result<Void> delete(@PathVariable String productId) {
        productFacade.deleteProduct(productId, CurrentUser.empId());
        return Result.success();
    }
}
```

**注解定义（由 common-aop 提供）：**

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface BizAudit {
    String action();
    AuditLevel level() default AuditLevel.MEDIUM;
    String resourceType();
    String resourceIdExpr() default "";        // SpEL 表达式
    boolean captureBeforeSnapshot() default false;
    boolean captureAfterSnapshot() default true;
    String snapshotLoaderBean() default "";    // 提供快照的 Bean，实现 SnapshotLoader 接口
}
```

### 4.3 Snapshot Loader 实现

对于需要前后快照的接口，需提供 `SnapshotLoader` 实现：

```java
@Component("productSnapshotLoader")
public class ProductSnapshotLoader implements SnapshotLoader {
    private final ProductInfoMapper mapper;

    @Override
    public Object load(String resourceId) {
        ProductInfo p = mapper.selectById(resourceId);
        if (p == null) return null;
        // 脱敏处理 + 裁剪非必要字段
        return ProductSnapshotDTO.from(p);
    }
}
```

### 4.4 审计失败降级

**原则：审计失败不影响主业务**

- `sys_audit_log` 写入异常时，降级到 `application.log` 记录 WARN 级别日志（带完整审计 payload）
- 运维通过 ELK 日志聚合兜底
- 降级日志由 `AuditFailureFallback` 组件处理，统一前缀 `[AUDIT_FALLBACK]`

```java
try {
    auditLogMapper.insert(record);
} catch (Exception ex) {
    log.warn("[AUDIT_FALLBACK] writeAuditFailed, payload={}", JsonUtil.toJson(record), ex);
}
```

## 5. 审计数据脱敏规范

### 5.1 必须脱敏的字段

| 字段 | 脱敏规则 | 示例 |
|---|---|---|
| `mobile` | 保留前 3 后 4 位 | `13812345678` → `138****5678` |
| `email` | 保留 @ 前 3 字符 | `zhangsan@bank.com` → `zha***@bank.com` |
| `idNumber`（如涉及） | 保留前 6 后 4 | 未在 portal 模块直接涉及 |

**脱敏时机：** 写入审计日志之前，由 `SensitiveDataMasker`（common-security 提供）统一处理。

### 5.2 禁止记录的字段

- 密码（hash 或明文均禁止）
- Session Token
- 任何形式的鉴权凭据
- 用户输入的搜索关键词中可能包含的个人隐私（如身份证号）

## 6. 审计查询与告警

### 6.1 审计查询接口

**由 system-governance-center 提供统一接口：**

```
GET /api/governance/audit/search
  ?module=portal-content-center
  &action=PRODUCT_DELETE
  &operatorEmpId=E10023
  &startTime=2026-04-01 00:00:00
  &endTime=2026-04-10 23:59:59
  &page=1
  &size=20
```

**portal 模块不提供独立审计查询接口。**

### 6.2 高危动作告警

由 governance 模块统一消费审计流，触发告警：

| 告警规则 | 阈值 | 通知方式 |
|---|---|---|
| 单用户单日产品删除 > 5 | 5 次 | 企业微信 + 运维邮件 |
| 单用户单日产品导出 > 10 | 10 次 | 企业微信 |
| 产品导出单次行数 > 5000 | 5000 | 运维邮件 |
| EMPLOYEE_EDIT_BY_OTHER 单日 > 50 | 50 次 | 运维邮件 |
| 审计日志写入失败率 > 1% | 1% | PagerDuty 实时告警 |

## 7. 审计日志保留与归档

| 级别 | 在线存储时长 | 归档方式 |
|---|---|---|
| HIGH | 1 年（MySQL） + 5 年（冷归档 MinIO/OSS） | 月度归档 |
| MEDIUM | 6 个月（MySQL） + 2 年（冷归档） | 月度归档 |
| LOW | 3 个月（MySQL） | 直接清理 |

**归档任务由 governance 模块统一调度**，portal 模块无需自行处理。
