# 门户与内容中心 — 后端架构

> 文档版本: v1.0
> 对应模块: `portal-content-center`
> 技术栈: Spring Boot 3.2.3 + JDK 17 + MyBatis 3.0.3 + MySQL 8.0 + Redis 6.X

## 1. 模块职责边界

### 1.1 负责范围
- **工作台聚合**：聚合其他模块数据，提供统一的工作台数据视图
- **网址导航管理**：`portal_nav` 表的 CRUD
- **快捷入口管理**：`portal_shortcut` 表的 CRUD 和个性化配置
- **通讯录管理**：`addrbook_employee` 表的维护、查询、搜索
- **产品资料管理**：`product_info` 表的维护、查询、负责人反向关联
- **文档管理**：`doc_info` 表的维护和下载授权
- **附件元数据管理**：产品附件、文档附件的 `fileObjectId` 绑定
- **60天定时提醒**：通讯录/产品的更新提醒任务
- **领域事件发布**：产品负责人变更、通讯录更新事件

### 1.2 不负责范围
- **不审批业务**：所有审批流程由 `workflow-center` 负责
- **不计算 KPI**：指标计算由 `performance-engine-center` 负责
- **不管理流程状态**：流程状态由 `workflow-center` 持有
- **不直接操作 Flowable API**：所有流程相关能力都必须经过 `workflow-center` 标准契约；当前代码侧使用 `WorkflowQueryAdapter` 封装正式 `WorkflowQueryApi` 并负责降级
- **不管理认证授权**：用户、组织、权限校验由 `auth-permission-center` 负责
- **不存储文件内容**：文件本体存储在 MinIO，本模块只存 `fileObjectId`

## 4. 分层规范

### 4.1 Controller 层
**职责**：接收 HTTP 请求、参数校验、调用 Service、返回统一响应

**规范**：
- 所有方法必须标注 `@BizAuth`（由 `auth-permission-center` 的注解拦截器处理）
- 所有入参必须使用 `@Valid` + JSR-303 注解校验
- 所有响应必须使用 `common-web` 的 `ApiResult<T>` 包装
- Controller 不允许直接访问 `Mapper`，必须经过 `Service`
- Controller 不持有任何业务逻辑，只做参数转换和调用转发

**示例**：
```java
@RestController
@RequestMapping("/api/admin/nav")
@Tag(name = "网址导航管理")
public class NavController {

    @Resource
    private NavService navService;

    /**
     * 新增导航
     *
     * @param req 新增请求
     * @return 新增后的导航 ID
     */
    @PostMapping
    @BizAuth(bizType = "NAV", action = "WRITE")
    @Operation(summary = "新增网址导航")
    public ApiResult<Long> createNav(@Valid @RequestBody NavCreateReqDTO req) {
        Long id = navService.createNav(req);
        return ApiResult.success(id);
    }
}
```

### 4.2 Facade 层
**职责**：对外 `Api` 接口的实现，负责编排 `Service` 层方法，转换为 DTO 返回

**规范**：
- `Facade` 类实现对应的 `Api` 接口，并通过 Spring Bean 暴露
- `Facade` 不包含业务逻辑，只做参数转换、调用 `Service`、组装 DTO
- 被其他模块调用的入口必须在 `Facade` 层，不允许其他模块直接调用 `Service`
- `Facade` 层的方法天然是事务的读视图，不涉及跨事务写操作

**示例**：
```java
@Service
public class ProductApiImpl implements ProductApi {

    @Resource
    private ProductService productService;

    @Resource
    private ProductConverter productConverter;

    @Override
    public Optional<ProductDTO> getProduct(String productId) {
        ProductInfo entity = productService.getById(productId);
        if (entity == null || entity.getDeleted() == 1) {
            return Optional.empty();
        }
        return Optional.of(productConverter.toDTO(entity));
    }

    @Override
    @Cacheable(value = "portal:product:support-available", key = "'all'")
    public List<ProductDTO> listSupportAvailableProducts() {
        List<ProductInfo> list = productService.listSupportAvailable();
        return list.stream().map(productConverter::toDTO).collect(Collectors.toList());
    }
}
```

### 4.3 Service 层
**职责**：业务逻辑、事务管理、二次权限校验、事件发布

**规范**：
- 所有 `public` 方法必须有注释，说明业务目的、入参、出参、异常
- 写操作方法必须加 `@Transactional`
- 写操作必须在基于实体层面做二次权限校验（防止 URL 越权）
- 跨模块调用通过注入的 `*Api` Bean 实现，不允许直接 HTTP 调用
- 业务异常通过抛出 `BizException(PortalErrorCode.XXX)` 的方式传递
- 所有读接口必须应用 `DATA_SCOPE` 数据范围

**示例**：
```java
@Service
public class ProductServiceImpl implements ProductService {

    @Resource
    private ProductInfoMapper productInfoMapper;

    @Resource
    private CurrentUserApi currentUserApi;

    @Resource
    private BizScopeApi bizScopeApi;

    @Resource
    private ApplicationEventPublisher eventPublisher;

    /**
     * 更新产品信息。
     *
     * @param id 产品 ID
     * @param req 更新请求
     * @throws BizException PORTAL-40302 无权维护非本机构产品
     */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void updateProduct(Long id, ProductUpdateReqDTO req) {
        ProductInfo entity = productInfoMapper.selectById(id);
        if (entity == null || entity.getDeleted() == 1) {
            throw new BizException(PortalErrorCode.PRODUCT_NOT_FOUND);
        }

        // 二次权限校验：仅本维护组织可编辑
        String currentOrgCode = currentUserApi.getCurrentUser().getOrgCode();
        if (!Objects.equals(currentOrgCode, entity.getProductDeptOrgCode())
                && !currentUserApi.isAdmin()) {
            throw new BizException(PortalErrorCode.PRODUCT_NO_WRITE_PERMISSION);
        }

        // 更新字段
        BeanUtil.copyProperties(req, entity, CopyOptions.create().ignoreNullValue());
        entity.setUpdatedBy(currentUserApi.getCurrentUser().getEmpId());
        entity.setUpdatedTime(LocalDateTime.now());
        productInfoMapper.updateById(entity);

        // 发布事件（产品更新后可能影响缓存）
        eventPublisher.publishEvent(new ProductResponsibleUpdatedEvent(id));
    }
}
```

### 4.4 Mapper 层
**职责**：数据访问，基于 MyBatis 实现

**规范**：
- Mapper 接口必须放在 `mapper` 包下，XML 放在 `resources/mapper/`
- 所有查询必须传入数据范围参数（`dataScope`）用于 SQL 拼接
- 禁止跨模块查询其他模块的表（跨模块数据通过 `*Api` 获取）
- 复杂查询必须使用 XML，禁止在接口上用 `@Select` 写长 SQL
- 所有更新必须带乐观锁或 `updated_time` 条件，防止并发覆盖
- 逻辑删除字段统一为 `deleted`（0 未删除，1 已删除）

### 4.5 Entity 层
**职责**：数据库表到 Java 对象的映射

**规范**：
- 每个实体对应一张表，类名为表名的驼峰形式（`addrbook_employee` → `AddrbookEmployee`）
- 使用 Lombok `@Data` 注解简化 getter/setter
- JSON 字段使用 `TypeHandler` 自动序列化/反序列化
- 枚举字段使用 `String` 存储，由 Service 层转换

### 4.6 Converter 层
**职责**：Entity 与 DTO 之间的转换

**规范**：
- 使用 MapStruct 或手写转换器
- Entity → DTO 时脱敏敏感字段（手机号、邮箱）
- DTO → Entity 时忽略 null 值

## 5. 错误码（前缀 PORTAL）

### 5.1 错误码枚举定义
```java
public enum PortalErrorCode implements ErrorCode {

    // 40000 段：资源不存在
    NAV_NOT_FOUND("PORTAL-40001", "导航不存在"),
    EMPLOYEE_NOT_FOUND("PORTAL-40002", "通讯录员工不存在"),
    PRODUCT_NOT_FOUND("PORTAL-40003", "产品不存在"),
    SHORTCUT_NOT_FOUND("PORTAL-40004", "快捷入口不存在"),
    DOC_NOT_FOUND("PORTAL-40401", "文档不存在"),

    // 40300 段：权限错误
    ADDRBOOK_NO_WRITE_PERMISSION("PORTAL-40301", "无权编辑本人以外的通讯录"),
    PRODUCT_NO_WRITE_PERMISSION("PORTAL-40302", "无权维护非本机构产品"),
    NAV_NO_WRITE_PERMISSION("PORTAL-40303", "无权维护网址导航"),
    DOC_NO_WRITE_PERMISSION("PORTAL-40304", "无权维护文档"),

    // 40900 段：业务冲突
    PRODUCT_CODE_DUPLICATE("PORTAL-40901", "产品代码已存在"),
    EMPLOYEE_RESIGNED("PORTAL-40902", "通讯录员工状态已离职"),
    NAV_NAME_DUPLICATE("PORTAL-40903", "导航名称在同一分类下已存在"),
    PRODUCT_RESPONSIBLE_LIMIT("PORTAL-40904", "单个员工负责产品数量超过上限"),

    // 42200 段：参数校验错误
    SHORTCUT_TYPE_INVALID("PORTAL-42201", "快捷入口类型非法"),
    NAV_URL_INVALID("PORTAL-42202", "导航URL格式非法"),
    FILE_OBJECT_NOT_EXIST("PORTAL-42203", "附件对象不存在"),

    // 50000 段：系统错误（降级场景）
    METRIC_SERVICE_UNAVAILABLE("PORTAL-50001", "指标服务暂时不可用"),
    WORKFLOW_QUERY_FAILED("PORTAL-50002", "待办查询失败");

    private final String code;
    private final String message;

    PortalErrorCode(String code, String message) {
        this.code = code;
        this.message = message;
    }

    @Override
    public String getCode() { return code; }

    @Override
    public String getMessage() { return message; }
}
```

### 5.2 错误码使用规范
- 业务异常统一抛出 `BizException(PortalErrorCode.XXX)`
- 全局异常处理器（`common-web` 提供）自动转换为 `ApiResult.error(code, message)`
- 错误码前缀固定为 `PORTAL-`，编号按语义段划分
- 新增错误码必须同步到 `PortalErrorCode` 枚举，不允许在代码中直接构造字符串

## 7. 核心业务流程

### 7.1 工作台聚合流程
```
用户请求 GET /api/portal/workspace
    ↓
PortalController.getWorkspace()
    ↓
PortalAggregateService.aggregate(empId)
    ├─→ 并行调用 WorkflowQueryAdapter.listPending/countPending (线程 1)
    ├─→ 并行调用 NotifyApi.queryNotifications(empId)       (线程 2)
    ├─→ 并行调用 MetricApi.queryMetricCards(empId, codes)  (线程 3，弱依赖可降级)
    └─→ 并行调用 ShortcutService.listByEmp(empId)         (线程 4)
    ↓
合并结果为 WorkspaceDTO
    ↓
返回 ApiResult.success(workspace)
```

**实现要点**：
- 使用 `CompletableFuture` 并行发起四个调用
- 每个调用独立 try-catch，失败时返回空结果不影响其他
- 总超时时间 500ms，超时的区域返回空列表
- 使用 `@Async` + 自定义线程池，线程池大小 10

### 7.2 通讯录编辑流程
```
用户提交 PUT /api/employees/{empId}
    ↓
AddressBookController.updateEmployee()
    ├─→ @BizAuth(bizType=ADDRBOOK, action=WRITE) 前置校验
    ↓
AddressBookService.updateEmployee(empId, req)
    ├─→ 二次权限校验 (SELF 或 ORG 范围)
    ├─→ 查询原有 responsible_product_ids
    ├─→ 计算新增/移除的产品列表
    ↓
@Transactional 事务开始
    ├─→ 更新 addrbook_employee 表
    ├─→ 对每个新增产品，调用 ProductService.addResponsibleEmp()
    ├─→ 对每个移除产品，调用 ProductService.removeResponsibleEmp()
    ├─→ 发布 AddrbookUpdatedEvent
    └─→ 发布 ProductResponsibleUpdatedEvent
事务提交
    ↓
返回 ApiResult.success()
```

### 7.3 产品负责人同步流程
```
AddressBookService.updateEmployee() 调用
    ↓
ProductService.addResponsibleEmp(productId, empId)
    ├─→ 查询 product_info
    ├─→ 检查 responsible_emp_ids 是否已包含 empId
    ├─→ 若未包含，JSON_ARRAY_APPEND 追加
    ├─→ 检查负责产品数量是否超限（V1 上限 20）
    ├─→ 更新 responsible_emp_ids
    └─→ 清理缓存 portal:product:*
```

### 7.4 60天提醒定时任务流程
```
每日 02:00 触发 UpdateReminderService.checkAddrbook()
    ↓
查询 addrbook_employee WHERE updated_time < NOW() - 60 DAY
    ↓
对每个过期员工：
    ├─→ 检查 Redis key portal:reminder:addrbook:{empId} 是否存在
    ├─→ 若存在则跳过（15天内已提醒）
    ├─→ 调用 NotifyApi.sendNotification()
    ├─→ 调用 NotifyApi.sendEmail()
    └─→ 设置 Redis key TTL 15 天

每日 02:30 触发 UpdateReminderService.checkProduct()
    ↓
查询 product_info WHERE updated_time < NOW() - 60 DAY AND status = ACTIVE
    ↓
对每个过期产品：
    ├─→ 查询维护部门秘书
    ├─→ 检查 Redis 去重 key
    ├─→ 调用 NotifyApi.sendNotification()
    └─→ 设置 Redis key TTL 15 天
```

```java
@Configuration
@EnableAsync
@EnableScheduling
public class PortalConfig {

    @Bean("portalAggregateExecutor")
    public Executor portalAggregateExecutor(
            @Value("${portal.async.core-pool-size:5}") int corePoolSize,
            @Value("${portal.async.max-pool-size:10}") int maxPoolSize,
            @Value("${portal.async.queue-capacity:50}") int queueCapacity) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(corePoolSize);
        executor.setMaxPoolSize(maxPoolSize);
        executor.setQueueCapacity(queueCapacity);
        executor.setThreadNamePrefix("portal-aggr-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}
```

## 9. 关键设计决策

### 9.1 为什么工作台聚合接口不加 @BizAuth？
工作台数据天然受当前登录用户约束（`CurrentUserContext.getEmpId()`），不需要 `@BizAuth` 再做一次资源级别的权限校验。登录态由 `common-security` 的过滤器统一拦截，未登录请求无法进入 Controller。

### 9.2 为什么产品负责人由通讯录"认领"而非产品端录入？
- 符合业务习惯：员工主动声明自己负责的产品比部门管理员代为指定更符合实际
- 简化管理：避免双端维护的数据不一致问题
- 便于负责人离职时一键清理

### 9.3 为什么使用 JSON 字段存储 responsible_emp_ids 和 responsible_product_ids？
- 关联关系较简单，不需要独立表维护
- 数据量小（单员工负责产品上限 20，单产品负责人上限 10）
- MySQL 8.0 支持 `JSON_CONTAINS`、`JSON_ARRAY_APPEND` 等操作
- 查询时直接反序列化为 List，避免额外的 join 查询

### 9.4 为什么弱依赖 performance-engine-center？
- 指标卡片不是工作台的必需组件，缺失时不影响核心业务
- 性能模块计算量大，可能出现短暂不可用
- 使用弱依赖 + try-catch 降级可避免级联故障

### 9.5 为什么使用事件驱动同步产品负责人？
- 解耦通讯录与产品模块内部的写逻辑
- 便于后续扩展（例如触发 ES 索引重建、缓存失效、审计日志等）
- 避免长事务（事件监听器可以异步消费）

## 10. 监控与可观测性

### 10.1 关键指标
- 工作台聚合接口响应时间（P50/P95/P99）
- 各子调用（待办/通知/指标/快捷入口）的响应时间和失败率
- 60天提醒任务的执行成功率和提醒发送数量
- 产品和通讯录的缓存命中率

### 10.2 告警规则
- 工作台聚合接口 P95 > 500ms 持续 5 分钟
- `MetricApi` 调用失败率 > 10%（降级阈值）
- 60天提醒任务执行失败
- 产品缓存命中率 < 50%

### 10.3 日志规范
- 所有 Controller 入口打印 `traceId + empId + action` 的 INFO 日志
- 所有跨模块调用打印 `targetApi + 耗时 + 是否成功`
- 权限拒绝打印 WARN 日志（包含原因）
- 定时任务执行打印 `执行耗时 + 处理数量 + 失败数量`
