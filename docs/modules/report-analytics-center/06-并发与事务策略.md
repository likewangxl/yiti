# 报表分析中心 -- 并发与事务策略

> 版本：V1 | 最后更新：2026-04-10
> 模块代号：report-analytics-center
> 参考依据：`docs/common-dev-guide.md` 第 5 章（事务边界）/ 第 6 章（审计切面）

---

## 1. 纯只读原则

报表分析中心 V1 的根本特征是 **"以只读为主、极少数写操作"**：

| 数据类型 | 读写特征 |
|:---|:---|
| 业务数据（指标值、客户、KPI） | **全部只读**，且通过 Api 间接读 |
| 保存方案（rpt_saved_query） | 用户私有 CRUD，低频写 |
| SQL 探查历史（sql_probe_history） | 审计写入，仅追加 |
| 缓存（Redis） | 读多写少，TTL 自动过期 |

**核心原则**：

1. **查询接口禁用事务**：所有 `GET /api/reports/*` 接口**不得**使用 `@Transactional`，避免锁数据库连接；
2. **自有表写操作使用 READ_COMMITTED**：MyBatis 默认隔离级别，防止脏读；
3. **跨模块 Api 调用不在事务内**：严格遵守 `common-dev-guide.md` 第 5.3 节的"Api 调用不跨事务"原则；
4. **Redis 缓存操作不纳入事务**：缓存写入失败不回滚业务操作。

## 2. 查询方案管理

### 2.1 保存方案的并发场景

| 场景 | 并发压力 | 风险 | 处理策略 |
|:---|:---:|:---|:---|
| 同一用户创建新方案 | 极低 | 无 | 普通 INSERT |
| 同一用户编辑不同方案 | 极低 | 无 | 普通 UPDATE |
| 同一用户在两个标签页编辑同一方案 | 低 | 丢失更新 | **乐观锁**（version 字段） |
| 多用户同时保存各自方案 | 中 | 无 | 各自隔离，无锁 |
| 同一用户连续保存导致超 10 条 | 低 | 数据不一致 | **单事务内先删最旧再插入** |

### 2.2 "每用户 10 条"限制的实现

```java
@Service
public class SavedQueryServiceImpl implements SavedQueryService {

    private static final int MAX_PER_USER = 10;

    @Transactional(rollbackFor = Exception.class)
    public SavedQueryRespDTO save(SavedQuerySaveCmd cmd) {
        String empId = CurrentUserContext.get().getEmpId();

        // 1. 校验当前数量（在事务内查询，防并发超限）
        int count = savedQueryMapper.countByEmpId(empId);

        // 2. 超限则先删最旧的
        if (count >= MAX_PER_USER) {
            int needDelete = count - MAX_PER_USER + 1;
            savedQueryMapper.deleteOldestByEmpId(empId, needDelete);
        }

        // 3. INSERT 新方案
        SavedQueryEntity entity = buildEntity(cmd, empId);
        savedQueryMapper.insert(entity);

        return toRespDTO(entity);
    }
}
```

**对应 Mapper XML 片段**：

```xml
<!-- 按创建时间升序删除最旧的 N 条 -->
<delete id="deleteOldestByEmpId">
    DELETE FROM rpt_saved_query
    WHERE id IN (
        SELECT id FROM (
            SELECT id FROM rpt_saved_query
            WHERE emp_id = #{empId}
            ORDER BY created_time ASC
            LIMIT #{limit}
        ) t
    )
</delete>
```

**注意**：

- MySQL 不支持 `DELETE FROM t WHERE id IN (SELECT FROM t)`，必须加一层子查询别名；
- 事务隔离级别为 `READ_COMMITTED`，超高并发下可能出现"同时超限但都进入 delete 分支"，实际上每用户 QPS 不会超过 1，可接受。

### 2.3 乐观锁实现（编辑同一方案）

```java
public SavedQueryRespDTO update(String id, SavedQueryUpdateCmd cmd) {
    String empId = CurrentUserContext.get().getEmpId();

    // 读取当前版本
    SavedQueryEntity entity = savedQueryMapper.selectById(id);
    if (entity == null || !empId.equals(entity.getEmpId())) {
        throw new BusinessException("RPT-4041", "方案不存在或无权访问");
    }

    // 传入 version 做乐观锁更新
    int affected = savedQueryMapper.updateWithVersion(
        id, cmd.getName(), cmd.getSubjectIds(), cmd.getMetricCodes(), cmd.getVersion()
    );

    if (affected == 0) {
        throw new BusinessException("RPT-4091",
            "方案已被其他会话修改，请刷新后重试");
    }

    return toRespDTO(savedQueryMapper.selectById(id));
}
```

**对应 Mapper XML**：

```xml
<update id="updateWithVersion">
    UPDATE rpt_saved_query
    SET name = #{name},
        subject_ids = #{subjectIds},
        metric_codes = #{metricCodes},
        version = version + 1
    WHERE id = #{id} AND version = #{version}
</update>
```

## 3. SQL 探查并发控制

### 3.1 并发控制目标

| 维度 | 目标 | 手段 |
|:---|:---|:---|
| 单用户并发 | 同一用户同时只能有 1 个 SQL 探查请求 | **Redis 分布式锁** |
| 全局并发 | 全系统同时最多 10 个 SQL 探查 | **Redis 计数器（Semaphore）** |
| 执行超时 | 默认 30 秒，超时立即中断 | **Statement.setQueryTimeout** |
| 结果行数 | 最大 1000 行 | **SQL 自动改写 LIMIT** |

### 3.2 单用户锁实现

```java
@Service
public class SqlProbeServiceImpl implements SqlProbeService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String LOCK_KEY_PREFIX = "report:sql-probe:lock:";
    private static final long LOCK_TIMEOUT_SECONDS = 35; // 略大于 SQL 超时

    public SqlProbeRespDTO execute(SqlProbeCmd cmd) {
        String empId = CurrentUserContext.get().getEmpId();
        String lockKey = LOCK_KEY_PREFIX + empId;
        String lockValue = UUID.randomUUID().toString();

        // 1. 获取用户级锁
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, LOCK_TIMEOUT_SECONDS, TimeUnit.SECONDS);

        if (!Boolean.TRUE.equals(acquired)) {
            throw new BusinessException("RPT-4291",
                "您有另一条 SQL 正在执行，请等待完成或刷新历史记录");
        }

        try {
            return doExecute(cmd, empId);
        } finally {
            // 2. 释放锁（Lua 脚本保证原子性）
            releaseLock(lockKey, lockValue);
        }
    }

    private void releaseLock(String key, String value) {
        String script = "if redis.call('get', KEYS[1]) == ARGV[1] "
                      + "then return redis.call('del', KEYS[1]) "
                      + "else return 0 end";
        redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList(key), value);
    }
}
```

### 3.3 全局信号量实现

```java
public class SqlProbeSemaphore {

    private static final String SEMAPHORE_KEY = "report:sql-probe:semaphore";
    private static final int MAX_CONCURRENT = 10;
    private static final long TIMEOUT_MS = 2000; // 等待锁 2 秒

    public boolean acquire() {
        long deadline = System.currentTimeMillis() + TIMEOUT_MS;
        while (System.currentTimeMillis() < deadline) {
            Long current = redisTemplate.opsForValue().increment(SEMAPHORE_KEY);
            if (current != null && current <= MAX_CONCURRENT) {
                redisTemplate.expire(SEMAPHORE_KEY, 60, TimeUnit.SECONDS);
                return true;
            }
            // 超限立即回滚计数
            redisTemplate.opsForValue().decrement(SEMAPHORE_KEY);
            try {
                Thread.sleep(100);
            } catch (InterruptedException ignored) {
                Thread.currentThread().interrupt();
                return false;
            }
        }
        return false;
    }

    public void release() {
        Long current = redisTemplate.opsForValue().decrement(SEMAPHORE_KEY);
        if (current != null && current < 0) {
            // 异常情况：计数为负，重置为 0
            redisTemplate.opsForValue().set(SEMAPHORE_KEY, "0");
        }
    }
}
```

### 3.4 超时控制

使用独立的只读数据源 + `Statement.setQueryTimeout`：

```java
@Resource(name = "dataSourceReadOnly")
private DataSource readOnlyDataSource;

private SqlProbeResult doExecuteSql(String sql, int timeoutSeconds) {
    try (Connection conn = readOnlyDataSource.getConnection();
         PreparedStatement stmt = conn.prepareStatement(sql)) {

        // 设置查询超时（MySQL 驱动会发送 KILL QUERY 中断）
        stmt.setQueryTimeout(timeoutSeconds);
        // 设置最大返回行数
        stmt.setMaxRows(1000);

        long startTime = System.currentTimeMillis();
        try (ResultSet rs = stmt.executeQuery()) {
            List<Map<String, Object>> rows = parseResultSet(rs);
            long duration = System.currentTimeMillis() - startTime;
            return new SqlProbeResult(rows, duration, SqlProbeStatus.SUCCESS);
        }

    } catch (SQLException e) {
        if (e.getMessage() != null && e.getMessage().contains("timeout")) {
            return new SqlProbeResult(null, 0, SqlProbeStatus.TIMEOUT, e.getMessage());
        }
        return new SqlProbeResult(null, 0, SqlProbeStatus.FAILED, e.getMessage());
    }
}
```

### 3.5 历史记录的事务边界

| 阶段 | 事务行为 |
|:---|:---|
| T1：执行前 INSERT 占位 | 独立短事务，提交后立即释放 |
| T2：执行 SQL | **不在事务内**（只读查询） |
| T3：完成后 UPDATE 状态 | 独立短事务 |

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public String insertPlaceholder(String empId, String sql, String reason) {
    SqlProbeHistoryEntity entity = new SqlProbeHistoryEntity();
    entity.setId(IdUtil.simpleUUID());
    entity.setEmpId(empId);
    entity.setSqlText(sql);
    entity.setRemark(reason);
    entity.setStatus("RUNNING");
    sqlProbeHistoryMapper.insert(entity);
    return entity.getId();
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void updateResult(String id, SqlProbeResult result) {
    sqlProbeHistoryMapper.updateResult(id,
        result.getStatus().name(),
        result.getRowCount(),
        (int) result.getDurationMs(),
        result.getErrorMsg());
}
```

**理由**：

- 占位 INSERT 要立即可见，便于失联场景追溯；
- SQL 执行时间可能长达 30 秒，不能阻塞其他事务；
- 更新结果是审计证据，必须独立提交。

## 4. 异步导出任务

### 4.1 同步 vs 异步的判定规则

| 数据规模 | 处理方式 | 超时 |
|:---|:---|:---|
| ≤ 5000 行 | 同步 HTTP 响应流式返回 Excel | 10 秒 |
| > 5000 行 | 异步任务 + Redis 队列 | 5 分钟 |

判定在 Controller 层完成：先调用 Api 预估行数，超限转异步。

### 4.2 异步导出流程

```
用户 ─请求导出─> Controller
                   │
                   ├─ 预估行数（同步调用 MetricApi.estimateRowCount）
                   │
                   ├─ 同步路径（≤5000）：
                   │    └─ 直接查询 + ExcelWriter 流式输出
                   │
                   └─ 异步路径（>5000）：
                        ├─ 生成 taskId
                        ├─ 推入 Redis Stream（key: report:export:queue）
                        ├─ 返回 taskId 给前端
                        └─ Worker 监听 Stream：
                             ├─ 取出任务
                             ├─ 分页拉取数据（每页 1000 行）
                             ├─ 写入临时 Excel
                             ├─ 上传 MinIO（调用 FileApi.upload）
                             ├─ 更新任务状态（Redis Hash）
                             └─ 发送通知（调用 NotificationApi.send）
```

### 4.3 Redis 数据结构

| Key | 类型 | 说明 | TTL |
|:---|:---|:---|:---|
| `report:export:queue` | Stream | 任务队列 | 永久 |
| `report:export:task:{taskId}` | Hash | 任务状态（status/progress/fileId/errorMsg） | 24 小时 |
| `report:export:user:{empId}` | Set | 用户当前任务列表 | 24 小时 |

### 4.4 Worker 线程模型

```java
@Component
public class ExportTaskWorker {

    @Value("${report.export.worker.threads:3}")
    private int workerThreads;

    @PostConstruct
    public void init() {
        // 固定线程池，3 个 Worker 并行消费
        ExecutorService executor = Executors.newFixedThreadPool(workerThreads,
            new NamedThreadFactory("report-export-worker"));
        for (int i = 0; i < workerThreads; i++) {
            executor.submit(this::pollAndExecute);
        }
    }

    private void pollAndExecute() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                ExportTaskCmd task = pollFromStream(); // Redis Stream XREADGROUP
                if (task != null) {
                    doExport(task);
                }
            } catch (Exception e) {
                log.error("Export worker error", e);
            }
        }
    }

    private void doExport(ExportTaskCmd task) {
        String taskId = task.getTaskId();
        try {
            updateStatus(taskId, "RUNNING", 0);

            // 分页拉数据并写 Excel
            File tempFile = generateExcel(task, progress ->
                updateStatus(taskId, "RUNNING", progress));

            // 上传 MinIO
            FileObjectDTO fileObject = fileApi.upload(tempFile, task.getEmpId());

            // 记录审计（补充）
            auditApi.log(buildExportAuditLog(task, fileObject));

            // 通知用户
            notificationApi.send(task.getEmpId(), "报表导出完成",
                String.format("您的报表「%s」已导出完成，点击下载", task.getReportName()));

            updateStatus(taskId, "SUCCESS", 100, fileObject.getId());

        } catch (Exception e) {
            updateStatus(taskId, "FAILED", 0, null, e.getMessage());
            log.error("Export task {} failed", taskId, e);
        }
    }
}
```

### 4.5 状态查询与取消

- 前端轮询 `GET /api/reports/export/task/{taskId}` 获取进度；
- 用户主动取消调用 `DELETE /api/reports/export/task/{taskId}`：
  - 将 Hash 中 `status` 置为 `CANCELLED`；
  - Worker 每次更新进度前检查该字段，发现为 `CANCELLED` 则中断；

## 5. 缓存策略

### 5.1 Redis 缓存布局

| Key 模式 | 类型 | 内容 | TTL | 失效场景 |
|:---|:---|:---|:---|:---|
| `report:dashboard:president:{orgCode}` | String(JSON) | 分行行长仪表盘 | 5 分钟 | sys_control 更新事件 |
| `report:dashboard:org:{orgCode}:{date}` | String(JSON) | 机构业绩汇总 | 5 分钟 | sys_control 更新事件 |
| `report:metric:tree:{dim}:{level}` | String(JSON) | 指标树元数据 | 30 分钟 | metric_def 变更事件（V2） |
| `report:dict:{dictType}` | String(JSON) | 字典缓存 | 1 小时 | 字典变更事件 |

### 5.2 缓存读写模板

```java
public DashboardPresidentDTO getPresidentDashboard(String orgCode) {
    String cacheKey = "report:dashboard:president:" + orgCode;

    // 1. 尝试读缓存
    String cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return JsonUtil.parse(cached, DashboardPresidentDTO.class);
    }

    // 2. 缓存穿透保护：短锁防止并发回源
    String lockKey = cacheKey + ":lock";
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);

    if (!Boolean.TRUE.equals(locked)) {
        // 有人在回源，等待 100ms 后重试缓存
        sleep(100);
        cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return JsonUtil.parse(cached, DashboardPresidentDTO.class);
        }
    }

    try {
        // 3. 回源查询
        DashboardPresidentDTO data = buildDashboardData(orgCode);

        // 4. 写缓存（5 分钟 TTL）
        redisTemplate.opsForValue().set(cacheKey,
            JsonUtil.stringify(data), 5, TimeUnit.MINUTES);

        return data;
    } finally {
        redisTemplate.delete(lockKey);
    }
}
```

### 5.3 缓存失效机制

**触发失效的事件**：

| 事件 | 来源 | 处理 |
|:---|:---|:---|
| `performance.sys-control.updated.v1` | performance-engine-center | 清除所有 `report:dashboard:*` 和 `report:metric:*` |
| `performance.kpi-calc.completed.v1` | performance-engine-center | 清除对应周期的 `report:dashboard:*` |
| `governance.dict.updated.v1` | system-governance-center | 清除 `report:dict:*` |

**事件处理**：

```java
@Component
public class ReportCacheInvalidator {

    @EventListener
    @Async
    public void handleSysControlUpdated(SysControlUpdatedEvent event) {
        // 使用 SCAN 避免 KEYS 阻塞
        Set<String> keys = scanKeys("report:dashboard:*");
        if (!keys.isEmpty()) {
            redisTemplate.delete(keys);
        }
        keys = scanKeys("report:metric:*");
        if (!keys.isEmpty()) {
            redisTemplate.delete(keys);
        }
        log.info("Cleared {} report cache keys due to sys-control update",
            keys.size());
    }
}
```

### 5.4 不缓存的场景

- **动态查询结果**：用户参数组合极多，缓存命中率低，不缓存；
- **SQL 探查结果**：语义要求实时，不缓存；
- **异步导出任务状态**：本身就在 Redis，不需二层缓存。

## 7. 幂等策略

### 7.1 SQL 探查 -- 不做幂等

**原因**：SQL 探查的语义是"探索性查询"，同一条 SQL 多次执行可能得到不同结果（数据在变），用户期望每次都能拿到最新数据。

**处理**：每次请求都作为新记录写入 `sql_probe_history`，`id` 自动生成。

### 7.2 查询方案保存 -- 乐观锁

详见第 2.3 节，通过 `version` 字段实现。

### 7.3 异步导出任务 -- 按 taskId 幂等

- 创建任务：前端可通过 `Idempotency-Key` 头（V2 扩展）保证同一用户同一分钟不重复创建同样的导出；
- V1 实现：Service 层检查用户 Set 中是否有进行中的同名导出，有则直接返回现有 taskId；

```java
public String createExportTask(ExportTaskCmd cmd) {
    String empId = CurrentUserContext.get().getEmpId();
    String userSetKey = "report:export:user:" + empId;

    // 查找用户是否已有相同报表的任务
    Set<String> existingTaskIds = redisTemplate.opsForSet().members(userSetKey);
    if (existingTaskIds != null) {
        for (String taskId : existingTaskIds) {
            String hashKey = "report:export:task:" + taskId;
            Map<Object, Object> taskInfo =
                redisTemplate.opsForHash().entries(hashKey);
            if (taskInfo.isEmpty()) continue;
            String status = (String) taskInfo.get("status");
            String reportKey = (String) taskInfo.get("reportKey");
            if ("RUNNING".equals(status) && cmd.getReportKey().equals(reportKey)) {
                // 已有同名任务在执行，返回旧 taskId
                return taskId;
            }
        }
    }

    // 创建新任务
    String newTaskId = IdUtil.simpleUUID();
    initTaskInfo(newTaskId, cmd, empId);
    redisTemplate.opsForSet().add(userSetKey, newTaskId);
    pushToQueue(newTaskId, cmd);
    return newTaskId;
}
```

### 7.4 领域事件订阅 -- 按 eventId 幂等

接收 `performance.sys-control.updated.v1` 等事件时：

```java
@Component
public class ReportEventListener {

    @EventListener

            log.debug("Event {} already processed, skip", eventId);
            return;
        }

        // 处理事件
        doHandle(event);
    }
}
```

## 9. 异常与回滚

### 9.1 自动回滚清单

默认 Spring 只对 `RuntimeException` 和 `Error` 回滚。本模块所有 `@Transactional` 必须声明 `rollbackFor = Exception.class`，防止 IOException 等受检异常导致部分提交。

### 9.2 不回滚的情况

- Redis 写入失败：捕获异常并记录日志，不影响主业务；
- Api 调用失败：由 `common-trace` 的降级机制处理，返回空列表或默认值；
- 审计日志写入失败：独立线程池异步写入，失败不影响主流程（但会告警）。

## 10. 压力测试与容量规划

| 场景 | V1 目标 | 评估依据 |
|:---|:---|:---|
| 仪表盘 QPS | 50/秒 | 200 活跃用户 × 每 4 秒刷新一次 |
| 动态查询 QPS | 10/秒 | 20 分析师 × 平均 30 秒一次查询 |
| 异步导出并发 | 3 任务 | Worker 线程数 |
| SQL 探查并发 | 10（信号量上限） | 技术运维团队规模 |
| 缓存命中率 | ≥ 80% | 5 分钟 TTL + 事件失效 |
| 平均响应时间（仪表盘） | < 200ms | 命中缓存时 |
| 平均响应时间（动态查询） | < 500ms | 实时查询 |
