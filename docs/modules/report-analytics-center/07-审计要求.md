| 序号 | 接口 | HTTP 方法 | 动作类型 | 资源类型 | 审计级别 | reason 必填 |
|:---:|:---|:---:|:---:|:---:|:---:|:---:|
| 1 | /api/reports/dynamic-query/export | POST | EXPORT | DYNAMIC_QUERY | 高危 | 否 |
| 2 | /api/reports/touch-task-summary/export | GET | EXPORT | TOUCH_TASK_REPORT | 高危 | 否 |
| 3 | /api/reports/perf-summary/export | GET | EXPORT | PERF_REPORT | 高危 | 否 |
| 4 | /api/reports/cust-contribution/export | GET | EXPORT | CUST_CONTRIBUTION | 高危 | 否 |
| 5 | /api/reports/sql-probe/execute | POST | EXECUTE_SQL | SQL_PROBE | **最高危** | **是** |
| 6 | /api/reports/dashboard/president | GET | READ | DASHBOARD | 敏感 | 否 |
| 7 | /api/reports/export/task/{taskId}/download | GET | DOWNLOAD | EXPORT_FILE | 高危 | 否 |

### 1.2 审计级别说明

| 级别 | 说明 | 保留期 | 告警策略 |
|:---|:---|:---:|:---|
| 最高危 | SQL 探查，可触达原始业务数据 | 5 年 | 单人每天 > 20 次告警 |
| 高危 | 数据导出、下载 | 3 年 | 单人每天 > 10 次告警 |
| 敏感 | 行长级仪表盘（只读但含全行核心指标） | 2 年 | 单人每小时 > 100 次告警 |
| 普通 | 方案管理、指标元数据读取 | 1 年 | 不告警 |

### 1.3 不审计的接口

以下接口**不**写 `audit_log`，仅依赖 `common-trace` 的请求日志：

- `GET /api/reports/saved-query/list`（列出自己的保存方案）
- `GET /api/reports/meta/metric-tree`（指标树元数据）
- `GET /api/reports/export/task/{taskId}`（查询任务状态）
- `POST /api/reports/dynamic-query/preview`（动态查询实时结果 ≤ 500 行）

**理由**：低敏感度、高 QPS，若全部写审计会产生 > 10 万条/天的日志，影响存储和可观测性。

## 3. SQL 探查审计特殊要求

SQL 探查是本模块审计等级最高的操作，有以下特殊约束：

### 3.1 必须记录的字段

| 字段 | 说明 | 必填 |
|:---|:---|:---:|
| 完整 SQL 文本 | 未脱敏的原始 SQL，包括所有字面量 | 是 |
| reason（备注） | 执行原因，业务语义 | **是**（接口层强校验） |
| 执行耗时 | 毫秒级精度 | 是 |
| 影响行数 | 成功时填充真实行数；失败/超时填 NULL | 视状态 |
| 执行状态 | SUCCESS / FAILED / TIMEOUT | 是 |
| 错误信息 | 失败时必填 | 视状态 |
| 操作人 | 工号、机构、角色 | 是 |
| 客户端 IP | 从 HTTP 头获取 | 是 |

### 3.2 双写存储

SQL 探查审计**同时写入两个表**：

| 表 | 作用 | 写入时机 | 内容完整度 |
|:---|:---|:---|:---|
| `sql_probe_history` | 便捷查询、用户自助复盘 | 执行前 INSERT 占位，执行后 UPDATE | 完整 |
| `audit_log` | 安全合规审计 | 执行后一次性写入 | 完整（SQL + reason + 结果） |

**实现顺序**：

```
1. 接口进入：校验 reason 非空
2. insertPlaceholder() → 生成 probeHistoryId，写入 sql_probe_history(status=RUNNING)
3. 获取用户锁 + 全局信号量
4. 执行 SQL（超时 30 秒）
5. updateResult() → 更新 sql_probe_history 最终状态
6. auditApi.log() → 写入 audit_log（带 probeHistoryId 关联）
7. 释放资源
```

### 3.3 失败也必须审计

**重要规则**：无论 SQL 执行结果如何（成功/失败/超时/白名单拒绝/SQL 语法错误），都必须完整写入两个表。

**原因**：

- 失败的 SQL 往往更值得关注（攻击尝试、越权访问）；
- 审计要追溯"某人试图做什么"，而不仅仅是"某人做成了什么"；
- 白名单拒绝的 SQL 是最有价值的安全事件证据。

### 3.4 不允许的审计省略

**禁止**做以下优化：

- ❌ 只审计成功的 SQL（丢失攻击证据）
- ❌ SQL 文本截断（必须完整保留）
- ❌ 同一用户短时间连续探查合并为 1 条（每条独立审计）
- ❌ 本地批处理后异步批量写入（必须在响应返回前写入完成）

### 3.5 SQL 探查告警规则

| 告警条件 | 级别 | 触达渠道 |
|:---|:---:|:---|
| 单用户 5 分钟内失败 ≥ 5 次 | P1 | 钉钉群 + 邮件 |
| 单用户每天执行 SQL > 20 次 | P2 | 钉钉群 |
| 全局每小时 SQL 探查 > 100 次 | P2 | 钉钉群 |
| 单条 SQL 执行超时（30 秒） | P3 | 日志 |
| 白名单拒绝 | P2 | 钉钉群 |

告警通过 `system-governance-center` 的通知能力或独立的告警组件实现（V2 考虑接入 Prometheus）。

## 4. 导出审计特殊要求

### 4.1 必须记录的导出参数

所有导出接口必须在 `after` 字段记录以下参数（JSON 格式）：

| 参数 | 说明 | 示例 |
|:---|:---|:---|
| dim | 维度 | "EMP" |
| subjectCount | 对象数 | 50 |
| metricCount | 指标数 | 5 |
| dataDate | 数据日期 | "2026-03-05" |
| dateFrom / dateTo | 日期范围 | "2026-03-01" / "2026-03-05" |
| rowCount | 实际导出行数 | 50 |
| fileId | 文件 ID（关联 FileApi） | "f-20260306-0001" |
| orgCode | 机构范围 | "ORG_001" |
| cycleType | 周期类型 | "MONTHLY" |

### 4.2 异步导出的补充审计

异步导出的审计**在 Worker 完成后补充写入**，而非接口返回时：

```
1. 用户提交导出 → Controller
2. Controller 只记录"任务创建"审计（action=CREATE_EXPORT_TASK，级别=普通）
3. 前端获得 taskId
4. Worker 异步执行
5. Worker 完成后，补充写"导出完成"审计（action=EXPORT，级别=高危）
6. Worker 失败时，写"导出失败"审计（action=EXPORT，status=FAILED，级别=高危）
```

**原因**：任务创建时尚不知道实际导出行数，无法填充完整审计信息。

### 4.3 下载审计

文件下载是独立的审计动作（action=DOWNLOAD），与导出（action=EXPORT）区分：

- 一次导出可能被多次下载，每次下载都必须审计；
- 审计记录中必须包含 taskId 和 fileId 的关联，便于溯源。

## 5. 审计实现指南

### 5.1 使用 @AuditLog 注解

报表模块使用 `common-dev-guide.md` 第 6 章定义的统一审计切面：

```java
@RestController
@RequestMapping("/api/reports")
public class ReportExportController {

    @PostMapping("/dynamic-query/export")
    @BizAuth(resourceId = "R_REPORT_EXPORT", action = ActionType.EXPORT)
    @AuditLog(
        action = "EXPORT",
        resourceType = "DYNAMIC_QUERY",
        resourceIdExpr = "#result.taskId",
        afterExpr = "{'dim':#cmd.dim,'subjectCount':#cmd.subjectIds.size(),"
                  + "'metricCount':#cmd.metricCodes.size(),'dataDate':#cmd.dataDate}"
    )
    public ResponseWrapper<ExportTaskRespDTO> exportDynamicQuery(
            @RequestBody @Valid DynamicQueryExportCmd cmd) {
        return ResponseWrapper.success(exportService.createExportTask(cmd));
    }
}
```

### 5.2 SQL 探查的特殊审计（手动调用）

由于 SQL 探查需要双写（`sql_probe_history` + `audit_log`），不适合使用纯注解，必须手动调用：

```java
@RestController
public class SqlProbeController {

    @Autowired
    private SqlProbeService sqlProbeService;
    @Autowired
    private AuditApi auditApi;

    @PostMapping("/api/reports/sql-probe/execute")
    @BizAuth(resourceId = "R_REPORT_SQL_PROBE", action = ActionType.EXECUTE_SQL)
    public ResponseWrapper<SqlProbeRespDTO> execute(
            @RequestBody @Valid SqlProbeCmd cmd) {

        // 1. reason 强校验（审计要求）
        if (!StringUtils.hasText(cmd.getReason())) {
            throw new BusinessException("RPT-4001",
                "SQL 探查必须填写执行原因（reason）");
        }

        // 2. 执行（内部包含 sql_probe_history 双写）
        SqlProbeRespDTO resp = sqlProbeService.execute(cmd);

        // 3. 手动写 audit_log（同步，失败则抛异常）
        auditApi.log(AuditLogCmd.builder()
            .action("EXECUTE_SQL")
            .resourceType("SQL_PROBE")
            .resourceId(resp.getProbeHistoryId())
            .status(resp.getStatus())
            .after(JsonUtil.stringify(buildAuditAfter(cmd, resp)))
            .reason(cmd.getReason())
            .build());

        return ResponseWrapper.success(resp);
    }

    private Map<String, Object> buildAuditAfter(SqlProbeCmd cmd, SqlProbeRespDTO resp) {
        Map<String, Object> map = new LinkedHashMap<>();
        map.put("sql", cmd.getSql());
        map.put("rowCount", resp.getRowCount());
        map.put("executionTimeMs", resp.getExecutionTimeMs());
        map.put("probeHistoryId", resp.getProbeHistoryId());
        if (resp.getErrorMsg() != null) {
            map.put("errorMsg", resp.getErrorMsg());
        }
        return map;
    }
}
```

### 5.3 异步导出的补充审计

```java
@Component
public class ExportTaskWorker {

    public void doExport(ExportTaskCmd task) {
        long startTime = System.currentTimeMillis();
        try {
            // ... 实际导出逻辑 ...
            FileObjectDTO fileObject = fileApi.upload(tempFile, task.getEmpId());

            // 成功后写审计
            auditApi.log(AuditLogCmd.builder()
                .action("EXPORT")
                .resourceType(task.getResourceType())
                .resourceId(task.getTaskId())
                .operatorEmpId(task.getEmpId())
                .status("SUCCESS")
                .after(JsonUtil.stringify(buildExportParams(task, fileObject.getId())))
                .durationMs((int) (System.currentTimeMillis() - startTime))
                .build());

        } catch (Exception e) {
            auditApi.log(AuditLogCmd.builder()
                .action("EXPORT")
                .resourceType(task.getResourceType())
                .resourceId(task.getTaskId())
                .operatorEmpId(task.getEmpId())
                .status("FAILED")
                .after(JsonUtil.stringify(Map.of("error", e.getMessage())))
                .durationMs((int) (System.currentTimeMillis() - startTime))
                .build());
            throw e;
        }
    }
}
```

## 6. 敏感字段脱敏规则

参考 `docs/common-dev-guide.md` 第 9 章（日志规范）：

| 字段类型 | 审计日志中的处理 |
|:---|:---|
| 员工工号 | 保留完整（审计需要） |
| 客户 ID | 保留完整（审计需要） |
| 客户姓名 | 脱敏（"张*三"） |
| 手机号 | 脱敏（"138****5678"） |
| 身份证号 | 脱敏（"110***********1234"） |
| 账号 | 脱敏（"6225****1234"） |
| 金额 | 保留完整（审计需要） |
| 指标数值 | 保留完整 |
| SQL 文本 | **完整保留**（不脱敏，审计最高要求） |

**注意**：SQL 探查审计中，即使 SQL 包含手机号、身份证等字面量，也**不进行脱敏**（审计优先级高于隐私），由 `sys_config_kv.sql.probe.forbidden.keywords` 在 SQL 执行前阻止敏感字段查询。

## 8. 合规要求

### 8.1 数据保留期

| 数据类型 | 保留期 | 依据 |
|:---|:---|:---|
| SQL 探查审计（audit_log） | **5 年** | 金融监管最高要求 |
| SQL 探查历史（sql_probe_history） | 3 个月 | 便捷查询，过期归档到审计 |
| 导出审计（audit_log） | **3 年** | 数据导出合规要求 |
| 导出文件（file_object） | 30 天 | 由 file_object.expires_at 控制 |
| 仪表盘访问审计（audit_log） | **2 年** | 敏感数据访问追溯 |
| 通用业务审计（audit_log） | **1 年** | 常规合规 |

### 8.2 审计查询接口（只读）

```
GET /api/reports/audit/sql-probe
    - 查询 SQL 探查历史（自己 or 全部，取决于角色）
    - 支持按时间、用户、状态筛选
GET /api/reports/audit/export
    - 查询导出审计
    - 支持按时间、用户、资源类型筛选
```

这些接口本身不参与审计（避免"审计审计"无限循环）。

### 8.3 不可变性

- `audit_log` 表**禁止 UPDATE 和 DELETE**（数据库层面通过 Trigger 或仅应用层不提供接口控制）；
- `sql_probe_history` 允许 UPDATE（执行状态更新），但禁止 DELETE（除归档任务外）；
- 归档任务必须先备份到冷存储再删除（V2 要求）。

## 9. 审计日志写入失败处理

### 9.1 失败场景

- `audit_log` 表不可写（MySQL 故障）
- `AuditApi` 调用超时
- JSON 序列化异常

### 9.2 处理策略

| 场景 | 处理 |
|:---|:---|
| SQL 探查审计写入失败 | **拒绝执行 SQL**，返回 500 错误 |
| 导出审计写入失败 | **回滚导出**，返回 500 错误 |
| 仪表盘访问审计写入失败 | 记录 ERROR 日志，**允许继续**（避免影响用户体验） |
| 普通操作审计写入失败 | 记录 ERROR 日志，允许继续 |

### 9.3 降级方案

- 若 `audit_log` 持续写入失败（> 1 分钟），切换到**本地文件审计**（`/var/log/branch-platform/audit-fallback.log`）；
- 本地文件采用 JSON Lines 格式，故障恢复后由运维批量导入 `audit_log`；
- 降级期间所有高危接口**必须**告警。

## 10. 审计追溯示例

### 10.1 场景：追溯某用户的数据导出历史

```sql
SELECT a.request_time, a.action, a.resource_type, a.resource_id, a.after, a.reason
FROM audit_log a
WHERE a.operator_emp_id = 'E10010'
  AND a.action IN ('EXPORT', 'DOWNLOAD')
  AND a.request_time BETWEEN '2026-03-01' AND '2026-03-07'
ORDER BY a.request_time DESC;
```

### 10.2 场景：追溯某条 SQL 探查的完整上下文

```sql
-- Step 1: 查 sql_probe_history 拿到 probe_id
SELECT * FROM sql_probe_history
WHERE emp_id = 'E99001' AND created_time > '2026-03-06 15:00:00'
ORDER BY created_time DESC LIMIT 10;

-- Step 2: 用 probe_id 反查 audit_log（resource_id = probe_id）
SELECT * FROM audit_log
WHERE resource_type = 'SQL_PROBE' AND resource_id = 'ph-20260306-001';
```

### 10.3 场景：检测异常导出行为

```sql
-- 某用户一天内导出超过 10 次
SELECT operator_emp_id, COUNT(*) AS export_count
FROM audit_log
WHERE action = 'EXPORT'
  AND DATE(request_time) = '2026-03-06'
GROUP BY operator_emp_id
HAVING COUNT(*) > 10;
```
