# COMMON 基础层 — 关键组件设计

> 本文记录公共组件的稳定语义和使用边界。实现细节、方法完整签名和枚举全集以对应源码为准；业务模块不得复制本文形成平行实现。

## 1. Web 响应与分页

### 1.1 ResponseWrapper<T>

常规 JSON API 使用 `ResponseWrapper<T>`，统一承载 `code`、`message`、`traceId`、`data` 和 `timestamp`；分页响应额外承载 `page`。成功码和异常码由统一实现及业务契约决定。

文件下载、重定向等明确的特殊响应不强制套 JSON 信封。

### 1.2 PageRequest / PageResult<T>

- `PageRequest` 统一页码、页大小和排序参数：页码从 1 开始，默认页大小 20，最大 100；排序方向只允许 `asc`/`desc`，排序字段必须经过调用方白名单校验。
- `PageResult<T>` 统一返回 `pageNo`、`pageSize`、`total` 和 `records`，并提供总页数计算。
- 业务模块可扩展查询条件，但不得绕过公共分页和排序校验。

## 2. 异常模型

异常层次为 `BizException` → `AuthException` / `PermissionDeniedException`：

| 类型 | 语义 | 统一 HTTP 映射 |
|:---|:---|:---:|
| `BizException` | 可预期业务错误，携带业务错误码和消息 | 按统一异常处理器约定 |
| `AuthException` | 未认证、登录态失效或认证失败 | 401 |
| `PermissionDeniedException` | 资源、数据范围或实体写权限不足 | 403 |

不可预期异常由 `GlobalExceptionHandler` 统一转换；业务代码应抛出带明确错误码的异常，不以通用容器替代类型化契约。

## 3. 安全元数据与枚举

- `BizType` 表示业务域，`BizAction` 表示业务动作，`DataScopeType` 表示数据范围。三者合法值以 `common-security` 的枚举源码为准，本文不维护完整值列表。
- `@BizAuth` 只声明 Controller 方法所需的 `bizType` 和 `action`（默认 `READ`），不等于完整授权。资源登记、角色 RBAC、实体归属和数据范围判定由 auth-permission-center 完成。
- `@AuditLog` 声明审计动作和资源类型，并可要求 `reason`。需要在业务事务内记录结构化前后快照时使用 `serviceManaged=true`，由业务服务调用审计 SPI；普通场景由 `AuditLogAspect` 采集。

## 4. 请求上下文

### 4.1 CurrentUserContext

`CurrentUserContext` 是可序列化的当前登录用户上下文，由认证模块构建。稳定字段语义如下：

| 字段 | 语义 |
|:---|:---|
| `empId`、`username`、`displayName` | 用户身份与展示信息，员工 ID 口径为 `PT_USER.USER_ID` |
| `mainOrgCode`、`mainOrgName`、`orgLevel` | 主机构信息 |
| `roleIds`、`roleCodes` | 当前全部有效角色 |
| `candidateGroupKeys` | 按当前角色/用户/组织解析的流程候选组标识 |
| `systemAdmin` | 是否含 `SYS_ADMIN` 角色；不代表绕过全部业务门禁 |
| `activeRoleId` | 旧 Session 兼容字段；当前权限按全部有效角色并集计算 |

该对象需要兼容 Spring Session JDBC 的序列化；新增或变更字段需考虑已有 Session 的反序列化。

### 4.2 DataScopeContext

`DataScopeContext` 使用 ThreadLocal 保存当前请求的 `bizType`、`action`、`scope`、员工、机构、机构子树和候选组信息。调用方通过 `set`/`current`/`clear` 管理上下文；每个请求、异步任务和异常路径都必须清理，不能依赖线程复用自动回收。

## 5. ObjectMetaRegistry

`ObjectMeta` 描述需要通用数据范围能力的业务对象：对象标识、数据表、归属机构/创建人/分配人/本人关联列、业务键、视图业务类型和支持的范围集合。只有确需通用元数据时才注册，`objectKey` 必须全局唯一。

`ObjectMetaRegistry` 提供并发安全的注册和查询；重复注册失败，查询不到对象时 `getRequired` 失败。对象不支持请求的范围必须拒绝，不能默认放大为 `ALL`。复杂 JOIN、权限和实体状态仍由业务模块负责。

## 6. 锁与数据库基础设施

### 6.1 LockManager

跨实例业务互斥使用 `LockManager` 抽象及其 JDBC 实现，锁记录存放在 `PT_LOCK`。获取和释放必须使用同一业务键并校验 holder；释放失败不能静默释放其他持有者的锁。Quartz 作业的集群互斥遵循 system-governance 的调度约束。

### 6.2 脱敏与签名

#### SensitiveDataMasker

`SensitiveDataMasker` 提供手机号、身份证号、银行账号和金额的统一静态脱敏方法。接口日志、审计快照和异常消息不得记录原始手机号、证件号、账号、金额或凭据；新增敏感字段先定义脱敏口径再接入日志。

#### SignatureUtils

`SignatureUtils` 使用 HmacSHA256 对参数签名和验签：参数按 key 字典序拼接，并将 `timestamp`、`nonce` 纳入待签名内容，结果使用 Base64。签名工具只负责规范化和密码学计算；调用方仍需校验时间窗口、nonce 唯一性和密钥来源，不能把携带 timestamp/nonce 误认为已自动实现防重放。
