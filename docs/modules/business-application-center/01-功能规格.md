> 模块代码：`business-application-center`
> 基础包名：`com.bank.branch.platform.bizapp`
> 文档版本：V1.0
> 对齐文档：`project_ana.md` 4.3 节 + `project_ana_技术方案与架构拆分.md`

## 1. 模块概述

### 1.1 定位

业务申请中心是省分行一体化营销与绩效平台的 **核心业务域** 模块，承载两大类业务申请场景：

1. **资产投放申请**（公司类授信申请）
2. **中场支持申请**（中台专业部门支持申请）

它是"营销线索 → 客户触达 → 业务落地"闭环中 **落地环节** 的唯一载体，也是 `performance-engine-center`（绩效）和 `report-analytics-center`（报表）最重要的事实源。

### 1.2 业务边界

| 维度 | 归属本模块 | 不归属本模块 |
|---|---|---|
| 资产投放申请单的建模 | ✅ | — |
| 中场支持申请单的建模 | ✅ | — |
| 场景 A/B 的路由决策 | ✅ | — |
| 多产品拆单逻辑 | ✅ | — |
| 秘书派单/转交逻辑 | ✅ | — |
| 节点专属表单校验（如信贷会字段） | ✅ | — |
| 业务侧状态机（DRAFT/IN_APPROVAL/...） | ✅ | — |
| 客户池/客户资料管理 | ❌ | 归属 `customer-marketing-center` |
| 产品资料/产品元数据管理 | ❌ | 归属 `portal-content-center` |
| 通讯录/员工信息 | ❌ | 归属 `portal-content-center` |
| 工作流引擎交互（Flowable） | ❌ | 归属 `workflow-center` |
| 审批日志详情查询 | ❌ | 归属 `workflow-center` |
| KPI/绩效计算 | ❌ | 归属 `performance-engine-center` |
| 字典/系统配置/附件存储 | ❌ | 归属 `system-governance-center` |

### 1.3 核心设计原则

1. **贫血模型 + 显式流程**：实体只承载数据，状态迁移由 `BizStateMachine` 统一管理。
2. **跨模块只走 Api**：严格禁止直连 `customer-marketing-center`、`portal-content-center` 的 `mapper`/`entity`。
3. **工作流发起与业务分离**：业务申请单和 Flowable 流程实例通过 `business_key = LOAN:{id}` / `SUPPORT:{id}` 双向绑定，`workflow-center` 是唯一能操作 Flowable API 的出口。
4. **节点表单解耦**：公司部审核节点的"是否需要上信贷会"等特殊字段，通过 `wf_node_form_conf` 动态声明，本模块仅执行校验。
5. **双视图权限**：中场支持以 `SUPPORT`（发起侧）和 `SUPPORT_DEPT`（承接侧）两种业务类型隔离权限。

## 2. 资产投放申请（对应 project_ana 4.3.1）

### 2.1 业务定义

资产投放申请是客户经理为已审批通过的 **公司类客户** 发起的、以获取银行授信额度为目标的正式流程性申请。申请一经提交即进入多层审批流程，流程完成后生成可在核心系统发起放款的授信批复。

### 2.2 入口

| 入口 | 说明 |
|---|---|
| 工作台"新建业务申请"快捷按钮 | 首页快捷入口，支持 TraceID 透传 |
| 本模块列表页"新增"按钮 | `/api/loans` 页面右上角按钮 |
| 由"触达任务"跳转（可选） | 从 `customer-marketing-center` 的触达任务详情页跳转时，自动带入 `sourceTouchTaskId`，客户字段锁定 |

### 2.3 客户选择规则

1. **必须是公司类客户**：`CustomerQueryApi.getCustomerCategory(custId)` 返回 `COMPANY`。
2. **必须已审批通过**：`CustomerQueryApi.getCustomerStatus(custId)` 返回 `APPROVED`。
3. **不强制要求归属本机构**：允许跨机构代办（场景：总行集中团队服务异地客户），但需通过 `DATA_SCOPE` 权限校验。
4. **分页搜索**：前端调用 `CustomerQueryApi.searchApprovedCompanyCustomers(keyword, pageNo, pageSize)`，按客户名称 / 统一社会信用代码 / 客户编号模糊匹配。
5. **客户信息冗余**：`loan_apply` 表不存客户全量信息，只存 `cust_id`；详情页展示时通过 `CustomerQueryApi.getCustomerBrief(custId)` 即席获取并做 5 分钟本地缓存。

### 2.4 字段定义

| 字段 | 中文名 | 类型 | 必填 | 字典 | 说明 |
|---|---|---|---|---|---|
| `custId` | 客户 | String | ✅ | — | 客户 ID，触达来源时锁定 |
| `sourceTouchTaskId` | 来源触达任务 | String | ❌ | — | 非空时关联到 `customer-marketing-center` |
| `projectType` | 项目类型 | String | ✅ | `PROJECT_TYPE` | 如：新增授信 / 续作 / 调整 |
| `bizType` | 业务类型 | String | ✅ | `BIZ_TYPE` | 如：流动资金贷款 / 项目贷款 / 银行承兑汇票 |
| `guaranteeType` | 主要担保方式 | String | ✅ | `GUARANTEE_TYPE` | 如：抵押 / 质押 / 保证 / 信用 |
| `creditAmount` | 授信金额 | BigDecimal | ✅ | — | 单位万元，精度 2 位，> 0 |
| `creditExposureAmount` | 授信敞口金额 | BigDecimal | ✅ | — | 单位万元，精度 2 位，≥ 0，且 ≤ 授信金额 |
| `attachmentIds` | 附件 | List\<String\> | ❌ | — | 通过 `FileApi` 上传后获取的文件 ID |

**校验规则**：

- 所有字典字段必须在对应字典启用项范围内，否则抛 `BIZ-40904`。
- `creditAmount >= creditExposureAmount`，否则抛 `BIZ-40905`。
- 同一客户同时存在的 `IN_APPROVAL` 状态申请不超过 3 条（可通过配置 `loan.maxRunningPerCust` 调整），超过时需二次确认（前端弹窗）。

### 2.5 审批流程节点序列

资产投放走固定流程 `loan_approve_v1`（在 `workflow-center` 注册）：

```
[开始]
   │
   ▼
[客户经理提交]  ← 业务发起人（userTask：loan_submit）
   │
   ▼
[经营机构负责人审核]  ← 发起人所在机构的负责人（userTask：loan_org_review）
   │
   ▼
[公司业务部审核]  ← 公司部有审核权限的人员（userTask：loan_corp_review）
   │  节点专属表单：
   │    - isNeedCreditMeeting (Boolean, 必填)
   │    - creditMeetingConclusion (String, 当 isNeedCreditMeeting=true 时必填)
   ▼
[授信审查]  ← 授信审查专员（userTask：loan_credit_review）
   │
   ▼
[授信批复]  ← 授信批复人（userTask：loan_credit_approve）
   │
   ▼
[结束]
```

**节点路由参数**：通过 `workflow-center` 的 `WorkflowApi.startProcess(processKey, businessKey, variables)` 传入，本模块只传 `loanApplyId`, `creditAmount`, `projectType` 等用于网关判断的变量。

### 2.6 公司部审核节点特殊规则

这是 **V1 唯一一个带节点专属表单的硬编码场景**，必须单独实现。

**交互规则**：

1. 处理人进入公司部审核节点后，页面右侧渲染"节点表单区域"。
2. 字段来源：调用 `GET /api/loans/{id}/node-form/loan_corp_review` 返回 `wf_node_form_conf` 的字段声明。
3. 核心字段：
   - `isNeedCreditMeeting`（是否需要上信贷会）：单选框，Boolean，必填
   - `creditMeetingConclusion`（信贷会结论）：文本域，String，条件必填，规则 = `isNeedCreditMeeting == true`

**校验入口**：处理人点击"审批通过"时，请求先进入 `workflow-center` 的统一办理接口，内部回调 `LoanFormValidator.validateNodeForm(nodeKey, formData)`；校验失败直接抛 `BIZ-42201` / `BIZ-42202`，不调用 Flowable 的 `complete` 方法。

**存储**：节点表单数据通过 `WorkflowApi.setTaskVariables(taskId, variables)` 存储到流程变量，本模块 **不落库到 `loan_apply` 表**；未来需要查询时调用 `WorkflowApi.getTaskHistoricalVariables(processInstanceId)`。

### 2.7 节点专属表单机制

虽然 V1 只有公司部审核节点使用该机制，但必须按通用能力实现，为后续扩展预留空间。

**数据流**：

```
wf_node_form_conf（system-governance-center / workflow-center 共管）
      │
      │   node_key = "loan_corp_review"
      │   required_fields = ["isNeedCreditMeeting","creditMeetingConclusion"]
      │   field_rules = JSON（含条件必填规则）
      ▼
LoanFormValidator（本模块）
      │
      │   validateNodeForm(nodeKey, formData)
      ▼
若校验通过 → 调用 WorkflowApi.completeTask(taskId, formData)
若校验失败 → 抛 BizException(BIZ-42201 / BIZ-42202)
```

### 2.8 双维度处理页面

资产投放的"处理页面"是本模块最复杂的交互，分为 **流程视图** 和 **处理视图** 两个并列区域。

**流程视图**（只读）：

- **进度图**：调用 `WorkflowApi.getProcessDiagram(processInstanceId)`，展示 BPMN 节点的完成状态、当前节点高亮。
- **审批日志**：调用 `WorkflowApi.listApprovalLogs(processInstanceId)`，展示各节点的办理人、办理时间、审批意见。

**处理视图**：

- **信息展示区**：展示 `loan_apply` 所有字段 + 客户信息 + 产品信息 + 附件列表。
- **办理日志区**：展示 **本申请** 业务侧日志（不等同于审批日志，如草稿修改记录、附件补充记录），数据源 `pt_audit_log` 中 `biz_type=LOAN` 的记录。
- **操作区**：根据当前用户对该申请的可办理状态，展示"编辑草稿"/"提交"/"删除"/"审批通过"/"审批驳回"等按钮。

**可办理状态判定**：

```
canEdit = status == DRAFT && createdBy == 当前用户
canSubmit = status == DRAFT && createdBy == 当前用户
canApprove = status == IN_APPROVAL && 当前用户是流程当前节点候选人之一
canDelete = status == DRAFT && createdBy == 当前用户
canCancel = status == IN_APPROVAL && createdBy == 当前用户 && 流程尚未到达授信审查节点
```

### 2.9 权限与审计

| 角色 | 业务类型 | 动作 | 数据范围 | 说明 |
|---|---|---|---|---|
| 客户经理 | LOAN | WRITE, READ, LIST, SUBMIT | SELF_CREATED | 仅能看自己发起的 |
| 经营机构负责人 | LOAN | READ, LIST | ORG_SUBTREE | 本机构及子机构 |
| 公司部审核人员 | LOAN | READ, LIST, APPROVE | WORKFLOW_PARTICIPANT | 仅自己参与过的流程 |
| 授信审查人员 | LOAN | READ, LIST, APPROVE | WORKFLOW_PARTICIPANT | 仅自己参与过的流程 |
| 授信批复人员 | LOAN | READ, LIST, APPROVE | WORKFLOW_PARTICIPANT | 仅自己参与过的流程 |
| 本行运营人员 | LOAN | LIST, EXPORT | ORG_SUBTREE / ALL | 导出为高危操作 |

**审计要点**：

- 提交、撤回、删除草稿：审计级别 `HIGH`，落 `pt_audit_log`。
- 节点审批通过 / 驳回：审计由 `workflow-center` 负责，本模块不重复落日志。
- 导出：审计级别 `HIGH`，记录查询条件和命中行数。

## 3. 中场支持申请（对应 project_ana 4.3.2）

### 3.1 业务定义

中场支持申请是客户经理在客户经营过程中，针对自身专业能力无法独立处理的需求（如理财产品方案、私行产品方案、信贷政策咨询等），向中台专业部门（公司业务部、零售业务部、私人银行部等）提出的协助申请。

### 3.2 统一页面承载

**V1 设计原则**：查询、发起、办理全部在 `/support-requests` 一个页面内完成，通过顶部 Tab 切换：

| Tab | 可见性 | 说明 |
|---|---|---|
| 我发起的 | 客户经理、经营机构负责人 | 映射 SUPPORT SELF_CREATED / ORG_SUBTREE |
| 待我派单 | 中场支持部门秘书 | 映射 SUPPORT_DEPT ORG |
| 待我处理 | 中场支持部门人员 | 映射 SUPPORT_DEPT SELF_ASSIGNED |
| 全部（只读） | 运营 / 审计 | 映射 SUPPORT LIST ALL |

### 3.3 来源单选逻辑

用户创建中场支持申请时，**来源类型**必选一个：

| 来源类型 | 代码 | 业务规则 |
|---|---|---|
| 来自触达任务 | `TOUCH_TASK` | 必须填写 `sourceTouchTaskId`；当前用户必须是该触达任务的执行人；客户字段自动带出并锁定 |
| 存量客户 | `EXISTING_CUSTOMER` | 无需触达任务 ID；客户必须已在本机构认领范围内；允许手动选择客户 |

**校验链路**：

```
sourceType == TOUCH_TASK
  → 调用 TouchTaskQueryApi.getTouchTask(sourceTouchTaskId)
  → 校验 touchTask.executorEmpId == 当前用户 → 否则 BIZ-40302
  → 取 touchTask.custId 作为 custId（锁定）

sourceType == EXISTING_CUSTOMER
  → 校验 CustomerQueryApi.isCustomerOwnedByOrg(custId, 当前用户.orgId) == true → 否则 BIZ-40303
```

### 3.4 产品选择

**产品列表数据源**：调用 `ProductApi.listSupportAvailableProducts()`，过滤条件（在 `portal-content-center` 内部完成）：

- `enabled = true`（产品已启用）
- `supportForSupportRequest = true`（产品支持"中场支持"场景）

**显示**：按产品类型分组展示（信贷产品 / 理财产品 / 私行产品 / ...），支持多选。

**场景 A / 场景 B 判定**：

```
if (productIds 非空 && otherDemand 为空) {
  场景 = A  // 明确产品
}
else if (productIds 为空 || otherDemand 非空) {
  场景 = B  // 含模糊需求
  supportDeptId 必填
}
else {
  非法，抛 BIZ-40903
}
```

### 3.5 多产品拆单机制（V1 必须实现）

当用户选择了 **多个产品** 时，提交后按产品拆分为多个独立申请单，每个独立走流程。

**拆单规则**：

1. 生成一个统一的 `submit_group_id = UUID`，关联所有拆单结果。
2. 对每个 `productId` 生成独立的 `support_request` 记录（相同 `cust_id`、相同 `submit_group_id`、独立的 `request_no` 和 `business_key`）。
3. 每条记录独立调用 `WorkflowApi.startProcess`，独立走场景 A 流程（因为多产品时 `otherDemand` 为空，必走场景 A）。
4. 每条记录的状态独立演进，互不影响。

**拆单返回**：

```json
{
  "submitGroupId": "a1b2c3d4...",
  "requests": [
    {"id": "req_001", "productId": "prod_001", "processInstanceId": "piid_001"},
    {"id": "req_002", "productId": "prod_002", "processInstanceId": "piid_002"}
  ]
}
```

**查询**：`SupportApi.getBySubmitGroup(submitGroupId)` 可一次拉取同组所有申请，用于前端"我刚刚提交的这一批"展示。

### 3.6 支持部门选择（仅场景 B 必填）

- 场景 B（`otherDemand` 非空或未选产品）必须填写 `supportDeptId`。
- 部门候选数据源：`AddressBookApi.listSupportDepartments()` —— 返回标记为"中场支持部门"的机构列表。
- 权限映射：`support_dept_id` 决定了 `SUPPORT_DEPT ORG` 范围内哪个秘书可以看到该申请。

### 3.7 其他需求文本框

- 字段名：`otherDemand`
- 类型：`TEXT`，最大长度 2000
- 使用场景：客户需求无法用具体产品表达时的自由描述
- 非空时强制走场景 B

### 3.8 流程路由（场景 A / B）

| 场景 | 流程定义 Key | 节点序列 |
|---|---|---|
| 场景 A | `support_simple_v1` | 提交 → 具体产品负责人审核 → 结束 |
| 场景 B | `support_complex_v1` | 提交 → 中场支持初审（秘书派单） → 具体支持人员办理 → 结束 |

**场景 A 的"产品负责人"候选人**：调用 `ProductApi.getProductResponsibles(productId)`，返回 `List<empId>`。候选人由 `workflow-center` 作为用户任务的 Candidates 写入 Flowable。

**场景 B 的秘书候选人**：`AddressBookApi.listOrgSecretaries(supportDeptId)`，返回该部门秘书。秘书执行派单动作（`POST /api/support-dept/requests/{id}/dispatch`）后，`assignedEmpId` 被写入，流程推进到该人员处。

### 3.9 发起规则

**来源 TOUCH_TASK 时**：

- 当前用户 `empId` 必须 == 该触达任务的 `executorEmpId`，否则 `BIZ-40302`。
- 客户 `custId` 自动锁定为该触达任务的客户，前端不可修改。

**来源 EXISTING_CUSTOMER 时**：

- 当前用户所在机构必须已认领该客户，否则 `BIZ-40303`。
- 客户可分页搜索选择。

### 3.10 SUPPORT vs SUPPORT_DEPT 双视图设计

这是中场支持最核心的权限模型。

| 业务类型 | 字段关联 | 角色 | 典型数据范围 |
|---|---|---|---|
| `SUPPORT` | `owner_org_id` + `created_by` | 客户经理（发起侧） | `SELF_CREATED` |
| `SUPPORT` | `owner_org_id` | 经营机构负责人 | `ORG_SUBTREE` |
| `SUPPORT_DEPT` | `support_dept_id` | 中场部门秘书 | `ORG`（本部门） |
| `SUPPORT_DEPT` | `assigned_emp_id` | 中场部门人员 | `SELF_ASSIGNED`（本人） |

**字段映射含义**：

- `created_by` / `owner_org_id`：发起侧维度，回答"谁发起的 / 属于哪个经营机构"
- `support_dept_id`：承接部门维度，回答"哪个支持部门要处理它"
- `assigned_emp_id`：承接人维度，回答"该部门内部具体指派给谁"

**Controller 层面分离**：

- `SupportController`（发起侧）：处理 `SUPPORT` 业务类型的所有读/写/提交/删除
- `SupportDeptController`（承接侧）：处理 `SUPPORT_DEPT` 业务类型的派单/转交/办理完成

### 3.11 并行流程提示（对应 project_ana 3.2.3）

同一客户允许同时存在多个进行中的中场支持申请，但发起新申请时前端需给出提示：

```
"该客户当前已存在 N 条进行中的业务申请（含 X 条资产投放、Y 条中场支持），
 请确认是否继续提交？"
```

**实现**：前端在提交前调用 `BizApplyQueryApi.countRunningApplications(custId)`；大于 0 时弹出二次确认框，用户确认后在 Header 带上 `X-Confirm-Parallel: true`；后端 Service 层看到未带此 Header 且存在并行时直接 409。

## 4. 客户并行流程规则（对应 project_ana 3.2.3）

### 4.1 规则定义

- **允许并行**：不同业务申请（LOAN / SUPPORT）之间、同一业务申请的不同产品之间允许并行进行。
- **仅提示 + 二次确认**：不做强制拦截，但前端必须明确提示存在的并行申请数量及类型，由用户确认后继续。
- **提示数据源**：`BizApplyQueryApi.countRunningApplications(custId)` 返回结构包括 `loanRunningCount`、`supportRunningCount`。

### 4.2 限制例外

- 同一客户的 **同一产品** 不允许同时存在 2 条以上进行中的中场支持（场景 A）申请。若已有则直接拦截（`BIZ-40906`），避免重复发起。
- `loan_apply` 允许同时发起多条，不强制拦截（公司类客户可能需要同时申请多条不同类型的授信）。

以下功能在架构设计中保留了扩展口径，但在 V1 版本 **明确不实现**：

## 7. 状态机定义

### 7.1 LoanStatus

```
DRAFT（草稿）
  │
  │ submit()
  ▼
IN_APPROVAL（审批中）
  │
  ├─ Flowable 流程完成 → COMPLETED（已完成）
  ├─ Flowable 流程驳回 → REJECTED（已驳回）
  └─ 发起人撤回 → CANCELLED（已取消）

DRAFT → 删除（仅物理删除，不转状态）
```

### 7.2 SupportStatus

```
DRAFT（草稿）
  │
  │ submit()
  ▼
IN_APPROVAL（审批中，场景B派单前）
  │
  │ dispatch()（秘书派单）
  ▼
IN_PROGRESS（办理中，已有 assigned_emp_id）
  │
  ├─ complete(result=SUCCESS) → COMPLETED
  ├─ complete(result=FAILED) → REJECTED
  └─ 发起人撤回 → CANCELLED
```

**说明**：

- 场景 A 的流程直接 `DRAFT → IN_APPROVAL → COMPLETED`，无 `IN_PROGRESS` 中间态。
- 场景 B 经过秘书派单后进入 `IN_PROGRESS`。
- 所有状态迁移由 `BizStateMachine` 统一执行，非法迁移抛 `BIZ-42301`。
