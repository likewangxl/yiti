## 1. 草稿创建事务

### 1.1 创建草稿

**事务边界：** 单个 `INSERT` + 附件关联，单一事务内完成。

```java
@Service
public class LoanApplyFacadeImpl implements LoanApplyApi {

    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
    public LoanApplyDTO createDraft(LoanCreateCmd cmd) {
        // 1. 获取当前用户上下文(不进入事务)
        CurrentUserContext ctx = currentUserApi.getCurrentUserContext();

        // 2. 参数校验(事务内执行,异常时回滚)
        validateCustomer(cmd.getCustId());
        validateTouchTaskIfPresent(cmd.getSourceTouchTaskId());
        validateDictValue("PROJECT_TYPE", cmd.getProjectType());
        validateDictValue("BIZ_TYPE", cmd.getBizType());
        validateDictValue("GUARANTEE_TYPE", cmd.getGuaranteeType());

        // 3. 生成业务编号(依赖序列生成器,独立事务)
        String applyNo = applyNoGenerator.next("LA");  // 独立事务+乐观锁

        // 4. 构建实体
        LoanApply entity = LoanApply.builder()
            .id(IdUtil.uuid())
            .applyNo(applyNo)
            .custId(cmd.getCustId())
            .sourceTouchTaskId(cmd.getSourceTouchTaskId())
            .projectType(cmd.getProjectType())
            .bizType(cmd.getBizType())
            .guaranteeType(cmd.getGuaranteeType())
            .creditAmount(cmd.getCreditAmount())
            .creditExposureAmount(cmd.getCreditExposureAmount())
            .status("DRAFT")
            .ownerOrgId(ctx.getOrgCode())
            .createdBy(ctx.getEmpId())
            .createdTime(LocalDateTime.now())
            .deleted(0)
            .build();

        // 5. 插入主表
        loanApplyMapper.insert(entity);

        // 6. 绑定附件(如果有)
        if (CollUtil.isNotEmpty(cmd.getAttachmentFileIds())) {
            for (String fileObjectId : cmd.getAttachmentFileIds()) {
                fileApi.bindFile("LOAN", entity.getId(), fileObjectId, null);
            }
        }

        // 7. 转换返回DTO
        return LoanApplyConverter.toDTO(entity);
    }
}
```

**要点：**
- 默认传播行为 `REQUIRED`，如有外层事务则加入；
- 回滚规则 `rollbackFor = Exception.class`，确保所有异常都回滚；
- 业务编号生成器使用独立事务 + 乐观锁，避免长事务持锁；
- 附件绑定在事务内执行，保证"主表 + 附件"一致性。

### 1.2 更新草稿

**事务边界：** 状态校验 + `UPDATE`（带乐观锁）。

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void updateDraft(String id, LoanUpdateCmd cmd) {
    // 1. 加锁查询现有数据(行级锁,确保读写一致)
    LoanApply entity = loanApplyMapper.selectByIdForUpdate(id);
    if (entity == null) {
        throw new BizException("BIZAPP.4040.NOT_FOUND", "申请不存在");
    }
    // 2. 状态校验(仅DRAFT可改)
    if (!"DRAFT".equals(entity.getStatus())) {
        throw new BizException("BIZAPP.4090.STATUS_INVALID", "仅草稿状态可修改");
    }
    // 3. 归属校验(权限二次确认)
    String currentEmpId = currentUserApi.getCurrentEmpId();
    if (!Objects.equals(entity.getCreatedBy(), currentEmpId)) {
        throw new BizException("BIZAPP.4030.NOT_OWNER", "只能修改自己的草稿");
    }
    // 4. 更新字段
    applyUpdates(entity, cmd);
    entity.setUpdatedBy(currentEmpId);
    entity.setUpdatedTime(LocalDateTime.now());
    // 5. 乐观锁更新(带 updated_time 版本控制)
    int updated = loanApplyMapper.updateByIdWithVersion(entity);
    if (updated == 0) {
        throw new BizException("BIZAPP.4090.CONCURRENT_UPDATE", "数据已被其他操作修改,请刷新重试");
    }
}
```

**Mapper SQL（乐观锁）：**

```xml
<update id="updateByIdWithVersion">
    UPDATE loan_apply
       SET cust_id = #{custId},
           project_type = #{projectType},
           biz_type = #{bizType},
           guarantee_type = #{guaranteeType},
           credit_amount = #{creditAmount},
           credit_exposure_amount = #{creditExposureAmount},
           updated_by = #{updatedBy},
           updated_time = #{updatedTime}
     WHERE id = #{id}
       AND updated_time = #{originalUpdatedTime}  -- 乐观锁
       AND deleted = 0
</update>
```

**锁策略选择：**

| 场景 | 选型 | 理由 |
|------|------|------|
| 草稿更新 | 乐观锁(updated_time) | 并发更新概率低,乐观锁无锁开销更小 |
| 草稿提交 | 悲观锁(SELECT FOR UPDATE) | 提交不可回退,必须串行化 |
| 秘书派单 | 悲观锁 | 派单是互斥操作,串行化更稳妥 |
| 节点办理 | Flowable 内置锁 | runtime task 由 Flowable 管理互斥 |

### 1.3 删除草稿

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void deleteDraft(String id) {
    LoanApply entity = loanApplyMapper.selectByIdForUpdate(id);

        throw new BizException("BIZAPP.4040.NOT_FOUND", "申请不存在");

        throw new BizException("BIZAPP.4030.NOT_OWNER", "只能删除自己的草稿");

    // 解绑附件(附件不物理删除,仅解绑)
    fileApi.unbindFilesByBiz("LOAN", id);
```

## 2. 提交审批事务

### 2.1 核心事务边界

提交审批是本模块**最关键**的事务，必须原子化执行以下五步：

```
┌──────────────────────────────────────────────────────────────┐
│ TX BEGIN                                                     │
│                                                              │
│ ┌─ Step 1 ─────────────────────────────────────────────┐    │
│ │ SELECT 当前状态 FOR UPDATE(悲观锁)                   │    │
│ │   WHERE status = 'DRAFT'                             │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                              │
│ ┌─ Step 2 ─────────────────────────────────────────────┐    │
│ │ 业务规则校验                                          │    │
│ │   - 客户有效性 (CustomerQueryApi.isValidCustomer)    │    │
│ │   - 来源合法性 (isClaimedByOrg / touchTask)          │    │
│ │   - 产品可用性 (ProductApi.getProduct)               │    │
│ │   - 必填字段完整性                                    │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                              │
│ ┌─ Step 3 ─────────────────────────────────────────────┐    │
│ │ UPDATE status = 'IN_APPROVAL'                        │    │
│ │   business_key = 'LOAN:{id}'                         │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                              │
│ ┌─ Step 4 ─────────────────────────────────────────────┐    │
│ │ WorkflowApi.startProcess(StartProcessCmd)            │    │
│ │   返回 processInstanceId                              │    │
│ │   (workflow-center 内部也在同一事务上下文)           │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                              │
│ ┌─ Step 5 ─────────────────────────────────────────────┐    │
│ │ UPDATE process_instance_id = xxx                     │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                              │
│ TX COMMIT  (任一步失败全事务回滚)                            │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 代码示例

```java
@Override
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED, timeout = 30)
public LoanSubmitResp submitForApproval(String id) {
    // Step 1: 悲观锁读取
    LoanApply entity = loanApplyMapper.selectByIdForUpdate(id);
    if (entity == null) {
        throw new BizException("BIZAPP.4040.NOT_FOUND", "申请不存在");
    }
    if (!"DRAFT".equals(entity.getStatus())) {
        throw new BizException("BIZAPP.4090.STATUS_INVALID", "仅草稿状态可提交");
    }
    String currentEmpId = currentUserApi.getCurrentEmpId();
    if (!Objects.equals(entity.getCreatedBy(), currentEmpId)) {
        throw new BizException("BIZAPP.4030.NOT_OWNER", "只能提交自己的草稿");
    }

    // Step 2: 业务规则校验
    if (!customerQueryApi.isValidCustomer(entity.getCustId())) {
        throw new BizException("BIZAPP.4001.CUSTOMER_INVALID", "客户不存在或未审批通过");
    }
    if (entity.getSourceTouchTaskId() != null) {
        TouchTaskDTO task = touchTaskQueryApi.getTouchTask(entity.getSourceTouchTaskId());
        if (task == null) {
            throw new BizException("BIZAPP.4001.TOUCH_TASK_INVALID", "来源触达任务不存在");
        }
    }
    validateRequiredFields(entity);

    // Step 3: 更新状态为 IN_APPROVAL,回填 business_key
    String businessKey = "LOAN:" + entity.getId();
    int updated = loanApplyMapper.markInApproval(entity.getId(), businessKey, currentEmpId);
    if (updated == 0) {
        throw new BizException("BIZAPP.4090.CONCURRENT_UPDATE", "提交失败,请刷新重试");
    }

    // Step 4: 启动流程(同事务)
    StartProcessCmd startCmd = StartProcessCmd.builder()
        .processDefinitionKey("loan_approve_v1")
        .businessKey(businessKey)
        .bizType("LOAN")
        .bizId(entity.getId())
        .startUser(currentEmpId)
        .startOrgId(currentOrgCode)
        .title("资产投放审批-" + entity.getId())
        .variables(buildVariables(entity))
        .build();
    WorkflowLaunchResp launchResp = workflowApi.startProcess(startCmd);

    // Step 5: 回填 processInstanceId
    loanApplyMapper.updateProcessInstance(entity.getId(), launchResp.getProcessInstanceId());

    return new LoanSubmitResp(entity.getId(), launchResp.getProcessInstanceId());
}
```

### 2.3 关键控制点

| 控制点 | 策略 | 说明 |
|-------|------|------|
| 事务超时 | 30 秒 | 避免异常情况下事务长时间持锁 |
| 悲观锁 | SELECT ... FOR UPDATE | 防止并发提交导致重复启动流程 |
| 状态校验 | `WHERE status = 'DRAFT'` | SQL 层面双重校验 |
| 流程启动 | 同事务 | 确保"状态更新 + 流程启动"原子化 |
| 流程变量 | `buildVariables` 抽取 | 金额、客户ID、归属机构等传入流程 |
| 回填 processInstanceId | 独立 UPDATE | 避免循环依赖 |

### 2.4 异常场景与回滚

| 失败位置 | 回滚对象 | 用户感知 |
|---------|--------|---------|
| Step 1 锁查询失败 | 事务回滚,无副作用 | 返回 404 或 409 |
| Step 2 业务校验失败 | 事务回滚,无副作用 | 返回 422 + 错误原因 |
| Step 3 状态更新失败 | 事务回滚,无副作用 | 返回 409 CONCURRENT_UPDATE |
| Step 4 流程启动失败 | 回滚 Step 3 的状态更新 | 返回 500,状态仍为 DRAFT |
| Step 5 processInstanceId 回填失败 | 全回滚(极罕见) | 流程也会同步回滚 |

**workflow-center 事务传播：**
- `WorkflowApi.startProcess` 内部使用 `@Transactional(propagation = REQUIRED)`；
- 与本模块事务属于**同一个事务上下文**；
- 任一方异常，Flowable 的 `ACT_RU_*` 和业务主表均回滚。

### 2.5 资产立项撤回的节点守卫与一致性顺序

`POST /api/loans/{id}/cancel` 使用业务行 `SELECT ... FOR UPDATE`，先校验
`IN_APPROVAL`、创建人和非空 `processInstanceId`，再调用
`WorkflowQueryApi.getProcessNodes(processInstanceId)`。仅当查询结果中恰好存在一个 `ACTIVE` 的 `userTask`，且其 `nodeKey` 为
`branch_approve` 或 `corp_review` 时放行。多个 ACTIVE 用户节点（即使其中有允许节点）、
未知/空节点或查询异常均 Fail Close，返回 `BIZ-50001`，不调用撤回命令。
若唯一 ACTIVE 用户节点为 `credit_check` 或 `credit_approval`，返回领域错误
`BIZ-42304`（公司部审核通过后不可撤回），同样不调用撤回命令。

通过节点守卫后，事务内严格按以下顺序执行：

1. `WorkflowApi.cancelProcess(processInstanceId, reason)`；
2. `LoanApplyMapper.conditionalUpdateStatus(id, 'IN_APPROVAL', 'CANCELLED', updatedBy)`。

条件更新返回 0 时抛出状态冲突异常并回滚当前事务，不能改用无条件状态更新；这样 Flowable
撤回与业务状态写入要么一起提交，要么一起回滚，避免出现流程与业务状态分叉。

## 3. 多产品拆单事务

### 3.1 事务边界

**V1 策略：整批事务（Big Transaction）**

```java
@Override
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED, timeout = 60)
public BatchSubmitResp batchSubmitSupport(BatchSupportSubmitCmd cmd) {
    String submitGroupId = IdUtil.uuid();
    List<String> createdIds = new ArrayList<>();
    CurrentUserContext ctx = currentUserApi.getCurrentUserContext();

    // 校验客户(只校验一次)
    if (!customerQueryApi.isValidCustomer(cmd.getCustId())) {
        throw new BizException("BIZAPP.4001.CUSTOMER_INVALID", "客户无效");
    }

    for (String productId : cmd.getProductIds()) {
        // 1. 校验产品
        ProductDTO product = portalProductApi.getProduct(productId)
            .orElseThrow(() -> new BizException("BIZAPP.4001.PRODUCT_INVALID", "产品不存在: " + productId));

        // 2. 场景路由
        String sceneKey = supportScenarioRouter.route(product);  // support_simple_v1 / support_complex_v1

        // 3. 查询候选人(场景A=产品负责人;场景B=部门秘书)
        SceneAssigneeResp assignee = resolveAssignee(product, sceneKey);

        // 4. 创建 support_request
        SupportRequest entity = buildSupportRequest(cmd, productId, product, submitGroupId, sceneKey, assignee, ctx);
        supportRequestMapper.insert(entity);

        // 5. 绑定附件(同一批附件复用同一份文件对象)
        if (CollUtil.isNotEmpty(cmd.getAttachmentFileIds())) {
            for (String fileId : cmd.getAttachmentFileIds()) {
                fileApi.bindFile("SUPPORT", entity.getId(), fileId, null);
            }
        }

        // 6. 启动流程(每个产品独立流程实例)
        String businessKey = "SUPPORT:" + entity.getId();
        StartProcessCmd startCmd = StartProcessCmd.builder()
            .processDefinitionKey(sceneKey)
            .businessKey(businessKey)
            .bizType("SUPPORT")
            .bizId(entity.getId())
            .startUser(ctx.getEmpId())
            .startOrgId(ctx.getOrgCode())
            .title("中场支持申请-" + entity.getId())
            .variables(buildVariables(entity, product, assignee))
            .build();
        WorkflowLaunchResp launchResp = workflowApi.startProcess(startCmd);

        // 7. 回填
        supportRequestMapper.updateProcessInstanceAndKey(entity.getId(), launchResp.getProcessInstanceId(), businessKey);
        createdIds.add(entity.getId());
    }

    return new BatchSubmitResp(submitGroupId, createdIds);
}
```

### 3.2 事务语义

| 特性 | 语义 |
|------|------|
| 原子性 | 任一产品失败 → 整批回滚,所有 support_request 都不存在 |
| 一致性 | 所有产品状态 = IN_APPROVAL,processInstanceId 均已回填 |
| 隔离性 | 悲观锁 + Flowable 内部锁 |
| 持久性 | 事务提交后所有副作用生效 |

### 3.3 V1 限制与 V2 演进

**V1 限制：**
- 单批次产品数 ≤ 10（通过 DTO 层校验限制）；
- 事务超时 60 秒（保守设置，预留流程启动耗时）；
- 如某产品配置异常（如产品负责人为空），整批失败。

**V2 演进方向：**
- 异步化：主事务只插入 support_request，流程启动通过 MQ 异步触发；
- 部分成功：失败的记录标记 `status = FAILED`，支持重试；
- 拆分事务：每个产品独立事务，通过 `submit_group_id` 聚合。

### 3.4 场景路由无状态

```java
@Component
public class SupportScenarioRouter {

        // 无状态路由,根据产品配置决定流程
```

## 5. 节点办理并发

### 5.1 互斥机制

节点办理的并发控制由 **Flowable 内置的 Runtime Task 表**保证：

| 机制 | 说明 |
|------|------|
| `ACT_RU_TASK` | 任务表,每个任务一条记录 |
| `assignee` 字段 | 办理人分配后写入 |
| `claim` 操作 | Flowable 内置 claim 机制,claim 后其他人不可办理 |
| `complete` 操作 | 完成时写入表单 + 删除 runtime task |

**Flowable 自动处理：**
- 两人同时点击"办理"：第一个人 claim 成功，第二个人收到 `ActivitiTaskAlreadyClaimedException`；
- 重复 complete：重复完成返回 `ActivitiObjectNotFoundException`。

### 5.2 办理事务流程

```java
@Override
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED, timeout = 30)
public void completeTask(String taskId, CompleteTaskCmd cmd) {
    CurrentUserContext ctx = currentUserApi.getCurrentUserContext();

    // 1. 查询 runtime 权限(办理前校验)
    RuntimeAccessDTO access = workflowParticipantService.resolveRuntimeAccess(taskId, ctx.getEmpId());
    if (!access.isCanOperate()) {
        throw new BizException("BIZAPP.4030.NO_OPERATE_PERMISSION", "无办理权限");
    }

    // 2. 节点表单字段校验
    NodeFormConfDTO conf = workflowQueryApi.getNodeFormConf(access.getProcessDefinitionKey(), access.getNodeKey());
    validateFormFields(conf, cmd.getFormData());

    // 3. 调用 workflow 完成任务(由 Flowable 保证互斥)
    CompleteTaskCmd wfCmd = CompleteTaskCmd.builder()
        .taskId(taskId)
        .operatorEmpId(ctx.getEmpId())
        .formData(cmd.getFormData())
        .comment(cmd.getComment())
        .build();
    workflowApi.completeTask(wfCmd);

    // 4. 根据节点类型更新业务表冗余字段(如秘书派单节点)
    if ("dispatch".equals(access.getNodeKey())) {
        updateSupportDispatchInfo(access.getBusinessKey(), cmd.getFormData());
    }
    // 5. 业务状态变更事件由 workflow-center 发布,本模块监听回写
}
```

### 5.3 并发异常处理

```java
try {
    workflowApi.completeTask(wfCmd);
} catch (FlowableTaskAlreadyClaimedException e) {
    throw new BizException("BIZAPP.4090.TASK_CLAIMED", "任务已被其他人认领");
} catch (FlowableObjectNotFoundException e) {
    throw new BizException("BIZAPP.4040.TASK_NOT_FOUND", "任务不存在或已完成");
}
```

## 6. 流程结束状态回写

### 6.1 事件驱动回写

流程结束由 `workflow-center` 监听 Flowable 的 `PROCESS_COMPLETED` / `PROCESS_CANCELLED` 事件，发布领域事件：

```
Flowable Event → workflow-center EventPublisher
    │
    ▼
  事件主题: workflow.process.completed.v1
  事件主题: workflow.process.rejected.v1
    │
    ▼  Spring Event / RocketMQ
    │
business-application-center 监听器回写业务主表
```

### 6.2 监听器实现

```java
@Component
@Slf4j
public class WorkflowCompletedEventListener {

    @Autowired private LoanApplyMapper loanApplyMapper;
    @Autowired private SupportRequestMapper supportRequestMapper;
    @Autowired private IdempotentGuard idempotentGuard;

    /**
     * 监听流程完成事件,回写业务主表状态
     * 使用 AFTER_COMMIT 确保 workflow-center 事务已提交,避免回滚不一致
     */
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void onProcessCompleted(WorkflowProcessCompletedEvent event) {
        // 幂等保护: eventId 去重
        if (!idempotentGuard.tryMark("wf_completed:" + event.getEventId(), 7 * 24 * 3600)) {
            log.info("Event already processed: {}", event.getEventId());
            return;
        }

        String businessKey = event.getBusinessKey();
        String outcome = event.getOutcome();  // COMPLETED / REJECTED

        if (businessKey.startsWith("LOAN:")) {
            String loanId = businessKey.substring(5);
            String newStatus = "COMPLETED".equals(outcome) ? "COMPLETED" : "REJECTED";
            int updated = loanApplyMapper.updateStatusFromInApproval(loanId, newStatus);
            if (updated == 0) {
                log.warn("Loan status already updated or not in IN_APPROVAL: {}", loanId);
            }
        } else if (businessKey.startsWith("SUPPORT:")) {
            String requestId = businessKey.substring(8);
            String newStatus = "COMPLETED".equals(outcome) ? "COMPLETED" : "REJECTED";
            int updated = supportRequestMapper.updateStatusToFinal(requestId, newStatus);
            if (updated == 0) {
                log.warn("Support request status already updated: {}", requestId);
            }
        }
    }
}
```

### 6.3 关键设计

| 设计 | 说明 |
|------|------|
| `AFTER_COMMIT` | 确保 workflow-center 事务已提交,避免脏读 |
| `REQUIRES_NEW` | 独立事务,回写失败不影响流程侧 |
| 幂等保护 | `eventId` 去重,重复投递安全 |
| 状态条件 UPDATE | `WHERE status = 'IN_APPROVAL'` 防止覆盖其他状态 |
| 失败重试 | 失败的事件通过死信队列或定时任务补偿 |

### 6.4 Mapper SQL

```xml
<update id="updateStatusFromInApproval">
    UPDATE loan_apply
       SET status = #{newStatus},
           updated_time = NOW()
     WHERE id = #{id}
       AND status = 'IN_APPROVAL'   -- 仅从IN_APPROVAL状态变更
       AND deleted = 0
</update>

<update id="updateStatusToFinal">
    UPDATE support_request
       SET status = #{newStatus},
           updated_time = NOW()
     WHERE id = #{id}
       AND status IN ('IN_APPROVAL', 'IN_PROGRESS')
       AND deleted = 0
</update>
```

### 6.5 事件回写 vs 同步回写

为什么选择事件驱动而非同步回写？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 事件驱动(V1) | 解耦,workflow-center 不感知业务 | 最终一致,可能短暂不一致 |
| 同步回写 | 强一致 | workflow-center 需要依赖业务模块 |

**V1 采用事件驱动**，实现模块间解耦，接受 1-2 秒的最终一致性。

## 7. 秘书派单事务

### 7.1 派单操作

场景B的核心节点，由部门秘书将未派单的支持请求分派给具体办理人。

```java
@Override
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED, timeout = 15)
public void dispatch(String requestId, DispatchCmd cmd) {
    // 1. 悲观锁读取
    SupportRequest entity = supportRequestMapper.selectByIdForUpdate(requestId);
    if (entity == null) {
        throw new BizException("BIZAPP.4040.NOT_FOUND", "支持请求不存在");
    }
    // 2. 状态校验: 必须在 IN_APPROVAL 且未派单
    if (!"IN_APPROVAL".equals(entity.getStatus())) {
        throw new BizException("BIZAPP.4090.STATUS_INVALID", "仅审批中状态可派单");
    }
    if (entity.getAssignedEmpId() != null) {
        throw new BizException("BIZAPP.4090.ALREADY_DISPATCHED", "已派单,请使用转交功能");
    }
    // 3. 权限校验: 派单人必须是该部门秘书
    CurrentUserContext ctx = currentUserApi.getCurrentUserContext();
    if (!isDeptSecretary(ctx.getEmpId(), entity.getSupportDeptId())) {
        throw new BizException("BIZAPP.4030.NOT_SECRETARY", "非部门秘书不可派单");
    }
    // 4. 校验被派单人合法性
    EmployeeDTO assignee = addressBookApi.getEmployee(cmd.getAssignedEmpId());
    if (assignee == null || !Objects.equals(assignee.getOrgCode(), entity.getSupportDeptId())) {
        throw new BizException("BIZAPP.4001.ASSIGNEE_INVALID", "被派单人不属于该部门");
    }
    // 5. 更新业务表派单信息
    LocalDateTime now = LocalDateTime.now();
    int updated = supportRequestMapper.updateDispatchInfo(
        entity.getId(),
        cmd.getAssignedEmpId(),
        ctx.getEmpId(),
        now
    );
    if (updated == 0) {
        throw new BizException("BIZAPP.4090.CONCURRENT_DISPATCH", "派单冲突,请刷新重试");
    }
    // 6. 调用 WorkflowApi 设置任务 assignee / 完成派单节点
    workflowApi.setAssignee(entity.getProcessInstanceId(), "dispatch", cmd.getAssignedEmpId());
    // 或者: 完成派单节点(Flowable task complete)
    // workflowApi.completeTask(buildDispatchTaskCmd(entity, cmd));
}
```

### 7.3 转交操作

```java
@Override
@Transactional(rollbackFor = Exception.class, timeout = 15)
public void transfer(String requestId, TransferCmd cmd) {
    if (StrUtil.isBlank(cmd.getReason())) {
        throw new BizException("BIZAPP.4000.REASON_REQUIRED", "转交必须填写原因");
    }
    SupportRequest entity = supportRequestMapper.selectByIdForUpdate(requestId);
    // 状态校验: IN_PROGRESS 才可转交
    if (!"IN_PROGRESS".equals(entity.getStatus())) {
        throw new BizException("BIZAPP.4090.STATUS_INVALID", "仅处理中状态可转交");
    }
    // 权限: 当前用户必须是秘书
    CurrentUserContext ctx = currentUserApi.getCurrentUserContext();
    if (!isDeptSecretary(ctx.getEmpId(), entity.getSupportDeptId())) {
        throw new BizException("BIZAPP.4030.NOT_SECRETARY", "非部门秘书不可转交");
    }
    String previousAssignee = entity.getAssignedEmpId();
    // 更新业务表
    supportRequestMapper.updateAssignee(entity.getId(), cmd.getNewAssignedEmpId(), ctx.getEmpId());
    // 更新 Flowable 任务 assignee
    workflowApi.setCurrentTaskAssignee(entity.getProcessInstanceId(), cmd.getNewAssignedEmpId());
    // 记录审计(高危,reason必填)
    auditApi.log(AuditLogCmd.builder()
        .action("TRANSFER")
        .resourceType("SUPPORT_REQUEST")
        .resourceId(entity.getId())
        .businessKey(entity.getBusinessKey())
        .before("{\"assignedEmpId\":\"" + previousAssignee + "\"}")
        .after("{\"assignedEmpId\":\"" + cmd.getNewAssignedEmpId() + "\"}")
        .reason(cmd.getReason())
        .build());
}
```

## 8. 缓存策略

### 8.1 缓存层级

| 层级 | 组件 | TTL | 数据 |
|------|-----|-----|------|
| L1 | 本模块不缓存业务主表 | - | loan_apply / support_request 详情直接查DB |
| L2 | 依赖模块缓存 | 依赖方决定 | CustomerApi / ProductApi / AddressBookApi |
| L3 | 字典缓存 | 30 分钟 | DictApi(通过 AOP 注解) |

### 8.2 为什么本模块不缓存业务表？

| 原因 | 说明 |
|------|------|
| 变化频繁 | 草稿阶段频繁修改,缓存命中率低 |
| 一致性要求高 | 状态变化需要立即反映,缓存会引入不一致 |
| 数据量小 | 活跃数据量不大,索引查询足够快 |
| 权限复杂 | 数据范围过滤依赖运行时用户上下文,缓存粒度难以掌握 |

### 8.3 可选的列表缓存

高频访问的列表可在 **网关层** 或 **Controller 层** 做短期缓存：

```java
@Cacheable(
    cacheNames = "loan_apply_list",
    key = "'org:' + #orgCode + ':status:' + #status + ':page:' + #pageNum",
    unless = "#result == null or #result.total == 0",
    sync = false
)
public PageResult<LoanApplyDTO> listByOrg(String orgCode, String status, Integer pageNum) {
    // ...
}
```

- TTL：60 秒（极短）；
- 失效：状态变化时通过 `@CacheEvict` 清除；
- 注意：列表缓存只用于"只读的只读场景"，不可用于需要最新数据的场景。

**V1 不启用列表缓存**，V2 根据监控数据决定是否引入。

### 8.4 依赖方缓存

| API | 缓存策略 | 本模块依赖方式 |
|-----|--------|------------|
| `CustomerQueryApi.getCustomer` | customer-marketing 内部缓存 | 直接调用 |
| `ProductApi.listSupportAvailableProducts` | portal-content 内部缓存 | 直接调用,页面初次加载即命中 |
| `AddressBookApi.getEmployee` | portal-content 内部缓存 | 派单页面多次调用 |
| `DictApi.getDictItems` | governance 内部缓存 | 字典下拉框初次渲染 |

## 9. 幂等策略

### 9.1 幂等场景清单

| 操作 | 幂等键 | 生效范围 | 实现方式 |
|------|-------|--------|---------|
| 创建草稿 | clientRequestId (可选) | 单用户 30 秒 | Redis SETNX + TTL |
| 更新草稿 | 乐观锁(updated_time) | 全局 | UPDATE ... WHERE updated_time=? |
| 提交审批 | 状态校验(DRAFT→IN_APPROVAL) | 全局 | UPDATE ... WHERE status='DRAFT' |
| 秘书派单 | 状态校验(assigned_emp_id IS NULL) | 全局 | UPDATE ... WHERE assigned_emp_id IS NULL |
| 节点办理 | Flowable Runtime Task 互斥 | 全局 | Flowable 内置 |
| 事件消费 | eventId | 7 天 | Redis SETNX + TTL |

### 9.2 clientRequestId 机制

防止前端重复提交：

```java
@Component
public class IdempotentGuard {
    @Autowired private StringRedisTemplate redisTemplate;

    public boolean tryMark(String key, long ttlSeconds) {
        Boolean ok = redisTemplate.opsForValue().setIfAbsent(
            "idempotent:" + key,
            "1",
            Duration.ofSeconds(ttlSeconds)
        );
        return Boolean.TRUE.equals(ok);
    }
}
```

**使用：**
```java
@PostMapping("/api/loans")
public ApiResult<LoanApplyDTO> createDraft(
    @RequestHeader(value = "X-Client-Request-Id", required = false) String clientRequestId,
    @RequestBody LoanCreateCmd cmd
) {
    if (clientRequestId != null) {
        if (!idempotentGuard.tryMark("loan_create:" + clientRequestId, 30)) {
            throw new BizException("BIZAPP.4090.DUPLICATE_REQUEST", "请勿重复提交");
        }
    }
    return ApiResult.ok(loanApplyApi.createDraft(cmd));
}
```

### 9.3 事件幂等

流程结束事件监听器必须支持重复投递：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onProcessCompleted(WorkflowProcessCompletedEvent event) {
    if (!idempotentGuard.tryMark("wf_completed:" + event.getEventId(), 7 * 24 * 3600)) {
        return;  // 重复投递,直接返回
    }
    // ... 业务回写
}
```

### 9.4 状态条件 UPDATE

通过 SQL 的 `WHERE` 条件保证状态变更的幂等性：

```sql
-- 提交审批
UPDATE loan_apply
   SET status = 'IN_APPROVAL', business_key = 'LOAN:...'
 WHERE id = ? AND status = 'DRAFT';
-- 更新影响行数=1 表示成功;=0 表示状态已变更(幂等成功或失败)

-- 派单
UPDATE support_request
   SET assigned_emp_id = ?, dispatch_time = NOW()
 WHERE id = ? AND assigned_emp_id IS NULL AND status = 'IN_APPROVAL';
```

## 10. 事务传播行为总览

| 操作 | 入口 | 事务边界 | 传播行为 | 超时 | 隔离级别 | 说明 |
|-----|------|--------|--------|-----|--------|------|
| 创建草稿 | Facade | 单事务 | REQUIRED | 15s | 默认(REPEATABLE_READ) | INSERT主表+绑定附件 |
| 更新草稿 | Facade | 单事务 | REQUIRED | 15s | 默认 | 悲观锁读+UPDATE |
| 删除草稿 | Facade | 单事务 | REQUIRED | 10s | 默认 | 逻辑删除+解绑附件 |
| 提交审批 | Facade | 单事务 | REQUIRED | 30s | 默认 | 核心事务:状态变更+流程启动+回填 |
| 多产品拆单提交 | Facade | 单事务 | REQUIRED | 60s | 默认 | 批量操作,整批事务 |
| 秘书派单 | Facade | 单事务 | REQUIRED | 15s | 默认 | UPDATE派单信息+调用workflow |
| 秘书转交 | Facade | 单事务 | REQUIRED | 15s | 默认 | UPDATE+审计 |
| 节点办理(Complete) | Facade | 单事务 | REQUIRED | 30s | 默认 | 调用workflow.completeTask |
| 流程结束回写 | EventListener | 独立事务 | REQUIRES_NEW | 15s | 默认 | AFTER_COMMIT触发,避免循环 |
| 审计日志 | AOP拦截 | 独立事务 | REQUIRES_NEW | 10s | 默认 | 不影响主事务 |
| 导出下载 | Controller | 无事务 | NEVER | - | 默认 | 只读查询,不开事务 |

### 10.1 传播行为说明

| 传播行为 | 使用场景 | 本模块使用点 |
|---------|--------|------------|
| REQUIRED | 主业务流程 | 默认选择,所有Facade写方法 |
| REQUIRES_NEW | 独立事务,不受外层影响 | 事件监听器、审计日志 |
| NEVER | 禁止事务 | 只读查询、大数据导出 |
| NESTED | 嵌套事务 | 本模块不使用 |
| SUPPORTS | 有则加入,无则不用 | 通用查询方法 |

### 10.2 隔离级别

本模块统一使用 MySQL InnoDB 默认的 `REPEATABLE_READ`：
- 防止脏读和不可重复读；
- 避免幻读由 Gap Lock 配合 Next-Key Lock 实现；
- 无需特殊调整。

### 10.3 超时设置

超时的作用：防止长事务持锁导致库资源耗尽。

| 操作 | 超时 | 依据 |
|------|-----|-----|
| 短事务(创建/更新草稿) | 10-15s | 简单INSERT/UPDATE,不应超过1秒 |
| 中事务(提交审批) | 30s | 涉及流程启动,留足余量 |
| 长事务(批量拆单) | 60s | 10个产品启动流程,每个约5秒 |
| 事件回写 | 15s | 单表UPDATE,快速完成 |

**超时异常处理：** Spring 抛出 `TransactionTimedOutException`，前端提示"操作超时，请重试"。

## 11. 死锁预防

### 11.1 锁顺序一致性

跨表操作时，始终按固定顺序加锁，避免交叉死锁：

```java
// 正确: 先锁 loan_apply, 再调用 workflow 内部锁
selectByIdForUpdate(loanId);    // LOCK loan_apply
workflowApi.startProcess(...);  // LOCK workflow 内部表

// 错误示例: 先调 workflow, 再锁 loan_apply
workflowApi.startProcess(...);
selectByIdForUpdate(loanId);    // 可能与其他事务形成交叉死锁
```

### 11.2 避免长事务

| 禁止 | 替代 |
|------|-----|
| 事务内调用远程HTTP | 放在事务外或异步 |
| 事务内读大量数据 | 分页读取,独立事务 |
| 事务内执行复杂计算 | 前置计算好再开事务 |
| 事务内等待锁过久 | 悲观锁配合 NOWAIT / timeout |

### 11.3 批量操作使用 `FOR UPDATE OF` (MySQL 8.0+)

批量锁定时，只锁定需要的表：

```sql
-- MySQL 8.0 支持
SELECT l.* FROM loan_apply l
  JOIN cust_master c ON l.cust_id = c.id
 WHERE l.id IN (?,?,?)
 FOR UPDATE OF l;  -- 只锁 loan_apply, 不锁 cust_master
```

### 11.4 死锁重试

极少数情况下 InnoDB 检测到死锁会抛出 `SQLIntegrityConstraintViolationException`，对关键操作启用**有限重试**：

```java
@Retryable(
    value = DeadlockLoserDataAccessException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 100, multiplier = 2)
)
public LoanSubmitResp submitForApproval(String id) {
    // ...
}
```

### 12.1 事务监控指标

| 指标 | 告警阈值 | 监控方式 |
|------|--------|--------|
| 提交审批 P99 耗时 | > 3s | Micrometer + Prometheus |

### 12.2 日志埋点

```java
long startNs = System.nanoTime();
try {
    // 业务执行
    loanApplyMapper.insert(entity);
    long costMs = (System.nanoTime() - startNs) / 1_000_000;
    log.info("loan_apply_create OK id={} cost={}ms", entity.getId(), costMs);
```

### 12.3 慢事务告警

通过 `@Transactional` 的 AOP 拦截记录耗时超过阈值的事务：

```java
@Aspect
@Component
public class TransactionMonitorAspect {
    @Around("@annotation(org.springframework.transaction.annotation.Transactional)")
    public Object monitor(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (cost > 5000) {  // 超过 5 秒告警
                log.warn("SLOW_TX: {} cost={}ms", pjp.getSignature().toShortString(), cost);
            }
        }
    }
}
```
