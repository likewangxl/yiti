# 业务申请中心 — 并发与事务策略

> 本文只记录当前 `SUPPORT_REQUEST` 实现中的事务、锁和幂等语义；不约定未实现的批量提交、缓存或异步导出方案。

## 1. 事务边界

以下 Service 方法使用 Spring `@Transactional`，业务表写入在同一数据库事务内完成：

| 方法 | 事务内动作 |
|---|---|
| `SupportService.create` | 校验客户、场景路由、产品校验/重复检查并插入一条或多条 `DRAFT` |
| `SupportService.submit` | 锁定草稿、校验创建人和状态、调用 `WorkflowApi.startProcess`、保存流程实例和状态、发布提交事件 |
| `SupportService.cancel` | 锁定申请、校验状态、更新为 `CANCELLED` |
| `SupportService.deleteDraft` | 锁定申请、确认 `DRAFT`、设置 `deleted=1` |
| `SupportDeptService.dispatch` | 锁定申请、校验承接关系、更新派单人/时间/承接人并转 `IN_PROGRESS` |
| `SupportDeptService.transfer` | 锁定申请、确认当前承接人、更新承接人 |
| `SupportDeptService.complete` | 锁定申请、校验当前承接人、按 `success` 更新为 `COMPLETED` 或 `REJECTED` |

多产品创建是一个事务：任一产品校验或插入失败，整次创建回滚；创建后每条记录的提交仍是独立事务和独立流程。

## 2. 行锁与状态迁移

`SupportRequestMapper.selectForUpdate` 对有效记录执行 `SELECT ... FOR UPDATE`，用于提交、撤回、删除和承接侧操作。所有迁移先调用 `BizStateMachine.validateSupportTransition`：

```text
DRAFT       -> IN_APPROVAL
IN_APPROVAL -> IN_PROGRESS | COMPLETED | REJECTED | CANCELLED
IN_PROGRESS -> COMPLETED | REJECTED | CANCELLED
```

状态更新必须同时写入 `updated_by` 和 `updated_time`；逻辑删除不改变业务状态，只设置 `deleted=1`。非法迁移返回 `BIZ-42301`。

## 3. 创建与重复申请

场景 A 每个产品执行 `countActiveByCustomerAndProduct`，统计条件为相同客户、相同产品且状态为 `IN_APPROVAL` 或 `IN_PROGRESS`、未逻辑删除。达到当前实现的重复阈值时返回 `BIZ-40906`。场景 B 不带产品，不执行该产品维度检查。

多产品记录共享 `submit_group_id`，但不共享状态、流程实例或提交事务。`SupportApi.getBySubmitGroup` 仅用于事后查询同组记录。

## 4. 提交与外部流程

提交事务顺序为：

1. `selectForUpdate` 读取有效草稿；
2. 校验当前操作人为 `created_by`，并校验 `DRAFT → IN_APPROVAL`；
3. 组装 `StartProcessCmd`，业务键为 `SUPPORT:{id}`，流程键按场景选择；
4. 调用 `WorkflowApi.startProcess`；
5. 将返回的 `processInstanceId` 和 `IN_APPROVAL` 写回申请，并发布 `SupportSubmittedEvent`。

当前撤回实现只更新申请表，不调用工作流取消接口；不要在事务文档中假设外部流程回滚或取消已自动完成。

## 5. 承接侧并发

- 派单使用行锁，只有承接部门人员可操作；成功后写入 `dispatch_emp_id`、`dispatch_time`、`assigned_emp_id`，再发布 `SupportDispatchedEvent`。
- 转交使用行锁，当前实现要求操作者是当前 `assigned_emp_id`，只更新新承接人，不发布派单事件。
- 办理完成使用行锁，当前承接人才能操作；`success=true` 进入 `COMPLETED`，否则进入 `REJECTED`，然后发布 `SupportCompletedEvent`。

状态校验和写入均在 Service 层执行，不能仅依赖前端按钮或列表查询结果。

## 6. 工作流回调幂等

`SupportWorkflowListener`：

- 使用 `@TransactionalEventListener(phase=AFTER_COMMIT)`，只在工作流事务提交后处理；
- 使用 `@Transactional(propagation=REQUIRES_NEW)` 开启独立回写事务；
- 过滤 `businessKey` 为空或不以 `SUPPORT:` 开头的事件；
- 以 `conditionalUpdateStatus(id, IN_APPROVAL, targetStatus, SYSTEM)` 实现条件更新；
- 影响行数为 0 表示已处理、状态已变化或记录不存在，直接跳过事件发布；
- 成功更新后按 outcome 发布完成/驳回事件并发送申请人通知，通知异常被记录但不传播到工作流引擎。

## 7. 事件与重试边界

业务事件在对应 Service 事务中发布；工作流完成事件由上游提交后触发回调。回调的条件更新提供数据库层面的重复消费保护。当前未实现通用幂等键、分布式锁、异步导出任务或批量流程提交，不应以预留字段或示例 SQL 代替实现依据。

## 8. 查询一致性

所有 Mapper 查询带 `deleted=0`。发起侧列表按 `owner_org_id` 过滤，承接侧列表按 `support_dept_id`/`assigned_emp_id` 过滤；历史、同组、统计查询也只读取未逻辑删除记录。查询条件和数据范围由 facade/service 传入，调用方不得绕过公共 API 直连表。
