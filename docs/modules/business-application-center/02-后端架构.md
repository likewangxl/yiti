# 业务申请中心 — 后端架构

> 本文只记录当前中场支持申请实现的稳定分层和组件归属。类、端点数量和版本流水不作为架构契约。

## 1. 职责边界

本模块拥有 `SUPPORT_REQUEST` 的申请生命周期、场景路由、多产品拆单、承接侧派单/转交/办理和只读查询。客户、产品、组织、工作流、通知分别由对应模块提供能力；本模块不直接访问这些模块的内部表或实现类。

## 2. 模块依赖

Maven 依赖以本模块 `pom.xml` 为准，当前跨模块依赖及用途如下：

| 模块 | 使用契约 | 用途 |
|---|---|---|
| `common-*` | web、security、aop、db、trace | 统一响应、鉴权、审计、持久化和链路 |
| `auth-permission-center` | `CurrentUserApi`、`OrgApi` 及 DTO | 当前用户、机构信息和数据范围基础能力 |
| `workflow-center` | `WorkflowApi`、`StartProcessCmd`、`ProcessCompletedEvent` | 启动流程和接收流程完成事件；Flowable API 只由 workflow-center 直接操作 |
| `customer-marketing-center` | `CustomerQueryApi`、`AssetProjectQueryApi` 及 DTO | 客户有效性、客户展示和跨域资产统计 |
| `portal-content-center` | `ProductApi` 及 DTO | 支持产品列表、产品校验和产品负责人信息 |
| `system-governance-center` | `NotifyApi` 及公共 AOP 能力 | 审批结果通知和统一审计基础设施 |

## 3. 稳定分层与组件归属

```text
controller  ->  service  ->  mapper/entity
     |             |
     v             +--> customer / portal / workflow API
    api DTO

workflow ProcessCompletedEvent -> listener -> conditional status update -> domain event/notify
```

| 分层 | 当前归属 | 边界 |
|---|---|---|
| `api` | `SupportApi`、`SupportQueryApi`、`BizApplyQueryApi`、对外 DTO | 只读跨模块契约；不暴露 Entity |
| `controller` | `SupportController`、`SupportDeptController` | REST 入参校验、`@BizAuth`、`@AuditLog`、响应包装 |
| `service` | `SupportService`、`SupportDeptService`、`SupportScenarioRouter`、`SupportProductSplitService`、`BizStateMachine`、统计服务 | 业务规则、状态迁移、事务和跨模块 API 调用 |
| `facade` | `SupportApiImpl`、`SupportQueryApiImpl`、`BizApplyQueryApiImpl` | 实现公共 API，转换 DTO，隐藏 Mapper |
| `mapper/entity` | `SupportRequestMapper`、`SupportRequest` | `SUPPORT_REQUEST` 持久化；Mapper 继承 MyBatis-Plus `BaseMapper`，自定义 SQL 仅用于查询、行锁、条件更新和统计 |
| `listener/event` | `SupportWorkflowListener`、Support 领域事件 | 工作流完成回写和本模块事件发布 |
| `config` | `BizAppCacheConfig` | 仅保留当前公共缓存常量；业务表查询不因文档约定而新增缓存 |

## 4. 核心组件协作

1. `SupportService.create` 校验客户并调用 `SupportScenarioRouter`；场景 A 委托 `SupportProductSplitService` 逐产品插入草稿，场景 B 插入单条草稿。
2. `SupportService.submit` 在事务中锁定申请、校验创建人和 `DRAFT → IN_APPROVAL`，通过 `WorkflowApi.startProcess` 启动对应流程并保存 `processInstanceId`。
3. `SupportDeptService` 负责部门列表、派单、转交和办理结果；派单把 `IN_APPROVAL` 转为 `IN_PROGRESS`，办理结果转为 `COMPLETED` 或 `REJECTED`。
4. `SupportWorkflowListener` 只消费 `businessKey` 以 `SUPPORT:` 开头的 `ProcessCompletedEvent`。监听器使用 `AFTER_COMMIT` + `REQUIRES_NEW`，以条件更新保证回调幂等；通知失败不阻断状态回写。

## 5. 状态与权限边界

状态值为 `DRAFT`、`IN_APPROVAL`、`IN_PROGRESS`、`COMPLETED`、`REJECTED`、`CANCELLED`。状态迁移集中在 `BizStateMachine`，不能由 Controller 或 Mapper 直接拼接。

`SUPPORT` 发起侧使用 `owner_org_id`/`created_by`，`SUPPORT_DEPT` 承接侧使用 `support_dept_id`/`assigned_emp_id`。所有写操作在 Service 层基于数据库目标行再次校验操作者，列表/详情/导出等读操作使用统一数据范围。

## 6. 维护约束

- 跨模块只依赖公开 `*Api`、`*QueryApi` 和 DTO，不引用对方 Mapper、Entity、Service 或实现类。
- 新增 REST、DTO、错误码或鉴权动作时，必须同时更新 `03-接口设计与报文.md`、`04-对外API契约.md`、资源登记及契约检查。
- 表结构和字段以目标库实际 schema 与 `SupportRequest` 映射为准；本文不承担 DDL 或初始化执行说明。
