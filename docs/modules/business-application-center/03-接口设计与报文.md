# 业务申请中心 — 接口设计与报文

> 当前 REST 契约以 `SupportController`、`SupportDeptController` 及其 DTO 为准。所有接口返回 `common-web` 统一响应，并通过 `@BizAuth` 做业务权限校验；资源登记以 `PT_RESOURCE` 为准。

## 1. 公共约定

- 分页请求使用 `pageNo`（默认 1）和 `pageSize`（默认 20）；列表结果使用 `PageResult<DTO>`。
- DTO 只暴露业务展示字段，不返回 Entity 的 `deleted` 字段。
- 业务异常由 `BizException` 交给统一异常处理；具体消息以 `BizAppErrorCode` 枚举为准。
- 申请业务键固定为 `SUPPORT:{id}`，ID 为 32 位无连字符 UUID。

## 2. 发起侧 REST（`SUPPORT`）

Controller：`com.bank.branch.platform.bizapp.controller.SupportController`，根路径 `/api/support-requests`。

### 2.1 列表与详情

| 方法 | 路径 | 鉴权 | 请求参数/响应 |
|---|---|---|---|
| GET | `/api/support-requests` | `SUPPORT/LIST` | Query：`keyword`、`status`、`onlyMine`、`pageNo`、`pageSize`；`R<PageResult<SupportRequestListItemDTO>>` |
| GET | `/api/support-requests/{id}` | `SUPPORT/READ` | Path：`id`；`R<SupportRequestDTO>` |

发起侧查询按 `keyword`（申请编号）和 `status`过滤，机构范围由当前用户和数据范围策略注入。`onlyMine=true` 时服务端从当前会话注入创建人工号，并与机构/数据范围条件取交集；客户端不能传入任意员工号。不要把未实现的客户、产品、来源或时间过滤参数写入调用契约。

`SupportRequestListItemDTO` 字段：`id`、`requestNo`、`submitGroupId`、`custName`、`productName`、`supportDeptName`、`scenario`、`status`、`createdTime`。

`SupportRequestDTO` 在上述基础字段外包含 `custId`、`sourceTouchTaskId`、`productId`、`supportDeptId`、`otherDemand`、`dispatchEmpId`、`dispatchTime`、`assignedEmpId`、`businessKey`、`processInstanceId`、`ownerOrgId`、`createdBy`、`createdTime`、`updatedBy`、`updatedTime` 以及客户、产品、承接部门名称等展示字段。

### 2.2 创建

`POST /api/support-requests`，鉴权 `SUPPORT/WRITE`，审计动作 `CREATE_SUPPORT_REQUEST`。

请求体为 `CreateSupportReq`：

| 字段 | 类型 | 约束 |
|---|---|---|
| `custId` | String | `@NotBlank` |
| `productIds` | `List<String>` | 场景 A 使用 |
| `sourceTouchTaskId` | String | 可选，保存来源关联 |
| `otherDemand` | String | 场景 B 使用 |
| `supportDeptId` | String | 场景 B 必填 |

路由和写入规则：

1. 客户必须通过 `CustomerQueryApi.isValidCustomer` 校验。
2. `productIds` 非空且 `otherDemand` 为空进入场景 A；否则进入场景 B。
3. 两者同时为空返回 `BIZ-40903`；场景 B 缺少 `supportDeptId`返回 `BIZ-40902`。
4. 场景 A 每个产品先通过 `ProductApi` 校验支持中场支持并检查同客户同产品活动申请，随后生成共享 `submitGroupId` 的多条 `DRAFT`；场景 B 生成一条 `DRAFT`。

响应为 `R<SupportRequestCreateRespDTO>`：

| 字段 | 说明 |
|---|---|
| `submitGroupId` | 本次创建批次的分组 ID |
| `productCount` | 创建的申请数；场景 A 为拆单数，场景 B 为 1 |
| `requests` | `id`、`requestNo`、`productId`、`scenario`、`processInstanceId`；草稿阶段流程 ID 为 `null` |

### 2.3 提交、删除、撤回

| 方法 | 路径 | 鉴权/审计 | 说明 |
|---|---|---|---|
| POST | `/api/support-requests/{id}/submit` | `SUPPORT/WRITE` / `SUBMIT_SUPPORT_REQUEST` | 无请求体；只有创建人能提交 `DRAFT`，返回 `SubmitRespDTO` |
| DELETE | `/api/support-requests/{id}` | `SUPPORT/WRITE` / `DELETE_SUPPORT_REQUEST` | 只允许创建人删除 `DRAFT`，逻辑删除，返回 `R<Void>` |
| POST | `/api/support-requests/{id}/cancel` | `SUPPORT/WRITE` / `CANCEL_SUPPORT_REQUEST` | 无请求体；`IN_APPROVAL` 或 `IN_PROGRESS` 可撤回，返回 `R<Void>` |
| GET | `/api/support-requests/export` | `SUPPORT/EXPORT` / `EXPORT_SUPPORT_REQUEST` | 当前固定返回 `ResponseWrapper.error("501", "Not Implemented")` |

提交响应字段为 `processInstanceId`、`businessKey`、`status=IN_APPROVAL`。多产品拆单必须逐条调用提交接口，每条申请独立启动流程。

## 3. 承接侧 REST（`SUPPORT_DEPT`）

Controller：`com.bank.branch.platform.bizapp.controller.SupportDeptController`，根路径 `/api/support-dept/requests`。

| 方法 | 路径 | 鉴权/审计 | 请求体 | 结果 |
|---|---|---|---|---|
| GET | `/api/support-dept/requests` | `SUPPORT_DEPT/LIST` | Query：`supportDeptId`、`status`、`assignedEmpId`、`pageNo`、`pageSize` | `R<PageResult<SupportRequestListItemDTO>>` |
| POST | `/api/support-dept/requests/{id}/dispatch` | `SUPPORT_DEPT/WRITE` / `DISPATCH_SUPPORT_REQUEST` | `assignedEmpId`（必填）、`dispatchRemark`（可选） | `IN_APPROVAL → IN_PROGRESS`，返回 `R<Void>` |
| POST | `/api/support-dept/requests/{id}/transfer` | `SUPPORT_DEPT/TRANSFER` / `TRANSFER_SUPPORT_REQUEST` | `newAssignedEmpId`（必填） | 更新承接人，返回 `R<Void>` |
| POST | `/api/support-dept/requests/{id}/complete` | `SUPPORT_DEPT/WRITE` / `COMPLETE_SUPPORT_REQUEST` | `success`（boolean） | true→`COMPLETED`，false→`REJECTED`，返回 `R<Void>` |

派单、转交和办理均由 Service 层以目标申请行和当前用户再次校验；转交请求体当前没有 `reason` 字段，但审计注解要求原因，实际接入应遵循统一审计组件的处理结果。

## 4. 辅助接口

`GET /api/support-requests/available-products` 使用 `SUPPORT/READ`，无请求体，直接返回 `ProductApi.listSupportAvailableProducts()` 的 `List<ProductDTO>`，由产品模块负责可用性过滤。

## 5. 对外 Java 查询契约

### 5.1 `SupportApi`

公开只读方法：`getSupportRequest(id)`、`getSupportRequestByBusinessKey(businessKey)`、`getCustomerSupportHistory(custId)`、`getBySubmitGroup(submitGroupId)`、`getSupportRequestBatch(ids)`。集合无数据返回空集合，调用方不得直连 `SupportRequestMapper`。

### 5.2 `SupportQueryApi`

公开方法：`pageQuery(SupportQueryConditionDTO)`、`countCompletedByCreator(empId,startTime,endTime)`、`countCompletedByAssignee(empId,startTime,endTime)`。条件 DTO 仅包含 `keyword`、`status`、`ownerOrgId`、`supportDeptId`、`pageNo`、`pageSize`。

### 5.3 `BizApplyQueryApi`

公开方法：`countRunningApplications`、`hasRunningLoan`、`hasRunningSupport`、`getEmpStatistics`、`getEmpStatisticsByPeriod`。DTO 中仍保留兼容字段名 `runningLoanCount`、`totalLoans`、`completedLoans`；这些资产统计由 `customer-marketing-center.AssetProjectQueryApi` 提供，本模块不暴露资产申请表或旧 REST 路径。

## 6. 错误码

错误码名称和消息以 `BizAppErrorCode.java` 为唯一来源。当前支持申请直接使用的主要码如下：

| code | 场景 |
|---|---|
| `BIZ-40301` | 客户无效 |
| `BIZ-40304` | 非承接部门人员或非当前承接人 |
| `BIZ-40305` | 非申请创建人 |
| `BIZ-40401` | 申请不存在 |
| `BIZ-40901` | 产品不支持中场支持 |
| `BIZ-40902` | 场景 B 缺少承接部门 |
| `BIZ-40903` | 产品和其他需求同时为空 |
| `BIZ-40906` | 同客户同产品重复申请 |
| `BIZ-42301` | 非法状态迁移 |
| `BIZ-42303` | 非草稿不可删除 |

## 7. 领域事件

业务事件使用 Spring `ApplicationEventPublisher` 发布，事件字段以对应 Java class/record 为准：

| 事件 | 发布时机 |
|---|---|
| `SupportSubmittedEvent` | 提交成功后 |
| `SupportDispatchedEvent` | 派单成功后 |
| `SupportCompletedEvent` | 承接办理成功或流程审批通过后 |
| `SupportRejectedEvent` | 流程审批驳回后 |

`SupportWorkflowListener` 消费 workflow-center 的 `ProcessCompletedEvent`，仅处理 `SUPPORT:` 业务键，并对 `IN_APPROVAL` 做条件更新以保证重复回调不重复发布领域事件。
