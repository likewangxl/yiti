## A. 字典管理

### A.1 GET /api/sys/dicts -- 查询字典类型列表

- **权限**：`@BizAuth(bizType = SYS_CONFIG, action = READ)`
- **说明**：查询字典类型列表，支持按类型精确匹配、按关键词模糊搜索、按状态筛选

**Query 参数：**

| 参数 | Java类型 | 必填 | 校验 | 说明 |
|:---|:---|:---|:---|:---|
| dictType | String | 否 | `@Size(max=100)` | 精确匹配字典类型 |
| keyword | String | 否 | `@Size(max=100)` | 按字典类型/标签模糊搜索 |
| status | String | 否 | `ACTIVE/DISABLED` | 状态筛选 |

**响应体 `ResponseWrapper<List<DictTypeRespDTO>>`：**

**DictTypeRespDTO：**

| 字段 | Java类型 | 说明 |
|:---|:---|:---|
| dictType | String | 字典类型编码 |
| dictTypeLabel | String | 字典类型显示名称（取该类型下首条记录的 remark 或 dictType） |
| itemCount | Integer | 该类型下字典项数量 |
| status | String | 状态（取该类型下是否有 ACTIVE 项） |

**响应示例：**

```json
{
  "code": "0",
  "message": "success",
  "traceId": "a1b2c3d4",
  "data": [
    {
      "dictType": "INDUSTRY",
      "dictTypeLabel": "行业分类",
      "itemCount": 15,
      "status": "ACTIVE"
    }
  ],
  "timestamp": "2026-04-01T10:00:00"
}
```

### A.3 POST /api/admin/sys/dicts -- 新增字典项

- **权限**：`@BizAuth(bizType = SYS_CONFIG, action = CONFIG)`
- **说明**：新增一个字典项

**请求体 DictCreateReqDTO：**

| 字段 | Java类型 | 必填 | 校验注解 | 字典/取值范围 | 示例值 |
|:---|:---|:---|:---|:---|:---|
| dictType | String | 是 | `@NotBlank @Size(max=100) @Pattern(regexp="^[A-Z_]+$")` | 大写字母+下划线 | `"INDUSTRY"` |
| dictCode | String | 是 | `@NotBlank @Size(max=100)` | - | `"IT"` |
| dictLabel | String | 是 | `@NotBlank @Size(max=200)` | - | `"信息技术"` |
| dictValue | String | 是 | `@NotBlank @Size(max=500)` | - | `"IT"` |
| sortOrder | Integer | 否 | `@Min(0)` | 默认 0 | `1` |
| remark | String | 否 | `@Size(max=500)` | - | `"信息技术行业"` |

**响应体 `ResponseWrapper<DictItemRespDTO>`：**

返回新增的字典项完整信息。

**业务规则：**
1. `dict_type + dict_code` 唯一，重复返回 `GOV-40901`（`DictService.createDict`，`GovErrorCode.DICT_CODE_DUPLICATE`；订正：原文误写 `GOV-40002`，该码实为 `CONFIG_NOT_FOUND`）
2. 新增字典项默认 `status=ACTIVE`
3. 新增后清除该 dictType 的缓存（本地内存缓存 `MemoryCacheService`/Caffeine，非 Redis，见脚注 [^cache]）

**错误响应示例：**

```json
{
  "code": "GOV-40901",
  "message": "字典编码重复",
  "traceId": "a1b2c3d4",
  "data": null,
  "timestamp": "2026-04-01T10:00:00"
}
```

[^cache]: `DictService`/`ConfigService`/`CalendarService` 均已从 Redis 切换为 `config/MemoryCacheService`（Caffeine 单实例，`maximumSize=10000`，`expireAfterWrite=1小时`）；`put(key, value, ttl)` 方法保留 `ttl` 入参仅为兼容原 `RedisTemplate` 调用签名，**实际不区分 per-entry TTL**，所有写入统一按全局 1 小时过期（不区分本文档历史遗留的"10 分钟"/"24 小时"等描述）。写操作后仍会显式 `evict()` 清除对应 key，语义不变。

## B. 工作日历

> **2026-07-19 订正**：本节原 B.1 描述的字段形状（`day` 为字符串、`isWorkday` 为 Boolean、含 `dayOfWeek`）实际对应的是**公共**接口 `GET /api/sys/calendar`（`PublicCalendarController`），而**管理端**同名路径下还另有一个**受保护**的月历/年历接口 `GET /api/admin/sys/calendar`（`CalendarController.getWorkingDays`），此前遗漏未收录，字段形状也不同（`day` 为 `LocalDate`、`isWorkday` 为 Integer 1/0、无 `dayOfWeek`）。现补记为 B.0，原 B.1 保留描述公共接口。

### B.0 GET /api/admin/sys/calendar -- 查询日历（管理端，受保护）

- **权限**：`@BizAuth(bizType = SYS_CONFIG, action = READ)`
- **说明**：`CalendarController.getWorkingDays`。`month` 缺省时返回**整年**日历数据（`CalendarService.getWorkingDays`，走 24 小时量级的缓存——实际为 `MemoryCacheService` 全局 1 小时过期，见 A.3 脚注 [^cache]）；传入 `month` 时仅返回该月数据（`CalendarService.getDaysByMonth`，不走缓存，实时查库）。与 B.1 公共接口相比：字段形状不同、`year` 必填但 `month` 选填、需要 `SYS_CONFIG/READ` 权限。

**Query 参数：**

| 参数 | Java类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| year | int | 是 | 年份 |
| month | Integer | 否 | 月份（1-12），缺省返回整年数据 |

**响应体 `ResponseWrapper<List<CalendarDayDTO>>`：**

**CalendarDayDTO**（`api/dto/CalendarDayDTO`，与 CalendarApi 对外 DTO 复用，**与 B.1 的 `CalendarDayRespDTO` 是两个不同类**）：

| 字段 | Java类型 | 说明 |
|:---|:---|:---|
| day | LocalDate | 日期（JSON 序列化为 `yyyy-MM-dd` 字符串） |
| isWorkday | Integer | 是否工作日：**1=工作日，0=休息日**（注意不是 Boolean） |
| remark | String | 备注 |

2. 扩展名不在白名单（`jpg/jpeg/png/gif/pdf/doc/docx/xls/xlsx/ppt/pptx/txt/zip/rar`，硬编码常量集合）返回 `GOV-42203`（`GovErrorCode.FILE_FORMAT_INVALID`；订正：原文误写 `GOV-40903`，该码实为 `TASK_ALREADY_RUNNING`「任务正在执行中」，与文件业务完全无关）
3. 大小二次校验（对 `byte[]` 直传场景，重复上一步的边界检查）同样返回 `GOV-42204`
4. MD5 去重：相同 MD5 直接复用已有 `file_object` 记录，不重复写 OBS
5. OBS 读取/写入/MD5 计算异常统一返回 `GOV-50001`（`GovErrorCode.MINIO_ERROR`；订正：原文的码本身正确，但**枚举常量名与提示文案仍字面写着 "MINIO_ERROR"/"MinIO服务异常"**——这是代码里遗留的历史命名，当前语义已是 OBS 异常，非文档笔误）

> **2026-07-19 订正**：`SqlProbeController` 真实 `@RequestMapping` 是 `/api/admin/sql-probe`（**无 `sys` 段**），本文历史版本 H.1/H.2 路径均误写为 `/api/admin/sys/sql-probe/...`，已订正。业务规则也已按 `SqlProbeService` 源码全面核实重写。

### H.1 POST /api/admin/sql-probe/execute -- 执行SQL

- **权限**：`@BizAuth(bizType = SYS_CONFIG, action = EXECUTE_SQL)`
- **说明**：执行只读 SQL 查询。属于 EXECUTE_SQL 高危动作，需审计。

**请求体 SqlProbeReqDTO：**

| 字段 | Java类型 | 必填 | 校验注解 | 说明 |
|:---|:---|:---|:---|:---|
| sql | String | 是 | `@NotBlank @Size(max=5000)` | SQL 语句（仅 SELECT） |
| remark | String | 否 | `@Size(max=500)` | 备注 |

**响应体 `ResponseWrapper<SqlProbeRespDTO>`：**

**SqlProbeRespDTO：**

| 字段 | Java类型 | 说明 |
|:---|:---|:---|
| columns | List\<String\> | 列名列表 |
| rows | List\<Map\<String,Object\>\> | 结果数据 |
| rowCount | Integer | 返回行数 |
| executionTime | Integer | 执行耗时（ms） |

**响应示例：**

```json
{
  "code": "0",
  "message": "success",
  "traceId": "a1b2c3d4",
  "data": {
    "columns": ["id", "dict_type", "dict_code", "dict_label"],
    "rows": [
      {"id": "1", "dict_type": "INDUSTRY", "dict_code": "IT", "dict_label": "信息技术"}
    ],
    "rowCount": 1,
    "executionTime": 35
  },
  "timestamp": "2026-04-01T10:00:00"
}
```

**业务规则（以 `SqlProbeService.executeSql` 源码为准，全部订正）：**
1. 非 `SELECT` 开头（大小写不敏感，`trim().toUpperCase().startsWith("SELECT")`）返回 `GOV-42201`（`GovErrorCode.NOT_SELECT_SQL`；与本文历史版本一致，未变）
2. 并发数超限返回 `GOV-42202`（`GovErrorCode.SQL_CONCURRENCY_EXCEEDED`；**订正**：原文将此码标注为"超时"，实际语义是**并发数超限**——`Semaphore(3)` 硬编码信号量，`tryAcquire()` 非阻塞获取，达到 3 个并发探查立即拒绝，并非 sys_config_kv 可配置）
3. SQL 执行期间抛出的任意 `SQLException`（含真正的查询超时、语法错误、连接异常等）统一捕获为 `GOV-50003`（`GovErrorCode.SQL_EXECUTION_TIMEOUT`，500 类；**订正**：原文误写为 `GOV-42202`，且未提及此码——查询超时阈值固定 `QUERY_TIMEOUT_SECONDS=30` 秒硬编码，通过 `Statement.setQueryTimeout(30)`）
4. **删除**：原文"访问白名单外的 Schema/表返回 GOV-42203"——当前 `SqlProbeService` 源码**未实现任何 Schema/表白名单校验逻辑**，且 `GOV-42203` 实际是 `FILE_FORMAT_INVALID`（文件格式非法），与 SQL 探查完全无关，本文历史版本这条业务规则纯属虚构，据实删除
5. SQL 中不含 `"LIMIT"` 子串（大小写不敏感）时追加 `" LIMIT 1000"`；**订正**：`DEFAULT_LIMIT=1000` 是硬编码常量，**并非**从 `sys_config_kv` 读取，也没有"最大值"上限校验——若调用方提交的 SQL 已自带 `LIMIT` 子句（哪怕 `LIMIT 100000`），不会被二次收窄或拒绝
6. **订正**：审计日志（`bizType=SQL_PROBE, bizAction=EXECUTE_SQL`）仅在**执行成功**路径显式调用 `auditLogService.log()` 写入，记录 `requestParams=sql`、`responseStatus=200`（硬编码，非实际状态码）、`reason`；**执行失败时不写审计日志**，且该调用本身**不携带** `executionTime`/`rowCount` 字段（这两个字段只出现在响应体 `SqlProbeRespDTO` 中，未同步进审计记录）

**错误响应示例：**

```json
{
  "code": "GOV-42201",
  "message": "SQL语法校验失败：仅允许SELECT语句",
  "traceId": "a1b2c3d4",
  "data": null,
  "timestamp": "2026-04-01T10:00:00"
}
```
