# 系统治理中心并发与事务策略

本文只描述当前 Service、Facade、Quartz Listener 和存储客户端的实际边界。事务配置以源码注解和运行配置为准。

## 1. 总体原则

1. 数据库是治理状态的持久权威；缓存、Quartz 调度状态和 OBS 对象都是协同状态，不能用其中一个替代其他状态。
2. Service 是写入、目标记录校验、事务和外部副作用的边界；Facade 只负责公开 API 和 DTO 转换。
3. 所有幂等要求同时依赖 Service 预检查和数据库唯一约束。并发请求仍可能竞态，调用方必须正确处理唯一键冲突和可重试错误。
4. 外部系统调用不能参与数据库原子提交；对于可补偿的对象操作记录失败并执行明确的清理或人工处置。

## 2. 本地缓存并发

字典、配置和年度日历共用 `MemoryCacheService` 的 Caffeine Cache，当前限制为 `maximumSize=10000`、写入后统一一小时过期。缓存读写线程安全，但只在当前进程内有效。

### 2.1 读路径

1. Service 以治理前缀加业务键查缓存。
2. 命中直接返回；未命中查询数据库并写入缓存。
3. 缓存缺失或过期不会改变数据库语义；查询结果必须按数据库状态过滤。

### 2.2 写路径

字典类型、配置键或日历年份的数据库写入成功后调用 `evict`。写事务回滚时不应把未提交结果放入缓存；跨实例不会自动广播失效，部署或配置变更后应通过运行检查确认各实例状态。

## 3. 字典、配置和日历

| 操作 | Service 事务 | 并发/一致性要求 |
| --- | --- | --- |
| 字典新增、部分更新、逻辑禁用、状态设置 | `@Transactional` | `(dict_type, dict_code)` 唯一；成功后清除类型缓存 |
| 配置更新 | `@Transactional` | `config_key` 唯一；成功后清除键缓存；类型由 Service 校验 |
| 日历单日设置 | `@Transactional` | 目标日期存在则更新，不存在则插入；成功后清除年份缓存 |
| 日历年初始化 | `@Transactional` | 重置指定年份后逐日写入，调用方需避免与该年份维护并发 |
| 日历 Excel 导入 | `@Transactional` | 解析后批量更新/插入；过去日期跳过；受影响年份成功后清缓存 |

日历单日设置拒绝过去日期。年初始化会重建整年数据，因此不是“合并更新”；必须将其视为覆盖性管理操作。两个管理员同时维护同一字典项、配置键或日期时，最后提交者可能覆盖前一个提交，审计记录应保留操作顺序。

## 4. Quartz 调度并发

### 4.1 注册与启停

- `JobApi.registerJob` 在事务中校验 Cron、Job 类并 upsert `SYS_JOB_CONF`；Scheduler 可用时随后注册 JobDetail/CronTrigger。同一 `jobKey` 重复调用是覆盖语义。
- `unregisterJob` 在事务中清理配置；Quartz 删除异常记录告警后仍继续处理数据库记录，完成后需要检查调度状态。
- 暂停/恢复在事务中更新配置状态并调用 Scheduler；Scheduler 不可用或调用异常返回 `GOV-50005`/`GOV-50006`，数据库状态由事务回滚保护。外部 Scheduler 状态仍需通过运行检查确认。

### 4.2 触发和执行日志

- `triggerJobByKey` 不写运行日志表；它把触发类型、操作人、理由及可选日期放入 `JobDataMap`，成功提交给 Scheduler 后立即返回。
- 全局 `JobExecutionLogger` 在 Quartz Job 开始时插入 `RUNNING`，结束时更新 `SUCCESS`/`FAILED` 和 `last_run_time`；内部异常被隔离，不阻断 Job 本身。
- JDBC JobStore 使用 Quartz 的 `QRTZ_LOCKS` 和集群状态实现同一调度器集群的协调。业务模块不得自行写 `SYS_JOB_RUN_LOG` 或以另一套锁替代 Quartz 调度锁。
- `JobApi.isJobRunning` 是只读观察，不是跨请求的独占锁。需要避免业务重复排队时，调用方仍须结合自己的业务唯一键/事务约束设计。

### 4.3 启动同步

应用启动时读取 `SYS_JOB_CONF` 的 `ACTIVE` 行并注册到 Scheduler。Scheduler 不存在或被禁用时安全跳过；单个配置的 Cron、Job 类或注册错误只记录并继续，其余配置不受影响。

## 5. 审计事务

- `AuditLogService.log` 使用 `Propagation.REQUIRES_NEW`，即使外层业务事务回滚，也可以独立保存审计记录。
- `AuditLogAspect` 在请求结束时采集状态、耗时和异常；`GovAuditLogHandler` 将事件转换后调用审计 Service。切面处理异常被记录并隔离，不能把主请求静默改成成功。
- 使用 `serviceManaged=true` 的 Service 必须自己完成目标、前后快照和理由审计，切面不会重复写通用记录。
- 审计内容在写入前脱敏和截断；审计失败的补偿由运维或业务审批决定，不通过重放主业务请求补写。

## 6. 通知事务与部分成功

`NotificationService.sendNotification` 是同步单条插入，当前 Service 本身不包裹业务事务。调用方若要求“业务提交后发送”，应在自己的事务上注册事务提交后监听器。

`batchSendNotifications` 逐条调用发送；单条异常被记录并继续，结果可能部分成功。需要全量原子语义的业务不得直接把该批量 API 当作全量事务，应自行编排事务和补偿。

## 7. 文件对象与数据库的一致性

### 7.1 上传

```text
校验扩展名/大小
      ↓
流式计算 MD5，查询 FILE_OBJECT
      ├─ 命中：复用元数据，按需幂等绑定
      └─ 未命中：写 OBS → 插入 FILE_OBJECT → 按需写 BIZ_FILE_REL
```

上传 Service 使用事务包裹元数据/关联写入，但 OBS 写入不受数据库回滚控制。若新对象落库失败，Service 尝试删除本次对象；删除失败必须保留服务端错误并由运维核对对象与元数据。

MD5 去重是内容级复用，不等于业务关联；命中对象时不得删除或覆盖共享对象。调用方应根据 `newlyCreated` 和业务关联结果决定补偿动作。

### 7.2 绑定、解绑和删除

- `bindFile` 使用业务三元组唯一约束和存在性检查保证重复绑定幂等。
- `unbindFile` 只删除指定业务关联，事务提交后文件对象保持不变。
- `deleteFile` 在事务方法中删除 OBS 对象、文件元数据和所有关联；当前不执行引用计数判断，因此调用方必须在删除前确认没有其他业务引用。OBS 删除失败时不会继续假装数据库清理已完成。

## 8. 标签导入与成员并发

- 标签名称、标签+员工、标签+机构编号依赖数据库唯一约束；创建或添加成员遇到并发冲突时返回对应治理错误。
- 成员新增按 `EMP`/`ORG` 维度分别处理，同维度重复成员跳过，另一维度不互相覆盖。
- 全局导入和指定标签成员导入使用 `@Transactional(rollbackFor = Exception.class)`；文件解析、用户/机构存在性校验和重复判断完成后再写库，任一行错误整体回滚。
- 指定标签导入是所选维度的全量替换：先替换该维度，再保留另一维度；并发导入同一标签同一维度时以后提交者为最终结果，必须以审计和操作时间追溯。

## 9. SQL 探查并发

SQL 探查只接受 `SELECT` 开头的请求，自动限制结果行数；每进程使用 3 个并发许可，JDBC 查询超时为 30 秒。获取不到许可直接返回 `GOV-42202`，资源在成功、异常和超时路径都必须释放。探查不提供写事务和结构变更能力，每次成功执行写入审计。

## 10. 失败处理与重试边界

1. 数据库事务异常：由统一异常处理器返回治理错误；重试前确认唯一键和外部副作用状态。
2. Quartz 注册/触发异常：保留 `SYS_JOB_CONF` 和服务端日志，检查 Scheduler、Job 类、Cron 和 QRTZ 状态后再由授权人员重试。
3. OBS 异常：不要盲目重试删除或上传；先按文件 ID、MD5 和对象 key 核对，避免误删共享对象。
4. 审计/通知部分失败：保留 Trace、错误日志和业务结果，按各自的独立补偿流程处理。
