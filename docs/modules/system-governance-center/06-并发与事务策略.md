# 系统治理中心 -- 并发与事务策略

> 版本：V1 | 最后更新：2026-04-02

---

## 1. 字典管理

### 1.1 唯一约束防重复

- `sys_dict` 表通过 `UK(dict_type, dict_code)` 唯一约束保证同一字典类型下编码不重复
- 新增字典时，若违反唯一约束，Service 层捕获 `DuplicateKeyException` 并转为业务异常返回
- 种子数据使用 `INSERT IGNORE` 实现幂等导入

### 1.2 Redis 缓存策略

| 缓存 Key | 格式 | TTL | 说明 |
|:---|:---|:---|:---|
| `gov:dict:{dictType}` | `List<DictVO>` 序列化为 JSON | 10 分钟 | 按字典类型缓存全部字典项列表 |
| `gov:dict:all-types` | `List<String>` | 10 分钟 | 所有字典类型列表（用于管理页面） |

**缓存读取流程**：

```
1. 前端/Service 调用 DictQueryApi.listByType(dictType)
2. 先查 Redis Key: gov:dict:{dictType}
3. 命中 → 直接返回
4. 未命中 → 查 DB → 写入 Redis（TTL=10min）→ 返回
```

**缓存清除策略**：

```
1. 字典新增/编辑/删除操作成功后
2. 清除对应 dict_type 的缓存：DEL gov:dict:{dictType}
3. 同时清除类型列表缓存：DEL gov:dict:all-types
4. 粒度：按 dict_type 级别清除，不做全量清除
```

### 1.3 事务边界

```java
@Transactional(rollbackFor = Exception.class)
public void createDict(DictCreateDTO dto) {
    // 1. 校验 dict_type + dict_code 唯一性（应用层预校验）
    // 2. INSERT sys_dict
    // 3. 事务提交后清除缓存（通过 @TransactionalEventListener）
}
```

**关键约束**：
- 缓存清除必须在事务提交后执行，避免事务回滚后缓存已被清除导致缓存不一致
- 使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 处理缓存清除

### 1.4 并发写场景

- 字典管理为低频管理操作（系统管理员使用），并发写概率极低
- 依赖数据库唯一约束兜底，不需要分布式锁
- 极端情况下两个管理员同时编辑同一字典项：后提交的 UPDATE 覆盖先提交的（Last Write Wins），可接受

## 2. 工作日历

### 2.1 主键天然防重复

- `sys_calendar_day` 以 `day` DATE 类型作为主键，天然保证一天只有一条记录
- 不存在并发写同一天的合理场景（管理员操作）

### 2.2 年初批量初始化

```java
@Transactional(rollbackFor = Exception.class)
public void initYear(int year) {
    // 1. 生成 year 年 1月1日 ~ 12月31日 共 365/366 天的记录
    // 2. 默认周一至周五为工作日，周六周日为休息日
    // 3. 使用 INSERT IGNORE 批量写入（幂等，重复执行不报错）
    // 4. 批量大小：每批 100 条，减少 SQL 语句长度
}
```

**幂等保证**：
- `INSERT IGNORE INTO sys_calendar_day (day, is_workday, ...) VALUES (?, ?, ...)`
- 已存在的日期行被忽略（不覆盖已手动调整的数据）
- 重复调用初始化接口安全无副作用

### 2.3 单日切换 (UPSERT)

```sql
INSERT INTO sys_calendar_day (day, is_workday, remark, updated_by, updated_time)
VALUES (#{day}, #{isWorkday}, #{remark}, #{updatedBy}, NOW())
ON DUPLICATE KEY UPDATE
  is_workday = VALUES(is_workday),
  remark = VALUES(remark),
  updated_by = VALUES(updated_by),
  updated_time = NOW();
```

- 使用 MySQL `ON DUPLICATE KEY UPDATE` 实现 UPSERT 语义
- 无论日期记录是否存在，均可安全执行

### 2.4 批量导入（Excel/CSV）

```java
@Transactional(rollbackFor = Exception.class)
public ImportResultDTO batchImport(List<CalendarImportRow> rows) {
    // 1. 校验日期格式、is_workday 取值范围
    // 2. 逐条 UPSERT（ON DUPLICATE KEY UPDATE）
    // 3. 统计成功/跳过/失败条数
    // 4. 返回导入结果摘要
}
```

- 批量导入在单事务内执行，任一行失败则全部回滚
- 单次导入上限建议 366 条（一年最多天数）

## 3. 任务调度

### 3.1 手动触发防重复执行

```java
public void triggerJob(String jobId, String reason) {
    // 1. 查询 sys_job_conf，校验 allow_manual_trigger = 1
    // 2. 查询 sys_job_run_log 是否存在 job_id = #{jobId} AND status = 'RUNNING'
    //    存在 → 抛出异常 "该任务正在执行中，请等待完成后再触发"
    // 3. 不存在 → 创建 sys_job_run_log 记录（status=RUNNING, trigger_type=MANUAL）
    // 4. 异步执行任务逻辑
    // 5. 任务完成后更新 sys_job_run_log（status=SUCCESS/FAILED, end_time）
}
```

**并发控制**：
- 检查 RUNNING 状态使用 `SELECT ... FOR UPDATE`（悲观锁），防止两个管理员同时触发
- 或使用 Redis 分布式锁 `gov:job-lock:{jobId}`，TTL 根据任务预期执行时间设置

### 3.2 任务状态更新

```java
@Transactional(rollbackFor = Exception.class)
public void completeJobRun(String runLogId, String status, String errorMsg) {
    // 在同一事务内完成：
    // 1. UPDATE sys_job_run_log SET status=#{status}, end_time=NOW(), error_msg=#{errorMsg}
    // 2. UPDATE sys_job_conf SET last_run_time=NOW() WHERE id=#{jobId}
}
```

- `start_time` 在创建 run_log 记录时写入，`end_time` 在完成时更新
- `status` 从 `RUNNING` 变更为 `SUCCESS` 或 `FAILED`，在同一事务内确保一致性

### 3.3 定时触发

- 定时任务由 Spring `@Scheduled` 或 Quartz 调度器触发
- 定时触发时同样需要检查是否有 RUNNING 状态的执行记录
- 若上一次执行未完成，跳过本次触发并记录 WARN 日志

### 3.4 任务暂停/恢复

```java
@Transactional(rollbackFor = Exception.class)
public void pauseJob(String jobId) {
    // 1. UPDATE sys_job_conf SET status='PAUSED' WHERE id=#{jobId} AND status='ACTIVE'
    // 2. 影响行数为 0 → 任务已暂停或不存在
    // 3. 暂停后调度器不再触发该任务
}
```

- 暂停操作不影响正在执行中的任务运行
- 仅阻止后续的定时触发

## 4. 审计日志

### 4.1 写入模式

- 审计日志采用**同步写入**模式，在请求处理完成后立即写入 `audit_log` 表
- 通过 `@AuditLog` 注解 + AOP 切面自动捕获请求信息

### 4.2 append-only 约束

- `audit_log` 表为**只追加（append-only）**，不可修改、不可删除
- Service 层不提供 UPDATE 和 DELETE 方法
- Mapper 层不映射 UPDATE 和 DELETE 语句
- 物理删除仅在归档清理流程中由 DBA 通过 DROP PARTITION 操作

### 4.3 高并发写入优化

在高并发场景下（如全行用户同时操作），审计日志写入可能成为瓶颈：

**V1 策略（同步单条写入）**：
- 每次请求完成后同步 INSERT 一条审计记录
- 适用于当前规模（数百并发用户）
- 审计写入失败不影响业务请求返回（catch 异常并记录 ERROR 日志）

**V2 优化方向（预留）**：
- 引入内存队列 + 批量写入（每 100 条或每 1 秒刷盘一次）
- 或通过消息队列异步写入
- 按月分区减少单分区数据量

### 4.4 事务隔离

```java
// 审计日志写入使用独立事务，不影响业务事务
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public void log(AuditLogCreateDTO dto) {
    auditLogMapper.insert(buildEntity(dto));
}
```

- 使用 `REQUIRES_NEW` 传播行为，确保审计日志写入独立于业务事务
- 业务事务回滚不影响审计记录（操作失败也需要被审计）
- 审计写入失败不影响业务事务

## 5. 通知消息

### 5.1 通知发送（异步）

```java
// 业务事务提交后发送通知
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onBusinessEvent(BusinessEvent event) {
    // 1. 构建通知内容
    // 2. INSERT user_notification
    // 3. 如需实时推送，通过 WebSocket/SSE 推送至前端
}
```

**关键设计**：
- 通知发送在业务事务提交后执行（事件驱动）
- 确保只有业务操作真正成功后才发送通知
- 通知写入失败不回滚业务事务（降级为日志告警）

### 5.2 批量发送

```java
@Transactional(rollbackFor = Exception.class)
public void batchSendNotifications(List<NotificationCreateDTO> notifications) {
    // 批量 INSERT，每批 200 条
    // 使用 MyBatis batch insert
    for (List<NotificationCreateDTO> batch : partition(notifications, 200)) {
        notificationMapper.batchInsert(batch);
    }
}
```

### 5.3 标记已读

```java
// 单条标记已读 - 无并发风险
public void markAsRead(String notificationId, String empId) {
    // UPDATE user_notification SET is_read=1, read_time=NOW()
    // WHERE id=#{notificationId} AND emp_id=#{empId} AND is_read=0
    // 影响行数为 0 → 已读或不存在，直接返回成功（幂等）
}

// 批量标记已读 - 按用户维度限制范围
public void batchMarkAsRead(String empId, List<String> notificationIds) {
    // UPDATE user_notification SET is_read=1, read_time=NOW()
    // WHERE emp_id=#{empId} AND id IN (#{notificationIds}) AND is_read=0
    // 限制：必须带 emp_id 条件，避免跨用户操作
}
```

**幂等保证**：
- 重复标记已读返回成功，不报错
- WHERE 条件中包含 `is_read=0`，已读的记录不会被重复更新

## 6. 文件管理

### 6.1 文件上传事务

```java
@Transactional(rollbackFor = Exception.class)
public FileUploadResultDTO uploadFile(MultipartFile file, String bizType, String bizId) {
    // 1. 计算文件 MD5
    // 2. 上传至 MinIO（先存储再入库）
    //    上传失败 → 抛异常，事务回滚（实际无 DB 操作需回滚）
    // 3. INSERT file_object（记录文件元信息）
    // 4. INSERT biz_file_rel（关联业务记录）
    //    biz_file_rel 有 UK(biz_type, biz_id, file_object_id) 防重复关联
    // 5. 返回文件ID和访问路径
}
```

**异常处理**：
- MinIO 上传成功但数据库写入失败 → 事务回滚，MinIO 中产生孤立文件
- 通过定期清理任务处理孤立文件（对比 MinIO 文件列表与 file_object 表）

### 6.2 文件删除

```java
@Transactional(rollbackFor = Exception.class)
public void deleteFile(String fileObjectId) {
    // 1. 查询 biz_file_rel 是否有关联记录
    //    有关联 → 先删除 biz_file_rel 关联记录
    // 2. 查询 file_object 获取 storage_path 和 bucket_name
    // 3. DELETE file_object WHERE id=#{fileObjectId}
    // 4. 事务提交后删除 MinIO 对象（异步或事务后事件）
}
```

**注意**：
- MinIO 对象删除放在事务提交后执行
- 若 MinIO 删除失败，数据库记录已删除，MinIO 中产生孤立对象
- 通过定期清理任务补偿处理

### 6.3 MD5 去重（可选）

```java
public FileUploadResultDTO uploadWithDedup(MultipartFile file) {
    String md5 = DigestUtils.md5Hex(file.getInputStream());
    FileObject existing = fileObjectMapper.selectByMd5(md5);
    if (existing != null) {
        // 文件已存在，直接复用，只创建新的 biz_file_rel
        return buildResult(existing);
    }
    // 文件不存在，正常上传流程
}
```

- MD5 去重为可选功能，默认不启用
- 启用后相同内容的文件只存储一份，减少存储空间
- 注意：MD5 碰撞概率极低但理论上存在，生产环境可选择 SHA-256

## 7. 幂等策略总览

| 场景 | 幂等机制 | 说明 |
|:---|:---|:---|
| 字典新增 | UK(dict_type, dict_code) + INSERT IGNORE | 种子数据重复导入不报错 |
| 字典编辑 | 乐观更新（Last Write Wins） | 低频管理操作，可接受 |
| 日历初始化 | PK(day) + INSERT IGNORE | 重复初始化不覆盖已调整的数据 |
| 日历单日设置 | PK(day) + ON DUPLICATE KEY UPDATE | UPSERT 语义，天然幂等 |
| 任务手动触发 | RUNNING 状态检查 + 分布式锁 | 防止同一任务重复触发 |
| 通知标记已读 | WHERE is_read=0 条件 | 重复标记返回成功 |
| 文件上传 | MD5去重（可选） | 相同文件不重复存储 |
| 文件关联 | UK(biz_type, biz_id, file_object_id) | 防止重复关联 |
| 审计日志 | 无需幂等（append-only） | 每次写入都是新记录 |
| 系统配置 | UK(config_key) | 配置键全局唯一 |

| Service 方法 | 传播行为 | 说明 |
|:---|:---|:---|
| DictService.create/update/delete | REQUIRED | 标准事务，缓存清除在事务后 |
| CalendarService.initYear | REQUIRED | 批量写入，全部成功或全部回滚 |
| CalendarService.setDay | REQUIRED | 单条 UPSERT |
| CalendarService.batchImport | REQUIRED | 批量导入，全部成功或全部回滚 |
| JobService.triggerJob | REQUIRED | 创建 run_log 记录 |
| JobService.completeJobRun | REQUIRED | 更新 run_log + job_conf |
| AuditLogService.log | REQUIRES_NEW | 独立事务，不影响业务事务 |
| NotificationService.send | REQUIRES_NEW / 事务后事件 | 通知写入独立于业务事务 |
| NotificationService.markAsRead | REQUIRED | 简单 UPDATE |
| FileService.upload | REQUIRED | MinIO 上传 + DB 写入 |
| FileService.delete | REQUIRED | DB 删除 + 事务后清理 MinIO |
| ConfigService.update | REQUIRED | 标准事务 |
